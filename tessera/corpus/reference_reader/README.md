# Tessera reference reader (independent, pure-Python) — the v1.0 conformance gate

This is a **second, independent** implementation of the Tessera read path, written in pure Python
**from `tessera/docs/SPEC.md` alone** — no access to the Rust engine. It exists to prove the spec is
sufficient: a fresh implementer, given only the spec, must be able to open every `.tsra` test vector
and reproduce its golden `id` / `content_hash` / `manifest_hash` (and verify each block's digest).

This is the **v1.0 release gate** (ROADMAP P8 / #211). It was produced by a spec-only agent and
reproduced all 6 corpus goldens on the first attempt; the clarifications it surfaced are folded back
into `SPEC.md`.

## What it depends on

Only the container (§6) + canonical hashing (§2–§4): Python stdlib `zipfile` + `json`, plus `blake3`
and an RFC 8785 `jcs` encoder. It does **not** decode array/table payloads — reproducing the identity
triple needs only the stored bytes, not the pcodec/Vortex codecs.

## Run it

```sh
uv run --no-project --with-requirements requirements.txt \
  python -B run.py
uv run --no-project --with-requirements requirements.txt \
  python -B make_seal_cases.py
uv run --no-project --with-requirements requirements.txt \
  python -B make_refusal_fixtures.py
```

Exit code 0 ⇔ all fixtures reproduce their goldens, every stored pair in `corpus/seal-cases.json` reaches its
`verdict`, every case in `corpus/schema-cases.json` reaches its `verdict` (and every corpus product passes its own
embedded schema), and the reader refuses each crafted refusal archive for its stated reason. The Rust reader checks the
same seal-case file (`tessera-core/tests/seal_cases.rs`), and so does `tessera-wasm` (natively and, in the
`wasm-bindgen-smoke` check, compiled to wasm in Node), so the three readers are compared case by case. The file is
generated by `make_seal_cases.py` from the corpus, each case by one named edit. The refusal
archives today list a block name twice (SPEC §5, #734), with a foreign digest and with the block's own, built from a
corpus fixture and re-sealed; the Rust reader refuses the same two (`tessera-io/tests/unique_block_names.rs`).
The committed `corpus/refusals` fixtures (`make_refusal_fixtures.py`) are outside SPEC §6's member set: a repeated
`manifest.seal` or `manifest.json` whose last entry is the product's own, and each of the two DEFLATED. A reader
that resolves a name to its last entry or inflates a member verifies all four; this one refuses each before reading
any member, as the Rust reader does over the same files (`tessera-io/tests/canonical_members.rs`). A seal case holds
the manifest bytes as the UTF-8 string they spell, or as `manifest_hex` when they are not UTF-8; every reader takes
the bytes.

The corpus includes `recon_int16_indexed.tsra`, produced with the real indexed-array writer. Its
`volume.cidx` is a derived block: `content_hash` equals the primary-only Merkle root and the
unindexed `recon_int16` golden. `run.py` removes the sidecar and re-seals a second archive to prove
the root stays unchanged while the seal changes. Rust checks the same archive; the wasm smoke gate
extracts every corpus manifest and seal with `tests/corpus_members.py` and compares them with
`corpus.json` in Node.

## What it checks

`stored_verdict(manifest, seal)` (and `verify_tsra`, which adds the container and block payloads) returns a
verdict for every input; neither raises (`verify_tsra` reports an archive `zipfile` can't read, such as an
encrypted member, as not ok). Before it reads any member, `verify_tsra` refuses an archive outside SPEC §6's
member set: a member name listed twice, or an entry that is not STORED. The seal is `digest(manifest.json bytes)`,
read from `manifest.seal`; nothing is re-serialised to compute it (ADR-0066). In SPEC §7's order, so a manifest
with two faults gets the verdict of the first:

0. **Refused, the layout (ADR-0066 rules 3, 10):** no `manifest.seal` (the pre-ADR-0066 alpha layout: no
   migration), or a seal that is not exactly `blake3:` and 64 lower-case hex digits.
1. **Refused, not I-JSON (SPEC §1, §4):** text that is not JSON or not UTF-8 (UTF-16, a byte-order mark), a key
   repeated in any object, `NaN` / `Infinity`, a number outside a double's range, a number whose value is an integer
   beyond ±(2^53−1) (`9007199254740993`, `9007199254740993.0`, `1e300`: `parse_int` / `parse_float` see each token,
   the double JCS writes decides), a lone surrogate (refused explicitly, `_lone_surrogate`), nesting deeper than
   127 objects/arrays.
1a. **Refused, not its own JCS form (ADR-0066 rule 4):** `jcs.canonicalize(parse(bytes)) != bytes` (key order,
   whitespace, an escape or number spelling JCS doesn't write such as #901's `64.0`, a pretty layout); then a
   top-level `manifest_hash` key (the seal in band).
1b. **Tampered:** `manifest.seal` ≠ `digest(manifest.json)`.
2. **Refused, outside the declared shape (SPEC §5):** `reader.MANIFEST` is one declarative table, one row per field
   of the Rust `Manifest`, `BlockRef`, `Source`, `Producer`, `Generation` and `IngestTransform`, checked at every
   depth: each record is an object (never the array form), each declared field has its JSON type (string, boolean,
   an object for a map, an array for a list), a block `kind` is one of `array`/`table`/`chunk_index`/`blob`, a block
   `class`, when present, is exactly `"derived"` (`"primary"` and `null` are refused: a primary block has no
   `class` key), a block `name` follows the ADR-0063 grammar, every `id_inputs` value is a string,
   `producer` is a Producer object or a legacy string, and a required field is present. `null` stands for an
   absent value only where the Rust
   field is optional (`producer`, `generation`, `schema`, `study`, `content_hash`, a block's `digest`, a source's
   `content_hash`, Producer's `git_*`/`dirty`, `generation.config_ref`); the maps and lists refuse it. Opaque
   values hold any JSON: `schema`, `blocks[].spec`, and the values of `metadata`, `extra`, `generation.config` and
   `ingest_transform[].params`. A key the table doesn't declare is a newer field: it is sealed, never type-checked.
   The check walks each record's **declared** keys only, so a newer key is never visited and nothing is exempted
   by a path string: a top-level key literally named `producer.agents` can't stand in for the nested field. This
   reader doesn't report newer-field paths (the `newer_fields` of `seal-cases.json` are the Rust view's, rendered
   as SPEC §4 defines), and the case `recon_int16/key-spelling-a-nested-path-resealed` holds both readers to it.
3. **Refused:** a `tessera_version` whose major (before the first `.`) is not an optional `+` and ASCII digits, or
   is above the supported major.
4. **Refused:** a block name listed twice (SPEC §5).
5. **Tampered:** `id` ≠ `digest(JCS(id_inputs))`.
6. **Refused:** a block without a `digest` (SPEC §5).
7. **Tampered:** `content_hash` ≠ the MMR root of the **primary** block digests in manifest order (a missing one
   is tampered). A derived block (`"class": "derived"`, ADR-0028 §4) is skipped: its digest is covered by the seal
   and checked against its payload like any block's, but it is no leaf of `content_hash`.

Separately from the seal, `schema_verdict(schema, metadata)` applies a product schema's **number rules** (SPEC §5
"Field rules", #895) and returns `ok`, `schema` (a field declaration is refused: an unknown dtype, an `int64`/`uint64`
without `"encoding": "string"`, an encoding on another dtype, a range on a non-numeric dtype, beyond ±(2^53−1) or
empty) or `value` (a metadata value breaks its field's encoding or range; integers are compared exactly). `run.py`
checks it against every case of `corpus/schema-cases.json`, which `tessera-core/tests/schema_cases.rs` checks for the
Rust reader, and against each corpus product's own embedded schema (all pass).

Deliberate differences from the Rust reader, each outside what these verdicts cover:

- It reads **manifests only**. A collection (`collection.json`) and the embedded product schema are checked by the
  Rust reader alone: the seal-case corpus has no collection or schema cases yet, and SPEC doesn't define a
  collection's `content_hash` leaf, so a spec-only reader can't verify one.
- It **doesn't validate the embedded schema** (`schema` is opaque here, as it is to the Rust manifest verify).
- Integers beyond 2^53 (in opaque values) are hashed as each JCS encoder renders them; whether the two readers
  agree there is open in #886.

## Why it matters

Until a second codebase reads Tessera correctly from the spec alone, "the spec" is really "whatever
the Rust does." This reader closes that gap — and re-running it after any spec or corpus change keeps
the spec honest.

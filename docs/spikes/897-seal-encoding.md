# Spike #897 — how tessera seals its JSON-shaped documents: A vs A′ vs B

**Status:** evidence for the owner's decision; recommendation **A′** (proposed in
[ADR-0066](../adr/0066-seal-encoding.md), status Proposed). Issue: #897. Prototypes, commands and raw output:
[`897-seal-encoding/`](897-seal-encoding/README.md). Every number below comes from a file in
`897-seal-encoding/results/`, regenerated by `run.sh` (exit 0, 2026-11-17).

- **A**: alpha.6 as PR #894 ships it (JCS + I-JSON, the verifier re-serialises what it parsed), plus #895
  (schema-declared 64-bit values as strings).
- **A′**: JSON kept. `manifest.json` is stored as exactly its JCS bytes with no `manifest_hash` key; the seal is
  `blake3` over the stored bytes and lives outside them (a `manifest.seal` member); readers refuse bytes that are not
  their own JCS form; I-JSON and #895 stay.
- **B**: the stored manifest is deterministic CBOR: RFC 8949 §4.2.1 core deterministic encoding plus a tessera
  profile (text keys only, no tags, no NaN/±∞, and **numeric reduction** as in dCBOR: an integral float is written
  as its integer). JSON is a derived view. B is sealed over its stored bytes too (see "Rejected alternatives").
  **B0** is the same profile without numeric reduction; the spike keeps it only to show what that rule buys.

**Reading.** A′ and B both close the class A leaves open: under both, one seal has one byte string and one meaning
in every reader the spike ran (0/59 respellings, 0/7 sealed reader splits; A: 59/59 and 7/7). B needs numeric
reduction for that; without it (B0) the S7 split is back. Between the two, the choice is **native 64-bit
integers (B)** against **every existing seal and signature kept, no dependency, stock writers and decoders, and
`jq` legibility (A′)**. #895's typed strings give A′ exact 64-bit values in all three readers, so the spike
recommends A′.

## 1. What the current design hashes, and why the bypass class keeps coming back

A hashes `JCS(parsed − manifest_hash)`: the verifier re-serialises what it parsed. Every bypass so far lived in
the gap between the stored text and that re-serialisation: keys a typed model dropped (#573), a struct read from an
array (#873), duplicate keys whose winner differs per parser (#883), integers a double can't hold (#886). Each got
its own rule. The rules work (A refuses S1–S6, § 3), but the gap itself stays: any byte string whose
re-serialisation is the sealed one verifies, so one seal covers many files, and a reader that interprets the
text, not the re-serialisation, can disagree with the seal's meaning. The attack replay shows this is real (S7).

The alternatives every comparable format uses (issue comment of 2026-11-17): OCI, git, BagIt and DSSE hash the
**stored bytes** and keep the digest outside them. A′ applies that to tessera's JSON; B applies it to CBOR.

## 2. Prototypes (`corpus`)

`cargo run --release -- corpus` over the 13 tracked products (`results/corpus.md`):

- **A′ keeps every seal.** `digest(JCS(manifest − manifest_hash))` is, by definition, the seal A computes, so
  storing exactly those bytes makes `blake3(manifest.json)` equal the recorded `manifest_hash`: **13/13**, and
  **8/8** equal `corpus/corpus.json`'s goldens. `id` and `content_hash` don't depend on the stored form. So no
  golden, `Source` edge, collection member pin, repository ref or OCI annotation changes, and no signature either:
  the `ed25519-env-v1` envelope binds six fields, and the only one taken from the product is the `manifest_hash`
  string, whose value is unchanged.
- **A′ verifies its own form** 13/13; **B verifies** 13/13 and **round-trips** 13/13 (decode → encode gives the
  same bytes; decode → JSON is the original object under JCS, where reduction's `1.0` → `1` is invisible).
- **`id` needs no decision.** JCS is compositional: `JCS(id_inputs)` appears verbatim inside the A′ bytes and
  hashes to `id` (13/13). "JCS over `id_inputs`" and "hash the `id_inputs` byte slice" are the same bytes, so A′
  keeps the definition and a reader may use either.
- **Sizes.** Today's pretty JSON totals 40,804 B; JCS 27,103 B (66 %); CBOR 22,567 B (55 %); CBOR with the
  `blake3:` strings as 32-byte byte strings 20,656 B (51 %). The largest manifest is 5.7 KB; JCS and CBOR differ
  by at most 661 B per product (pretty JSON and CBOR by up to 2.5 KB), against block payloads of megabytes to
  gigabytes (ADR-0054: size is a non-argument).

What the table says:

- **Everything after sealing is caught or refused by all three** (T1–T3, T8–T10: 77/77). Under A and A′, T10 is
  refused by the I-JSON rule, not by the seal. Under A that rule is all that stands between T10 and a verify:
  JCS writes `2^53+1` and `2^53` the same, so their A seals are equal. Under A′ the two stored byte strings have
  different seals (`results/numbers.txt`).
- **Respelling is A's open class.** T4–T7 keep A's seal on 46 files; S8 shows the same freedom for 13 files. On its
  own a respelling is malleability: one seal, many files, so the OCI layer digest of a `.tsra` changes while its
  `manifest_hash` doesn't. **T7/S7 turn it into a reader split under one valid seal.** The seal over
  `"shape":[64.0,…]` equals the seal over `[64,…]`. Rust's typed block read refuses `64.0` for a `u64`
  (`invalid type: floating point 64.0, expected u64`), Python reads a `float`, and JavaScript reads `64`
  (`results/agree-python.txt`, `results/agree-js.txt`). Closing it under A takes yet another rule per spelling.
- **A′ refuses every respelling at the bytes** (59/59, and S7 7/7), with one rule: the bytes must equal their own
  JCS. That rule is **required**: without it A′ still catches T4–T7 (the seal is over the bytes), but S7 and S8 are
  sealed by the attacker and would verify, which reopens the split.
- **B refuses respellings by construction, and S7 only with numeric reduction.** CBOR has separate float and
  integer types, so without reduction (B0) a sealed `64.0` is a different value, the seal verifies, and the
  readers split as under A (7/7), because JavaScript has one number type. With reduction, an integral float is not
  in the profile (7/7 refused). A non-integral float in an integer field (`64.5`) is a typed-layer rule under
  every option.
- **The reader-side I-JSON rule stays required under A′.** The canonical check alone does not refuse every
  integer beyond 2^53. `9007199254740992` and `1730000000123456800` are exact doubles, so each is its own JCS form
  (`results/numbers.txt`), so the byte comparison alone would pass them; S5b shows A′ refusing `…800` through
  I-JSON. (The prototype runs I-JSON inside the strict parse, before the comparison, so S5b does not run the
  comparison on its own; that half rests on `numbers.txt`.) Such values are what a rounding writer emits (JCS
  turns `…789` into `…800`), so readers refuse them too, as PR #894 decided.
- **S2–S4 are typed-layer rules in every option.** A duplicate block name and an array-form record are encodable
  in JSON and CBOR alike; the encoding cannot remove them. tessera-core's typed layer refuses them for all three.
  The B prototype reaches it through a JSON bridge; a real B needs ADR-0060's declared-field walk and
  `from_declared_form` ported to CBOR values.
- **S5/S5b are B's genuine win**: an epoch-ns stored as a number verifies and stays exact. A and A′ refuse it at
  the door (fails closed, with the advice to write a string) and rely on #895 to type it.

## 4. Reader agreement on 64-bit values (`vectors`, `agree`)

Vectors: `u64::MAX`, `i64::MIN`, epoch-ns `1730000000123456789`, `2^53+1`.

| Reader | A/A′ as JSON numbers | A/A′ as #895 strings | B as CBOR integers |
|---|---|---|---|
| Rust (tessera-core `parse_strict` / profile decoder) | refused (I-JSON) | exact | exact (`u64`/`i64`) |
| Python `json` / `cbor2` | exact without the hook; refused with the reference reader's hook | exact (`int()`) | exact (`int`) |
| JavaScript `JSON.parse` / `cbor-x` | **rounded 4/4** (`…123456800`, `…552000`) | exact (`BigInt()`) | exact as `BigInt`; with `int64AsNumber` **rounded 4/4** |

- Under A/A′ the exact value lives in a string, so every reader gets it exactly and the schema says how to type it
  (JSON-LD's `{"@value": "…", "@type": "xsd:long"}` pattern, #895).
- Under B, `cbor-x` returns `BigInt` for the four large values and `number` for `42`, so the JS type of one field
  depends on its magnitude (JavaScript refuses arithmetic mixing `BigInt` and `number`; not probed here); the
  common `int64AsNumber` option rounds
  silently. B's derived JSON view (`tessera inspect --json`) has the same choice to make: exact integer text
  rounds in `JSON.parse`.
- **Round trips.** Decode-then-re-encode reproduces the stored bytes: A′ in Python and JS 13/13; B in `cbor2`
  (`canonical=True`) and `cbor-x` 13/13. B0 in `cbor-x` only 10/13: the stored float `1.0` (`rescale_slope`,
  `f9 3c00`) decodes to the JS number `1` and re-encodes as the integer `01`. Numeric reduction is necessary for
  JavaScript to reach B's bytes, not sufficient: the corpus's only floats are integral (`1.0`, `-1024.0`, in 3
  products), and `cbor-x` writes a non-integral float such as `1.5` as a 9-byte double, which profile B refuses.
  A product holding `0.5` would not round-trip through `cbor-x`; the `cbor2` 13/13 carries the same caveat.
- Lone surrogate: `JSON.parse` and Python `json.loads` accept `"\ud800"`; Rust refuses; Python's `jcs` raises on
  it, JS `canonicalize` throws. Under B it can't be expressed in valid UTF-8, but `cbor-x` decodes the CESU-8
  bytes to `"���"` where Rust and `cbor2` refuse.

## 6. Determinism: what each option rests on

Cross-arch byte identity (x86_64 vs aarch64) is out of reach on this seat. What each option's determinism rests on:

- **A and A′**: JCS. Object keys sorted by UTF-16 code units, fixed string escaping, and ECMAScript number
  formatting (shortest round-trip decimal; `serde_jcs` uses `ryu-js`, an integer-arithmetic algorithm). Probe:
  200,000 doubles (random bit patterns across all exponents, plus edge cases such as `5e-324`, `1e21`, `1e-7`,
  `65505`) format identically in `serde_jcs`, Python `jcs` 0.2.1 and JS `canonicalize` 5.1.0
  (`results/floats.txt`, 200000/200000 each). Under A a writer that disagrees is invisible; under A′ it is refused,
  so a determinism bug becomes a refusal, never a silent second seal.
- **B**: shortest integer heads (trivial), bytewise key order, numeric reduction (an exactness test), and float
  narrowing f64 → f32 → f16 only when exact (bit operations; IEEE casts are deterministic). Probe: the prototype's
  preferred serialization and `cbor2` 6.3.0 `canonical=True` agree on the same 200,000 doubles (that sample
  reaches the f16-subnormal path only through its edge cases, which the unit tests pin). No library tested
  implements the reduction. `minicbor` and `cbor4ii` write `1.5` as 9 bytes (`fb…`) where the profile needs 3
  (`f9 3e00`), and `minicbor` writes a map in the caller's iteration order without sorting
  (`results/libprobe.md`).

## 8. Pre-mortem: it shipped, and a year later it failed. How?

Each failure is a probe result, not a guess.

**A.** A signed product's `manifest.json` passes through a tool that reformats JSON (a pretty-printer, `jq`, a
proxy). The seal still verifies (T4–T6, 39/39). One such tool writes `64.0` for a float-typed intermediate (T7).
The seal verifies, Rust refuses the block, and a JS viewer shows the volume. The archive now holds two `.tsra`
with one `manifest_hash` and different OCI digests, and three readers disagree on one of them. The fix is rule
number five.

**A′.**
- *A third-party writer emits "canonical JSON" that isn't JCS.* Python's obvious
  `json.dumps(sort_keys=True, separators=(",",":"), ensure_ascii=False)` matches JCS on all 13 corpus manifests
  but writes `1.0`, `1e-07` and `-0.0` where JCS writes `1`, `1e-7` and `0` (`results/premortem-python.txt`).
  Its products are refused, loudly. Mitigation: the SPEC names JCS libraries, and the three tested agree on
  200,000 doubles.
- *A reader skips the canonical check* and only hashes. It accepts sealed `64.0` (S7), and the split returns in
  that reader. *A reader drops I-JSON* as "redundant": it accepts S5b's rounded epoch-ns. Both rules must be in
  every reader (Rust, reference reader, wasm), and the seal cases must carry S5b and S7.
- *Someone treats `manifest.seal` as trust.* It is self-attesting, exactly like today's in-band
  `manifest_hash`: it detects accidents. Trust stays where it is today: the signature envelope, `Source` edges,
  collection pins, citations `id@manifest_hash`, OCI annotations.
- *A 64-bit value arrives as a number* from a DAQ config in `generation.config`. It is refused at the writer
  (S5, 13/13), with the advice to write a string; #895 types the declared fields. Opaque bags fail closed rather
  than round.

**B.**
- *A Python or JS writer encodes floats with its library.* `cbor2` (`canonical=True`) writes `1.0` as a float,
  which the profile refuses; `cbor-x` writes `1.5` as a 9-byte double, also refused. Every writer outside the
  reference implementation needs a reducing, preferred-float encoder first.
- *A Python consumer uses `cbor2.loads` as its reader.* It accepts trailing bytes after the manifest (a sealed
  16-byte item it never sees), NaN, `undefined`, duplicate keys (last wins) and unsorted maps; its own canonical
  re-encode check misses NaN and `undefined` (`results/agree-python.txt`, `results/premortem-python.txt`).
- *A JS viewer uses `cbor-x`*: invalid UTF-8 shows as `"���"` where Rust refuses; `int64AsNumber` rounds every
  64-bit value.
- *The profile ships without numeric reduction* (B0, or a later relaxation): S7's split returns (7/7) and JS
  round trips break (10/13).
- *Cutover*: every `manifest_hash` changes, so every signature, `Source` edge, collection pin and citation made in
  alpha stops verifying.

## 9. Recommendation: A′, with #895

A′ removes the re-serialisation class by construction (the seal is a hash of a file), and its one extra rule
(bytes = their own JCS) removes respelling and the S7 reader split, which A leaves open. It keeps every seal,
golden and signature, needs no dependency, reads with `jq`, and every stock JCS library tested reproduces its bytes
exactly. Its honest cost: one format change to where the seal lives (eight sub-issues, mostly mechanical), and
64-bit values must be strings typed by the schema (#895), so an untyped integer beyond 2^53 in an opaque bag is
refused instead of stored.

Readers **must** run both the canonical check and I-JSON (§3, S5b and S7). Migration: readers refuse the alpha
layout; `tessera migrate` converts it losslessly (seal-preserving, so signatures carry over).

**When B is the better choice.** B with numeric reduction is equally sound on the attack replay. It is the only
option that stores arbitrary 64-bit integers natively, including in schema-less places (opaque
`generation.config`, `extra`). If that is a hard requirement, ship B: the profile with numeric reduction, the seal
over the stored bytes, our own strict decoder and reducing writer in all three languages, and a full re-seal at
cutover (§7, eleven items).

### Rejected alternatives

- **A as is (+#895)**: cheapest, but the seal still covers many byte strings and the reader split of S7 exists
  today; each new spelling class costs another rule (the four bypasses so far were four rules).
- **A′ without the canonical check**: catches tampering, not attacker-sealed respellings (S7/S8).
- **A′ without the reader-side I-JSON check**: accepts the rounded integers of S5b.
- **B without numeric reduction (B0)**: the S7 split returns and JavaScript can't reproduce the bytes (§3, §4).
- **B with the seal kept inside the manifest**: hashing "the manifest minus one key" is a re-serialisation again,
  even if exact; the seal belongs outside the bytes in B as in A′.
- **A stored, unsealed `manifest.json` copy beside `manifest.cbor`** (owner, 2026-11-17): a second, unverified
  view, the same class as the zip differential.
- **TOML, YAML, RON, JSON5/KDL/EDN, Protobuf, FlatBuffers/Cap'n Proto, bincode/postcard, MessagePack, BSON/Avro**:
  rejected in the issue against the four criteria (an IETF/ISO spec, a standard deterministic encoding, mature
  readers in Rust/Python/JS, exact integers).
- **Amazon Ion**: typed arbitrary-precision integers and decimals, text and binary forms that are isomorphic,
  but no standard canonical encoding for hashing and a niche ecosystem in Python/JS; it would need a tessera
  canonical form of its own, which is the problem JCS and RFC 8949 §4.2 already solve.

### Signatures under each option

- **A′**: the `ed25519-env-v1` envelope is unchanged and stays valid (of its six bound fields, only the
  `manifest_hash` string comes from the product, and A′ preserves its value). Its payload is still a JCS
  re-serialisation, but of six known string fields after a strict parse; no number and no unknown key is
  involved, so the bypass class has nothing to act on. Moving the envelope to DSSE-style "sign the stored payload
  bytes" is a later, independent choice.
- **B**: COSE_Sign1 (RFC 9052) is the natural envelope (`coset` is maintained); `signer`, `signed_at` and
  `key_format` become protected-header parameters. Either way, every alpha signature must be redone.

### Option C (per-field commitments for PHI redaction), one paragraph

Both A′ and B hash the whole stored manifest, so redacting a field changes the seal in either. Per-field redaction
needs per-field salted digests inside the document, which is structure, not encoding. Prior art exists on both
sides: SD-JWT (IETF, JSON, salted disclosures whose digests sit in the signed document), ISO/IEC 18013-5 mdoc
(CBOR + COSE, a signed map of per-element digests), and Blockchain Commons' Gordian Envelope on dCBOR. C composes
slightly more naturally with B (digests as byte strings, COSE), but nothing in A′ blocks an SD-JWT-style design,
and ADR-0040's sidecar approach is independent of either.

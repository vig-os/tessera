# #828 round 2 — A3 re-measure and the M4b sweep (tessera-table-v2)

> **Status:** measurement report for the owner's A3 decision (#828, owner notes of 2026-11-22:
> [decisions](https://github.com/vig-os/tessera/issues/828#issuecomment-7078645489),
> [protocol](https://github.com/vig-os/tessera/issues/828#issuecomment-7078648876)). No profile constant is changed

## 1. Verdict

- **The A3 miss is real, not seat load.** In a reserved ksb slice, v2's whole-writer CPU time per event is **2.00×
  (GE) / 1.93× (Siemens)** v1's (v1/v2 = **0.50× / 0.52×**, floor ≥ 1.00×). User-space instructions per event
  (seat, whole process, exactly reproducible): v2 **+1,145 (GE) / +908 (Siemens)** instructions per event over v1.
  Round 1's 0.51× / 0.54× wall-clock ratios were right.
- **No point of the M4b sweep reaches A3.** The cheapest points reach 0.60× (GE: Pco 4, 65,536 values/page,
  262,144-row chunks, 197.9 ns/ev, 3.405 B/ev) and 0.57× (Siemens: Pco 4, 8,192, 65,536, 235.1 ns/ev, 6.987 B/ev).
  Pco level 8 → 4 saves 12–18 % of the CPU on GE and ≈ 9 % on Siemens, and costs +6.6 % (GE) / +0.35 % (Siemens)
  of size; values per page and framing move CPU by < 10 %.
- **On Siemens the cost is not Pco's.** Its CPU barely moves with the Pco level (235–266 ns/ev across all twelve
  points): two of its eleven columns are Pco, nine are `vortex.zstd` at level 9. Measurement M6 (round 1) put Zstd
  levels 1, 3 and 9 within 0.5 % of each other in size (5.856 / 5.850 / 5.829 B/ev on the 8-bit columns). The Zstd
  level was not a swept axis here; it is the obvious next lever for Siemens (§4).
- **On this host A4 and A5 miss for v2 too** (GE take-500 119.5 ms vs ≤ 100; full-scan decode 381 CPU-MiB/s vs
  ≥ 500), where round 1 on the seat passed (79.4 ms, 610 MiB/s). The floors are per core on an unnamed host; the
  ksb core (Xeon w9-3575X vCPU) is about 1.3–1.7× slower than the seat's on this code (v1 encode 8.4 vs 10.8 M ev/s
  per core, v1 decode 1572 vs 2745 MiB/s). The owner's A3 decision should name the host the A4/A5 floors refer to.

## 2. A3 re-measure

every run pinned to CPU 4 (`taskset`), host `compute-vm` (Intel Xeon w9-3575X). v1 = dev `f390528e`
(tessera-table-v1), v2 = #828 head `d0e87498` (tessera-table-v2), both built by crane in the job's closure, never in
the pod, from the **same** harness source (`tessera/crates/tessera-io/examples/table_profile.rs` with
`bench/ksb/828-m4b/harness-cpu-perf.patch`, sha256 `089b7e12…f616569`). Inputs: the #822 fixtures, sha256-verified
in the job, decompressed to the pod's local scratch; outputs on local scratch; binaries in the nix store (nothing on
`/mnt/HDD`). Each write is the real streaming writer (`StreamWriter::push_table`, one worker); its timed section
excludes loading the columns. v1, v2, v1, v2 … × 5 rounds per fixture; median (min–max). Table bytes of every run
were checked equal to round 1's (GE 211,421,352 / 174,329,624; Siemens 412,902,352 / 382,995,576).

**CPU time** is user + system of all threads (`/proc/self/stat`) over the timed section. **Instructions** could

## 3. M4b sweep (same job, same protocol)

v2 with the three parameters read from the environment by a job-only seam (`bench/ksb/828-m4b/m4b_seam.py`, applied
to the job's source copy, never committed; with nothing set it is the #828 profile, row 9 of each table): Pco level
{4, 6, 8} × values per page {8,192, 65,536} × numeric chunk framing {65,536 rows = one row-group, 262,144 rows = four
row-groups}. 65,536 values per page is one page per row-group; 262,144 rows is one Pco chunk at `vortex-pco`'s
2^18-value cap and one Zstd frame per four row-groups. The Zstd level stays 9. Five interleaved rounds per point
(every point once per round); decode (3 repetitions) and take (5) on the last round's file.

Reading the tables against the floors: A1 holds on Siemens at every point and on GE only at Pco level 8 (level 6:
3.251–3.276, level 4: 3.405–3.430 > 3.25); A3 (≥ 1.00×, i.e. ≤ 119.5 ns/ev on GE and ≤ 135.1 on Siemens) holds at
none; A4's ≤ 100 ms take-500 fails on GE at every point on this host (116–187 ms) and holds on Siemens only with the

≥ 500 MiB/s full-scan decode fails at every point on this host (234–426 CPU-MiB/s).

## 4. What the owner can choose from (no recommendation is implemented)

1. **Keep the profile and accept A3 ≈ 0.5×** (re-decide the floor): best size at 2× v1's encode CPU.
2. **Pco level 4–6 at the committed framing:** −10 to −12 % CPU on GE (−5 to −9 % on Siemens), A3 still ≈ 0.55×;
   both levels break A1 on GE.
3. **Add the Zstd level to the sweep** (not run; outside this round's axes): Siemens' encode is dominated by Zstd 9
   on nine columns, M6 shows levels 1/3 cost ≤ 0.5 % size. A follow-up job is one more axis in `run.py`.
4. **A cheaper numeric codec for some columns** would be a new design decision (outside the accepted note).

  tessera/bench/ksb/828-m4b/seat_instructions.sh

Raw records: the job's `results.jsonl` (every run with its host state before and after) and `summary.json`, and the
seat's `results.jsonl`, kept with the run record on ksb-ws (`/mnt/HDD/larsgerchow/t828/r2/`,
`/mnt/HDD/larsgerchow/t828/seatperf-results.jsonl`). They are not committed: they are measurement logs of a private
fixture's runs (no fixture data in them).

The committed scripts differ from the ones that ran only in output plumbing and lint fixes (`print` → `sys.stdout`,
`mkdir -m`, and the seat script's unused `task-clock` field, which its run recorded empty); the measured code paths
are the same.

Friction recorded on the way: (1) the fixture inside the job's nix snapshot made preparation's `nix copy` time out
at 1,800 s (`tessera-828-m4b-probe-1`), so it is staged into the job's results volume instead; (2) the job image has
no `getconf` (`tessera-828-m4b-r2-1` failed on it after building); (3) ksb pods cannot count instructions
(seccomp). Item (2)'s failed job left its staged fixture copy in its results directory; the job script now deletes
the staged copy on every exit.

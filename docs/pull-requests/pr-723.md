# [PR 723](https://github.com/vig-os/tessera/pull/723) ci: fail the nix flake check summary on a missing, extra or empty check set

Closes #722. Three findings from the review of #700.

## 1. The summary fails on a missing, extra or empty check set

The summary trusted whatever `nix eval .#checks.<system>` returned. `{}` with status 0 printed "0 passed, 0 failed" and the leg stayed green.

- `.github/nix-flake-checks.txt` lists the flake's Linux checks by name, with a literal `count:`. It is the one list, and two consumers hold to it:
  - **flake.nix** throws at evaluation when `checks` differs from the list (on Darwin, minus the Linux-only checks). It names the unlisted and undefined checks, so a new check can't land without the list being updated.
  - **`scripts/nix-check-summary.sh`** is the summary step, moved out of the workflow YAML. It fails the leg when the evaluated names differ from the list and names what is `missing` and what is `unexpected`. Names are compared as exact whole lines with `sort`/`comm`, never with jq `inside`/`contains`. The list's count must be positive and match its names. A failed evaluation now fails the leg instead of re-raising nix's status.
- `--self-test` stubs `nix` and `nix-store` and runs 18 cases, and the case count is pinned. The cases cover an empty set, an evaluation that prints nothing, a non-numeric `CHECK_RC`, a missing check, an extra check, a substring-named check, a failed or non-object evaluation, a red row on a green run, and an invalid list. The new `nix-check-summary` flake check runs it on both arches.

Fail-before proof, using the same stubbed `nix` and the list `{alpha, beta, gamma}`:

| stubbed eval | old inline summary | `scripts/nix-check-summary.sh` |
|---|---|---|
| `{}` | exit 0 | exit 1: `missing: alpha beta gamma; unexpected: none` |
| `{alpha, beta}` | exit 0 | exit 1: `missing: gamma; unexpected: none` |

I also ran a mutant with the set comparison disabled. The self-test failed it on 4 cases: empty, missing, extra and substring.

## 2. The registry check's EXIT trap

`start_registry` installed `trap … EXIT`, which replaced stdenv's `exitHandler` trap and every `exitHooks`/`failureHooks` entry with it. The registry is now stopped through `exitHooks`, and on failure `failureHooks` prints its log first, as `s3-range-read` does. I checked this with a probe derivation that registers an exitHook and then sources the script. The old script never ran the hook; the new one does. A failing probe still prints the registry log.

## 3. Cache trust

The script now carries a note next to the cached-output lookup. Counting a substituted check as passed is sound only while fork code cannot write to the shared ksb cache. The note cites why that holds today:

- fork PRs never reach ksb: the workflow fork guard, the approval setting, and exo-pet/exo-fleet#949;
- ARC pods only read `http://10.0.2.2:8092/ksb` and hold no attic token (exo-pet/exo-fleet#911);
- the only writers are the `ksb-attic-push` units on the ksb host and the seat (g-fleet `hosts/ksb/attic-push.nix`, exo-pet/exo-fleet#919).

The remaining gap is that the seat pushes whatever its users build. That gap is already tracked in exo-pet/exo-fleet#911 (a host-only CI cache key).

`s3-range-read` and `tessera-io/src/cloud.rs` are untouched; they belong to #707.

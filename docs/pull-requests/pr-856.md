# [PR 856](https://github.com/vig-os/tessera/pull/856) ci(release): keep main equal to the latest release

Keeps `main` equal to the latest release from now on. #855 promotes `main` to v0.1.0-alpha.5 once, and this PR makes the promotion part of every release.

## Why `main` can't be auto-merged
`main`'s ruleset (Main protection, 24163538) requires a pull request with **one approving review**, a green `nix flake check`, and no force-push. Only an organization admin can bypass it. So no bot fast-forwards or merges `main`, and this PR changes no ruleset. Automation does everything up to the approval.

**The human step:** when a release is cut, approve and merge (merge commit) the `release/promote-v<version>` PR that the bot opens. It is step 4 of the new release checklist, `docs/RELEASING.md`.

## Which App mints the token, and why
The workflow uses the **vigos-devkit-upgrade** App. Its installation (all repos) grants contents, pull_requests and workflows write. Its org secrets `DEVKIT_UPGRADE_APP_CLIENT_ID` / `DEVKIT_UPGRADE_APP_PRIVATE_KEY` are shared with this repo, and `devkit-upgrade.yml` mints it successfully every week. The token requests exactly contents, pull-requests and workflows write.

`workflows: write` is required: a promotion branch carries every workflow change since `main`'s last release (`ee277ad..v0.1.0-alpha.5` touches 9 workflow files), and GitHub refuses an App such a ref or commit without that permission. The release-plz App (RP_APP_*) has no `workflows` permission. By owner decision (2026-11-15) it keeps none, since the release PR it opens never touches a workflow.

## What changed
- **`.github/workflows/promote-main.yml`** runs after every successful `Release` run on a tag, and on `workflow_dispatch` (`tag`, `dry_run`). It opens `release/promote-<tag>` → `main` with a vigos-devkit-upgrade App token (contents, pull-requests and workflows write; see above). With that token the PR's CI runs, and its bot author is exempt from the branch-name check. It runs on a hosted runner (#688), and its actions are pinned by SHA.
  - **Trigger is `workflow_run`, not `release: published`.** cargo-dist publishes the Release with `GITHUB_TOKEN`, and those events start no workflows. That's why `release-nix.yml` has never run on its own (#438, `gh run list -w release-nix.yml` shows only one manual dispatch). The workflow runs nothing from the triggering run. zizmor's `dangerous-triggers` finding is suppressed inline, and the header explains why.
  - **The head is usually a GitHub-made merge commit, not the bare tag.** The ruleset sets `strict_required_status_checks_policy: true`. After a promotion `main` has a merge commit that the next tag lacks, so a bare-tag head is *behind*. #855 is in that state now (`viewerCanUpdateBranch: true`). Merging it would take "Update branch", which pushes a new head. That dismisses the approval (`dismiss_stale_reviews_on_push`) and restarts `nix flake check`. Instead the workflow cuts the branch at `main`'s tip and merges the tag into it with `POST /merges`, which GitHub signs. When `main` is an ancestor of the tag, the head is the tag commit itself.
- **`scripts/promotion-plan.sh`** computes the plan. It opens nothing when `main` already contains the tag. It refuses a non-`v<semver>` tag, a tag that moved since the Release run built it, and a release older than the newest tag. It also refuses a merge that conflicts or whose tree is not exactly the tag's tree. If GitHub refuses the merge, the run deletes the branch it just created at main's tip, and only while the branch still points there. The workflow checks GitHub's merge commit against that tree, and checks that it is signature-verified.
- **`release-promotion` flake check** runs the planner's `--self-test` on throwaway repos. It is listed in `.github/nix-flake-checks.txt` (count 31).
- `TAG_RE` / `semver_sort` / `semver_le` move to `scripts/lib/semver.sh`, which `last-release-tag.sh` sources too. `release-tag-resolution` still passes.
- **Docs:** new `docs/RELEASING.md` (the checklist, the promotion design, and what each failure means). `CONSUMING.md` now says `main` is the latest release. `release-plz.toml` and `release-plz.yml` point to the checklist.

## Proof
- `bash scripts/promotion-plan.sh --self-test`: 13/13 ok, exit 0. `nix build .#checks.x86_64-linux.release-promotion .#checks.x86_64-linux.release-tag-resolution`: exit 0.
- Each rule fails the self-test when it is removed. These are mutations of a scratch copy: no tree check, no latest-release check, no no-op, no sha check, always-merge. Each one gives exit 1 with the matching `FAIL` line.
- Real repo before #855: `scripts/promotion-plan.sh v0.1.0-alpha.5 origin/main 5373f61…` gives `action=open head=merge tree=85a3b0f…`. That tree equals `v0.1.0-alpha.5^{tree}`. For `v0.1.0-alpha.4` it fails with "not the latest release (v0.1.0-alpha.5 is)".
- prek hooks (actionlint, check-action-pins, ksb fork guard, shellcheck, pymarkdown, typos) pass. `zizmor --offline` reports no findings. `guardrails-gates` and `nix-check-summary` build.
- **Not exercised before merge:** the live API path (mint, `git/refs`, `merges`, `pr create`). A `workflow_run` workflow only runs from the default branch. Once this merges, run `gh workflow run promote-main.yml -f tag=v0.1.0-alpha.5 -f dry_run=true`. After #855 merges, the same run reports the no-op. The first real promotion is the next release.

Closes #854

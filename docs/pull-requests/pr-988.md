# [PR 988](https://github.com/vig-os/tessera/pull/988) docs(adr): collection refs, version edge and gc through members (Accepted)

ADR-0067, **Accepted** (owner, 2026-11-26), for #947. It covers refs to collections, a version edge on collections,
and `gc` that marks through members. These are what a kit workspace needs to be a second lineage of `current`
collections over a shared base. Docs only; the implementation is still to come, so #947 stays open.

## What the owner decided (2026-11-26)

The repository layout is designed greenfield; compatibility with earlier builds is not a goal.

- **D1, repository layout 2.**
  - Refs are typed records, `<kind> <address>`, in two separate namespaces, `refs/lineages/` and `refs/pins/`. The
    lineage log cache moves under `log/lineages/`.
  - A record's kind is checked against the object it names.
  - Both namespaces use #975's percent-encoding. PR #990 lands first.
  - A `layout` marker makes every other layout a refusal that names the layout found and the one required.
  - There is no migration verb, the same policy as ADR-0066 rule 10.
- **D2, a sealed and additive `sources` list on collections.** `supersedes` pins the predecessor's `manifest_hash`.
- **D3, `gc` marks through members, recursively.** Members are closed inside the repository; edges stay open.
- **D4, pins live in `refs/pins/`.**
- **D5, the kit flow.** A new `forked_from` role, plus a required, caller-supplied `fork` token in `id_inputs`.
- **D6 to D9.** The member diff; discard cost after the #987 measurement; retention across a fork; no branches and
  no content merge.

Each rejected option is kept, with one line on why it was rejected. The ADR also has failure modes, a test plan per
step, and an eight-step build plan whose first step introduces layout 2.

**Coordination with #990:** its `migrate-refs` verb, and its text about the old `refs/pin:` reservation, have no place
under this ruling. The ADR asks for them to be dropped from #990 before it lands; if they land, step 1 removes them.

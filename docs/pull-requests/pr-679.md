# [PR 679](https://github.com/vig-os/tessera/pull/679) fix(io): bound every StreamWriter job with a credit window released on in-order commit

Part of #677 (PR 1 of 2: gap 2, end-to-end StreamWriter backpressure). The file-backed single-table sink
(gap 1, `encode_streaming`) follows in a separate PR.

## Root cause

`StreamWriter` bounded only its input channel. `commit_loop` drained the output channel into an unbounded
`BTreeMap` reorder buffer, so channel capacity did not bound the encoded payloads it held. With job 0
held and jobs 1..N finished, the committer kept all N payloads while the producer kept pushing.

## Contract (ADR-0026 amendment "StreamWriter memory contract")

A job takes a credit when it is **pushed** and gives it back only when it is **committed in order**. So
one window covers queued, encoding and reorder-pending jobs. With `J = max_in_flight`,
`B = max_in_flight_bytes`, `W` workers and `P` the largest job's encoded payload (data + companions):

- jobs in flight `≤ J`;
- encoded bytes held `< B + min(W, J) × P`.

Gate 1 (`push`) waits while `J` jobs are in flight or `B` bytes are held. Gate 2 (encode start) waits
while `B` bytes are held, **except** for the job the committer waits on, which always runs. So there is
no deadlock, and a job larger than `B` runs alone. A failed encode or commit, or a panicking worker,
closes the window, so `push` errors instead of hanging. The committer also errors if a pushed job is
missing at the end, instead of sealing a truncated product.

## Public API

- `StreamWindow { max_in_flight, max_in_flight_bytes }` (`#[non_exhaustive]`), built with
  `StreamWindow::new` (both clamped to ≥ 1).
- `StreamWriter::with_window(session, workers, window)` and `StreamWriter::window()`.
- `StreamStats { peak_in_flight_jobs, peak_in_flight_bytes, max_job_bytes, jobs_pushed, jobs_committed,
  producer_stalls }` (`#[non_exhaustive]`), read live via `StreamWriter::stats()` or from
  `StreamWriter::finish_with_stats(out) -> (Manifest, StreamStats)`.
- `WriteConfig::stream_window(unit_bytes)`.
- Unchanged signatures: `StreamWriter::new(session, workers, capacity)` now uses a window of
  `capacity + workers` jobs and `DEFAULT_RAM_BUDGET` bytes. `StreamWriter::with_config` uses
  `ring_depth(unit_bytes) + workers` jobs and `ram_budget` bytes.

The default adds `+ workers` to the queue capacity on purpose. A window of only `capacity` would leave
workers idle whenever `workers > capacity` (e.g. `examples/stream_write`'s `cap=2, w=4`), which loses
today's throughput.

## Tests (`tessera-io` `stream::tests`, all timing-free)

- `held_first_job_cannot_grow_in_flight_past_the_window`: job 0 is held at a barrier. Exactly `J` jobs
  are admitted, the producer stalls on job `J`, and nothing past the window is encoded. After release,
  the output is in order and byte-identical to an unthrottled run. **Before the fix** (same scenario
  through the public API, on `origin/dev`): `32 jobs were pushed and 31 encoded and buffered behind the
  held job 0, past a window of 4`, exit 101.
- `byte_budget_bounds_encoded_bytes_while_the_first_job_is_held`: the byte credit stops the producer,
  and the peak stays `< B + min(W, J) × P`.
- `encode_gate_stops_new_encodes_once_the_byte_budget_is_held`: isolates gate 2. Removing its byte check
  fails it (`jobs encoded past a held byte budget`, left 4, right 0).
- `job_larger_than_the_byte_budget_completes_alone`: a 1-byte budget with 1 and 4 workers completes, and
  the peak is reported.
- `content_hash_is_identical_across_workers_and_windows`: workers 1/4/16 × windows 1/2/2-with-1-byte/
  default give identical `content_hash`, `manifest_hash` and sealed file bytes.
- `failed_encode_…` and `panicking_worker_closes_the_window_instead_of_hanging_the_producer`: liveness.

`cargo test -p tessera-io` passes (exit 0). `cargo clippy -p tessera-io -p tessera-ingest --all-targets
-D warnings` and `cargo fmt --check` pass (exit 0).

# [PR 634](https://github.com/vig-os/tessera/pull/634) fix(io): chunk statistics on nullable columns with nulls

## Root cause

`ColumnData::as_i64` returns the **present** values of a nullable column, with NULLs dropped, so its result
is not row-aligned. Its length is the non-NULL count. `table_chunk_index` converted the whole stat column
once and then sliced that result by each row-group's **row** range (`stat_vals[start..end]`). With one NULL
in 3 rows, the slice `[0..3]` hit a 2-element vector: `range end index 3 out of range for slice of length 2`.

## Fix

`ColumnData::chunk_stats` is now the single definition of a row-group's statistics. `table_chunk_index` takes
it over each row-group's **slice** of the column, so the rows are sliced first and the values extracted second.
NULLs are excluded from `count`/`min`/`max`/`sum`/`sum_sq`. An all-NULL row-group carries the empty chunk's
stats (`ChunkStats::identity()`), which pruning skips for every range. That is exact, because no NULL lies in a
value range. No `ChunkStats` field is added; a NULL count is format work for #522. The rustdoc on `as_i64`,
`chunk_stats` and `table_chunk_index` now documents the semantics and the non-row-aligned `as_i64` contract.

## Sites checked

| Site | Before | Now |
|---|---|---|
| `table::table_chunk_index` (batch stats) | **bug**: whole-column `as_i64` sliced by row range, which panicked | per-group `slice().chunk_stats()` |
| `accumulate::TableStreamWriter::flush` (live fold) | correct: slices the group first, then `as_i64` | same helper (`chunk_stats`), so batch and streaming cannot drift |
| `multiblock::LogicalTableView` stats fallback | correct: whole-column stats, no slicing | same helper |
| group digest ("every column's LE bytes") | row-aligned `slice().to_le_bytes()`, no indexing bug | unchanged; but it hashes the bytes under a NULL, see #632 |
| `.cidx` builder (`chunk_index_block`) | serialises the `ChunkIndex`, never touches columns | unchanged |
| pruning (`ChunkStats::overlaps`, `ChunkIndex::prune`) | reads min/max only; `None` → skip | unchanged; an all-NULL chunk is skipped correctly |
| CLI `stats` sidecar path | array blocks only, which are never nullable | unchanged |

The `u64 > i64::MAX` case still errors when the value is **present**. If the whole column cannot convert, some
group cannot either. A fresh review found one more instance of the root cause: `as_i64` on a nullable column
checked the `u64` range over **every** slot before filtering by validity. A `u64::MAX` under a NULL therefore
refused the column: the batch index errored and the live fold silently folded empty stats. The fix filters by
validity first (`ints_where`), so the value under a NULL never decides anything.

## Determinism

Before this fix, any table with a NULL in its stat column panicked before sealing. No existing product, sidecar
or corpus golden changes: the `conformance` corpus test passes unchanged.

## Tests

Each acceptance case has a regression test. Before the fix, six of them panicked at
`table.rs:1487:47` (`cargo test -p tessera-io --lib -- chunk_index_ live_index_fold` → rc=101, 6 failed):

- the issue's minimal repro (3 rows, 1 NULL, nullable `i1`)
- NULLs at the start, middle and end, with `i8::MAX` under each NULL, so a leaked NULL would show as the max
- a nullable float with NaN and NULL next to the stat column, with the digest pinned to "every column's LE bytes"
- a nullable string column: this is a typed rejection (#457: not representable yet), never a panic. It never
  panicked, because `validate_nullable` rejects it first
- an all-NULL chunk, alone and next to a populated chunk
- a multi-chunk table where only the middle chunk has NULLs
- batch ≡ streaming: the live fold's root **and** aggregate equal `table_chunk_index` over nullable `i8`/`f4` columns
- a `u64::MAX` under a NULL, on the batch path (present out-of-range values still refuse the column)
- batch ≡ streaming over an all-NULL row-group plus a `u64::MAX` under a NULL. With `as_i64` reverted to
  range-check-then-filter, both of the last two tests fail (rc=101)

After the fix: `cargo test -p tessera-io` rc=0 (164 lib + 7 integration + 6 doc), `cargo test -p tessera-core`
rc=0 (157), `clippy -p tessera-io --all-targets -D warnings` rc=0, `fmt --check` rc=0.

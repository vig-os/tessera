# [PR 487](https://github.com/vig-os/tessera/pull/487) feat(cli): tessera bench compare — head-to-head size and latency vs HDF5

`tessera bench compare` — the one command that produces the numbers `why-tessera.md` promised, so the
Parquet/HDF5 pitch (#390 scored it 2/5) can be checked instead of believed.

Closes #388

## Stage 1 of 2 — and why

**#460 is still open, so the arrow/parquet Rust crates are not on dev.** A Rust-native Parquet row
would have meant adding the same dependency that PR is adding. This ships `.tsra` vs HDF5 — both
native in the tree today, zero new compilation — and Parquet becomes an additive row when #460 lands.
The output says so in both formats, so nobody reads the table thinking Parquet was omitted for
flattering reasons.

Prior art matters here too: `tessera/bench/ecosystems/` (#143) already compares seven formats through
real-library adapters. This does not replace it; it applies a stricter method to the two formats the
AX pitch actually turns on. Backporting that method to the broader harness is filed as **#485**.

## Results, after the review's fairness fixes (Xeon w9-3575X x88, ext4, kernel 6.8.0-31, median of 5)

Volume, 256³ int16 (32 MiB raw):

| format | settings | size | full read | ROI read (warm) |
|---|---|---|---|---|
| Tessera | pcodec (default), 64³ | 256.1 KiB | 0.0244s | 0.0008s |
| Tessera | zstd (tuned), 64³ | **225.5 KiB** | 0.0256s | **0.0003s** |
| HDF5 | contiguous, uncompressed | 32.0 MiB | **0.0162s** | 0.0005s |
| HDF5 | 64³ (= tessera's) + shuffle+gzip-4 | 698.8 KiB | 0.0506s | 0.0006s |

Table, 4M rows × (u8+2×f4) (61 MiB raw):

| format | settings | size | full read | 1 column | row ROI | write+seal |
|---|---|---|---|---|---|---|
| Tessera | Vortex cascade | 959.4 KiB | 0.0062s | 0.0024s | 0.0015s | 0.3179s |
| HDF5 | contiguous, uncompressed | 61.0 MiB | 0.0110s | **0.0017s** | **0.0001s** | **0.0361s** |
| HDF5 | 65536-row + shuffle+gzip-4 | **155.3 KiB** | 0.0682s | 0.0164s | 0.0023s | 0.3372s |

**The shuffle fix inverted the headline.** Adding the standard shuffle+deflate pairing took HDF5's
tuned table from 5.9 MiB to 155.3 KiB — so HDF5 is **6.2× smaller** than Tessera there, where the
previous revision of this PR showed Tessera winning by ~6×. The fixture (a monotonic u64 counter and
two floats with a tiny repeating period) is near-ideal for shuffle, which is precisely why omitting it
was not a neutral choice. Whether the ordering holds on real listmode floats is a question this
fixture cannot answer, and the docs say so rather than explaining the loss away.

**Everywhere else Tessera loses, also in the tables above:** writing is ~9× slower than uncompressed
HDF5 (it hashes and seals), uncompressed HDF5 wins the small raw-speed reads (row window by ~15×), and
the full volume read is slower than uncompressed HDF5 — while being ~2× faster than the compressed
HDF5 it is actually comparable to. Against the compressed configuration Tessera reads the table 11×
faster, a column 6.8× faster, and the volume 2× faster; the volume is also 2.7–3.1× smaller.

## The honesty rules, and what enforcing them cost

- **Same logical data**, generated once. The volume generator is lifted verbatim from
  `bench/ecosystems/common.py` (#143) so the two benchmarks can be read together.
- **Default AND tuned per format**, settings printed on every row.
- **Median of N with [min..max]**, never a single run.
- **Correctness gates timing** — reads are compared against what was written before their numbers
  count, so no format can win by returning something cheaper.
- **Cold eviction is verified, not assumed.** The first implementation evicted nothing: cold matched
  warm to four decimal places, because `POSIX_FADV_DONTNEED` skips dirty pages and the files had just
  been written. Fixed with an fsync first, and the report now prints the **measured** post-eviction
  residency via `mincore` — "eviction effective (worst residency 0.0%)" above. A cold-labelled row the
  kernel served from RAM is worse than no row, so the harness says which it got.
- **The settings line says what was ACTUALLY used.** An earlier draft printed "chunked 64³ (=
  tessera's)" on the *table* rows while the code chunked 1-D at 65536 — a fairness claim the code did
  not honour. Now per-modality: the volume gets tessera's cubic geometry so the ROI row compares
  layouts rather than chunk-size luck; the table says "65536 rows (1-D)". Unit-tested.
- **No invented knobs.** Tessera's array codec (pcodec/zstd) is a real tuned setting and is used; the
  table backend has no user-facing codec knob, and the report says exactly that instead of fabricating
  a lever.
- **The synthetic data is far more compressible than real acquisitions** (kept verbatim from #143 for
  comparability), so the size column is a ratio *between formats on identical input*. Printed as a
  CAVEAT in both output formats.

## Integrity is three different things, not one number

Per the review refinement: HDF5 gets a `fletcher32` variant and its checked read is timed, rather than
being written off as "n/a".

- **fletcher32** — per-chunk checksum. Detects *corruption* in the chunks you read. Unkeyed, covers no
  metadata; an attacker who rewrites a chunk rewrites its checksum.
- **tessera verify** — re-derives every block digest against a sealed manifest whose own hash also
  covers metadata and provenance, and which a signature (ADR-0037) binds to a signer.

Both catch a flipped bit. Only one answers "is this the artifact that was sealed, and by whom". The
timing column says what each costs; the report says what each buys.

## Output + tests

Human table and `--format json` (the JSON carries the method, the caveat and the eviction verdict, so
numbers cannot be consumed without their conditions). The trycmd walkthrough pins **structure** —
both settings tiers per format, the cache label, N, the caveat, the per-row claims, the integrity
wording — with `[..]` for every timing and size. 4 unit tests cover the median/spread statistic, the
per-modality settings fairness, the byte formatter and the cold verdict's ineffective-eviction path.

tessera-cli: 70 passed (was 59), 0 failed.

`hdf5-metno` and `ndarray` become direct tessera-cli dependencies; both were already in the build graph
(via tessera-ingest and hdf5-metno), so this adds no compilation.

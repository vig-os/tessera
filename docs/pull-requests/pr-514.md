# [PR 514](https://github.com/vig-os/tessera/pull/514) ci(nix): --max-jobs 2 --cores 4 — halve concurrent derivations, measured

`--cores 2` (#498) was not enough. #497 was **OOM-killed** — exit 137, the kernel's own killer, not a runner eviction — at 15.5 GB with four derivations still in flight, after memory jumped 6956 → 15531 MB inside one 4-minute window.

## What actually drives peak memory

The number of **concurrent derivations**. Each is a separate cargo/rustc process tree holding its own heap, so halving how many run at once halves the dominant term. `--cores` caps threads *inside* one derivation — the weaker factor.

The previous comment in this file framed the two as alternatives (*"`--cores 2` keeps four derivations in flight while `--max-jobs 2` serialises whole derivations and costs closer to 2x"*) and chose `--cores` on that basis. **That framing was the error.** They are independent knobs and the answer combines them.

## Measured, on scratch branches via `workflow_dispatch`

`--max-jobs 2 --cores 4` keeps total CPU at ~8 (2×4, as the old 4×2) while halving the concurrent process trees.

| leg | before (`--cores 2`) | after (`--max-jobs 2 --cores 4`) | Δ peak | Δ time |
|---|---|---|---|---|
| #497 x86_64 | 82m · 14651 MB · **1338 MB free** | 80m · **11171 MB** · 4818 MB free | −3480 MB (−24%) | −2m |
| #497 aarch64 | 66m · 11503 MB · 4444 MB free¹ | 54m · 11431 MB · 4516 MB free | −72 MB | −12m |
| #461 x86_64 | 85m · 13534 MB · 2454 MB free | 76m · **12980 MB** · 3008 MB free | −554 MB | −9m |
| #461 aarch64 | 69m · 11536 MB · 4410 MB free | 55m · 10690 MB · 5256 MB free | −846 MB | −14m |

¹ That baseline is **attempt 2**. Attempt 1 of the same run was the OOM-kill (15531 MB, exit 137, 48m), so under `--cores 2` this leg was *flaky near the ceiling* rather than deterministically dead.

**Wall-clock improved on all four legs** (−2, −12, −9, −14 min), which was **not** predicted — the argument had been that it would stay neutral since total CPU is unchanged. Max load1 held at 8.3–8.6 throughout, confirming CPU really was constant, so the gain is memory-pressure stalls disappearing. The memory fix paid a wall-clock dividend rather than costing one.

## The bar, and the leg that missed it

Accept criteria were fixed **before** the run: **peak < 12288 MB AND wall-clock < 100 min**.

**#461's x86_64 leg missed it — 12980 MB, over by 692 MB.** Reported as a miss rather than reinterpreted after the fact; fixing it in advance was the point.

Adopted anyway because the setting **dominates** the previous one on every leg measured — lower peak *and* lower wall-clock, four for four — and holding a measured improvement hostage to a 5% miss on one leg would be the worse call. But the ceiling risk on the heaviest branch is **reduced, not eliminated**: 3.0 GB of headroom.

**#495 stays open with that leg as the watch item.** A follow-up experiment (`--max-jobs 2 --cores 2` on #461) is already dispatched to test whether the stall-removal effect means halving concurrency again costs less wall-clock than a naive CPU-count argument predicts.

## Also in here

The `"cause stayed inferred"` caveat is removed, because it is now false. The sampler caught the mechanism twice: a leg pegged at 15.60 GB with ~340 MB available for 3m14s while load climbed 15.5 → 29.0 before taking the signal, and #497's outright exit-137 kill. Disk never fell below 58.9 GB across those runs — tested on six legs over four branches and never once supported as a cause.

A cross-reference to #507 is added where it is relevant and *not* conflated with this fix: there is no nix store cache, so every run recompiles the dependency graph (`tessera-deps` is a 19.4-minute serial prefix, 23% of a leg). That is a **wall-clock** issue, not a memory one — the deps phase peaks at 4.6 GB against a leg peak of 12.0 GB, so caching it would not lower the peak.

### Caveat on the #461 rows above: they measured a tree dev no longer has

The `#461` rows in the table were measured on a scratch branch cut from **`5d28854`**. `#461` then merged as **`84b1ed2`**, which added a new check derivation (`ingest-gate-a-npy-only`) — absent at `5d28854`, present on `dev` now. Verified:

```
5d28854    : 0 occurrences, 14 cargo derivations
origin/dev : 2 occurrences, 15 cargo derivations
```

So **dev today is heavier than what those two rows measured**, and reported margins on the merged content are worse:

| | x86 peak / avail | aarch64 peak / avail |
|---|---|---|
| #461 @ `5d28854` (measured here) | 13534 MB / 2454 MB | 11536 MB / 4410 MB |
| #461 @ `84b1ed2` (merged to dev) | 14286 MB / 1702 MB | **15095 MB / 852 MB** |

852 MB of aarch64 headroom is inside the band of the leg that was evicted at 313 MB. It passed, but *passed* and *has margin* are different claims.

**This does not invalidate the change** — the `#497` rows were measured on identical trees either side, and they carry the decision (14651 → 11171 MB on x86, 1338 → 4818 MB of headroom). But it does mean the `#461` rows should not be read as current-dev figures, and the disposition of "3.0 GB headroom on the heaviest branch" is stale in the wrong direction.

**My error, stated plainly:** I created the two `#461` scratch branches at different times from `origin/feat/386-generic-ingest-array` by *name* rather than by pinned SHA, so the branch moved under the second one. The cores-4 and cores-2 experiments on `#461` therefore ran against different source trees and are not comparable with each other. A re-run supplying the missing cell (`--max-jobs 2 --cores 4` on `84b1ed2`, the merged content) is dispatched; numbers to follow.

**Why the mechanism is worth stating precisely.** Adding a derivation did *not* raise the concurrency cap — `max-jobs` already defaulted to 4 on these runs (load held at ~8 with `--cores 2`, i.e. 4 × 2). What a new heavy derivation changes is **which four can be co-scheduled**, so it can create a heavier overlap than the previous mix allowed. That is a scheduling effect, not a count effect, and it is exactly what `--max-jobs 2` bounds: with the cap at 2, the worst possible pairing is strictly smaller, and adding further derivations costs wall-clock rather than peak. That is an argument *for* this PR, not against it — but it is a different argument from the one in the body, so it is recorded here rather than silently folded in.

### Matched-tree verdict — merge as-is with `--cores 4`

This PR was held for a same-tree comparison, because the earlier `--cores 2` "zero wall-clock cost" claim compared runs on **different** source trees. Both legs are now in, on identical content (`84b1ed2`):

| arch | `--max-jobs 2 --cores 4` (this PR) | `--max-jobs 2 --cores 2` | cost of cores-2 |
|---|---|---|---|
| x86_64 | **79m** · 10414 MB · 5575 MB free | 85m · 10256 MB · 5733 MB free | **+6 min** for 158 MB |
| aarch64 | **58m** · 10846 MB · 5101 MB free | 67m · 10289 MB · 5658 MB free | **+9 min** for 557 MB |

Both arches agree: `--cores 2` buys a few hundred MB of peak for 6–9 minutes of wall-clock. **This PR's setting is the right one**, and on this tree **both legs clear the pre-set bar** (peak < 12288 MB, < 100 min).

One honesty note on noise: #461's x86 leg peaked at **12980 MB** on `5d28854` and **10414 MB** here on `84b1ed2` — a heavier tree, a *lower* peak, same flags. Peak varies by ~2.5 GB run-to-run at n=1, so no single run should be read as the margin. #495 stays open as the watch item for exactly that reason.

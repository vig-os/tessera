# [PR 774](https://github.com/vig-os/tessera/pull/774) chore(devkit): adopt devkit 1.19.0

## Description

Adopts vigOS devkit **1.19.0** (from 1.17.0) through devkit's own upgrade path, `install.sh --force --version 1.19.0` in direnv mode on the host, plus the in-step `vigos` flake-pin advance.

Closes #771

## Why #557 failed at `Resolve toolchain` (run 41458295205)

1.18.0's gate message, from #557's log (1.19.0 words it slightly differently):

```text
##[error]flake.nix pins the devkit input 'vigos' to 1.17.0 but .vig-os DEVKIT_VERSION is 1.18.0 — the scaffold and its toolchain must move together. In one commit: bump the pin, run 'nix flake update vigos', and set DEVKIT_FLAKE_PIN_ADVANCE=true …
```

1.18.0 added a **flake-pin lockstep gate** to the scaffolded `ci.yml` (devkit#1752/#1756). The bot's upgrade bumped `DEVKIT_VERSION` but left tessera's **pinned** `vigos.url` at 1.17.0, because pinned inputs were never auto-advanced. That is a tessera config gap, not a devkit bug, and 1.19.0 still enforces the same gate. The fix is at the source:

- this PR moves the pin and the lock together (`flake-bump: advanced pinned input 'vigos' 1.17.0 -> 1.19.0`; the lock is at the 1.19.0 tag's `a2ac8e3`);
- `.vig-os` sets `DEVKIT_FLAKE_PIN_ADVANCE=true`, so every later upgrade, including the weekly bot PR, does the same. **I chose `true` over the empty default:** the 1.18.2 default advances the pin only while it still equals the pre-upgrade `DEVKIT_VERSION`, so a pin that ever fell out of step would be left behind and red. `true` advances any release pin. The reason is recorded in `flake.nix` next to the pin, because `.vig-os` comments are rewritten on every upgrade.

Proof: the scaffolded gate step, extracted from this branch's `ci.yml` and run locally:

| tree | result |
|---|---|
| dev's `flake.nix` (pin 1.17.0) + `DEVKIT_VERSION=1.19.0`, i.e. the #557 shape | `::error::flake.nix pins the devkit input 'vigos' to 1.17.0 …`, **exit 1** |
| this branch | `flake.nix pins the devkit input 'vigos' to 1.19.0, matching DEVKIT_VERSION.`, **exit 0** |

## Runner placement: 1.19.0 moves the `ci.yml` lanes onto ksb (open decision)

1.19.0 resolves every lane's runner from the `CI_RUNNER_SMALL/LARGE/XLARGE` **variables** (#1925), not from `.vig-os`. The vig-os **org** already sets them, with visibility `all`, to `ksb-vig-os-small/large/xlarge`. In direnv mode, nothing gates them. So adopting 1.19.0, with no `.vig-os` change, places on ksb small (2 CPU / 8 GiB): `Resolve toolchain`, lint, test, commit-checks, the extension and the summary in `ci.yml`, plus `sync-issues.yml` and `devkit-upgrade.yml`. This PR's own `Resolve toolchain` job is queued on `["ksb-vig-os-small"]`. Fork PRs fall back to hosted through devkit's fork-safe resolution (#1925/#1928). That is part of #772's scope arriving with this PR rather than after it. Two options:

- **keep it**: this PR's CI is the first evidence that the lanes run green on ksb small, and #772 shrinks to sizing, the non-scaffolded workflows and the measurements;
- **defer it**: set repo-level `CI_RUNNER_*` variables, which override the org ones, so tessera stays hosted until #772. That is a repository-settings toggle, not a code change, so I have not made it.

**The first CI run on 1.19.0 puts the `ci.yml` lanes on ksb small, and they time out there**

`Resolve toolchain` passed, which is the exact step #557 failed. Then the org's `CI_RUNNER_SMALL=ksb-vig-os-small` placed Lint & Format, Tests and Commit Messages on ksb small pods (2 CPU / 8 GiB). All three were **cancelled by the job timeout** inside `Set up devkit toolchain`, before running a single check:

| job | runner | `Set up devkit toolchain` | timeout |
|---|---|---|---|
| Commit Messages 128619410781 | ksb-vig-os-small-runner-7962m | 03:53:13 → cancelled 04:08:10 | 15m |
| Lint & Format 128619410777 | ksb-vig-os-small-runner-t6g2h | 03:59:17 → cancelled 04:14:02 | 15m |
| Tests 128619410776 | ksb-vig-os-small-runner-prv9t | 03:52:14 → cancelled 04:11:57 | 20m |

For comparison, the same step on hosted `ubuntu-26.04` in dev's last green run (42441529958) took **~1 min**.

Where the time went, from the Commit Messages log: a cold per-pod store. The ksb substituter `http://10.0.2.2:8093` refused connections and was disabled. Two flake `source` paths then took 5 min (03:53:41 → 03:58:45) and 8.5 min (03:59:21 → 04:07:52) from cache.nixos.org, so the dev-shell closure had only just started when the timeout hit. Raising the timeouts would hide this rather than fix it. The real fix belongs to #772: a persistent dev-shell gcroot (`DEVKIT_DEV_PROFILE_PATH`, #1601), the substituter, and sizing (`DEVKIT_CI_LANE_SIZES`).

That leaves this PR one decision short of green (see "Runner placement" in the body):
- **keep** the move: #772's ksb work lands on or before this PR;
- **defer** it: repo-level `CI_RUNNER_SMALL/LARGE/XLARGE` override the org values and keep tessera hosted until #772. That is a repository-settings change, which I have not made.

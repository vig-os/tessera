# [PR 279](https://github.com/vig-os/tessera/pull/279) feat(ingest): offline crypto-shred de-identification for DICOM (ADR-0047, #269)

## Why

De-identification today is a binary: destroy PHI at ingest (`--deidentify`, irreversible) or keep it (default — which also **sealed the full raw DICOM header into a shareable product**, the reviewer footgun). Neither serves the real clinical need: **de-identify for sharing, but let an authorized custodian re-link a finding to a patient later — and guarantee erasure by destroying a key.**

This is the user's ask ("can a key un-SOP itself, and shred by key destruction?") and the already-documented direction (ADR-0040 §2.2 crypto-shred + §3 `age` envelope; ADR-0041's ladder). This PR builds the **offline rung 1**.

## What

`tessera ingest dicom|dicom-series --crypto-shred --recipient <age1…>` (repeatable):
- **de-identifies** the sealed product (PS3.15 strip — same bytes as `--deidentify`), and
- **`age`-encrypts** the stripped identity (full pre-scrub header + curated identifying fields) to the recipient pubkey(s), carried as an `aux/identity/identity.age` envelope **inside** the `.tsra` but **outside the seal** (ADR-0042).

Because the envelope is aux, the de-identified data is **byte-identical to a plain `--deidentify` product** (`id` + `content_hash` equal; writer-determinism + conformance corpus untouched — `age` nonces every encrypt, which is exactly why the ciphertext can't live in the seal).

New verbs / flags:
- `tessera keygen --age` — mint an `age` X25519 keypair (secret `0600`, recipient `.pub`).
- `tessera reidentify --identity <age-key>` — decrypt the envelope, recover the identity ("a key un-SOPs itself"). Wrong key / tampered envelope → typed error.
- `tessera shred` — drop `aux/identity/` in place; the seal is untouched so the file still verifies. Destroying every private-key copy erases it from every distributed copy (ADR-0040 §2.2).

**Also fixes the #269 raw-header leak**: `extra["dicom_header"]` is now embedded **only** on a de-identified path. The keep-PHI default no longer seals the raw header (user decision); the WARN points at `--recipient` / `--source-label`.

**Completeness by construction**: the envelope carries the *whole* header and the sealed product keeps only allowlisted non-identifying fields — de-id stops being "did we blocklist every PHI tag?" and becomes "encrypt everything, allow the safe."

## Scope / non-goals
- Offline `age` only. **Not** ADR-0041 rung 2 (provider / KMS / broker, online revocation + audit) — explicitly out of scope, named in the ADR.
- Same analog-hole limit as ADR-0041 §4, and no revocation/audit (that's what rung 2 is for). The honest claim: *"identifying material is unreadable without the recipient private key, and destroying that key erases it from every copy."*

## Evidence
- `age` envelope: 5 unit tests (round-trip, wrong-key rejection, multi-recipient, empty-recipient refusal, bad-key typed error; ciphertext never contains the plaintext PHI).
- CLI end-to-end: `crypto_shred_deidentifies_yet_a_key_holder_can_reidentify` (PHI-free sealed container, aux envelope present, re-identify recovers PHI, wrong key fails, shred removes it + still verifies + then even the right key can't) and `crypto_shred_seal_equals_plain_deidentify` (data identity == plain de-id).
- New dep `age` (MIT/Apache-2.0), host-only on `tessera-ingest`, never in the wasm verify path.
- ADR-0047 + FEATURE-MATRIX row + README index.
- Hermetic `nix flake check`: **all checks passed!**

# [PR 727](https://github.com/vig-os/tessera/pull/727) ci: run the aarch64 nix flake check nightly, on release tags and by hand

Closes #725.

## What changes

The aarch64-linux `nix flake check` leg, the slowest (46-82 min hosted), comes off the per-PR path.

| event | legs |
|---|---|
| `pull_request`, push to `main` | x86_64-linux |
| `schedule`: nightly, `17 2 * * *` (02:17 UTC), on dev (the default branch) | x86_64-linux + aarch64-linux |
| push of a release tag (release.yml's pattern `**[0-9]+.[0-9]+.[0-9]+*`) | x86_64-linux + aarch64-linux |
| `workflow_dispatch` | x86_64-linux + aarch64-linux |

- `scripts/nix-check-legs.sh` is the one place the rule is written. `plan` names the legs for the
  event; `gate` (the required `nix flake check` job) asserts BY NAME that exactly the planned legs
  ran and passed, every unplanned leg was skipped, each known leg has one result, and the plan is
  non-empty and includes x86_64. It never counts "the legs that happened to run" (#722/#723).
- The legs are two jobs instead of a matrix (a matrix entry cannot be switched off per event); their
  steps moved unchanged into the composite action `.github/actions/nix-flake-check`.
- A failed nightly or release-tag run files a `bug` + `area:ci` issue, or comments on the open one
  with the same exact title (`scripts/ci-failure-issue.sh`, with `DRY_RUN=1`).
- Only pull requests cancel a superseded run; nightly, tag and dispatched runs queue.
- #723 review nit: `nix-check-summary.sh` accepted any number as `CHECK_RC`, and `return 256` wraps to
  0. Only empty or 0-255 is accepted now, with a self-test case that failed before the fix.
- Both new scripts' self-tests are flake checks; `.github/nix-flake-checks.txt` lists 29.

## What is traded away

Since #688 the ksb x86_64 leg runs Nix with `sandbox = false`, so the hosted aarch64 leg was the only
sandboxed flake check and the only cross-arch determinism check (#472/#468 class). A pull request now
gets neither; the nightly catches a regression within a day, traceable to that day's merges. Stated in
`nix-check.yml`, `FEATURE-MATRIX.md` and the book's conformance page. A PR touching the writer, codecs
or corpus can dispatch the workflow on its branch to get both legs before merging.

## Evidence

- Self-tests: `nix build .#checks.x86_64-linux.{nix-check-legs,ci-failure-issue,nix-check-summary}`
  exit 0 (28, 9 and 19 cases). The new 256 case failed before the fix: `exit 0, expected 1`.
- Mutants killed: `contains` instead of `==` for the issue title; a skipped planned leg accepted;
  a PR planned with both legs.
- Issue filing, dry run against this repo: a new title gives "would create an issue labelled bug
  area:ci"; an existing open `bug`+`area:ci` title gives "would comment on #653".
- This PR's own run: x86_64 leg only, aggregate green. Dispatched run on this branch: both legs.
  Run ids are in the comments below.

# [PR 471](https://github.com/vig-os/tessera/pull/471) ci(sync-issues): sync to an unprotected mirror branch so the push can land

## The issue's stated cause is already gone

#362 was filed for a 361-file backlog tripping GitHub's secondary rate limit. That is fixed, and
the devkit scaffold shipped both mitigations the issue asked for:

- `Save sync state` now runs `if: always()` (option 3 in the issue);
- `Compute incremental cutoff` takes a bounded **14-day look-back** on a cache miss instead of
  re-syncing from epoch, which is what made the backlog unbounded in the first place.

The backlog has drained — the latest failing run tried to commit **2 files, not 361**.

## What is actually broken

`sync-issues` has not pushed anything since `dev` gained branch protection:

```
Synced PR #444 with 0 comment(s) to docs/pull-requests/pr-444.md
Synced PR #443 with 0 comment(s) to docs/pull-requests/pr-443.md
Committing 2 file(s) to branch dev
##[error]Required status check "nix flake check" is expected.
```

The job pushes a commit directly via the API. `dev` requires the `nix flake check` context, and a
direct push has no checks attached, so GitHub refuses it.

**The green runs are vacuous.** The commit step is `if: steps.sync.outputs.modified-files != ''`,
so on a quiet day it *skips* and the job passes. Verified on the three most recent "successes":

| run | `Sync Issues and PRs` | `Commit and push changes via API` |
|---|---|---|
| 36303464714 | success | **skipped** |
| 36225555271 | success | **skipped** |
| 35831020452 | success | **skipped** |

So the push has never worked, and only a day with changes turns the job red. That is why this went
unnoticed.

## Fix

`DEVKIT_SYNC_TARGET=sync/issue-mirror` — devkit's sanctioned answer for a protected sync target
(vig-os/devkit#1227). The workflow edits are byte-for-byte what `render_sync_settings()` in
`init-workspace.sh` emits for that key (the dispatch-input default, both `|| 'dev'` fallbacks, and
the bootstrap step that creates the branch from the default-branch head when absent), so a future
re-scaffold is a no-op rather than a conflict.

## The cost, stated plainly

Mirror mode normally folds back into the trunk at release time (devkit#1424). **That fold is
rendered into `release-core.yml`, which this repo does not have** — `release` is in
`DEVKIT_FEATURES_DISABLED` because cargo-dist owns `release.yml` (#441).

So the **181 files** already under `docs/issues/` and `docs/pull-requests/` freeze as of this
commit, with no path back. This PR adds a `README.md` to both directories saying exactly that and
pointing at the mirror branch, so someone reading a stale `issue-123.md` is not misled. Interim by
intent, not a silent regression.

## Two upstream bugs found on the way — #362 stays open

- **vig-os/devkit#1757** — `Save sync state` with `if: always()` advances the watermark even when
  the push **failed**, so that delta is dropped and never retried. In run 36395811823 the two PR
  files were lost and no later run will reproduce them, because their `updated_at` is now behind the
  cutoff. Data-loss class, affects every consumer. Ironically it was presumably added to fix #362's
  non-self-healing loop — but the 14-day look-back already covers that far better.
- **vig-os/devkit#1758** — mirror mode plus a disabled `release` group renders the retarget and the
  bootstrap step but silently omits the fold, because the fold is `-f`-guarded on `release-core.yml`.
  The scaffold prints nothing.

Keeping #362 open and linked to both until upstream resolves them; the trunk archive can go live
again once it has a fold-back.

## Not fixed here

The alternative — converting `dev`'s classic protection to a ruleset with the commit App as a
bypass actor — would keep the archive on `dev` and needs no divergence at all, but it is a repo
settings change. Recorded on #362 as the preferred permanent fix if the divergence proves annoying.

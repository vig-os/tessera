# [PR 821](https://github.com/vig-os/tessera/pull/821) feat(capi): prototype the C ABI bridge end to end (spike)

Spike for #800 (epic #799): a working prototype of the C ABI bridge, so ADR-0065
(`docs/800-capi-bridge-adr`) can decide with evidence. This is not the final API. The report is
`docs/spikes/800-capi-prototype.md`.

## What is here

- `tessera/crates/tessera-capi`: staticlib + cdylib over `StreamWriter::push_table` (and
  `TableMultiBlockSink` for an unknown row count). Batches cross as Arrow C Data Interface struct
  arrays. Every entry point is behind `catch_unwind` and returns a status, with a last-error
  string. `include/tessera.h` is generated by cbindgen.
- `cpp/`: C++ programs built with nanoarrow and CMake + pkg-config: smoke test, threaded
  determinism check, throughput bench.
- `capi-smoke` flake check: header drift; CMake build against the installed header, `.pc` and
  nanoarrow, shared and static; smoke with known and unknown row counts; `tessera verify`; Rust
  readback; the threaded check.

## Evidence

- `cargo test -p tessera-capi --release`: 28 passed, exit 0 (threads tests also 20 times clean).
- **Correctness.** C++ products read back value for value, and `tessera verify` exits 0. Each one's
  content hash equals the one native `push_table` seals from the same rows, with known and unknown
  row counts and with shared and static linking.
- **#802.** One hash for N in {1, 4, 16} producer threads under shuffled schedules (C++ and Rust
  agree). Arrival-order keys give 9 distinct hashes in 9 runs. Mutating the buffer to ignore the key
  fails the test (exit 101).
- **The owner's push-path shape.** A thread that runs too far ahead blocks (back-pressure). A
  duplicate, a missing key at the end, and a stall are errors, never hangs. A stall means every
  declared producer thread is blocked on the window; it is detected exactly, with no timer. Peak
  out-of-order batches are at most the window in every run. `tsra_table_mark_done` keeps the keys
  dense. `StreamWriter` takes jobs only in submission order. The bridge sequences batches before
  rows form leaves, and needs no second scheduler.
- **Geant4 block size.** Geant4's default event modulo depends on the thread count. The block
  size B is therefore a declared, sealed session parameter (`seq_block_events`). With an event-id
  column, the bridge refuses a batch outside `[seq·B, (seq+1)·B)`. A pinned B gives one hash at
  1, 4 and 16 threads; the unpinned default gives a different hash at 16; a declared B rejects
  that cut (`tests/geant4_blocks.rs`).
- **Throughput.** 50 M rows on ksb (8 dedicated cores, `/dev/shm`): native 8.89 M rows/s, C ABI
  8.25 / 8.52 / 9.23 M rows/s with 1 / 4 / 16 producers, all within run-to-run noise. All 12 runs
  seal one hash.
- **Copies.** The import is zero-copy, and the bridge adds one copy, into `ColumnData`.
- **Linking.** No HDF5 or DICOM. The shared library exports 8 symbols. The static archive leaks
  zstd's symbols and fails to link next to a consumer's own `libzstd.a`; after `ld -r` +
  `objcopy --keep-global-symbols` it links fine.
- **Open questions for the ADR.** Where H4's NaN canonicalisation lives; #454 first or a 40-line
  clean-lane map; blocking window or spill.

A spike, above the 400-line guideline (about 3,000 lines with tests, C++ and the generated header).

Refs: #800

_Posted on November 11, 2026 at 03:26 AM_

A note for the `seq`-modulo negative case, from ADR-0065 §7.2 (PR #819 at `f8331e3`).

A thread-count-dependent block cut changes the sealed bytes **only when a batch is not a contiguous key range in key
order**. The rows are re-chunked to the row-group grid (`accumulate.rs:12-15`), so the bytes are a function of the
row sequence alone.

- If every batch `k` holds exactly the events `[k·M, (k+1)·M)` in order, then the concatenation in `seq` order is the
  same rows for any `M`, and the hash matches. Only the `seq` count and the gap/`expected_count` checks differ.
- So the negative case that shows **different bytes** needs non-contiguous batches. An example is a thread that
  accumulates the events of several tasks into one batch.
- The ADR's detectable case is the other negative: with `seq_key_column` declared, a batch whose keys fall outside
  `[seq·B, (seq+1)·B)` is refused with `TSRA_E_ORDER`.

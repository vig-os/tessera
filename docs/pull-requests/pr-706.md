# [PR 706](https://github.com/vig-os/tessera/pull/706) test(io): run the S3 range-read check against versitygw, sandbox-independent

Closes #702

## What changed
- **versitygw replaces MinIO.** The check runs versitygw (nixpkgs, posix backend), the S3 gateway the fleet deploys, on loopback. Every test and assertion is unchanged: GET counts, tail prefetch and cohort prune-before-fetch. The only code change is renaming the test helper `minio_store_or_skip` → `s3_store_or_skip`.
- **The `minio` insecure override is removed**, together with its rationale comment.
- **Renamed `minio-range-read` → `s3-range-read`.** The rename is propagated to `tessera/CLAUDE.md`, FEATURE-MATRIX (the evidence row), ADR-0002 §4, ADR-0062, the book (`distribution.md`, `intro.md`), the CI comments in `nix-check.yml` (comments only; runner lines untouched), the README and the test doc comments. The docs that described MinIO as *the* object store now say S3: ADRs 0033/0037/0039/0041/0054, the rfc, ROADMAP, MIGRATION and the cache-node example.

## Sandbox-independent fixture
- **Ephemeral port:** a free loopback port is picked at runtime and passed to both versitygw and `TESSERA_S3_ENDPOINT`. Nothing is fixed at 9101.
- **Private data dir:** data and metadata live under the build's own `$TMPDIR`. Metadata goes to a `--sidecar` dir, so there's no dependency on user xattrs.
- **Readiness wait:** a signed ListBuckets must answer 200 within a 30 s wall-clock deadline. If the deadline passes or the server exits, the check fails and prints the server log.
- **Ownership check:** the random per-run bucket must appear in *this build's* data dir. A server that wins the pick-then-bind race is refused. This includes a concurrent copy of this check with the same credentials, which a harness showed would otherwise pass the readiness probe.
- **Exit trap:** the server is stopped via stdenv's `exitHooks`/`failureHooks`, which run from the builder's EXIT trap. A bare `trap … EXIT` would replace stdenv's own handler.
- **Unique bucket:** a fresh random bucket per run.

## Results (seat, x86_64, rebased head 0e6fae8)
- **Sandboxed:** `nix build -L .#checks.x86_64-linux.s3-range-read` → exit 0, 6/6 passed.
- **Unsandboxed:** `nix build -L --option sandbox false .#checks.x86_64-linux.s3-range-read` → exit 0, 6/6 passed. The build dir was `/nix/.rw-store/builds/…` (a host path, so really unsandboxed), and no versitygw process was left after the build.
- **Before this change:** `minio-range-read` at b6de2d1 with the sandbox off and port 9101 already in use. Its readiness `curl -sf` has no timeout and hung for 12m56s until it was stopped.

## Server differences (findings)
- **Addressing:** given an endpoint, object_store sends path-style requests, which versitygw serves by default. Virtual-hosted style would need `--virtual-domain`.
- **Range, ETag, error codes:** no differences surfaced. All 6 cloud tests pass with unchanged assertions.
- **Checksums:** no `AWS_REQUEST_CHECKSUM_CALCULATION` / `AWS_RESPONSE_CHECKSUM_VALIDATION` needed.
- **Version:** the flake's nixpkgs pin ships versitygw **1.3.1**, not the 1.8.0 the issue mentions.
- **ksb disk load (residual risk, stated plainly):** per #688's pod measurements, MinIO's `503 SlowDownWrite` was its reaction to contention on the pod's single `/nix` volume, which is also where `$TMPDIR` lives.
  - versitygw has no throttle layer that turns slowness into a 503, but its posix backend writes to the same disk.
  - The objects here are a few KiB, far from the large registry upload that hit the 60 s cap, but slowness under heavy concurrent load is not ruled out.
  - The ksb leg of #688 is the real-pod evidence.

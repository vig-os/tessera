# [PR 991](https://github.com/vig-os/tessera/pull/991) fix(ingest): seal the linked decoder's version, not lockfile text

Closes #979

## The defect

ADR-0056 §6a seals `generation.config.ingest_decoder {name, version, features}`. `tessera-ingest/build.rs` read
`version` and the `features` pre-image from `Cargo.lock` and passed them to the library as `rustc-env` values.
Cargo never keys a build-script **run** on the package's normal dependencies (only on its build-dependencies and on
`links` dependencies), and it leaves a workspace member's path out of the unit hash. So two checkouts sharing one
`CARGO_TARGET_DIR` share that run, and the second reuses the first's values. A binary could link parquet 58.4.1 and
seal `=58.4.2`. A wider `rerun-if-changed` cannot fix this, because cargo checks those inputs by mtime and mtimes
cannot tell two checkouts apart.

## Options considered, and why this one

| Option | Verdict |
| --- | --- |
| `const` exported by the decoder | Exists for one lane root only: parquet's `DEFAULT_CREATED_BY`. `arrow-ipc`, `csv`, `zip`, `dicom` and the ~40 pinned crates of the pre-image export nothing. Kept as an independent **check** (below). |
| `DEP_*` metadata from a `links` key | None of the decoder crates declares `links`, and a wrapper crate's `links` run is no better keyed than ours. |
| `cargo metadata` at build time | Runs in a build script, so it sits in the same unkeyed run unit and has the same defect. |
| Wrapper crate's `env!("CARGO_PKG_VERSION")` | That is the wrapper's own version, not the decoder's. |
| **Read the resolution in the library compile unit** | **Chosen.** That unit's hash covers the version, source and resolved features of every crate it links, so a different decoder means a different unit, compiled afresh from the checkout being built. |

`tessera-ingest/src/linked.rs` takes `Cargo.lock` (and this crate's `Cargo.toml`, for the lanes) with
`include_str!`, using this compile's own `CARGO_MANIFEST_DIR`. It derives every version and lane pre-image from them
with the existing `decode_path` code. The features component is therefore keyed exactly like the version.
`build.rs` now only says whether a workspace lockfile exists (the `tessera_workspace_lock` cfg). That fact is the
same for every checkout. A packaged build still records the decoder's name alone. `tessera info` reads the same
values.

API: `Decoder`'s public `version` / `pins` fields become private lane keys. Values are read with the new
`Decoder::version()` and the existing `Decoder::feature_preimage()`. Nothing outside the crate used the fields.

## Nothing sealed moved

The derivation is the same code over the same files, so the output is identical. `gen_ingest_corpus` regenerated
after the change is byte-identical to `corpus/ingest-corpus.json` (`git diff --no-index` exit 0). No
`manifest_hash` moves, and the `v2` pre-image version is not bumped.

## Proof: #979's shared-target scenario

`tests/linked_decoder_identity.rs` reads the lockfile of the checkout under test **at test run time**. It requires
every sealed triple and every `tessera info` version to match that lockfile. It also requires the sealed parquet
version to equal the linked parquet's own `DEFAULT_CREATED_BY`.

The scenario uses one target slot. Checkout A is dev's `Cargo.lock` (zip 9.0.5). Checkout B is the same commit with
`zip` locked at 9.1.0.

Before the fix, B was built after A in the same target dir:

```text
test tessera_info_reports_the_versions_this_checkout_links ... FAILED
  `tessera info` would report a zip this checkout does not link (backend npz-member)
  left: Some("9.0.5")   right: Some("9.1.0")
test every_sealed_decoder_triple_matches_this_checkouts_resolution ... FAILED
  tessera/npz: the sealed feature pre-image names decoders this checkout does not link
  left:  ...,zip=9.0.5,...   right: ...,zip=9.1.0,...
test result: FAILED. 1 passed; 2 failed          (exit 101)
```

After the fix, the same sequence (A, then B, then A again in the same slot) gives 3/3 passed in B and 3/3 in A. B's
`decode_path_gate` separately flags `windows-sys`, which zip 9.1.0 brings in. That is the classification gate
correctly refusing an unclassified crate in the scratch bump, and it is not part of this change.

## Limits (documented in `linked.rs` and the ADR amendment)

- A lane's candidate set is the lockfile closure, which can name a crate this build does not link. Such a pin can
  go stale only between checkouts that link identical graphs.
- This crate's own sources (`Cargo.toml` lanes, `decode_path.rs`) are compared by mtime across a shared target dir.
  That is cargo's limit for every workspace crate.
- When `tessera-ingest` is a git or path dependency of another workspace, the lockfile it reads is tessera's own.
  That predates this change and is filed as #989.
- About 210 KiB of lockfile is embedded in binaries that link `tessera-ingest` (`tessera-cli`).

Docs: ADR-0056 §6a amendment (#979, 2026-11-25) and CHANGELOG Unreleased → Fixed.

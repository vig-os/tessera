# [PR 497](https://github.com/vig-os/tessera/pull/497) feat(cli): bench compare reports both table fixtures

Follow-up to the #493 investigation. The benchmark now reports **both** table fixtures, always, with
every row labelled by the fixture it came from.

Refs #493, #388

## Why not just replace the fixture

#493 established that the 6.2× table-size loss is a property of the fixture: its float columns have
periods 7 and 5, which is adversarial for value-distribution codecs — deflate's LZ77 window locks
onto the repeating byte block, while Pco, dictionary and bit-packing model the value *distribution*
and cannot exploit periodicity at all. On real DUPLET listmode tessera is **1.03× smaller** than
shuffle+gzip.

Swapping in a realistic fixture would have removed the loss. It would also have been tuning the
benchmark until we win, however honest the motive. So both are reported, always, each labelled:

| fixture | Tessera | HDF5 shuffle+gzip-4 | |
|---|---|---|---|
| **periodic** (adversarial for value-distribution codecs) | 959.4 KiB | **155.3 KiB** | HDF5 **6.2× smaller** |
| **continuous** (listmode-like) | **19.6 MiB** | 21.5 MiB | Tessera **1.10× smaller** |

Same encoder, same command, opposite verdicts. Publishing one without the other is choosing the answer.

## The continuous fixture is representative, not flattering

It is shaped after what #493 actually measured on real `/events_2p`:

- `t` is a **coarse millisecond clock**, advancing once per ~250 events, so ~99.6 % of its deltas are
  zero — matching the real column's run structure (and including the one column where tessera is
  genuinely 2× worse, so the fixture does not hide that either). Its run lengths are **Poisson**
  (exponential inter-arrival gaps), as a real clock's are. An exact period would have smuggled the
  periodic fixture's adversarial property into the fixture that is supposed to be realistic.
  Pinned by `continuous_clock_runs_are_poisson_not_a_fixed_stride`, which asserts on the number of
  DISTINCT run lengths — a fixed stride yields exactly one — and is A/B-verified against the old
  `k / 250` clock, where it fails with "run lengths look like a fixed stride: 1 distinct values".
  Re-measured afterwards: every size is byte-identical, because `t` compresses to almost nothing
  under either clock and is a small share of the file.
- `e0`/`e1` are drawn from a **continuous** distribution. (The earlier claim that they have "no
  repeated values at f32 precision" was false at 4M draws and is gone — the property is the
  distribution, not distinctness.)

Its 1.10× tracks the real data's 1.03×, which is the test of whether a fixture is representative.
Values come from a fixed-seed xorshift64*, so the benchmark stays byte-reproducible.

## What was dropped

An `--input <FILE.h5>` flag for running the comparison over a reader's own acquisition was in the
first draft and has been pulled. It only worked for the benchmark's own 3-column shape — a real GE
`/events_2p` is `ms u32`, `en_* f32`, `ax_* u8`, `tx_* u16`, none of which the verification path
accepts — and had a dataset got through, tessera would have been handed every column while the HDF5
side wrote three, the same asymmetry the #487 review caught. Requirements recorded in **#504**.

No real data is read, copied or committed by anything in this PR; only synthetic fixtures are. The
real-data runs behind #493 stayed local, per the no-PHI rule.

## Tests

trycmd regenerated (both cases pass; structure pinned, numbers wildcarded), and the new unit test
asserts every table row carries its fixture label and that every access pattern is present — the
labelling bug this PR fixes. tessera-cli 76 tests pass, 0 failed. No format or encoder change.

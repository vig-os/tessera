# [PR 497](https://github.com/vig-os/tessera/pull/497) feat(cli): bench compare reports both table fixtures and can run on real data

Follow-up to the #493 investigation. The benchmark now reports **both** table fixtures and can run on
the reader's own acquisition.

Refs #493, #388

## Why not just replace the fixture

#493 established that the 6.2× table-size loss is a property of the fixture: its float columns have
periods 7 and 5, which is adversarial for value-distribution codecs — deflate's LZ77 window locks
onto the repeating byte block, while Pco, dictionary and bit-packing model the value *distribution*
and cannot exploit periodicity at all. On real DUPLET listmode tessera is **1.03× smaller** than
shuffle+gzip.

Swapping in a realistic fixture would have removed the loss. It would also have been tuning the
benchmark until we win, however honest the motive. So both are reported, always, each labelled:

| fixture | Tessera | HDF5 shuffle+gzip-4 | |
|---|---|---|---|
| **periodic** (adversarial for value-distribution codecs) | 959.4 KiB | **155.3 KiB** | HDF5 **6.2× smaller** |
| **continuous** (listmode-like) | **19.6 MiB** | 21.5 MiB | Tessera **1.10× smaller** |

Same encoder, same command, opposite verdicts.

## The continuous fixture is representative, not flattering

It is shaped after what #493 actually measured on real `/events_2p`:

- `t` is a **coarse millisecond clock**, advancing once per ~250 events, so ~99.6 % of its deltas are
  zero — matching the real column's run structure (and including the one column where tessera is
  genuinely 2× worse, so the fixture does not hide that either).
- `e0`/`e1` are **continuous** energies with no repeated values at f32 precision.

Its 1.10× tracks the real data's 1.03×, which is the test of whether a fixture is representative.
Values come from a fixed-seed xorshift64*, so the benchmark stays byte-reproducible.

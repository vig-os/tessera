# [PR 503](https://github.com/vig-os/tessera/pull/503) feat(cli): add Parquet to the bench compare head-to-head (#388 stage 2)

Stage 2 of #388. #460 put the arrow/parquet crates on dev, so the third format in the AX pitch is now
measured with the real `parquet` crate instead of left as a promise.

Closes #388

**Stacked on #497** (the both-fixtures change) — review that first.

## Same rules as the other two formats

Default **and** tuned, both printed: parquet-rs's own default (snappy, dictionary, page statistics)
and a tuned variant (zstd-4, same dictionary/statistics). One row group per `ROWS_PER_GROUP`, matching
the chunk granularity HDF5 and Tessera get, so Parquet is not handed a free layout advantage.

Every timed read — full, projected, row window — is verified against the source before its numbers
count, for both fixtures.

Reads exercise what Parquet is actually good at: projection through `ProjectionMask`, and a row window
via **row-group selection**, which is its finest granularity. That is labelled, because Tessera's
`decode_rows` is row-exact and the two are not the same operation.

## Results — continuous fixture (corrected after review)

| | size | full read | 1 column | row window |
|---|---|---|---|---|
| Tessera | **19.6 MiB** | 0.0302s | 0.0159s | 0.0109s |
| HDF5, uncompressed | 61.0 MiB | **0.0103s** | **0.0015s** | **0.0001s** |
| HDF5, shuffle+gzip-4 | 21.5 MiB | 0.1235s | 0.0437s | 0.0039s |
| Parquet, uncompressed (crate default) | 44.9 MiB | 0.0442s | 0.0113s | 0.0009s |
| Parquet, snappy (pyarrow/Spark default) | 44.8 MiB | 0.0458s | 0.0120s | 0.0010s |
| Parquet, zstd-4 + BYTE_STREAM_SPLIT | 23.4 MiB | 0.0720s | 0.0221s | 0.0020s |

Periodic sizes: Tessera 959.4 KiB · HDF5 shuffle+gzip **155.3 KiB** · Parquet tuned 4.0 MiB ·
Parquet snappy 23.0 MiB · Parquet uncompressed 40.9 MiB.

**Two corrections from the review changed these numbers, both against us.**

**Tuned Parquet was missing its float tuning.** BYTE_STREAM_SPLIT (Parquet's counterpart to HDF5's
shuffle), with the dictionary off since a dictionary over continuous floats defeats the split. Adding
it takes tuned Parquet from 39.3 → **23.4 MiB** continuous and 11.2 → **4.0 MiB** periodic. The
earlier "2.0× under Parquet zstd" claim rested on that gap; it is **1.19×** once Parquet is tuned as
carefully as HDF5 already was. This is the same omission the #487 review caught for HDF5's shuffle,
and it flattered us the same way.

**The row window under-read.** `ROWS_PER_GROUP` is 65,536 and the window [2,000,000, 2,040,000)
straddles groups 30 *and* 31, but only group 30 was selected — 31,616 of 40,000 rows, 79 % of the
work, timed as if it were all of it. The verification missed it because it compared against *that
group's* slice rather than the exact window, so the shortfall verified clean. Now every overlapping
group is read, the exact window is sliced out, and the check is against the exact source window.

**The "default" label was false.** parquet-58's `DEFAULT_COMPRESSION` is UNCOMPRESSED; snappy is the
pyarrow/Spark default. Both are shown, labelled for what they are.

**Parquet still beats Tessera on the reads it should**, and it is in the table: the projected column
(0.0120s vs 0.0159s) and the row window (0.0010s vs 0.0109s). Tessera's column and window reads
decode from the whole sealed block, so they carry the block's bytes even when only part is wanted —
that, not row-exactness, is the cost.

## Integrity: stated, not measured, and here is why

The ask was to measure Parquet page CRCs like fletcher32. **parquet-rs 58's writer emits none.** The
format allows an optional per-page CRC32, but no `WriterProperties` setter enables it, and the reader
verifies one only under the crate's `crc` feature *and* only when the page header carries it (that
feature is not in our dependency's feature set, and would be pointless here since nothing writes a
CRC).

So for files this benchmark writes there is nothing to verify, and the row says exactly that rather
than timing a mechanism that is not in the file. HDF5's `fletcher32` **is** present and **is** timed —
the asymmetry is real and is the finding, not an omission.

## Also in here

A labelling bug this exposed: eight `push_*` call sites inside `compare_table` still passed the
literal `"table"` instead of the fixture label, so the continuous fixture's read rows were emitted
mislabelled and were indistinguishable from the periodic ones. Caught because the Parquet rows
labelled correctly and the others did not.

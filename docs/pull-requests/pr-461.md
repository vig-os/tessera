# Generic ingest, the array half: NumPy `.npy` and `.npz`

**Closes #386.** The second of two: #460 landed the table lane and is now **merged**, so this is no longer
stacked — it is a single commit on top of `dev`, and this diff is only the array half. Together the two
complete ADR-0056 P1.

Rebased rather than merged: with squash merges disabled on the repo, every commit on a branch becomes `dev`
history, so a `Merge remote-tracking branch 'origin/dev'` commit would land in the changelog permanently.

## Rebased onto #501, which changed what this lane must record

#501 (the fix for #477) landed while this branch's CI was green, making the sealed decoder digest **per
lane**. That turned a detail of this PR into a decision: the `npy` feature enabled `dep:zip`, so under
#501's rule ("a lane is a feature whose expansion enables at least one `dep:`") a plain `.npy` product
would have sealed a commitment to a zip library that never touched its bytes — **#477's own defect, one
scale down**, and invisible to #501's gate because the claim is over-broad rather than unclassified.

So the feature is now split: `npy = []` (in-tree parser) and `npz = ["npy", "dep:zip"]`.

| lane | sealed record | why |
| --- | --- | --- |
| `tessera/npy` | `{"name": "tessera/npy"}` | no third-party crate on the path; **no version** because the only one available is ours and that would move every `.npy` `manifest_hash` on every release (the churn ADR-0052 §1 removed and `build.rs` excludes the pre-image from for that reason) — pinning which in-tree parser ran is #508; **no digest** because one over an empty pre-image is identical for every build, i.e. a false claim of sameness |
| `tessera/npz` | name + digest pinning `zip` | `zip` decides where members begin and end, so it decides what bytes the parser is handed — classified `IN_DIGEST`, with its six incidental crates `EXCLUDED` each with the reason it cannot change a decoded value |

`ingest-gate-a-npy-only` exercises the split, and **it found something on its first run**: nothing had
ever built the array lane without a table lane, and the configuration did not compile.
`generic_column_meta` and `warn_unclassified_identifying_columns` were gated on
`any(parquet, arrow, csv)` while the array arm calls both; three targets hard-require a Parquet reader
and now declare `required-features` so cargo skips rather than fails them.

**Migration**: `content_hash` moved for **0 of 14** fixtures and `manifest_hash` for **14 of 14** — no
decoded value changed, and every seal moved because #501 redefined the digest. Regenerated under both
cargo profiles and written only after confirming they agree; `zip.txt` in the Gate B snapshots now
records the `npz` feature, so the split is structurally visible.

Where the table lane opened the normalising path to columnar data, this opens it to the other shape a
scientist actually holds:

```text
tessera ingest array volume.npy volume.tsra  --name scan-01   --timestamp 2024-03-01T12:00:00Z
tessera ingest array bundle.npz bundle-out/  --name bundle-01 --timestamp 2024-03-01T12:00:00Z
```

## Zero new dependencies

ADR-0056 §12 said *"`ndarray-npy` is deliberately NOT taken: NPY is a header parse plus a memcpy, and the
crate would drag `ndarray` into the tree for one format."* That holds — and the `.npz` reader is the `zip`
crate already present for the `.tsra` container, so **the lockfile gains nothing**. The `npy` feature gates
no dependency at all; it is a capability switch over in-tree code, still worth naming because ADR-0057 §5
wants *which decoders could have produced this artifact* to be a build-time fact.

The header is a Python dict literal, and it is **scanned, never evaluated** — `eval`-ing a literal out of
an untrusted file is how `allow_pickle` bugs happen. v1/v2/v3, and the tests cover the spellings real
writers emit (key order, double quotes, no padding).

## Four decisions the format forces — and the first two differ in an instructive way

| | Handling | Recorded? |
| --- | --- | --- |
| **Byte order** (hazard **H6**) | swapped to native before the waist | **No** |
| **Fortran order** | buffer *rewritten* to C order | **Yes** (`fortran_to_c_order`) |
| **Structured (record) dtype** | seals a **`table`**, not an array | `record_deinterleave` |
| **`object` dtype** | refused, never unpickled | — |

Byte order is not recorded *because* of §5's own fixture: H6 requires that "a `>f8` file and its `<f8` twin
must seal identically", and a transform record would make the twins differ in the seal. Fortran order is
recorded because it genuinely rewrites the buffer — and the **buffer** is rewritten rather than the shape
reversed, since reversing the shape would make the *axes* wrong instead of the bytes, which reads back
transposed with no record of why.

Two tests exist specifically because a weaker version of each would pass while broken: every dtype is
round-tripped in **both byte orders** (a 2-byte swap running over 4-byte elements passes an f8-only test),
and the Fortran transpose is tested at **rank 3** (a rank-2 test passes with the axes accidentally
swapped).

A structured dtype is ADR-0056 §1 in its purest form — the shape of the data decides the primitive, and
rows of typed fields are a table. It is the one place the primitive depends on the **file** rather than the
format, so `spec::validate` accepts `table` for this backend alone (an operator cannot know their own dtype
without opening the file) and the CLI reports the primitive it *sealed* rather than the one asked for.

An `object` dtype is refused and never unpickled: a pickled `.npy` is arbitrary Python code, and
`allow_pickle` is a remote-code-execution switch this tool does not have. Fixed-width strings, `datetime64`
and complex are each refused with a **route** (a table can carry text and an epoch; complex is #419)
rather than a bare failure.

## `.npz` is a collection

One array product per member — §10's shape rule one level up: archive members are independent arrays, not
slices of one grid. Each product is named after its member, so `np.savez(f, energy=…, counts=…)` gives you
products called `energy` and `counts`. The expansion names every member explicitly in the spec, so the spec
stays an honest archival record rather than saying "everything in this archive".

Keyed on the **source kind**, not the member count: a one-member archive is still a collection, because an
output shape that depends on the data is not one anyone can script against. §11's `arr_0` advisory fires
once on stderr and never blocks.

## Five corpus fixtures, and a relation rather than two hashes

`ingest_npy_endianness_{le,be}` is §5's named fixture, split in two because the claim is the **equality
between them** — so `the_endianness_twins_seal_to_the_same_payload` asserts that relation directly, and it
therefore holds even in a build where the goldens were just regenerated. Plus `ingest_npy_fortran`,
`ingest_npy_structured` (which seals a `table`, visible in the committed goldens) and `ingest_npz_member`.
**H6 joins `LIVE_HAZARDS`.**

The completeness claims are scoped to the full configuration: a reduced build compiles its array fixtures
out by design, and asserting completeness there would have to be weakened into asserting nothing. The
reduced configuration still checks the two things that matter to it — the declared fixture count and value
preservation over the fixtures it can run.

## A pre-existing Gate B blind spot, closed

**`zip` was missing from ADR-0057 Gate B's snapshot list** — the crate that frames every sealed byte was
unwatched, which is exactly what that script's own note warns about ("adding a codec crate to the write
path without adding it here leaves a blind spot").

Adding it paid for itself on its first day: it showed that zip's umbrella `deflate` feature drags in the
zopfli **compressor**, for a capability nothing uses — we only ever *read* these archives.
`["deflate-flate2", "flate2"]` gets the decompressor alone, and flate2 is already in-tree via parquet.
Hence zero new crates.

Gate B's delta for this PR is one new snapshot (`zip`, previously unwatched) and exactly one added feature
pair — `tessera-ingest/npy`, our own. No pre-existing seal-path crate gained or lost a feature.

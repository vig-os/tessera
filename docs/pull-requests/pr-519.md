# [PR 519](https://github.com/vig-os/tessera/pull/519) fix(ci): build test-target deps in cargoArtifacts so nextest stops recompiling them

`cargoArtifacts` never compiled the test-target dependency graph, so `workspace-test` recompiled it — 96 crates that `tessera-deps` had already built at the identical version, plus 59 dev-dependency-only crates it had never built at all.

## Cause

From the generated derivations:

```
tessera-deps:     cargo check --locked --all-targets     <- METADATA (.rmeta) for every target
                  cargo build --locked                   <- CODEGEN for lib/bin targets only
tessera-nextest:  cargo nextest run                      <- must LINK real test binaries
```

Confirmed in crane's own source (`lib/buildDepsOnly.nix`): `cargoCheckExtraArgs` defaults to `--all-targets`, `cargoBuildExtraArgs` defaults to `""`. The build step never sees it. So anything reachable only from test targets is type-checked and thrown away.

## Evidence

Measured on a green leg (#500, run 36543170354, x86_64):

| cohort | count | examples |
|---|---|---|
| same name **and** version as a crate `tessera-deps` compiled | **96** | `arrow-array 58.3.0`, `chrono 0.4.45`, `dicom-object 0.9.1` |
| never built by `tessera-deps` (dev-dependency-only) | 59 | `datafusion 54.0.0`, `arrow-csv/json/row`, `comfy-table` |
| workspace crates (expected) | 14 | `tessera-*` |

`workspace-test` is consequently **~96% compilation**: 58.5 min wall-clock, of which test execution is ~30 seconds across three batches (last `Compiling` at 09:52:57, derivation ends 09:55:05).

## Why this is the highest-value CI change available

`nextest` is the **serial floor** for every parallelism design:

```
deps (19.4) + nextest (58.5) = 77.9 min   vs an 84.8 min leg
```

That is why #517 measured a maximum gain of **6.9 min** from *any* job split, at 3.4× the runner-minutes. Lowering this floor bounds both #517 and #507 — it is worth more than either.

## The change

```nix
cargoArtifacts = craneLib.buildDepsOnly (
  commonArgs // { cargoBuildExtraArgs = "--all-targets"; }
);
```

Verified at the derivation level: the deps build step is now `cargo build --locked --all-targets`.

## What I expect, and what would falsify it

`tessera-deps` gets **slower** (it now codegens more) and `workspace-test` gets **faster**. The trade should be favourable because ~14 derivations inherit these artifacts while only one was paying the rebuild — but that is a prediction, and this PR's own CI run is the measurement. If the deps increase exceeds the nextest saving, the floor gets *worse* and this should be closed rather than argued for.

Numbers to be posted here once the legs land: before/after duration for `tessera-deps` and `tessera-nextest`, the new `Compiling` counts, leg wall-clock, and peak memory (more codegen in one derivation could raise it — relevant to #495).

## Correctness gates that must hold

- `seal-profile-determinism` — the dev-vs-release corpus comparison.
- Gate B feature snapshots.

**A change to how dependencies are compiled must not move any content hash.** If a sealed byte moves, that is a format decision, not a build tweak, and this stops here.

Closes #518

### Falsified by its own CI run — do not merge

The PR body set the criterion in advance: if `nextest` does not get cheaper, this should be closed rather than argued for. It did not get cheaper.

| | `tessera-deps` compiled | `nextest` compiled | same name+version in both | `nextest` duration |
|---|---|---|---|---|
| before (#500 x86) | 572 | 155 | 96 | 58.5 min |
| **this PR** (run 36572848609, x86) | **572** | **156** | **97** | **58.9 min** |

Nothing moved. `nextest` still recompiles the same ~97 crates `tessera-deps` already built, plus the same dev-only cohort.

**Why the diagnosis was wrong.** `tessera-deps` compiled exactly 572 crates both with and without `--all-targets` on the build step — and it *never* compiled `datafusion` either way. `cargo check --all-targets` already walks every target, so if `datafusion` were reachable from any target in the deps build it would have appeared there. It doesn't, which means the difference is not *which targets* are built but *which features* are resolved when `nextest` runs. `datafusion` is optional behind `tessera-cli`'s `sql` feature, and `cargo nextest run` passes no features — so something unifies `sql` on for the test build that the deps build does not see. That is the thread to pull; I have not found it yet and am not going to claim a cause I haven't shown.

I also only inspected `nextest`'s **buildPhase** when diagnosing (it just prints versions) rather than its **checkPhase**, which is where the real command runs. That gap is how a plausible-but-wrong mechanism got written into a PR body.

Converting to draft. The finding in #518 (the ~96-crate redundancy) stands; this fix for it does not.

Closing: the problem this fixes does not exist. The "nextest" measurements behind #518 pooled three different checks that shared the derivation name `tessera-nextest-0.0.0` (`workspace-test`, `sql-tests`, `minio-range-read`). The 59 "dev-only" crates were `sql-tests` compiling DataFusion by design; the 96 "redundant" rebuilds were arrow-*, chrono etc. rebuilt with the extra features the sql/cloud stacks unify in — different artifacts, legitimately. `cargo tree --workspace -e normal,dev -i datafusion` reports no match: DataFusion isn't in the default graph, so `workspace-test` never compiled it. That's why this PR moved no number. The real defect — indistinguishable log labels — is fixed in #536 (tracked in #535), with a guard that fails evaluation on any future collision.

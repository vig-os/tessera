# [PR 501](https://github.com/vig-os/tessera/pull/501) fix(ingest): per-lane decoder digest that carries each crate source and covers the whole decode path

Closes #477.

The sealed `ingest_decoder` digest (ADR-0056 §6a) committed to the wrong slice of reality three ways. The
design, the four measured derivation attempts and the impact numbers are [on the issue](https://github.com/vig-os/tessera/issues/477#issuecomment-5884651349);
this is what landed.

## 1. It was one global crate list for every lane

Adding `zip` for `.npz` moved the `manifest_hash` of every parquet and csv product, because a parquet seal
committed to a zip library that had no part in reading it. All **9** corpus fixtures across **3** lanes
carried the **same** digest, so it could not distinguish the Parquet decoder from the CSV one.

Now one digest per lane, keyed off the capability features that already declare each lane's crates. The
clearest illustration is the CSV lane, which ADR-0057 §5 discovered needs no arrow at all:

```
rust-csv            3 crates   v2;pins=csv=1.4.0,csv-core=0.1.13,memchr=2.8.2
arrow-rs/arrow-ipc 24 crates
arrow-rs/parquet   41 crates
```

It used to carry the whole arrow tree and `parquet` besides.

## 2. It ignored `source`

A decode-path crate pinned to a git fork at the same version was indistinguishable from the registry
release — the one question the digest exists to answer, wrong in exactly the case where someone
deliberately changed a decoder's behaviour. This repo already pins vortex to a fork, so the manoeuvre is
established practice; it did not bite only because vortex is the *encoder* and correctly off the decode
path (27 git-sourced crates in the lockfile, none reachable from a lane).

Each pin is now `crate=version` for a registry release and `crate=version@git+<url>#<rev>` otherwise, so a
fork-free build's per-crate shape is unchanged and only a fork reads differently. Tested directly on the
pre-image builder rather than waiting for the first fork to expose it.

## 3. It omitted most of the decode path

The hand-maintained list named 10 crates. Absent from it were:

- **`thrift`** and `integer-encoding` — Parquet's footer, schema and page headers *are* Thrift.
- **`flatbuffers`** — Arrow IPC's record-batch and schema messages.
- **Every page codec**: `snap`, `zstd`, `brotli`, `flate2`, `lz4_flex`. Swapping a snappy implementation
  moved nothing.
- `crc32fast` (page checksums), `num-bigint` (decimals), `memchr` (the scanner `csv-core` tokenises with).
- **`chrono-tz`** — the crate ADR-0056 §6a names as hazard H1's own mechanism.

Now 41 crates for parquet, 24 for arrow-ipc, 3 for csv.

## Membership cannot be derived — measured, not assumed

| Derivation | parquet | Why it fails |
| --- | --- | --- |
| Full lockfile closure | 114 | `syn`, `cc`, `windows-*`, `wasm-bindgen` |
| `cargo metadata`, normal deps only, proc-macro crates dropped | 92 | `syn` survives as a normal dep **of** a proc-macro crate |
| …never descend into a proc-macro subtree | 85 | platform shims arrive via `chrono → iana-time-zone` |
| …also cut the `iana-time-zone` subtree | 77 | still `hashbrown`, `bytes`, `slab` |

`hashbrown` is a genuine runtime dependency of the Parquet reader that provably cannot change a decoded
value, and **nothing in the dependency graph says so**.

So the **candidate set is derived** (the lockfile closure of the crates each lane's Cargo feature declares)
and the **membership is declared**, with `decode_path_gate` failing any candidate that is neither in the
digest nor excluded with a reason. **That inversion is the substance of the fix**: an unclassified crate now
stops the build, where a forgotten one used to narrow the sealed claim in silence — which is how three
crates' worth accumulated unnoticed. Over-claiming costs visible churn; under-claiming was invisible.

Verified by unclassifying `hashbrown` and watching the gate name the lane and the crate:

```
unclassified crate(s) on an ingest decode path — each must go into `IN_DIGEST` (it can change a
decoded value) or into `EXCLUDED` with the reason it cannot, in crates/tessera-ingest/src/decode_path.rs:
  lane arrow: hashbrown
  lane parquet: hashbrown
```

`decode_path` is shared verbatim by `build.rs` (which `include!`s it), the library and the gate, so the
digest and the gate cannot disagree about what the decode path *is*. It reads `Cargo.lock` rather than
shelling out to `cargo metadata`: no subprocess, no network, so the gate has the same teeth in the hermetic
flake check as it does locally. A gate that degrades to vacuous in CI is worse than no gate.

## The pre-image is versioned (`v1` → `v2;pins=…`)

This digest has been redefined three times — the crate's own feature set came out, `CARGO_PKG_VERSION`
came out, and now this — and each earlier redefinition was **silent**, so a reader comparing digests across
one read "the decoder changed" when only the derivation had. Three bytes ends that.

## Migration: self-verifying, and it verified

No format-version bump: no sealed field is added, removed or renamed, and the pre-image's *composition* is
not part of the format contract (it is printed by `tessera info`, never declared in a schema).

Because `content_hash` is the Merkle root over **block digests** while the triple lives in the manifest's
generation bag, regenerating *must* move `manifest_hash` and nothing else. Measured across the 9 fixtures:

| Field | Moved |
| --- | --- |
| `id` | **0 / 9** |
| `content_hash` | **0 / 9** |
| `manifest_hash` | 9 / 9 |
| `ingest_decoder.features` | 9 / 9 |
| distinct digests | 1 → **3** |

Had a `content_hash` moved, the corpus gate says so in as many words ("this is not a formality — a decoder
extracted different values"), and the change would have been wrong.

## Also

`decoder::ALL` is feature-gated, so `tessera info` no longer reports a lane that is not compiled in — the
same honesty problem in miniature. The pre-images themselves stay feature-selection-invariant, which §6a
requires and which `ingest-gate-a-sql` proves by regenerating the corpus byte-equal with `sql` on (the
configuration that flips `arrow-array/chrono-tz`).

`tessera info --json`'s single `ingest_decode_features`/`ingest_decode_digest` pair becomes one
`ingest_decode` entry per lane, each carrying its digest and the pre-image it is taken over, so the digest
stays invertible from any build rather than being an unfalsifiable label.

## Review round — false sameness inside the fix for false sameness

Review found a fourth instance of the defect, in this PR's own first fix: the lockfile was scanned **by
name**. A lockfile legitimately resolves several versions of one crate, and they are different code.
`base64` resolves here at both 0.21.7 and 0.22.1, `parquet` depends on **0.22.1**, and a name-keyed lookup
returned the first match — so the parquet digest sealed `base64=0.21.7`. **A real `base64` bump in the
Parquet reader would not have moved the digest**, which is precisely the false sameness this PR exists to
remove. Following only the first same-name package also silently dropped every crate reachable solely
through a second version: `foldhash`, `r-efi`, `rand_core`, `wasip2`, `wit-bindgen`, via the second
`hashbrown`/`getrandom`.

A package's identity is now `(name, version)` throughout. The lockfile is parsed once into resolved
packages; a dependency edge carrying a version resolves exactly; an edge without one resolves **only when
unambiguous**, rather than guessing; and a crate present at two versions on one path contributes **two**
pins. Parquet's closure grows 114 → 117 resolved packages accordingly. A gate test proves the property on
a synthetic lockfile, so it holds regardless of what this workspace happens to resolve.

Re-verified against the original baseline: **0/9 `id`, 0/9 `content_hash`, 9/9 `manifest_hash`**. Against
the first fix only the 6 parquet fixtures moved — the csv and arrow-ipc digests are byte-identical, which
is the right signature for a bug that only ever touched parquet's `base64`.

Also from review:

- Stale **`EXCLUDED`** entries now fail the gate, not only stale `IN_DIGEST` ones.
- **Patterns removed**; all 76 exclusions enumerated. `seq-macro` was the cautionary case the reviewer
  named: it generates Parquet's bit-unpacking code, so a `*-macro` rule would have waved through something
  that does bear on decoding.
- `lane_roots` handles a multi-line feature array, which the single-line scan silently truncated, and the
  gate pins each lane's exact roots rather than only the lane names.
- A **private registry** at the same version no longer reads as crates.io.
- ADR-0056 §6a records the **system-linked codec** limit (`zstd-sys`, `flate2`'s backend are pinned by
  crate version, not by the library actually linked), and the `serde_core` reason now correctly says it
  reaches the csv lane via `csv`.

Two deviations from the suggested fixes, both deliberate:

- **`toml` was not taken as a build-dependency.** A `[build-dependencies]` entry moves the resolved feature
  graph, which is an ADR-0057 §5 Gate B event — and `feature-snapshots` is exactly the gate that fires. The
  scan was made robust instead.
- **Path dependencies are refused, not hashed.** `Cargo.lock` records no path for one, so `name=version@path`
  cannot say which checkout was used and there is nothing in the file to improve it with. The gate refuses
  an in-digest path dependency, so the first one forces a deliberate decision. None exists today.

## Gates

Local: `ingest-gate-a`, `ingest-gate-a-sql`, `ingest-gate-a-workspace`, `ingest-gate-a-reduced` (the
both-profiles corpus event), `workspace-test`, `workspace-fmt`, `guardrails-gates`, `feature-snapshots`
(Gate B — unchanged, since no dependency was added) and `mdbook-build` all pass; `cargo clippy --workspace
--all-targets -D warnings` clean; whole workspace `cargo test` green.

ADR-0056 §6a carries an amendment recording all three findings, the `v1`→`v2` rationale, the
no-format-bump decision and what this does **not** close (a feature flipped inside the shared arrow tree
remains outside the digest; ADR-0057 Gate A still guards it).

# [PR 474](https://github.com/vig-os/tessera/pull/474) test(io): gate the seal against the build configuration, the axis #468 hid on

Closes the determinism hole #468 sits in, and pins #468 itself so the workaround it forced cannot
become permanent. The upstream bug is vortex's to fix; this PR is the gate, the reproducer and the
record.

## What the bug is

vortex 0.75.0 writes **different container bytes** for an integer column whose encoding produces
*patches*, depending on whether `debug_assertions` is enabled. `[i64::MIN, 0, i64::MAX]` is the minimal
case — it zigzags to `[u64::MAX, 0, u64::MAX-1]`, which bitpacks with exactly one exception:

| build | bare `PrimitiveArray` | through `table::encode` |
| --- | --- | --- |
| `debug_assertions` **on** | 2796 B | 2940 B |
| `debug_assertions` **off** | 2772 B | 2916 B |

The compression is **identical** in both: same chosen schemes (`vortex.int.zigzag → vortex.int.bitpacking`),
same `compressed_nbytes=19`, same estimated and achieved ratio `1.263157894736842`, `accepted=true`. The
difference is the file metadata written *around* the values.

## Why it is `debug_assertions` and not codegen

Toggling the cargo knobs independently, same target dir:

| build | `debug-assertions` | `overflow-checks` | bytes |
| --- | --- | --- | --- |
| release (default) | off | off | 2916 |
| release | **on** | on | **2940** |
| release | **on** | off | **2940** |
| release | off | on | 2916 |
| debug (default) | on | on | 2940 |
| debug | **off** | off | **2916** |

`debug_assertions` flips it in both directions; `overflow-checks` and the optimisation level do nothing.
So this is neither UB nor float/vector codegen.

The site is `vortex-array/src/patches.rs`, the only `debug_assertions`-gated code in the write path that
**calls an aggregate function** rather than performing a pure check — `is_sorted(&indices, …)`. Evaluating
it executes and annotates the patch indices array, and the written container reflects it: **an assertion
with a side effect**. Two independent measurements back it: only patch-producing inputs diverge
(`[i64::MIN, i64::MAX]`, byte-identical across profiles, produces no patch arrays at all), and the debug
trace carries a rewrite release does not — `execute_parent rewrote vortex.cast(u8, len=1) ->
vortex.primitive(u8, len=1)`, the indices being materialised.

Stated precisely: the `debug_assertions` dependence and the patch correlation are **measured**; that this
particular assert is the site is **by elimination**; the last hop from "indices annotated" to "+24
container bytes" is **inferred**, and upstream can confirm it instantly.

## Blast radius, honestly

The axis is `debug_assertions`, so **every release build agrees with every other release build, on any
architecture** — shipped binaries are mutually consistent. What diverges is a debug-built tool against a
release-built one. It is still an S15 violation, because "the bytes are a function of the data" has to
hold for *a* build of a version, not only the release ones. (The separate aarch64 float-fixture
divergence is **#472** — same profile, different arch, a different defect.)

## What is in here

1. **`known_limitation_468_full_span_int_container_bytes`** reproduces it through **vortex APIs only**,
   with the stock `WriteStrategyBuilder::default()` — no tessera types, no `exclude_schemes`, no Pco — so
   it cannot be mistaken for something our compressor configuration causes. It also asserts the same
   divergence reaches `table::encode`, a control shape that does *not*, and within-profile stability.

   It asserts the bug is **still present**, so it **fails when upstream fixes it**. That failure is the
   signal to restore the `i64` extremes that #460's `write_scalars` currently gives up. An `#[ignore]`
   would let the fix land unnoticed and leave that fixture permanently weaker.

2. **`seal-profile-determinism`** — a flake check regenerating the conformance corpus under **both** the
   dev and the release profile, requiring agreement with each other and with the committed file. Worth
   saying plainly: `corpus/corpus.json` was produced by a bare `cargo run` (dev profile) while
   `workspace-test` runs the same code release-built, so the two halves of our own CI were checking
   different builds and nothing compared them.

3. **ADR-0057 §5** records the lesson, which is sharper than "an exclusion list is not a proof":
   **a determinism argument about the codec does not cover the container.** The ALP/ALPRD exclusion's
   reasoning is sound and is about the encoding of *values*; this defect has identical codec decisions
   and differs in the metadata around them — and the seal covers the whole container.

## Notes for review

- The gate is built on **tessera-io's** corpus, not the ingest one: `ingestGateA` does not exist on `dev`
  (it arrives with #460), and after #460's fixture narrowing the pathological shape lives only in the
  reproducer. Adding the ingest corpus to the same check once #460 lands is a one-liner.
- Scoped to `-p tessera-io` on purpose — a second full-workspace profile would roughly double this leg
  for no extra coverage. It is still a new two-profile build; if the x86_64 leg's time becomes a problem
  this is a reasonable candidate to make release-only.
- `seal-profile-determinism` is verified to **evaluate** (`nix eval …drvPath`) but was **not built
  locally**: `/` is at 97%, and a two-profile derivation in one sandbox is what exhausted it when Gate A
  was a single derivation. CI has the disk.
- `cargo test -p tessera-io --lib known_limitation_468` passes in **both** profiles locally, so all five
  asserted byte counts are confirmed rather than copied from notes.

An upstream issue is drafted and awaiting a decision on filing; it is not filed by this PR.

# [PR 862](https://github.com/vig-os/tessera/pull/862) fix(io,py,deps): read a .tsra the one way every zip reader does (GHSA-m665-v7pm-7grj)

Closes #857. Supersedes #689 (Renovate's bump changes only `Cargo.lock` and fails CI).

## Advisory

[GHSA-m665-v7pm-7grj](https://github.com/advisories/GHSA-m665-v7pm-7grj) (CVE-2026-115905), critical. In
`zip <= 9.0.4`, `ZipArchive` trusts the central directory and `ZipStreamReader` trusts the local file
headers, so one archive can read two different ways. **9.0.5 adds the check only as an opt-in**
(`ZipReadOptions::enforce_header_consistency`, `ZipArchive::validate_header_consistency`), so the bump
alone changes no behaviour. This is the only vulnerable package Dependency Review flags on the promotion
PR #855.

## Impact assessment

- tessera opens a `.tsra` at `ArchiveOffset::Known(0)` and reads it only through the central directory.
  `by_name` takes the compression method from the CD, and every block digest is checked on the CD view.
  So tessera itself never reads unverified bytes.
- **`tessera verify` attested only the CD view, though.** On zip 9.0.4, a genuinely sealed `.tsra` crafted
  in any of the four ways below **verified**, while zip's own streaming reader saw a different archive.
  That is a real hole for an integrity format.

| crafted archive | what a streaming reader sees | caught by |
|---|---|---|
| a block's local header renamed to `manifest.json` | a second `manifest.json` | 9.0.5 per-member check |
| a STORED block whose sealed bytes are also a deflate stream; the LFH says DEFLATE and carries the inflated CRC | the same name with other content and a valid CRC | 9.0.5 per-member check |
| one block named twice in the CD, the forged copy first (zip resolves to the last record) | the forged block first | 9.0.5 duplicate-name check |
| a complete local entry in bytes no CD record covers | a hidden extra `manifest.json` | **tessera only**, by the tiling rule (9.0.5's validation accepts this archive) |

The `.npz` ingest reader is unchanged and stays central-directory-only. numpy's `np.load` reads the CD
through `zipfile` too, so tessera decodes the array numpy would load. A comment in `npy.rs` records this.

## Changes

- **Dependency:** zip 9.0.4 → 9.0.5. Only the zip entry in `Cargo.lock` moves, and the workspace floor is
  now `9.0.5`, so no resolve can go back.
- **Member reads:** every `.tsra` member read goes through `open_member`. It enforces header
  consistency, refuses any read from an archive with a duplicated name, and passes I/O errors through.
  This covers `Reader`, the aux rewrite and `read_manifest_unverified`. zip already reads that local
  header to find the data, so the extra cost is small.
- **Deep verify:** `Reader::verify_payloads` and `verify_payloads_parallel` first run `check_one_reading`,
  once before either branch. It runs zip's whole-archive validation, then tessera's own rule that the
  entries tile the archive from byte 0 to the central directory: no gap, no overlap, no data descriptor.
  A cheap (cloud) open is unaffected and still reads only the tail.
- **Python:** `Reader.verify()` and `tessera.verify()` now run `verify_payloads` instead of a
  `read_block` loop. They make the same pass as `tessera verify`, in bounded memory, and errors name the
  file.
- **SPEC:** §6 now states the one-reading rule, and §7 points to it.
- **Cloud reader (second commit):** the check reads each local header as three small reads, and
  `ObjectStoreReader` issued one range GET per read outside the cached tail. The first CI run's
  `s3-range-read` check caught it: opening a 10-entry archive cost 23 GETs against a budget of < 20. A read
  shorter than `READ_AHEAD` (4 KiB) that misses the tail now fetches a 4 KiB window in one GET. Payload-sized
  reads still go straight to the network. The same open now costs **9 GETs**, and the budget is unchanged.
  Pinned by `small_reads_in_one_region_share_one_get`.

## Why Renovate's #689 was red (root cause, not symptom)

Three goldens pin the zip version and moved with it. Each is a deliberate corpus event:

- `info.trycmd`: the `npz-member` backend version.
- `tests/feature-snapshots/zip.txt`: one line, `zip v9.0.4` → `v9.0.5`, with no edge added or removed.
  This is inert.
- `corpus/ingest-corpus.json`: `ingest_npz_member`'s `ingest_decoder.features` and `manifest_hash`
  moved. Its `id` and `content_hash` did not, so the decoded values are unchanged. No other fixture moved.

The `aarch64-apple-darwin` failure on #689 was "The configuration 'macos-14-arm64-us-default' is not
supported", a runner-image error on that run's base. macOS builds pass on dev since then.

## Tests

`tessera-io/tests/header_consistency.rs` crafts the four archives from sealed products. Each test first
asserts the differential is real (the stream view differs from the CD view, with valid CRCs), then asserts
that serial and parallel verify both refuse the file, as `Error::Container`.

Pre-fix run, on zip 9.0.4 with this test only (exit 101):

```text
test a_central_directory_naming_one_member_twice_is_refused ... FAILED
test a_block_whose_local_header_names_another_member_is_refused ... FAILED
test a_member_hidden_before_the_central_directory_is_refused ... FAILED
test a_stored_block_whose_local_header_claims_deflate_is_refused ... FAILED
test every_tessera_writer_and_corpus_file_satisfies_the_layout_rule ... ok
  panicked at header_consistency.rs:290: verified an archive two zip readers read differently
test result: FAILED. 1 passed; 4 failed
```

After the fix, all 5 pass. The positive control checks that the 8 committed corpus vectors and every
writer path (`pack`, `pack_streaming`, `pack_streaming_verified`, the aux rewrite, and `unpack` followed by
`pack_dir`) still verify and read identically both ways.

`smoke.py` adds the hidden-entry case for both Python verify surfaces. The same crafted files run through
the CLI: `tessera verify` refuses all 8 corpus-derived cloaks (rc=1), while `zipfile` lists them
unchanged and `testzip()` passes.

Local runs, all exit 0:

- `cargo test -p tessera-io`
- `cargo test -p tessera-ingest` (including `ingest_corpus`)
- `cargo test -p tessera-cli --test cli` (`info.trycmd`)
- `cargo clippy -p tessera-io -p tessera-py --all-targets -D warnings`

CI runs the full flake gate.

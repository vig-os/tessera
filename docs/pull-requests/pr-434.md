# [PR 434](https://github.com/vig-os/tessera/pull/434) ci(release): SHA-pin the actions in the generated release.yml via [dist.github-action-commits] (#433)

## Summary

- `.github/workflows/release.yml` is generated by cargo-dist (0.32.0, pinned in `dist-workspace.toml`); its `plan` job regenerates the file and fails if the checked-in copy differs, so hand-edits that dist wouldn't emit are not viable. The route to a compliant `release.yml` is the config, not the generated file.
- The SHA-pin guardrail (`scripts/check-action-pins.sh`, prek hook `check-action-pins`) requires every `uses:` to be a full 40-char commit SHA. `release.yml` was violating that policy in 16 places: `actions/checkout@v7.0.1` (5x, from #429), `actions/upload-artifact@v7` (6x, cargo-dist default), `actions/download-artifact@v8` (5x, cargo-dist default).
- Set all three entries in `[dist.github-action-commits]` to the resolved commit SHAs of their tags, then regenerated `release.yml` with the pinned `cargo-dist` (`dist generate --mode ci`) so the checked-in file is byte-exact with what the `plan` job emits.

## SHAs (each verified against the tag's git ref via `gh api repos/<o>/<r>/git/ref/tags/<tag>`; all are `type: commit`)

- `actions/checkout` v7.0.1 -> `3d3c42e5aac5ba805825da76410c181273ba90b1`
- `actions/upload-artifact` v7.0.1 -> `043fb46d1a93c77aae656e7c1c64a875d1fc6a0a`
- `actions/download-artifact` v8.0.1 -> `3e5f45b2cfb9172054b4087a40e8e0b5a5461e7c`

The only lines that changed in `release.yml` are the 16 `uses:` lines becoming `@<sha>` (no other drift from what dist emits).

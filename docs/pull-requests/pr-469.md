# [PR 469](https://github.com/vig-os/tessera/pull/469) ci: accept dependabot/** in the branch-name gate

## What

Unblocks every Dependabot PR. #443 and #444 each fail exactly one check, `Commit Messages`,
and are green on everything else — including both `nix flake check` arches and
`CodeQL Analysis (actions)`.

## Root cause

They never reach the commit-message validator. They fail one step earlier, at
**`Validate branch name`**:

```
##[error]Branch name 'dependabot/github_actions/dev/actions-minor-patch-64e3431685' does not
follow the convention <type>/<issue>-<summary> (types: feature,bugfix,hotfix,release,docs,test,
refactor) or chore/<summary>.
```

The allowlist covers Renovate's namespace but not Dependabot's:

```bash
ALLOWED+="|^renovate/.+$"      # present
# nothing for dependabot/**
```

devkit itself uses Renovate, so its own bot PRs match this and the gap was never hit.

Dependabot's `dependabot/` prefix is **not configurable** —
`pull-request-branch-name.separator` only changes the separator — so no `dependabot.yml`
setting can produce a conforming name. Hence a gate change rather than a bot-config change.

## Two things it is *not*

Recording these because they are the natural first guesses and both are wrong:

- **Not the `Refs:` line.** `validate_commit_range.py` already skips `…[bot]` authors
  (`BOT_AUTHOR_SUFFIX`), and `validate_title` marks every approved type Refs-optional. So
  `DEVKIT_REFS_OPTIONAL_TYPES` / `DEVKIT_REFS_POLICY` would be a no-op here.
- **Not the cause of #445.** `chore/devkit-1-17-0` matches the existing `chore/<slug>` clause.
  That PR fails `Lint & Format` because devkit 1.17.0 adds a `shellcheck-composite-actions`
  hook while `flake.nix` still pins `devkit/1.16.0`, so the binary is absent from the dev-shell.
  Filed upstream as vig-os/devkit#1756 — not fixed here.

## Verification

Tested the patched allowlist against the real branch names rather than by eye — all 16 cases
behave correctly:

| accepted | rejected |
|---|---|
| the 3 live `dependabot/**` shapes (incl. nested `pip/tessera/bench/ecosystems/...`) | `dependabot` (bare prefix) |
| `chore/devkit-1-17-0`, `ci/466-…`, `fix/356-…` | `Dependabot/x` (wrong case) |
| `dev`, `main`, `release/0.1.0`, `worktree/12`, `renovate/some.thing(1)` | `foo/dependabot/x` (not anchored) |
| | `mybranch`, `feat/nonumber-slug` |

The clause is as safe as the `renovate/.+` one above it: only the bot creates that namespace,
and creating a branch needs write access either way.

## Upgrade durability — read before merging

`ci.yml` is devkit-managed, so this is deliberately a **temporary local patch**:

- the real fix is upstream, **vig-os/devkit#1755**, and the added line carries a `REMOVE once
  devkit#1755 lands` comment;
- `DEVKIT_DRIFT_CHECK` is already `false` (#441), so the patch does not trip the drift gate;
- `devkit-upgrade.yml` regenerates `ci.yml`, so **a devkit upgrade will drop this line.** #466
  stays open as the reminder.
- I did **not** add `ci.yml` to `DEVKIT_UPGRADE_EXCLUDE`: that is the only preservation seam
  devkit offers and it freezes the entire workflow, forfeiting every future CI improvement to
  keep one clause. Losing the line on upgrade is the cheaper failure, and it is visible in the
  upgrade PR's diff.

Also filed #467: this repo has both `renovate.json` and `.github/dependabot.yml` configured for
the same ecosystems while only Dependabot actually runs. Standardising on Renovate would remove
this class of problem structurally, since devkit's allowlist already covers `renovate/*`.

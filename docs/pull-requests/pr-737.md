# [PR 737](https://github.com/vig-os/tessera/pull/737) fix(deps): move parquet/arrow to 58.4.1 for thrift 0.23 (RUSTSEC-2026-0435)

Closes #736

## Advisory

**RUSTSEC-2026-0435** (CVE-2026-43868): unbounded allocation in `thrift`'s `TBinaryInputProtocol::read_bytes`,
fixed in `thrift` 0.23.0. Path on `dev`: `thrift 0.17.0 ← parquet 58.3.0 ← tessera-ingest, tessera-cli`.
`cargo-deny … advisories` therefore failed on every PR.

## Decision: upgrade (no `deny.toml` ignore)

Evidence from the crates.io index:

| crate | version | `thrift` req | `arrow-*` req |
|---|---|---|---|
| parquet | 58.4.0 and earlier (incl. all of 50–57) | `^0.17` | — |
| parquet | **58.4.1** | **`^0.23`** | `^58.4.1` |

The arrow pin is compatible: vortex 0.75 (the `gerchowl/vortex` fork) declares `arrow-* = "58.3"` (caret) and
datafusion 54 declares `arrow`/`parquet` `^58.3.0`, so both accept 58.4.1. Vortex and datafusion don't move.
The workspace `=` pins on `arrow-array`/`-buffer`/`-schema`/`-ipc` and `parquet` move 58.3.0 → 58.4.1.

The lockfile changes only parquet's decode path:

- `arrow-{array,buffer,data,ipc,schema,select}` and `parquet` 58.3.0 → 58.4.1
- `thrift` 0.17.0 → 0.23.0, `ordered-float` 2.10.1 → 3.9.2
- thrift 0.23 depends on `uuid` (Thrift's UUID wire type). `uuid` was already in the lockfile.

The remaining arrow crates (`arrow`, `-arith`, `-cast`, `-csv`, `-json`, `-ord`, `-row`, `-string`, reached
through vortex/datafusion) stay at 58.3.0. That is semver-compatible.

The 58.3.0 → 58.4.1 source diff for the seven bumped crates includes parquet's legacy `Statistics` size limit,
AES-256 key support in the decryptor and a `ByteArray::into_builder` rewrite. It also includes one **writer**
byte-level change (correction after review): arrow-ipc's `writer.rs` now writes a 0-length validity buffer for a
column with `null_count == 0`, where it used to write a full all-valid bitmap. Tessera writes IPC only to generate
test fixtures, so the regenerated IPC corpus source bytes change. That source digest (`ingested_from`) moves along
with the `ingest_decoder` digest, per ADR-0056 §6a. No decode semantics change: 0/14 `content_hash` moved.
Follow-up #738 tracks keeping a full-bitmap IPC fixture under test.

## ADR-0056 corpus event (deliberate, self-verifying)

- `corpus/ingest-corpus.json`, regenerated with `cargo run -p tessera-ingest --example gen_ingest_corpus`:
  - **0/14 `content_hash` and 0/14 `id` moved.**
  - 7/14 `manifest_hash` moved: exactly the parquet and arrow-ipc fixtures, each next to a moved
    `ingest_decoder` (`=58.3.0` → `=58.4.1`, new digest). This is the routine case.
  - The csv, npy and npz fixtures are byte-unchanged.
- Gate B (`tests/feature-snapshots`): 4 files and 42 lines change, all version strings of the 7 bumped crates.
  With those versions normalised, old and new snapshots are identical (`diff` exit 0 for all 4 files), so no
  feature edge was added or removed.
- Decode-path gate: thrift 0.23 brings two new parquet-lane candidates. Both are `EXCLUDED` with a reason:
  - `uuid`: parquet 58.4.1's footer and page-index reader doesn't use the `thrift` crate's protocols at all. It
    decodes with its own `parquet_thrift::ThriftSliceInputProtocol`, which has no UUID field type. The `thrift`
    crate serves only the public legacy `format::*` types, which declare no UUID-typed field. The only reach is `TInputProtocol::skip` of an unknown field (`thrift-0.23.0/src/protocol/mod.rs:212`), which
    discards the value. `read_uuid` is a 16-byte `Uuid::from_bytes` copy (`protocol/compact.rs:311`).
    Parquet's UUID *logical* type is a FIXED_LEN_BYTE_ARRAY page value and never touches this crate.
  - `rand_core`: getrandom 0.4's RNG traits (thrift → uuid → getrandom). It generates randomness and never
    reads file bytes.
  - `uuid` 1.23.4, getrandom 0.4 and `rand_core` 0.10 were already in the lockfile through other paths. They are
    new only on the parquet decode path.
- **zstd re-check** (`deny.toml` asks for it on every parquet bump): parquet 58.4.1 still requires zstd `^0.13`, and
  its library code uses only `zstd::bulk` (`compression.rs:511-539`). The single `zstd::Decoder` is in the
  `parquet-fromcsv` binary, which isn't built. arrow-ipc 58.4.1 is bulk-only too. The zstd ignores still hold.
- `info.trycmd` and the version comments in `Cargo.toml` and `tessera-cli/Cargo.toml` now say 58.4.1.

# [PR 488](https://github.com/vig-os/tessera/pull/488) ci(nix-check): a red nix leg must name a real failing check

Closes #483.

## Problem

`nix flake check` stops at the first failing derivation. On #481 an unrelated `minio` substitution
failure therefore took down **all 17** aarch64 checks:

```
❓ checks.aarch64-linux.seal-profile-determinism (cancelled)
❓ checks.aarch64-linux.feature-snapshots        (cancelled)
❓ checks.aarch64-linux.workspace-test           (cancelled)
… 14 more, every one cancelled
```

The leg went red with **nothing naming a real failure**, and the determinism gates, clippy and the
wasm checks do not depend on minio at all. On a PR whose whole purpose was fixing an
*architecture-dependent* determinism bug, a red aarch64 leg reads as "the fix doesn't work on
aarch64". Two reviewers independently had to read the job log to establish otherwise — that is the
cost of a cancelled check and a failed check looking identical from the PR list.

## Changes

**`--keep-going`** — a failure no longer cancels the others, so every check reaches a verdict and the
failing one is named. This is the fix for the actual complaint.

**`--fallback`** — an unsubstitutable derivation is built from source instead of failing. Measured on
these exact runner images, for the derivation that actually bit us:

| | x86_64 | aarch64 |
|---|---|---|
| minio, substituted | 13s | 80s |
| **minio, from source** | **102s** | **73s** |

On aarch64 building it is *faster* than pulling its 36 MiB from cache.nixos.org — the download is the
slow part, not the Go build. Against the leg's existing 90-minute cap, noise.

Stated plainly because it is a real tradeoff: the flag applies to **every** derivation, so a
pathological outage on something large (a toolchain, LLVM) could build until that cap rather than
failing in seconds. Accepted deliberately — both outcomes are a red leg, `timeout-minutes: 90` already
bounds it, and in exchange the common case stops being a spurious failure.

**A per-check summary table**, so the PR page answers "what actually failed" without opening a log:

| check | result |
|---|---|
| `workspace-test` | ✅ passed |
| `minio-range-read` | ❌ failed or not built |

Derived from the **store**, not by parsing nix's human-readable output: a check whose output path is
valid was built, therefore passed. `--keep-going` is what makes that inference sound — every check is
attempted, so a missing output means that check failed rather than that it was skipped. Nothing to
drift against a format change. Both directions were verified locally (a built check reads as passed, an
unbuilt one as not built) rather than assumed.

## Deliberately not done

**`nix flake check` stays the command.** A per-check `nix build` loop would give exact verdicts and
keep-going semantics for free, and tidier reporting. But this file's header argues that the value of
`nix flake check` is that *the same command runs on a developer's machine and in CI* — "no passes
locally / fails in CI drift" — and that property is worth more than the reporting. Flags and a summary
were added around the existing command instead of replacing it.

No new `timeout-minutes`: the leg already has 90, with reasoning, and that is what bounds `--fallback`.

## Also: the insecure minio, documented where the decision is made

The check strips minio's `knownVulnerabilities` so nixpkgs will evaluate it. That was undocumented, and
surfaced while measuring (a direct `nix build nixpkgs#minio` refuses outright). Now explained in
`flake.nix` at the override: a test fixture, never shipped, started inside the nix build sandbox which
has no network, reached only over loopback by the test itself with a throwaway credential pair that is
in the same file. The alternative is having no test of the cloud range-read path against a real object
store. `meta` is not part of the derivation, so the override changes no output hash — the binary is
byte-identical to nixpkgs'.

## On the measurements

Worth recording because it nearly produced a wrong recommendation. My first two measurement attempts
used `--option substitute false`, which disables substitution **globally**: x86_64 then tried to build
the bootstrap toolchain (`gnutar-1.12`, `stdenv-linux`) and died in 2s, while aarch64's `copying path`
lines show it was still substituting, so its apparent "65s from-source" was nothing of the kind. That
65s looked entirely plausible. `--rebuild` is the correct instrument — it rebuilds the named derivation
locally while its inputs may still be substituted, which is the real failure shape — and it was
validated locally (28s on 88 cores) before spending another runner. The numbers above come from it, and
since `--rebuild` compares outputs they also show minio is bit-reproducible on both runners.

The throwaway measurement workflow is deleted in this PR.

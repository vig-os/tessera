# [PR 486](https://github.com/vig-os/tessera/pull/486) feat(cli): npy emits the array's native dtype, so 64-bit integers survive exactly

Closes the caveat #476 had to admit: `.npy` was written `'<f8'` whatever the array held, because the whole
nav value path converted to `f64` on the way in. `f64` has a 53-bit mantissa, so `int64`/`uint64` magnitudes
above 2^53 **could not survive** — the file was silently rounded while claiming to be the data.

**Relabelling to `'<i8'` would have been worse, not a fix.** The precision was already gone before the
writer saw the values, so the file would have claimed a fidelity it lacked. The fix is to stop converting
early, which is why this was its own issue rather than a one-line change in #476.

## The shape of it

`GridData` replaces `GridDtype` as what a grid writer receives:

| variant | when | emitted as |
|---|---|---|
| `Native(ArrayData)` | nothing transformed the samples | the array's own dtype |
| `Computed { values, source_dtype }` | `--physical`, or a reducing projection | `float64`, declared as such |

One type, so the npy descr, the text rendering and the JSON metadata **cannot disagree** about what is
being written — the `dtype`/`source_dtype` pair now falls out of the same value instead of being tracked
beside it.

## What changes for a user

- **`slice` without `--physical`** → `'<i2'`, `'<u8'`, `'|b1'`, … and exact bytes. `numpy.load()` hands back
  the dtype the product stores.
- **`project --mode max`** → also native, and **reduced natively**. `max` *picks* an existing sample, and an
  f64 comparison cannot even tell two `int64`s apart beyond 2^53 — so the old path could have picked the
  **wrong sample** as well as rounded it. (There is no `min` mode today; `max` is the only
  sample-picking reduction.)
- **`mean` / `sum` / `--physical`** → still `'<f8'`, declared `float64`. Unchanged.
- **Strict improvement, called out as asked:** the **text** paths are exact now too. `fmt_f64` routed every
  integer through `f64`, so CSV and JSON were *also* lossy above 2^53. `text_cell`/`json_cell` read the
  native sample, and `serde_json` carries `i64`/`u64` natively, so `u64::MAX` survives a JSON document.
- Everything else byte-identical: the committed corpus is int16, always exact through `f64`. **The only
  trycmd change is the intended `--format` help line** — reviewed line by line.

The byte-order char follows numpy's own convention: `|` for single-byte types (`i1`/`u1`/`b1`), `<`
otherwise, which is what `numpy.lib.format` writes.

`projection_map` factors the projection geometry out of `project_axis`, so the f64 reduction and the native
`max` cannot disagree about layout — two copies of that index arithmetic would be a silent-wrong-answer
waiting to happen.

## Review round (all three items fixed)

**1. Empty axis.** Zero-length dims are legal in an `ArraySpec`, and a reduction over an empty axis has no
value to report — yet the f64 path emitted `-inf` and my new native path its type's minimum (`i64::MIN`,
`0u8`, `false`), which looks like **real data** rather than an error. Both paths now refuse, naming the axis.

The related carried-over bug: `out_n.max(1)`. When a *different* axis is zero-length the projection is
genuinely empty, and clamping to 1 invented a cell the declared output shape says is not there — a grid that
disagreed with its own `shape`. `Projection::out_len()` is deliberately unclamped, so an empty projection
stays empty and `shape`/`rows_emitted`/`values` agree. Tested on both paths.

**2. Memory — the regression was mine**, introduced when I factored the geometry out. `projection_map`
materialised a `Vec<usize>` with one entry per *input* sample, for arithmetic that is a handful of divisions.
Computed from the allocation (`Vec<usize>` of length n — not an RSS measurement):

| | extra bookkeeping for a 512³ rank-3 projection |
|---|---|
| **before** | 134,217,728 × 8 B = **1,073,741,824 B = exactly 1.00 GiB**, on top of the samples |
| **after** | O(rank): strides + dims + out_shape = **64 B** |

The geometry stays shared — that was the point, so the f64 and native reductions cannot disagree about
layout — but as a `Projection` holding O(rank) state with an `output_index()` method, which both reductions
call. Same single source of truth, no table.

**3. `F16` joins the per-dtype descr test** (`'<f2'`, 2-byte width), so the `half::f16` use in the native
reduction is exercised rather than merely compiled.

## Testing

Verified against the **NumPy format spec** with an independent header parser, never against our own reader —
a test that round-trips through our own encoder would pass for a wrong one:

- `2^53 + 1`, `i64::MAX`, and negatives — with a first assertion that `2^53 + 1` really *is*
  unrepresentable as `f64`, so the test cannot quietly stop discriminating;
- `u64::MAX` from the unsigned side, through `npy`, **JSON and CSV**;
- every dtype's descr *and* element width (11 cases, including the `|` single-byte convention);
- a native `max` projection returning the exact sample it picked, while `mean`/`sum` still declare `<f8`.

`cargo nextest run` → **451 passed**; clippy `--workspace --all-targets -D warnings` clean; doctests pass;
`guardrails-gates`, `mdbook-build` and `workspace-test` all pass in the nix sandbox; `prek --all-files`
zero failures.

## One trap worth the comment it carries

`half` joins tessera-cli's dependencies to name `half::f16` in the native reduction: a bare `f16` resolves
to **Rust's unstable primitive** of the same name, which fails to compile with a misleading
"the type `f16` is unstable".

Closes #478

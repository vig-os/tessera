# [PR 751](https://github.com/vig-os/tessera/pull/751) test(io): check push_table's per-block heap model and document its bound

## Description

ADR-0064 PR F: the per-block heap model of `StreamWriter::push_table` (§8's two-part in-tree test), the bound in
`push_table`'s rustdoc, and ADR-0026's #681 *Known limit* replaced by a pointer to it.

Closes #714

## Type of Change

- [x] `test` -- Adding or updating tests
- [x] `docs` -- Documentation only

## Changes Made

- `tessera-io/tests/staged_job_memory.rs`: the counting allocator now also measures `push_table`, using the
  consumer's 24 B/row schema (`pkt` u64, nullable `ms` u32, 2 × `b1`, 7 × masked `u1`, `tof` i2), one freshly
  allocated row-group per pull, through `push_table_with_block_rows`. `ROWS_PER_GROUP` comes from the crate
  (65 536 on dev, so the numbers in #714 hold) and `r_mem` from `ColumnData::dtype_size`; the test asserts
  `r_mem == 24`.
  1. **Held heap:** `block_rows = 4 · ROWS_PER_GROUP` (`A` = 6 MiB) and `W = 2`. Every worker is held by
     `hold_table_reads` while `push_table` runs on another thread, until `producer_stalls` rises. The test then
     asserts that the **peak** heap since `heap_before` is `≤ s` (7 MiB), which is stricter than the ADR's live
     heap. Non-vacuity checks: exactly `W` jobs were pushed, one stall, and every leaf sealed.
  2. **Ceiling:** `peak(n, W) ≤ min(W, n) · p_block + s` at `W = 2, n ∈ {4, 8}` and `W = 1, n = 4`, with
     `block_rows = 16 · ROWS_PER_GROUP` (`A` = 24 MiB). `p_block` is calibrated from the `W = 1, n = 1` run, after a
     warm-up `W = 2` write.
  3. **Read-back side:** the calibration is itself held to `p_block ≤ p_enc + s`, where `p_enc` is the same block
     encoded from the same lazy row-groups into `io::sink()`. A worker that read its staged block back whole would
     raise `p_block` by `A` and pass the ceiling with it. This check catches it.
- **Isolation:** all the measurements run in sequence in this binary's **one** `#[test]`. `cargo test` runs a
  binary's tests on parallel threads of one process by default, and the allocator counts every thread. nextest
  runs each test in its own process. With one test, both runners give it a process to itself. The module doc
  states the rule.
- `push_table` rustdoc: a **Memory** section with the bound and the page-cache/tmpfs caveat.
- ADR-0026: the *Known limit* paragraph is kept struck through (`~~…~~`, ADR-0056 style), so the `≈ 0.4 × S` and
  7.7 GB figures stay on the record. It is marked superseded for `push_table` (dated, #714), and a present-tense
  note says the limit still holds for one block of any size (`table_block`, `Builder.add_table`, ADR-0064 §5.6).
  The ADR-0064 amendment, item 3, records the in-tree check.
- CHANGELOG (Unreleased, Added) and the FEATURE-MATRIX row.

## Testing

Release build (`cargo test --release -p tessera-io --test staged_job_memory`), exit 0, 4 runs:

| part | measured | bound |
| --- | --- | --- |
| held heap, `W = 2` | 2.29 MiB (all runs) | `s` = 7.00 MiB |
| `p_block` (calibration) | 21.25 MiB (all runs) | — |
| `W = 2, n = 4` | 42.27–43.22 MiB | 49.51 MiB |
| `W = 2, n = 8` | 42.42–43.72 MiB | 49.51 MiB |
| `W = 1, n = 4` | 22.79 MiB (all runs) | 28.25 MiB |
| read-back, `p_block` vs `p_enc + s` | 21.25 MiB | 28.24 MiB |

**Shown failing once** against a `push_table` that fills blocks in memory. This mutation was not committed.
`stage_group` pushes `group.clone()` into a `Vec<TableData>` on `Fill` instead of the staging file. `dispatch`
moves that `Vec` into a staged job that waits out the `ReadHold`, then encodes it through
`accumulate::compact_to` and holds the arrays through the encode. The run exited 101:

```text
held heap: 20485593 B (19.54 MiB) with all 2 workers held, over s = 7340032 B (7.00 MiB) — push_table holds staged input in RAM (2 + 1 blocks of 6291456 B would be 18874368 B)
ceiling: W = 2, n = 4: peak 118869778 B (113.36 MiB) over min(W, n) · p_block + s = 101637730 B (96.93 MiB; p_block = 47148849 B, s = 7340032 B)
ceiling: W = 2, n = 8: peak 117332640 B (111.90 MiB) over min(W, n) · p_block + s = 101637730 B (96.93 MiB; p_block = 47148849 B, s = 7340032 B)
ceiling: W = 1, n = 4: peak 73935286 B (70.51 MiB) over min(W, n) · p_block + s = 54488881 B (51.96 MiB; p_block = 47148849 B, s = 7340032 B)
```

The mutant inflates `p_block` by about `A` (44.96 vs 21.25 MiB) and exceeds the ceiling by 15.0–18.5 MiB. The model
predicts `A − s` = 17 MiB. The held-heap excess is 12.5 MiB, against a predicted `(W + 1) · A − s` = 11 MiB plus
the group in flight.

**Read-back mutant**, also not committed: `StagedInput::into_job` reads every record of the staged file into a
`Vec<TableData>` before `compact_to`. The run exited 101. The held heap (2.29 MiB) and all three ceilings passed
(85.84 / 89.35 / 46.50 MiB against 96.93 / 96.93 / 51.96), because the inflated `p_block` carries them. Only the
read-back check failed:

```text
read-back: p_block = 47148781 B (44.96 MiB) over p_enc + s = 29608342 B (28.24 MiB; the encoder alone peaks at 22268310 B) — a worker holds its staged input in RAM
```

**Rebase onto fb39323 (#750):** one conflict, at the head of the old test function. E3 had added
`#[allow(deprecated)]` to `staged_table_jobs_hold_no_more_than_the_encoder_itself`, which this PR renames to
`encoder_reference` (now called from the single `#[test]`). The resolution keeps E3's split
`#[allow(deprecated)] use …table_job_streaming` import and moves its per-function `#[allow(deprecated)]` onto
`encoder_reference`. E3's import comment now reads "`push_table`'s heap model (#714) is measured below".

# [PR 442](https://github.com/vig-os/tessera/pull/442) chore(ci): adopt the vigOS devkit scaffold (toolchain only, no release train)

Refs #364. **Not** `Closes` — see "What this does not do" below.

Adopts the vigOS devkit scaffold at **1.16.0**, in `direnv` mode on the gitflow model that matches this repo's long-lived `dev` + `main`. This is a **greenfield** adoption: there was no `.vig-os` manifest and not one devkit-managed file in the tree, so nothing is being upgraded.

Deliberately scoped to the **toolchain**. `DEVKIT_FEATURES_DISABLED=release` keeps the release train out: whether this repo moves off release-plz is an open decision (#441), and adopting the train here would have pre-empted it.

## Two commits, in order

1. **`7d1c670`** — preparation, so the scaffold diff is reviewable on its own.
2. **`ea7a77d`** — the scaffold output.

## Two filename collisions

Both are recorded in `.vig-os` beside the key that works around them, so the next reader finds the reasoning where they hit the problem.

### 1. `ci.yml` — handled

This repo's cross-arch determinism gate lives in `.github/workflows/ci.yml`; the scaffold ships a managed file of that name. It is renamed to **`nix-check.yml`** in the first commit.

The gate cannot move *into* the managed file — a `just` recipe cannot express a two-arch runner matrix — so it keeps its own workflow. **The required status check is unaffected:** branch protection matches the **job** name, and the aggregate job is still `nix flake check`. Nothing needs changing in the org config.

### 2. `release.yml` — structural, unresolved

devkit uses `.github/workflows/release.yml` for its release orchestrator. **cargo-dist generates a file of the same name**, and it must never be hand-edited — its `plan` job regenerates it and fails if the checked-in copy differs (#433).

- With the `release` group **disabled**, the scaffold **prunes** it. This is not theoretical: the first scaffold run deleted it, and it was restored by hand.
- With the group **enabled**, the scaffold would **overwrite** it.

There is no configuration that keeps both. Two mitigations, one of which is a genuine loss:

- **`DEVKIT_UPGRADE_EXCLUDE=.github/workflows/release.yml`** — `devkit-upgrade.yml` runs `git checkout --` over these paths after regenerating, so each upgrade restores the file.
- **`DEVKIT_DRIFT_CHECK=false`** — and this one is a cost, not a preference. The `scaffold-drift` job re-runs `init-workspace.sh --force` in CI and fails on any diff, so it would re-delete `release.yml` and fail every PR. `DEVKIT_UPGRADE_EXCLUDE` does not reach that job.

**Reviewers should weigh this.** Losing the drift gate means managed files can be hand-edited here without CI noticing — exactly the protection the scaffold is worth having for. It should be reverted the moment #441 settles who owns the name.

## Credentials

The managed workflows mint App tokens from **org** secrets with `visibility: selected`, and this repo was on none of those lists — a failure that is silent by construction. Granted in [vig-os/org-config#253](https://github.com/vig-os/org-config/pull/253), merged and verified live before this PR was opened:

```
COMMIT_APP_CLIENT_ID · COMMIT_APP_PRIVATE_KEY
DEVKIT_UPGRADE_APP_CLIENT_ID · DEVKIT_UPGRADE_APP_PRIVATE_KEY
```

The client-ID form only. At devkit 1.16.0 `sync-issues.yml` reads `client-id:` with no numeric fallback, and `devkit-upgrade.yml` takes the numeric ID only as a legacy fallback, so this repo is on the modern form from day one with no legacy entry to retire later.

`GHCR_PULL_TOKEN` and `CACHIX_AUTH_TOKEN` appear in the scaffolded workflows and need nothing: neither is an org secret, `h5v` runs the same scaffold with zero repo secrets, and both are optional fallbacks.

## What this does not do

`#364` also asks to retire the dedicated `tessera-sync-issues-bot` App. This PR switches `sync-issues.yml` to the org `commit-action-bot` credentials, which makes that App **unused** — but the retirement itself is a set of live actions to take *after* merge, once a sync run has proven green on the new credentials:

- delete the `APP_SYNC_ISSUES_ID` / `APP_SYNC_ISSUES_PRIVATE_KEY` repo secrets;
- uninstall and delete the `tessera-sync-issues-bot` App;
- drop the paired `orgs.newRepoSecret` declarations from `vig-os/org-config`.

Nothing here touches `release-plz.yml`, `release.yml`, `release-nix.yml` or `release-plz.toml`.

## Known wart

The scaffolded `justfile.project` recipes are Python-shaped, so `just lint` / `just test` no-op for a Rust workspace and the managed `ci.yml` passes vacuously. The real gate remains `nix-check.yml`. Adding Rust recipes is easy and deliberately out of scope here, to keep the scaffold diff clean — worth a follow-up.

# [PR 453](https://github.com/vig-os/tessera/pull/453) fix(ingest): seal the ADR-0058 recipe on the streaming path and surface it in inspect

Two halves of the same ADR-0058 gap: the streaming ingest path silently **dropped** the sealed
recipe, and no CLI verb could **read** it back. Four commits, TDD-paired.

Closes #416
Closes #417

## #416 — the streaming path dropped `[product.generation]` / `[product.producer]`

The batch path routes a spec's recipe + producer through `apply_spec_metadata`; the streaming path
had no counterpart, and `tessera-io::WriteSession` had no way to carry either. A large acquisition
that selected streaming sealed with **no `generation` at all** — and because the built-in schemas
ship `requires_generation = false` (deliberately, ADR-0058 §3), `validate()` did not catch it.
Silent provenance loss on exactly the products most likely to stream.

- `WriteSession::with_generation` / `with_producer`, mirroring `ProductBuilder`. Both live on the
  **durable header**, so they survive crash recovery, and they are applied through the same
  `ProductBuilder` the batch writer uses — a streamed product with a recipe is byte-identical to a
  batch-sealed one (asserted on `manifest_hash`).
- `StreamProvenance<'a>` bundles the five pre-seal inputs the streaming listmode path needs.
  The alternative was an 18-argument function; it also gives #325 a seam to extend without touching
  four call sites.

Everything must be declared before the first block commits — the streamed `.tsra` is sealed once,
straight to disk, with no post-build re-seal hook. That is *why* these two fields went missing
rather than landing late, so the fix is structural, not a forgotten line.

## #417 — `inspect` never printed `generation`

`inspect` rendered `producer` through `ProducerRef::display()` and stopped there, so `git_repo` and
`dirty` were unreachable, and `generation` — the ADR's headline artifact — appeared nowhere in the
CLI. Re-verifying a sealed recipe meant bypassing the tool with a `zipfile` + `json` one-liner.

```
producer      ge-listmode-daq/3.2
  git_repo    vig-os/ge-daq
  git_commit  0855f5f
  dirty       false
generation    4 config keys
  - coincidence_window_ns  4.5
  - detector_ring          "LYSO4x9"
  - energy_window_keV      "425-650"
  - tof_cal_ref            "cal-2024-01"
```

The config bag is **non-opinionated by construction** (ADR-0058 §2), so keys print in the manifest's
own order and are never interpreted, validated, or re-grouped. Long bags collapse at 8 keys with a
`… (+N more)` footer and long values elide, mirroring how `sources` collapses; `--full` prints
everything and spells the `config_ref` digest out. `inspect --json` dumps the whole sealed manifest —
the general form of the gap, so provenance is scriptable without the container internals.

Both renderers are pure `-> Vec<String>` and are unit-tested directly, not only through the snapshot.

## Tests

- `tessera-io`: a `WriteSession` test that a declared recipe survives a crash-recovery round-trip and
  seals to the same `manifest_hash` as the batch builder.
- `test(cli)` adds `provenance.trycmd` + a two-file `provenance.in/` fixture (tracked inputs only;
  the generated `out/` is gitignored, matching `persona_signing.in` / `versioning.in`). Verified
  **RED** on pre-feature code — dev printed `producer ge-listmode-daq/3.2 (0855f5f)` with no
  `git_repo`/`dirty` and no `generation` line, and `--json` did not exist.
- `nav.rs` unit tests for both renderers: every build field surfaced, the legacy bare-string producer
  round-tripping verbatim, the 8-key cap and its `--full` escape, `config_ref`-only, and empty.

Local: `tessera-io` 147 pass, `tessera-ingest` 61 pass, `tessera-cli` 58 + all 13 trycmd walkthroughs
pass. No sealed `content_hash` or golden hash changed — both additions are additive and the existing
corpus fixtures carry no generation, so no regen.

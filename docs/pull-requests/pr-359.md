# [PR 359](https://github.com/vig-os/tessera/pull/359) fix(io): let b1/str columns through the streaming write path

## The gap

#354 added `Bool` and `Utf8` to `ColumnData`, but only the buffer-everything `encode`/`decode` path could carry them. Every **streaming** producer — the DAQ `TableStreamWriter`, `TableMultiBlockSink`, and therefore GE-HDF5 ingest and the declarative `--spec` engine built on them — rejected the new types **at construction**.

So "first-class boolean & string columns" was true only for tables that fit in RAM.

## Two independent causes

**1. Validation used an element-size lookup as a support check.**

```rust
for c in &spec.columns {
    ColumnData::dtype_size(&c.dtype)?;   // errors on "str" — and on "b1"
}
```

`dtype_size` answers *"how many bytes per element?"*. `str` has no answer (correctly — it is length-prefixed), so using it to answer *"do we support this dtype?"* silently excludes every variable-width column.

- Adds `validate_dtype` for the support question, used at both front doors.
- `dtype_size` now knows `b1` is 1 byte in the flat LE form, and says *"variable-width and has no element size"* for `str` rather than *"unknown dtype code"*.
- Adds `dtype_is_fixed_width` for callers that genuinely need the distinction.

**2. The fragment format could not represent variable-width columns at all.**

```rust
let len = n_rows * ColumnData::dtype_size(&c.dtype)?;   // structurally wrong for Utf8
```

The staging format now stores an explicit `u64` byte length per column, so the reader never consults `dtype_size`:

```
magic · u64 n_rows · per column { u64 byte_len · le_bytes }
```

Fragments are transient but `sync_all`'d for crash recovery, so a stage dir written by an older binary can outlive it — and a v1 fragment parsed as v2 would split columns at the wrong offsets **silently**. Hence an explicit magic + version, plus a check that each decoded column's row count matches the header.

## Tests

| test | covers |
|---|---|
| `streaming_bool_and_utf8_equals_batch_encode` | `u8`+`b1`+`str` streamed across a group boundary in 9999-row batches with variable-length values (incl. empty strings), asserted **byte-identical to a batch encode** |
| `fragment_roundtrips_variable_width_columns` | the fragment framing itself, so a regression is attributed directly |
| `fragment_with_bad_magic_is_rejected` | a stale v1 staging file fails loudly instead of mis-parsing |

## Known remaining gap (not fixed here)

`str` still contributes **0** to reported byte totals where raw size is estimated — `ge_hdf5.rs:655`, `engine.rs:544`, `bench.rs:467/489`, and the encode trace. Those call `dtype_size(...).unwrap_or(0)`. A *reporting* inaccuracy, not a data-path defect; it deserves its own change.

# [PR 498](https://github.com/vig-os/tessera/pull/498) ci(nix-check): timeout 120m + --cores 2, per #495's eviction capture

#461's x86_64 leg was killed at **89 minutes** having done nothing wrong. The 90-minute cap is now
cutting real work rather than catching hangs.

## Measured

Same workflow, all GitHub-hosted runners:

| commit | x86_64 | aarch64 |
|---|---|---|
| 7d2eaf8d | 43m success | 41m success |
| 33aa5134 | 46m success | 43m success |
| vortex pin PR | 57m success | 43m success |
| 1442ba12 (#461) | **89m TIMEOUT** | 54m success |

## The axis is variance, not architecture

Worth being exact, because the single-sample reading is tempting and was proposed: from the 89m/54m run
alone it looks like *"x86_64 is ~1.7× slower than aarch64"*. But on the two runs above it, x86 is within
**5–7%** of aarch64.

- x86_64's own range: **43–89m, 2.1× spread**
- aarch64's own range: **41–54m, 1.3× spread**

There is no architectural constant to tune for. There is a wide distribution on one arch whose upper
tail now crosses the cap — and that leads to a different fix (headroom, plus finding the tail's cause)
than "x86 is slower" would (rebalancing work between arches).

## Why 120

The worst observed draw plus ~35%, following the principle the existing comment already states: *set
the cap above the observed spread, not just above the median.* Deliberately not higher — the cap still
has to fail a genuinely hung leg in reasonable time, and GitHub's ceiling is 6 hours.

## What this is not

**This raises the ceiling; it does not make anything faster.** The variance is the real defect, tracked
in #495. The sampler from #488 now records memory, disk and load average every 30s on every leg, printed
into the streamed step log so it survives a kill — so the next long draw can be *attributed* (memory
pressure / I/O starvation / slower silicon) rather than guessed at. Baseline from #488's green legs:
peak 10.2 GB (x86) and 11.6 GB (aarch64) of 16 GB, with 74–92 GB disk free throughout.

It is also a **hard prerequisite** for the `--max-jobs` work under #483: at 89 of 90 minutes, any change
trading wall-clock for peak footprint converts intermittent failures into reliable ones. That is why the
concurrency cap has not landed and should not land before this.

One contributing factor I should name, since it is mine: the vortex fork pin (#480) makes ~27 vortex
crates compile from a git source with no binary-cache substituter where they were previously downloaded.
That raised compile load on every leg. It was the right call for #468/#472 and it is temporary, but it is
part of why the tail moved now rather than earlier.

Refs #495, #483, #461

## [Comment #1](https://github.com/vig-os/tessera/pull/498#issuecomment-5885320393) by [@gerchowl](https://github.com/gerchowl)

_Posted on September 29, 2026 at 07:00 AM_

### Scope widened: `--cores 2` folded in, because the ordering deadlocked

This PR was just the timeout bump. It now also caps per-derivation cores, because **its own aarch64 leg
evicted while proving the point** — memory available fell to **461 MB** of 16 GB and the runner was
killed with `shutdown signal` / exit 143, disk untouched at 81 GB free. The cap bump cannot go green
while the legs are still evicting, so "cap first, then `--cores`" could never have landed in that order.

### The evictions are OOM, and now measured

The sampler from #488 caught one in the act on #500's leg:

```
[res] 06:42:17  mem avail=5167M   disk avail=60177M   load 16.11
[res] 06:43:47  mem avail=1654M   disk avail=59639M   load 13.85
[res] 06:44:47  mem avail= 924M   disk avail=59286M   load 13.59
[res] 06:45:47  mem avail= 412M   disk avail=58946M   load 13.30
06:46:08  ##[error]The runner has received a shutdown signal … exit code 143
```

**412 MB of 16 GB, 21 seconds before the kill.** The OOM killer took the runner *agent*, which is why
none of these jobs could print an error of their own and why they all looked like generic shutdowns.
Disk never fell below **57.6 GB free**, so the original disk hypothesis is excluded with a number.

### Why `--cores`, not `--max-jobs`

The trace picks the lever. Load averaged **13–16 on 4 cores**; nix's `max-jobs` defaults to the core
count, so four derivations build concurrently at ~4 compiler threads each — 4 × 4 = 16, matching the load
exactly. Peak memory tracks the count of concurrent `rustc`/LLVM processes, i.e. that product, so halving
either factor halves it:

| | concurrent rustc | wall-clock |
|---|---|---|
| today | ~16 | evicts |
| **`--cores 2`** | ~8 | four derivations still in flight |
| `--max-jobs 2` | ~8 | serialises derivations, ~2× the parallel portion |

`--cores` is the cheaper trade, and that matters here: x86_64 draws already reach 89 minutes, so a lever
doubling the parallel portion could reach even the new 120-minute cap.

### This PR verifies itself

The sampler reports peak memory on every leg, so **these legs are the experiment**: peak must fall well
below the 15.6 GB that evicted, with wall-clock inside 120 minutes. If the peak does not drop, the model
is wrong — I will report that rather than quietly lowering the number again, since `--max-jobs` would
then be the next lever and "tune it smaller" would be guessing.

Also merged `dev` in to pick up #492, so the header's local-command line stays truthful about the flags
CI runs — the whole point of that line.

Refs #495, #483, #461, #500

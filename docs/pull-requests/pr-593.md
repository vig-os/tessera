## Determinism evidence (zip writes the sealed `.tsra`)

**(a) Container bytes are unchanged.**
- Under zip 2.4.2 (baseline) and again under zip 9.0.4, `cargo run -p tessera-io --example gen_corpus_files` leaves `git status` clean. The sha256 sums of all 8 `corpus/files/*.tsra` are identical.
- A scratch probe wrote every writer path for every fixture: `pack`, `pack_streaming`, the `add_aux_members` rewrite, and `unpack` followed by `pack_dir`. That is 32 archives. Their sha256 sums under zip 9 `diff` empty against the zip 2 run.
- New permanent gate `conformance.rs::committed_corpus_files_are_byte_identical_to_a_fresh_pack`. The golden triple only pins the manifest. This gate also pins the container framing (local headers, central directory, zip64 records). A/B: removing `.large_file(true)` fails only this test, because every hash still matches.

**(b) STORED-only.** New `tests/stored_only.rs`:
- It gives tessera-io a dev edge to zip with `deflate-flate2-zlib-rs`, so `cargo test -p tessera-io` reproduces the workspace's unified-deflate build on its own.
- It proves the codec is compiled in (a Deflated round-trip).
- It asserts that `pack`, both streaming packers, the aux add/replace rewrites and `pack_dir` emit only STORED entries. The check reads `zip`'s central-directory view and the raw method field of both the central-directory record and the local header.
- A/B: switching `tsra_entry_options` to `Deflated` fails it (`entry 'mimetype' is not STORED`).

**(c) Reader paths. This found a real regression, now fixed.**
- zip 9's default `ArchiveOffset::Detect` scans **forward from byte 0** for the first central-directory header, so opening read the whole archive.
- Result: `range::reading_one_block_does_not_read_the_whole_archive` read 200462 of 170206 bytes, and `cloud::tail_prefetch_reduces_get_count_on_a_large_archive` saw 120 GETs for 10 entries.
- `.tsra` archives now open through one helper, `open_tsra_archive`, at `ArchiveOffset::Known(0)`. zip then checks only the position the EOCD names, and open costs just the file's tail again.
- SPEC §6 now states the rule this depends on. Sniffing already required it: **an archive begins at byte 0**. `Known(0)` alone only refuses a prefix glued in front of an unchanged archive (`an_archive_behind_an_unadjusted_prefix_is_refused`). A prefix whose offsets were rewritten to include it (`zip -A`, a shell/zip polyglot) is a well-formed zip and opened, as it does on dev. So `open_tsra_archive` also requires that entry 0 is `mimetype`, at byte 0 and STORED, otherwise it returns `Error::Container`. It checks central-directory metadata only (`by_index_data(&self)`: no read, no extra GET). New tests `a_polyglot_whose_offsets_include_the_prefix_is_refused` and `an_archive_whose_first_entry_is_not_mimetype_is_refused` both fail without the check. The zip64 end-record branch (no product-sized fixture reaches it) is pinned by `opening_a_zip64_archive_reads_only_its_tail`: 70 002 entries; under `Detect` it read 47647557 of 42492589 bytes, with `Known(0)` less than half. The `.npz` reader keeps `Detect` on purpose, with a comment explaining why. **Reviewer note:** this is the only behaviour change. A file with bytes before the zip, which zip 2 accepted when the CD arithmetic matched, is now refused. No tessera writer produces such a file.
- With the fix, the range test, all 5 in-process `cloud::` tests (tail-prefetch, prune-before-fetch) and the prefix test pass. With `Detect`, 3 of them fail. The MinIO path is covered by CI's `minio-range-read` check.
- I re-checked the reader comment that says zip takes an entry's compression method from the central directory against 9.0.4. It still holds; only the function names changed.

**(d) Feature snapshots.** Only `zip.txt` changes: the version, the `.npz` lane's feature (`["deflate-flate2", "flate2"]` → `deflate-flate2-zlib-rs`; zip 9 dropped the `flate2` feature, and its flate2 dependency names no backend; zlib-rs is already in-tree), and the tessera-io dev edge. The other 12 seal-path snapshots are unchanged.

## Ingest corpus: one deliberate corpus event

The ADR-0056 §6a decoder digest pins zip on the `.npz` lane, so `ingest_npz_member` changes `ingest_decoder.features` and `manifest_hash`. Its **`id` and `content_hash` are unchanged**: the decoded values are identical. The other 13 fixtures are byte-identical. The decode-path gate is reclassified for zip 9's closure:
- dropped the 6 stale zip 2 exclusions
- classified `typed-path` (extract-path sanitiser), `nix` (macOS/BSD extract permissions) and `cfg_aliases` (build-time)

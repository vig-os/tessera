# [PR 940](https://github.com/vig-os/tessera/pull/940) feat!: seal the stored canonical bytes (ADR-0066 A′ cutover)

Part 2 of 2 of ADR-0066 implementation step 4: the A′ cutover. **Breaking format change.** Part 1 (#938) added the
`stored` vocabulary and the `from_stored_members` door; this PR switches every writer and reader to it at once, so the
layout changes exactly once.

## The break

- `manifest.json` is stored as exactly its RFC 8785 JCS bytes, with **no** `manifest_hash` key. The seal,
  `blake3:<64 hex>` = blake3 of those bytes, is a new `manifest.seal` member: zip entry 2, after `mimetype` and before
  `manifest.json` (SPEC §6's canonical member set now includes it). In the exploded form it is a `manifest.seal` file
  beside `manifest.json`. A collection keeps its seal in `collection.seal` (`<stem>.collection.seal` for a
  sub-collection member).
- Every reader (Rust `.tsra` / exploded / repository / cloud, `tessera-py`, `tessera-wasm`, the Python reference
  reader) runs strict parse → JCS → byte compare → seal compare → typed layer, through `Manifest::from_stored` /
  `Collection::from_stored`. There is no second verify path: `from_json_verified`, `to_sealed_json`, `seal_of`,
  `from_json_with_seal`, `hash_without`, `bytes_without` and io `stored::canonical_form` are removed.
- **Products written before this change are refused** (rule 10, no migration verb). The error names the format it
  found (the declared `tessera_version`, the missing `manifest.seal`, an in-band `manifest_hash`, a non-JCS layout)
  and the format it requires. `TESSERA_VERSION` stays `"0.0.0"`. Re-ingest such products from their source.
- The signature envelope is unchanged (rule 8); `sign` and `verify-sig` read the seal member.
- `tessera inspect --json` no longer prints a `manifest_hash` key (the summary line still shows the seal);
  `tessera-py` gains `Reader.manifest_hash`; `tessera-wasm`'s `verify_manifest` / `verify_signature` take the seal
  member, and `seal_verdict` is new.

## Seal preservation (the proof that matters)

A′ moves only where the seal lives, never its value. All 13 tracked `.tsra` (12 distinct manifests) are re-packed,
and each `manifest.seal` equals the old in-band `manifest_hash` and blake3 of the new `manifest.json`. Blocks are
byte-identical. `corpus.json` and `ingest-corpus.json` are **unchanged** from this PR's base:
`git diff origin/dev -- tessera/corpus/corpus.json tessera/corpus/ingest-corpus.json` is empty.
`stored_bytes.rs::the_stored_seal_of_every_tracked_product_is_its_recorded_seal` checks every golden by name.

## Vectors

`corpus/seal-cases.json` is rewritten as `(bytes, seal)` vectors by `corpus/reference_reader/make_seal_cases.py` (150
cases, each one named edit of a corpus manifest), including T4–T7, S5b, S7 (#901's sealed `64.0`) and S8 from the
spike. Rust (`tessera-core/tests/seal_cases.rs`), the reference reader (`run.py`) and `tessera-wasm` (natively, and
compiled to wasm in Node in `wasm-bindgen-smoke`, with an N/N guard against a vacuous pass) reach the same verdict
on every case. #901's `64.0` is refused by all three. The `reference-reader` check also regenerates
`seal-cases.json` from the corpus and requires the committed bytes (a formatting-only edit to the file fails it while
all cases still agree, checked), so the vectors can't drift from their generator.

## Round 2: the two reader differentials

- **`tessera-wasm` takes the member bytes** (`Uint8Array`), not strings: `verify_manifest`, `seal_verdict`,
  `verify_signature`, `product_id`. A default `TextDecoder` drops a leading BOM and maps invalid UTF-8 to U+FFFD.
  So the string API returned `ok` for a BOM-prefixed manifest under its original seal, and for a 0xFF byte under the
  seal of its U+FFFD spelling. Both are refused natively and by the reference reader. Four new seal cases pin this
  (bytes that are not UTF-8 are carried as `manifest_hex`), and every harness takes the bytes.
  - Before the fix, the old API fed the `TextDecoder` output (Node) of the new vectors: exit 100. It returned `ok` on
    `byte-order-mark` and `invalid-utf8-under-the-seal-of-its-replacement`.
- **The reference reader enforces SPEC §6's member set** as the Rust reader does: no name twice and every entry
  STORED, refused before any member is read. Four committed fixtures in `corpus/refusals`
  (`make_refusal_fixtures.py`, byte-reproducible, regenerated and `diff -r`'d by the `reference-reader` check): a
  repeated `manifest.seal`, a repeated `manifest.json`, and each DEFLATED.
  - Before the fix, the old reader returned `ok` on all four. Now `run.py` refuses all four (13/13 refusal cases), and
    so does the Rust reader in the new `tessera-io/tests/canonical_members.rs`.

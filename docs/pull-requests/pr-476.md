# [PR 476](https://github.com/vig-os/tessera/pull/476) feat(cli): non-CSV array output with row caps, and read reaching extra/ blocks

Both AX gaps from the #390 audit, in three commits: the #303 TDD pair, then #387.

## Scope correction, stated up front

**#387's size guard for `read` already exists** — `--rows`/`--head`/`--tail`/`--at`/`--all` plus
`--limit 20`, landed in #391 from the same audit. So this PR is about `slice`/`project`, which had
neither a richer format nor any cap. Nothing was re-done.

## #303 — `read` could not reach `extra/` blocks

The root cause is more specific than the issue states: **`extra/*` is not a block at all**, it is manifest
metadata. So it matched neither `read`'s existing non-table-block guard (which already handles
Array/Blob/ChunkIndex with a good hint) nor any table prefix, and fell straight through to
`logical_table` — hence the internal `no blocks for prefix 'extra/dicom_header'`.

`ls`'s two inline `extra/` arms became a shared `write_extra` + `is_extra_path`, and `read` serves that
namespace as JSON before reaching the table path. **One renderer is the point:** a better-worded error
would have fixed the message and left the inconsistency, whereas sharing the renderer makes the error
*impossible* and stops the verbs drifting again.

Red-first is verifiable — check out `22559e0` and the test fails with **exactly** the issue's error. The
test also covers a scalar `extra` value, bare `extra` listing keys, and an unknown key — asserting the
error names the available keys **and** does not contain `logical_table`, so a later refactor cannot
quietly re-expose the internal message.

## #387 — non-CSV array output + a size guard

`--format` is now a clap `ValueEnum`, so a typo fails at parse time and `--help` lists the values from one
place instead of a doc string that can drift:

| | |
|---|---|
| `csv` / `tsv` | unchanged |
| `json` | self-describing — `{shape, dtype, values: [[row], …]}`. Integral values render as integers, the rule `fmt_f64` already applied to CSV, since `0.0` alongside `"dtype": "int16"` is incoherent |
| `npy` | NumPy v1.0 `'<f8'` — **the lossless path**. float64 because every value here has already been through `region_to_f64`, so it is what the CLI computed, not a widening added at the door |
| `png` | 8-bit greyscale preview, auto-windowed on the plane's finite min/max, `--window lo,hi` to override. **Not data** |

**PNG is self-describing on purpose.** The window actually used and the source dtype go into `tEXt`
chunks, so a preview that has been copied out of context cannot later be mistaken for the values; a
stderr note says it is lossy and points at `npy`. 8 bits cannot hold a Hounsfield range, let alone a float
activity map, so the mapping is lossy by construction rather than by choice.

**Caps follow `read`'s idiom.** Text formats default to 20 rows with `--all` to lift it, and the result
carries `shown`/`total`/`truncated` so `main` prints the note to **stderr** while stdout stays pure data —
`| head` and `> file` keep working. Binary formats always write the whole plane, because a truncated
`.npy`/`.png` is a **corrupt artifact** rather than a preview, and an explicit `--limit` with one is
therefore an **error naming the reason** rather than a silent no-op: a flag that does nothing is its own
foot-gun.

**Binary output to a TTY is refused** with a redirect hint, for the same reason — pipes and redirections
are not terminals, so the useful cases are unaffected and no `--out` flag was needed.

**One shared writer.** `slice` and `project` each carried a copy of the row-writing loop; both now go
through `write_grid`. That is the substance rather than tidiness — otherwise the two verbs drift on
rendering, capping and windowing independently, which is how they came to differ in the first place.

## How the new formats are tested

The expectations are derived **independently of our own writer**, because a test that echoes whatever we
emit would pass for a wrong encoder:

- **`.npy`** against the NumPy format spec — magic, version, `'descr': '<f8'`, `fortran_order: False`, the
  shape tuple, the **64-byte header alignment numpy requires**, a trailing newline, and the little-endian
  payload decoded back to the expected values.
- **`.png`** by decoding it with the `png` crate's *reader*: dimensions, bit depth, colour type, the
  `tEXt` values, and that min maps to black (0) and max to white (255) — then that `--window 0,24` makes
  the same sample mid-grey (128) and is what gets recorded.

`png` costs **no new dependency**: it was already in `Cargo.lock` via `image` on the DICOM pixel path.

## Docs-as-tests

`arrays.trycmd` gains two cases on the committed corpus volume — a `json` read and a capped read showing
the stderr note — recorded against real CT data:

```console
$ tessera slice ../../corpus/files/recon_int16.tsra volume --index "0,0:2,0:4" --format json
{"shape":[2,4],"dtype":"int16","values":[[-1024,-1023,-1022,-1021],[-960,-959,-958,-957]]}

$ tessera slice ../../corpus/files/recon_int16.tsra volume --index "0,0:5,0:4" --limit 2
-1024,-1023,-1022,-1021
-960,-959,-958,-957
note: showed 2 of 5 rows — pass --all or --limit N for more
```

Its `--help` snapshot is regenerated; the diff was reviewed line by line and is **entirely** the new
surface (17 insertions, 1 deletion), which was flagged as a known consequence of the `ValueEnum` switch
before the code was written.

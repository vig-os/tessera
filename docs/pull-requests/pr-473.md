# [PR 473](https://github.com/vig-os/tessera/pull/473) ci: run the PR checks on stacked PRs too

## Problem

`ci.yml`, `nix-check.yml` and `codeql.yml` filtered `pull_request` to three bases:

```yaml
  pull_request:
    branches:
      - dev
      - 'release/**'
      - main
```

A PR based on another topic branch (#461 on #460) matches none of them, so it ran **no** checks —
no lint, no tests, no commit-message validation, no `nix flake check`.

The quiet part: such a PR shows no *failing* check, it shows *no* checks, which reads as "nothing
to run" rather than "nothing was verified".

And the sting here specifically — **`nix flake check` is the required status check on `dev`**, and
it lives in the one of these three workflows that is *not* devkit-managed. So the required check
was precisely the one that could never run on a stacked PR.

## Fix

Two parts. Both are needed; the first alone would have made things worse.

**1. Widen the base filter.** Add `'**'` to each list. It matches any base, `/` included, so it
also covers the three named entries; a `pull_request` event matches the filter **once**, so this
adds no duplicate runs for normal PRs into `dev`. The named entries are kept deliberately rather
than replaced, so a devkit regeneration diff on the two managed files stays obvious and the added
line is trivial to drop once upstream lands.

**2. Give `codeql.yml` and `nix-check.yml` concurrency groups.** Neither had one — only `ci.yml`
does (#1602, via #442). Widening without this would leave a force-push to a stacked branch running
its superseded jobs, which is exactly the runner-waste problem #363 had just fixed, reintroduced
through the other two workflows. `nix-check` is the expensive lane (~40-60 min per leg, two arch
legs per run), so it is where an uncancelled superseded run actually hurts.

Both use `ci.yml`'s shape:

```yaml
concurrency:
  group: <name>-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name != 'push' }}
```

The `!= 'push'` carve-out is not copied blindly. CodeQL's push-to-main leg is post-merge analysis
feeding the security tab, and `nix-check`'s guards the required check on `main`, so in both cases
two rapid merges must each report rather than the first being cancelled.

## On "take the approach the devkit scaffold supports"

The issue asked for that so drift checks stay green. There is no such approach: devkit hardcodes
the three-entry list and renders no knob (`grep DEVKIT_CI_` finds only `DEVKIT_CI_RUNNER`). Filed
upstream as **vig-os/devkit#1759**, which proposes widening the default or exposing a
`DEVKIT_CI_PR_BASES` key — and now also records that a widening upstream has to add CodeQL's
concurrency group with it, for the reason above.

Durability, per file:

| file | managed? | outcome |
|---|---|---|
| `nix-check.yml` | tessera's own | **durable** — and it holds the required check and the expensive legs |
| `ci.yml` | devkit | dropped on next devkit upgrade; commented as such |
| `codeql.yml` | devkit | same, for both edits |

Drift is not a concern either way: `DEVKIT_DRIFT_CHECK=false` already (#441), and the
`Scaffold Drift` job is skipped.

## Cost

Stacked PRs now spend real runner time. That is the point of the issue — verification instead of
none — and part 2 keeps it from compounding on force-pushes. Flagging it as the one obvious
argument against merging.

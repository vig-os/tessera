# [PR 541](https://github.com/vig-os/tessera/pull/541) fix(export)!: label the RO-Crate edge hash per role instead of claiming a sha256

Closes #525. **Second pass** — the review blocked the first one for two real problems, both fixed below, plus the citation nits.

The original defect stands as described: the export emitted a BLAKE3 value under schema.org's
[`sha256`](https://schema.org/sha256) ("The SHA-2 SHA256 hash of the content of the item"), with the `blake3:`
prefix still attached, on a `Dataset` — a type outside that property's `MediaObject` domain. No `sha256` is
emitted now, because none is computed.

## Blocker 1 — the label was false for most roles (the same defect, one level down)

The first fix hard-coded *"BLAKE3 Merkle root over the source's ordered block digests (ADR-0028) … check it with
`tessera verify`"* onto **every** edge. `Source.content_hash` is not one construction. Verified against the
producers:

| role | what the value actually is |
|---|---|
| `derived_from`, `supersedes`, `snapshot_of` | the parent's `manifest_hash` — BLAKE3 over its canonical-JSON manifest (`Manifest::compute_manifest_hash`). **Not a Merkle root.** |
| `ingested_from` | BLAKE3 Merkle root over the **source files'** digests, one leaf per file (`tessera_ingest::provenance::source_digest`). **Not the product's block digests.** |
| `ingested_via_spec` | BLAKE3 over the canonical JSON of the parsed ingest spec (`spec::spec_hash`). |
| `emission_data`, `calibration`, … | whatever the producer of that role chose. |

So the label was wrong for three of the four known constructions, and `tessera verify` checks the product's own
hashes — not an edge's pinned hash — in all of them. I had fixed a false claim by writing a subtler one.

`edge_hash_label(role)` now derives the text from the role. **It is not a compiler-exhaustive match, and that is
a fact about the data model rather than a shortcut:** `Source.role` is a free-form `String` by design (domain
edges like `emission_data` are expected), so there is no enum to match on, and minting one would change a
serialised format field. The fallback arm is therefore written to be true of *any* role, and
`every_known_role_gets_a_truthful_label` pins all five in-tree roles plus a domain role, so a new role surfaces
as a test failure rather than inheriting someone else's description.

## Blocker 2 — the inline PropertyValue broke the flattened-graph rule

[RO-Crate 1.1's JSON-LD appendix](https://www.researchobject.org/ro-crate/specification/1.1/appendix/jsonld.html):

> *"all described entities must be JSON objects as direct children of the `@graph` element rather than being
> nested under another object or array"* … *"Properties referencing entities must use a JSON object with `@id` as
> the only key"*

The PropertyValue is now its own `@graph` child at `#edge-hash-<role>-<hex>`, referenced as `{"@id": …}`. Keyed on
role **and** hash, because two edges can pin the same hash under different roles and their labels differ — a
hash-only id would give one `@id` two descriptions. Entities are de-duplicated by that id.

`the_rocrate_graph_is_flattened_and_references_are_id_only` asserts the rule **structurally over the whole
document** — every nested object anywhere must be `{"@id"}`-only — rather than over the single property that was
wrong, and checks no identifier reference dangles.

## Citation corrections (review nits, both fair)

- **I misquoted the Workflow Run precedent.** Its checksum terms (`md5`, `sha1`, `sha256`, `sha512` under
  `https://w3id.org/ro/terms/workflow-run#`) have domain **`File` and `ContainerImage`**, not `File` alone.
- **1.2 *does* give identifier guidance**, which I wrongly implied was absent. Per
  [1.2 root data entity](https://www.researchobject.org/ro-crate/specification/1.2/root-data-entity.html), a
  PropertyValue identifier MUST have a human-readable `value` and SHOULD have a `url` *if the identifier is
  Web-resolvable*. So: `value` present; **`url` deliberately absent** (a content hash is not web-resolvable);
  `propertyID` a short code rather than the registry URI its example shows, because no registry defines this
  characteristic and a URI we do not serve would be worse than a plain code. My earlier claim that RO-Crate
  prescribes nothing holds only for **digests** specifically, which both 1.1 and 1.2 are silent on.
- **`docs/adr/0048-provenance-edge-shape.md`** still described the old `sha256` emission — amended with what
  replaced it and why.

## Breaking change — marked, not slipped in

`fix(export)!:` with a `BREAKING CHANGE:` footer. The `sha256` property is gone from provenance-edge entities.
Nothing in this repo read it, and the value was never a SHA-256, so any external consumer validating it was
already failing — but it is an output-format change in a published FAIR record. The digest is still there, under
`identifier`. A *genuine* SHA-256 fixity field is a separate additive proposal (#526 / ADR-0059).

## Verification, and one honest gap

9 export tests pass (6 before this work), trycmd suite green, clippy clean, prek clean, both commits signed.

**No external validator was run.** `rocrate-validator` and `ro-crate-py` are both unavailable here — `uv` has no
network in this sandbox and neither is in the nix inputs — so the flattening claim rests on the structural test
and the quoted spec text, not on a validator. Worth adding to the flake if we want it gated.

Unrelated but worth recording, since it cost time and has a sharper edge: a trycmd failure during this work
turned out to be a **stale build-script output in a `CARGO_TARGET_DIR` shared with another worktree** — the
binary reported `dicom 0.10.0` from a sibling branch while this branch's lock says `0.9.1`. `cargo clean -p
tessera-ingest` fixed it. The same `build.rs` emits the sealed `ingest_decoder` pre-image from the lockfile, so a
shared target dir can in principle make a local build seal a decoder claim that does not match its own lock. CI
builds fresh, so it is a local-only hazard — but it is the reason per-worktree target dirs matter.

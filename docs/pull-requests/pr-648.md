# [PR 648](https://github.com/vig-os/tessera/pull/648) fix(release): macOS dist builds + a PR-time macOS build gate

Fixes the two macOS defects that stopped the `v0.1.0-alpha.2` cargo-dist Release
([run 39203946447](https://github.com/vig-os/tessera/actions/runs/39203946447)), and adds a PR-time macOS gate so
this class fails before merge instead of at tag time.

## Root cause 1: `posix_fadvise` in `tessera-cli` (#487)

`bench_compare.rs` called `libc::posix_fadvise(POSIX_FADV_DONTNEED)` unconditionally; Darwin has neither.
A third error came from the same code: `mincore`'s residency vector is `*mut c_uchar` on Linux but `*mut c_char`
on Darwin (`error[E0308]: mismatched types`, bench_compare.rs:266 in the run log).

**Fix** (`fix(cli)`): the real `evict()` is compiled for `linux`/`android` only. `bench compare` checks `--cold`
before writing anything, and on any other OS returns
`bench compare: --cold is not supported on macos: cold-cache measurement needs posix_fadvise(POSIX_FADV_DONTNEED),
which only Linux provides. …`. It never times warm reads under a "cold" label (`bench/ecosystems/README.md`). The
`mincore` call casts the pointer, which is correct on both ABIs. Warm mode is unchanged. This is documented in the
module rustdoc, the `--cold` help text and `why-tessera.md`.

## Root cause 2: the `tessera-py` dylib link. Not a regression: alpha.1 hit it too, and dist hid it

The alpha.1 Release run ([35933703355](https://github.com/vig-os/tessera/actions/runs/35933703355)) failed in
**exactly the same way** on macOS, and still reported success. aarch64-apple-darwin leg:

```text
23:28:45 building aarch64-apple-darwin target, using cargo profile dist --workspace)
23:37:02 Undefined symbols for architecture arm64:
23:37:05 error: could not compile `tessera-py` (lib) due to 1 previous error
23:37:05 warning: build failed, waiting for other jobs to finish...
23:38:51 tessera (aarch64-apple-darwin)   <- linkage table of the CLI binary
23:38:51 dist ran successfully
```

Same runner images on both runs (`macos-14-arm64` 20260831.0302.1, `macos-15` 20260824.0482.1), same dist 0.32.0, same pyo3 0.29.0. So the
candidate "something changed since alpha.1" is ruled out by the logs. Why alpha.1 still went green is in cargo-dist
0.32.0's `build_cargo_target` (`cargo-dist/src/build/cargo.rs`): it spawns `cargo build`, parses the JSON messages
for artifacts, and calls `expected.process_bins(...)`. It **never checks cargo's exit status**. A failed crate whose
output dist doesn't ship is ignored as long as the `tessera` binary appeared. In alpha.2 `tessera-cli` itself failed
to compile (root cause 1), the binary was missing, and dist exited 255, so the long-masked `tessera-py` error
finally became visible beside it.

Two things in our setup were wrong:

- **dist built the whole workspace.** With `precise-builds` unset, dist runs `cargo build --workspace`, which also
  compiles the `tessera-py` cdylib and `tessera-wasm`. This channel ships neither; the wheel comes from the nix
  channel. **Fix** (`fix(release)`): `precise-builds = true` in `dist-workspace.toml`, the documented dist knob
  (`[dist] precise-builds`), so the build is `cargo build --package tessera-cli --features static-hdf5`.
  `dist plan` output is byte-identical before and after (artifact set, matrix, installers), and
  `dist generate --check` passes: `release.yml` is unchanged.
- **`tessera-py` didn't link on macOS at all.** With `extension-module`, pyo3 doesn't link libpython, and Apple's
  `ld` rejects undefined `_Py*` symbols unless the dylib is linked with `-undefined dynamic_lookup`. pyo3 can't emit
  that for a dependent crate (`rustc-cdylib-link-arg` only applies to the emitting package's own cdylib). maturin
  passes it for its own builds, but a plain `cargo build -p tessera-py` never got it. **Fix** (`fix(py)`): a
  `build.rs` calling `pyo3_build_config::add_extension_module_link_args()`, the mechanism the pyo3 0.29 guide
  documents ("Building and distribution → macOS"). It is a no-op off Darwin, so the Linux `.so` and the nix wheel
  are unchanged. `pyo3-build-config` 0.29 is a new build-dependency, already in the lockfile through pyo3. The
  lockfile gains one edge, and `scripts/feature-snapshots.sh` regenerates with **zero** diff.

## The gate: `.github/workflows/macos-build.yml` (`ci(macos)`)

- Runs on `pull_request` into dev and on `push` to dev, path-filtered to `tessera/**`, `**/Cargo.{toml,lock}`,
  `dist-workspace.toml` and the workflow itself. It is repo-owned; devkit's `ci.yml`/`codeql.yml` are untouched.
- The **`plan`** job installs the dist version pinned in `dist-workspace.toml`, runs `dist plan`, and takes the
  darwin legs of the same `artifacts_matrix` that release.yml consumes. It asserts the legs by name: exactly
  `aarch64-apple-darwin` and `x86_64-apple-darwin`. So each **`build`** leg uses release.yml's runner
  (`macos-14` / `macos-15-intel`), its dist install command, and its `dist build --artifacts=local --target <t>`
  arguments, by construction rather than by copy.
- Each leg then: asserts `tessera-cli-<t>.tar.xz` is in the manifest and on disk; builds the `tessera-py` cdylib
  with `--profile dist` (dist doesn't check cargo's exit status, so this is the only thing that would catch a
  broken link); runs the built binary: `--version`, a warm `bench compare`, and `bench compare --cold`, which must
  exit non-zero with the documented message.
- **`macOS build`** is a single aggregate job (`if: always()` plus an explicit result check). It is the one name to
  point branch protection at.

**Fails on unfixed dev:** run [39206712200](https://github.com/vig-os/tessera/actions/runs/39206712200), on
`07e1622` (this PR's first commit: the workflow alone on top of dev). Both legs fail with the release run's errors:
`posix_fadvise` / `POSIX_FADV_DONTNEED` / `mismatched types` in `tessera-cli`, then
`Undefined symbols for architecture {arm64,x86_64}` in `tessera-py`, and dist exits 255.

**Passes with the fixes:** run [39209345597](https://github.com/vig-os/tessera/actions/runs/39209345597) at `03e1156`. dist now logs `using cargo profile dist --package=tessera-cli`, `lib_native.dylib` links, warm `bench compare` runs, and `--cold` is refused with the documented message on both arches. Wall time per leg (cold, no cache): **aarch64-apple-darwin 13m07s** (`macos-14`), **x86_64-apple-darwin 19m20s** (`macos-15-intel`). Plan: 25s.

Follow-up found on the way, filed as #650: C objects (`zstd-sys`, `blake3`) built for macOS 14.5 are linked into a binary that targets 11.0 (`MACOSX_DEPLOYMENT_TARGET` unset). This was already present on alpha.1.

**Required check: the owner decides.** Making `macOS build` required is a branch-protection change, and this PR
doesn't touch protection. Because of the path filter, the workflow doesn't run on PRs outside those paths. A
required check that never reports blocks the merge, so requiring it needs either dropping the path filter or an
always-reporting stub.

## Tests

- `cargo test -p tessera-cli --bins` (Linux): 100 passed, exit 0. New tests:
  `cold_is_refused_off_linux_with_a_named_reason` (every OS name, on any host: refusal plus Linux pass-through),
  `cold_rule_matches_the_compiled_eviction` (the runtime rule equals the compile-time `cfg`), and
  `run_applies_the_cold_gate_first`. Before the fix, the macOS build of this code fails to compile; see the run
  above.
- macOS end to end, in the gate: the built `tessera` refuses `--cold` with the documented message, and warm
  `bench compare` works.
- `cargo build -p tessera-py` on Linux: exit 0.

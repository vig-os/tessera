# [PR 585](https://github.com/vig-os/tessera/pull/585) feat(py): Python provenance surface — pinned sources, producer, generation

## Description

Closes the two gaps that kept Python callers from writing ADR-0058 provenance:

- **#563.** `Builder.add_source` couldn't pin the parent's seal, so every edge written from Python failed
  `tessera provenance --require-complete` ("no pinned version").
- **#562.** `Builder` had no `with_producer` / `with_generation`. A Python-written product was always stamped with
  the packager (`tessera/0.0.0`) and couldn't carry a recipe.

Both bring Python to parity with the existing Rust API (`Source::with_content_hash`,
`ProductBuilder::with_producer` / `with_generation`). There are two commits, one per issue, and each carries its own docs.

## Changes Made

- `add_source(relation, reference, content_hash=None)`. `content_hash` is the parent's `manifest_hash` (SPEC §8):
  `tessera.open(parent).manifest()["manifest_hash"]`. Without it the key is **absent** from the manifest, so
  existing products and the conformance corpus hash exactly as before (no Rust format code changed). The value
  isn't format-checked at write time; the Rust API doesn't check it either.
- `with_producer(tool, version, git_commit=None, git_repo=None, dirty=None)`. Optional fields that aren't given are
  absent from the manifest, not `null`. A second call replaces the first.
- `with_generation(config=None, config_ref=None)`. `config` is converted to JSON strictly, in the binding, with no
  new dependency. Keys must be `str` at every level, NaN/inf and ints wider than 64 bits are rejected, and any
  non-JSON type raises `TypeError` naming the key path (for example `config["agent"]: key 2 is an int, not a str`).
  Nothing is coerced, unlike `json.dumps`, which silently turns `{1: ...}` into `{"1": ...}`. An empty recipe
  (neither argument, or `{}` without a ref) raises `TesseraError`, because `Generation::is_empty` treats it as
  absent. A second call replaces the first.
- `config` nesting is capped at a **fixed 125 levels** (dicts and lists, counting `config` itself), raising
  `TesseraError` that names the limit. That's exactly what the manifest reader parses back: serde_json reads at most
  127 nested levels, and `config` sits two below the manifest root. The tests seal and reopen a config at exactly 125
  levels and refuse 126, with `sys.setrecursionlimit(10**6)`. A bound tied to `sys.getrecursionlimit()` wasn't
  enough: the converted value is dropped and serialised recursively in Rust, so a raised limit plus a 5000-level config
  crashed `pack` (SIGSEGV), and anything past 125 levels sealed a product nobody could open. The walk itself is
  iterative (no native recursion). Self-reference raises `ValueError`, and a lone surrogate raises `TypeError` like
  every other non-JSON value. Error messages shorten long key paths.
- Nested config dicts are emitted key-sorted, so `manifest()` returns every level in the canonical (JCS) order the seal
  hashes, not only the top level.
- All three raise "builder already packed" after `pack`, through the existing guard.
- New `tests/provenance.py`, run by `tessera-py-import` and `tessera-wheel-import` and registered in
  `scriptsRunByChecks`. Every assertion reads the **sealed** manifest back through `tessera.open(...).manifest()`.
- Docs: rustdoc on each method; a `provenance` anchor in `tests/write_example.py`, `{{#include}}`d in
  `docs/book/src/bindings.md`, showing producer, generation and a pinned `derived_from` edge; the bindings method
  list; and one sentence in `provenance-signing.md`. `tests/api_drift.py` guards dtype codes and doesn't enumerate
  methods, so it needed no change.

### Acceptance criteria

1. **Pinned edge sealed, and absent when not pinned.** Covered by `provenance.py`.
2. **`--require-complete` end to end.** No flake check carries both the CLI and the wheel, so this one was **done
   by hand**. A parent and a child were written from Python with this branch's binding, then walked with the
   origin/dev CLI (fa581f5). `provenance.py` and the `write_example.py` anchor keep the automated half: they
   assert that the pinned edge equals the parent's `manifest_hash`.

   ```console
   $ tessera provenance --require-complete pinned/child.tsra
   t_product · child  [blake3:e4f839136f75…]
     ↳ derived_from t_product · parent  [pinned]
         file      pinned/parent.tsra
         producer  tessera/0.0.0

   1 hop(s) · 0 external leaf/leaves · chain complete
   # exit=0
   $ tessera provenance --require-complete unpinned/child.tsra
   t_product · child  [blake3:aad15e2f715b…]
     ↳ derived_from t_product · parent  [no pinned version]
         file      unpinned/parent.tsra
         producer  tessera/0.0.0

   1 hop(s) · 0 external leaf/leaves · 1 gap(s) — chain INCOMPLETE
   error: invalid product: provenance chain for unpinned/child.tsra is incomplete (--require-complete): some parents resolved to a different version or were not found. Point --search / --collection at them, or drop --require-complete to see the chain anyway.
   # exit=1
   ```

3. **`with_producer`: every field, their absence, replacement, and the default stamp left unchanged.**
   Covered by `provenance.py`.
4. **`with_generation`: nested values, both fields, ref only, replacement, and every error case.**
   Covered by `provenance.py`.
5. **`requires_generation` can't be reached from Python.** So no test was added, per the brief.
   - Every built-in schema comes from `schema()`, which sets `requires_generation: false`
     (`tessera/crates/tessera-core/src/schema.rs:415`). Nothing in the tree sets it to `true` outside a unit test
     (`schema.rs:1322`).
   - The Python `Builder` has no `with_schema`, and `seal` embeds only a built-in schema
     (`tessera/crates/tessera-core/src/product.rs:183-186`).
   - `bindings.md` states this.

### Follow-up filed

- #589: a manifest nested past the reader's parse limit seals but can't be opened. This PR closes the gap for
  `with_generation`; Python `set_field` (126+ levels, measured) and the Rust writers still reach it, so it stays open
  for the format-level bound in `tessera-core`.
- #575: the Python `Builder` can't carry a Blob block, so a Python `config_ref` can't name a carried config block
  (it's checked only by `inspect --resolve-config`). The docstring and the book point Python users to `config`.

# [PR 464](https://github.com/vig-os/tessera/pull/464) perf(ingest): align the streaming slab to the dataset's chunking

The `hdf-compound` streaming path was far slower than batch on real acquisitions. This aligns the
streaming slab to the dataset's chunking, which closes the gap.

Closes #325

## The issue's original diagnosis was wrong — twice, and this PR corrects the record

#325 was filed against a real DUPLET acquisition and self-corrected twice in its comments. Both the
original hypothesis and the correction are wrong, and I measured each away before looking further.
Recording it here because the wrong causes are plausible enough to be re-proposed later.

**Not disk I/O.** The issue opened at "~1 MB/s, disk-I/O-bound, the reader parses row-by-row". On a
contiguous synthetic `events_3p` the streaming path is *faster* than batch (3.3 s vs 3.8 s). There is
no gap at all to explain on that layout.

**Not the worker count.** Comment #2 concluded "the real bug is the DEFAULT worker count ≈ 1 — the
ingest path does not default to `available_parallelism()`". It does, and has since #372:
`resolve_write_config` bases on `WriteConfig::for_system()`, which is `available_parallelism()`.
Sweeping it on a contiguous 10 M-row file moves almost nothing:

| workers | 1 | 2 | 4 | 8 | 16 | 88 | `--auto` |
|---|---|---|---|---|---|---|---|
| time | 3.84 s | 3.40 s | 3.55 s | 3.33 s | 3.41 s | 2.89 s | 3.43 s |

**The actual cause is the dataset layout.** The gap only appears on a **chunked + compressed**
dataset — which is what every vendor acquisition is, and what a synthetic fixture is not unless you
ask for it. libhdf5 must materialise an ENTIRE chunk to serve any row inside it (for a compressed
dataset, inflate it), and the default per-dataset chunk cache is **1 MiB** — far smaller than one
chunk of a real acquisition. The reader asked for a fixed 65,536-row slab regardless of layout, so
against a 1,048,576-row chunk libhdf5 re-inflated every chunk **16 times over**. The batch path
issues one bulk read and touches each chunk once. That difference is the whole of #325.

## Evidence: the slab sweep

Same chunked + deflate file (10 M rows, 38 B/row, 1,048,576-row chunks), varying only `slab_rows`:

| slab_rows | vs chunk | time |
|---|---|---|
| 65,536 (the old default) | 1/16 | 20.78 s |
| 262,144 | 1/4 | 7.29 s |
| 1,048,576 | = 1 chunk | 5.07 s |
| 2,097,152 | 2 chunks | 4.85 s |

Monotonic in the chunk ratio, flattening exactly at one chunk. That is the signature of per-chunk
re-inflation, not of I/O bandwidth or thread starvation.

## The fix

`chunk_aligned_slab` rounds the requested slab up to a whole number of chunks. Reading *less* than
a chunk cannot cost less — the chunk is paid for either way — so one chunk is the floor. A
**contiguous** dataset has no such quantum and keeps the caller's slab verbatim, so that path is
byte-for-byte unchanged.

**On memory (corrected from an earlier draft of this body).** The 64 MiB `MAX_SLAB_BYTES` is a
*soft* ceiling on how many whole chunks are taken per `H5Dread`, not a hard cap on the buffer:
because one chunk is the floor, a dataset whose single chunk exceeds 64 MiB gets a slab that large.
Peak transient footprint is therefore about `2 × max(64 MiB, chunk_bytes)` — the raw read buffer and
the decoded columns are both live across the sink call. Sub-chunk reads cannot improve on that,
since libhdf5 materialises the whole chunk regardless.

**Why alignment rather than a bigger chunk cache.** `H5Pset_chunk_cache` on the dataset-access plist
fixes the same re-inflation. Alignment was chosen because it needs **no new FFI** — the cache route
adds another raw `hdf5-metno-sys` plist call on top of the existing unsafe block — and costs the
same memory, since a cache big enough to stop the re-reads must hold a chunk too.

## Before / after

Synthetic 10 M-row `events_3p` (38 B/row), 88 cores. Each ratio is computed **within its own run**
(batch and stream measured back to back under the same cache conditions), rather than across runs:

| run | fixture | batch | stream | ratio |
|---|---|---|---|---|
| pre-fix | chunked + deflate | 4.38 s | 17.66 s | **4.03×** |
| post-fix | chunked + deflate | 4.65 s | 7.19 s | **1.55×** |
| post-fix, best-of-3 (warm) | chunked + deflate | 4.38 s | 3.88 s | **0.88×** |
| pre-fix | contiguous | 3.82 s | 3.31 s | 0.87× |
| post-fix | contiguous | 3.78 s | 3.83 s | 1.01× |

The chunked rows are single runs except where marked; batch varies ~6 % between them (4.38–4.65 s),
which is the run-to-run noise floor here and is why the ratios are taken pairwise. The contiguous
rows are the control: streaming was never slow there, before or after.

Clears the issue's "within ~2× of batch" target. The amplification was per chunk rather than per
file, so the giant tables (`coin_2p` 18 GB, `singles` 81 GB) should inherit the same win — that is an
inference from the mechanism, not a measurement; I did not ingest at that scale here.

## Determinism

`content_hash` is **identical** across batch, streaming, before the fix, and after
(`blake3:47bfa05a…`). The change alters read sizing only, never output, so the writer-determinism
release gate is untouched and no conformance-corpus regen is needed.

## Tests

Mirrors the #352/#385 split — a correctness gate that runs everywhere, and a timing ratchet that
does not run where timing is meaningless:

- `chunked_stream_matches_bulk_read_including_a_ragged_tail` — **no timing, runs everywhere.** Slab
  sizing may change only HOW MUCH is read per `H5Dread`, never WHAT comes out, so a chunked
  compressed dataset with a deliberately ragged tail must still concatenate to exactly the bulk read.
- `chunked_stream_read_does_not_reinflate_each_chunk` — the ratchet. Relative and
  machine-independent (streaming read vs one bulk read of the same file, best-of-3), gated at
  ≥ 8 cores so it runs on dev machines with headroom and skips the small, build-saturated CI runners
  where a timing assertion is flaky.
- `chunk_aligned_slab_rounds_up_to_whole_chunks` — the pure helper: round-up, the byte cap, the
  never-below-one-chunk floor, the contiguous passthrough, and degenerate inputs.

**The ratchet's fixture is deliberately 16 slabs per chunk, not 8.** Both sides pay the same per-row
transpose, which dilutes the ratio: at 8× the pre-fix spread measured only 2.07× against a 2.0 gate —
a 3 % margin, i.e. a guard that would quietly stop catching the regression on a noisy day. At 16× it
measures 3.25–3.35×, giving ~65 % margin on the failing side and ~2× on the passing side. Verified
RED on pre-fix code at `streaming re-read overhead 3.25x vs one bulk read`.

`examples/gen_synth_3p.rs` generates the synthetic fixture every number above came from, so the
measurement is reproducible by anyone — and without touching patient data, which is why the whole
investigation used synthetic files.

# [PR 949](https://github.com/vig-os/tessera/pull/949) feat!: tessera-table-v2 per-column codec profile (ADR-0066 step 7)

Closes #828

`tessera-table-v2` becomes the table codec profile (ADR-0066 step 7), as decided in the accepted design note
`docs/spikes/915-tessera-table-v2.md` (#915, PR #919; owner rulings O0–O4). One rule for every product type, forced,
never sampled:

| Column dtype | Encoding | Parameters |
|---|---|---|
| `i2 i4 i8 u2 u4 u8 f4 f8` | `vortex.pco` | level 8, 8,192 values per page, one Pco chunk per 65,536-row group |
| `i1 u1` | `vortex.zstd` | level 9 (M6), one frame per row-group, no dictionary (O1) |
| nullable numeric | as its dtype; validity is Vortex's own child | |
| `b1`, `str` | `tessera-table-v1`'s BtrBlocks codec set, Zstd schemes excluded | unchanged |

> **⚠ A3 misses its floor (owner decision needed before merge, note §8).** The v2 whole writer encodes at
> **0.51× (GE) / 0.54× (Siemens)** of v1 per core, against the ≥ 1.00× floor. Cause (M4, `perf`): `pco` is 66 % of
> the v2 writer's CPU on GE, most of it per-chunk bin optimisation (`HistogramBuilder::apply_quicksort_recurse` 15 %,
> `optimize_bins` 11 %, `CompressionTable::binary_search` 11 %). The note's 22.3 M ev/s codec figure was measured with
> one Pco chunk per 2^22-row column; v2 pays the per-chunk optimisation once per 65,536-row group, 64× as often. I
> did not tune it away (brief). Every other acceptance row holds.

> **Size: ≈ 2,650 non-generated added lines, over the ~1,500 split threshold** (≈ 1,000 of them tests, ≈ 670 the
> measurement example and bench). Not split on my own; proposed split for the architect:
>
> - **A — `feat(io,cli): stored-encoding inspection, table measurement tooling and the v2 dtypes fixture`** (no
>   profile change, lands on dev's v1 first; ≈ 1,300 lines): `table::column_encodings`, `KNOWN_TABLE_CODEC_PROFILES`
>   (v1 only) + `unknown_codec_profile_note`, `inspect --encodings` + the notes + trycmd; `examples/table_profile.rs`,
>   `benches/table_read.rs`; `tests/table_v1_frozen.rs` decode test + the frozen payloads; the `table_v2_dtypes`
>   fixture (a new golden under v1, nothing moves) + its Pco-mode test.
> - **B — this PR's title** (≈ 1,350 lines, ≈ 650 tests): the v2 strategy, `canonical_validity`, the `Column.codec`
>   refusal, the drift guard, the v2 tests, `table_v2_workers.rs`, the `b1`/`str` fingerprint test,
>   `table_8bit_codecs.rs`, Cargo/feature changes, docs, and the regeneration commit (last).

> **⚠ Blocked on #804 (design question).** Note §2.5 item 2 requires nullable columns in the `table_v2_dtypes`
> corpus fixture. The `tessera-py-import` / `tessera-wheel-import` smoke reads every table of every corpus product
> from Python, and a nullable table column cannot be read there (#804: the validity trailer is appended to the
> values; `ValueError: buffer size must be a multiple of element size`). #804 leaves its API open ("a numpy masked
> array, or a `(values, mask)` pair"), so it needs a decision before this fixture can be in the corpus. Options:
> (1) land #804 first (my recommendation), then this PR as is; (2) keep the nullable columns out of the corpus
> fixture and cover them only by the Rust tests (they already are: `every_dtype_table`, `table_v2_workers.rs`), a
> deviation from §2.5 the owner would have to accept. Skipping the nullable columns in the Python smoke is not an
> option (a skipped test).

## What changed

- **`tessera-io::table`**: `TABLE_CODEC_PROFILE = "tessera-table-v2"`; `TableColumnCodec::for_dtype` (the rule);
  every numeric column gets its own layout strategy through `with_field_writer` (zones every 8,192 rows, then exact
  65,536-row chunks, then the forced codec; no dictionary probe, no sampling). `canonical_validity` makes the stored
  validity a pure function of the mask (found here: without it a batch encode and a streamed encode of the same
  nullable rows differed, caught by `stream::tests::staged_table_jobs_seal_the_in_memory_product_…`). Table
  writers refuse `Column::codec` (O3, pointing to `codec_profile`). `KNOWN_TABLE_CODEC_PROFILES`,
  `unknown_codec_profile_note`, `column_encodings`. Drift guard re-pinned: the rule, its parameters, `pco 1.0.2` and
  `zstd-sys 2.1.3+zstd.1.5.7` from `Cargo.lock`, then the (unchanged) BtrBlocks set. #468 guard now runs on the
  BtrBlocks set (still used by `b1`/`str` and zone maps) and asserts the v2 seal path writes no patches; #472 guard
  runs on v2 (floats are Pco).
- **`tessera-cli`**: `inspect --encodings` lists each table block's stored encodings per column (the footer is the
  record, O3); `inspect`/`verify` print the unknown-profile note on stderr.
- **`tessera-core`**: docs of `Column::codec` / `TableSpec::codec_profile`.
- **Cargo**: `vortex-file` `zstd` feature; direct `vortex-pco`, `vortex-zstd`, `vortex-error`; `vortex-zstd` joins the
  fork `[patch]`; dev-dep `pco` for M6. Lock: `zstd-sys` 2.0.16 → 2.1.3 (same libzstd 1.5.7).
- **Docs**: ADR-0024 amendment (2026-11-22), SPEC §5b (rule table, the two invariants, the refusal points),
  ADR-0066 step-7 status, FEATURE-MATRIX §B, CHANGELOG (breaking). The note gets one dated correction (below);
  #922's other nits are left to #922.
- **Benches/examples**: `benches/table_read.rs` (take/projection/full-scan at list-mode scale),
  `examples/table_profile.rs` (A1–A5, M1–M3 on a column directory), `examples/table_8bit_codecs.rs` (M6).

**Finding — the note's "does not move string bytes" is wrong at the file level** (dated correction in the note): a
Vortex file serialises the sorted list of every encoding ID its session registers and its edition allows, and each
array names its encoding by an index into it. Registering `vortex.zstd` (O1) changes that footer table for every
table, so even a `b1`/`str`-only table's bytes move. Their encodings and buffers do not:
`tests/table_v1_frozen.rs::bool_and_string_columns_keep_v1s_encodings_and_buffers` compares them chunk by chunk
against a frozen v1 payload.

## Acceptance (note §5 / §8)

Real DUPLET-campaign data, #822 fixtures (`tessera-vendor-2026-11`: GE 54,161,949 ev, Siemens 55,004,119 ev, columns
verified against their sha256 before use). Host `ksb-ws` (32 cores), one pinned core (`taskset -c 29`), binaries and
data on tmpfs, median of 3, v1 = dev `f390528e` and v2 = this branch built from the **same** example source
(`examples/table_profile.rs`). Load average 25–58 during the runs.
**Not on `ksb run --exclusive-cpus`**: the fixture is private and not a ksb dataset, and `tessera` has no ksb project
policy (`ksb caps --project tessera` → `dataset_refused`), so a job cannot read it. Command:

```sh
cargo build --release -p tessera-io --example table_profile --example table_8bit_codecs
taskset -c 29 table_profile write <dir> out.tsra 1        # A1, A3/M4
table_profile verify <dir> out.tsra                        # A2
taskset -c 29 table_profile decode out.tsra 3              # A5/M3
taskset -c 29 table_profile take out.tsra 5                # A4/M2
table_profile layout out.tsra events/0000                  # M1
taskset -c 29 table_8bit_codecs <siemens-dir>              # M6
```

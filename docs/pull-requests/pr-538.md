# [PR 538](https://github.com/vig-os/tessera/pull/538) feat(ingest): stream the generic table lanes in bounded memory

`ingest table` (#460) read the whole Parquet / Arrow IPC / CSV file into memory. This streams it
through the existing multi-block sealing path (`WriteSession` + `TableMultiBlockSink`), so memory is
bounded by a **block**, and routes by a threshold so small inputs keep the whole-file path.

Closes #458

## The invariant

Batch and stream seal the **same product** — `content_hash` and `manifest_hash` — at every size,
across batch sizes, worker counts and lanes, and against the committed conformance goldens.
Streaming is a memory/time trade and never a format decision.

Two properties make that true rather than hopeful, and the first revision of this PR had neither:

1. **The block partition is a function of the data alone.** Both paths split at `BLOCK_ROWS` through
   `tessera_io::partition_blocks` / `block_name`.
2. **The execution knobs are not identity.** `streaming` and `batch_rows` never enter `spec_hash`,
   so they cannot reach `manifest_hash` through the `ingested_via_spec` edge.

Written into ADR-0026 as a rule, with the reasoning.

## Two passes, because nullability is whole-file

Nullability is **by presence** (ADR-0029), decided over the entire input, and `ColumnData::Nullable`
is a *representation* rather than a flag — so `TableMultiBlockSink::new` needs the column schema up
front and **the first block cannot be encoded until the last row has been read**. Pass 1 establishes
the shape (schema, nullable leaf set, merged transform receipt; data dropped); pass 2 encodes,
coercing each batch up to the file-wide schema.

Rejected: inferring nullability from a prefix (moves `content_hash` away from batch), and trusting
the Parquet footer's `null_count` (optional, and the *producer's* unverified claim — filed as #502).
Routing **may** read the footer; identity may not.

## The hazard this PR is shaped by

The batch path applies the spec's metadata tiers **after** sealing, by re-sealing a built product. A
streamed `.tsra` is written once, straight to disk, with **no post-seal hook** — so a tier not
declared before the first block commits is dropped *silently*, and the loss moves `manifest_hash`
while leaving `content_hash` byte-identical. That is the one divergence class a content-hash
comparison cannot see, which is why every equality assertion here checks both.

`MetadataTiers` + `declare_table_with_tiers` therefore apply the tiers in **one** function, in the
one correct order (inherited → the lane's own → spec → producer), held as separate fields and never
pre-merged: an inherited value must lose to a product-own default while an explicit spec value beats
both, which a single flattened map cannot express.

## What review caught, and what it cost

The first revision passed CI twice and was still wrong in one important way. Both blockers are fixed;
both are worth reading as review outcomes rather than as footnotes.

**Blocker 1 — the central claim held only below one block.** `to_table_product` sealed exactly ONE
block whatever the row count, while streaming split at `BLOCK_ROWS`. Past 4,194,304 rows the same
bytes sealed two different `content_hash`es, and *which* you got was decided by `streaming`, by the
`stream_threshold` against an estimated size, or by whether the input happened to be a pipe — none of
which is recorded in the product. Every batch-equals-stream test used inputs of a few rows, so none
could see it. `block_count`'s own doc already called the partition a format invariant "shared by
every ingest path"; this path simply never called those helpers. Now tested at the production
constant (`BLOCK_ROWS + 1` rows) **and** across block boundaries through a seam.

**Blocker 2 — the CLI help over-promised.** It claimed both paths seal the same `manifest_hash`, but
non-default `--streaming` / `--batch-rows` were written into `spec_hash`. Re-running an archived
ingest with `--streaming stream` on a smaller machine therefore could not reproduce the archived
`manifest_hash`. The knobs are now never serialised at any value; the help says what makes the
promise hold.

**A correction to this PR's earlier description.** It listed the spec-hash problem as a third
"pre-existing `dev` bug". That was wrong: the knobs were added **by this branch**, so the defect and
its fix were both mine, and presenting them as a bug-plus-fix pair would have written a defect this
branch created into dev history as though it had been there. That commit is folded into the one that
added the knobs, which now declares them never-serialised from the start.

## Two pre-existing `dev` bugs it did surface

Both the same shape — `content_hash` identical, `manifest_hash` moved, loss silent — each fixed in
its own commit with A/B evidence and a regression test.

| Bug | Why nothing caught it |
| --- | --- |
| A spec `[product.generation]` **deleted the sealed decoder triple** (ADR-0056 §6a): `apply_spec_metadata` did a bare `with_generation` over the bag `declare_generic_table` had folded the triple into. Also hit the generic array lane and NIfTI's `geometry_source`. | The field is optional so nothing rejects its absence, and **no corpus fixture declares a recipe** — so every golden agreed either way. |
| `ProductBuilder::from_manifest` **dropped `ingest_transform`**, so every batch re-seal lost the ADR-0056 §6.2 canonicalisation receipt. | The batch-equals-stream helper compared `to_table_product`'s output, which is *before* the re-seal. |

Regenerating the corpus adds exactly **one** entry (the new fixture) and moves **no** existing
golden — verified field-by-field across all prior fixtures, which is also the evidence that none of
the fixes, nor the new partition, changed sealed bytes.

## Memory: the block is the encode unit

`TableMultiBlockSink` dispatches at `finish()`, so **one block** is the encode unit. Measured,
streaming four sizes in one process:

| rows | blocks | added to peak RSS |
| --- | --- | --- |
| 250 k | 4 | 41.6 MiB — every fixed cost |
| 1 M | 16 | 4.9 MiB |
| 4 M | 62 | **0 MiB** |
| 4 M again | 62 | 1.9 MiB |

Sixteen times the data added **nothing**; repeating the *same* size added 1.9 MiB, so the residual is
allocator warm-up rather than accumulation. **In production, peak is bounded by `BLOCK_ROWS`.**

The first version of that assertion used a flat 4 MiB budget against a 4 MiB fixture and went
**intermittent** under `cargo nextest`. It is now a quarter of what a file-proportional path would
need; teeth re-verified by injecting a whole-file read — fails at 174 MB against a 12 MB budget.

## Non-regular inputs fall back, and say why

Streaming reads the input twice, so a pipe cannot take it. Such inputs route to **batch** even under
an explicit `streaming = "stream"` (with a warning), because `tessera ingest table <(zcat big.csv.gz)`
works today — verified by running it. With Blocker 1 fixed, that fallback now seals the *same*
product, just without the memory bound. Parquet on a pipe explains the **footer** rather than blaming
the data.

**Found while verifying that fallback, filed as #542:** on a non-seekable input the sealed
`ingested_from` digest is *content-independent* (two CSVs with different `content_hash` seal the same
`source_digest`, because `source_digest` re-opens the drained descriptor and hashes zero bytes).
Pre-existing, on the batch path; this PR only routes pipes there. Being fixed separately.

## Review nits, all addressed

- The change guard now re-checks the fingerprint **and the row count** after the encode pass, not only
  around pass 1 — and records `ctime`, not `created()`, which is birth time and never moves on a write.
- A header-only CSV seals a 0-row table on **both** paths; it used to error under `stream`.
- A displaced doc comment reattached; `arrow_ipc_size_estimate` documented as a routing-only floor
  (IPC may be LZ4/ZSTD-compressed).
- The RSS test renamed for the bound it actually asserts (block, not batch).

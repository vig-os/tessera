# [PR 729](https://github.com/vig-os/tessera/pull/729) test(io): single-source the S3 endpoint contract; fail nextest checks that select no tests

Closes #726

Fixes both nits from the review of #724 (#707).

## 1. One source for the S3 required/skip contract
`tessera-cli/tests/cloud.rs` had a copy of tessera-io's `s3_endpoint`, with 2 of its 5 tests. The contract now lives in
**one file**, `tessera-io/src/cloud/s3_contract.rs`:
- in tessera-io it is a private `cfg(test)` child module, `cloud::s3_contract`, which `cloud::tests` imports from;
- tessera-cli's integration test compiles the same file via `#[path = "../../tessera-io/src/cloud/s3_contract.rs"]`.
  The CLI copy is deleted.
- It carries `s3_endpoint` (the pure contract), `s3_endpoint_or_skip` (the env reads plus the skip notice, which
  both crates had duplicated too) and the **5 contract tests**. Those tests run in **both** crates, as
  `cloud::s3_contract::tests::*` and `cloud_s3_contract::tests::*`, so the check's `cloud` filter selects them.

**Why `#[path]`, the least invasive option:** an integration test can't reach `cfg(test)` items. A public or
`#[doc(hidden)]` helper would put test policy into tessera-io's API. A test-support crate, or a feature turned on
through a dev-dependency, adds a dependency edge that churns Gate B's feature snapshots. `#[path]` changes neither the
API nor the dependency graph, and the repo already does it (`tests/encode_trace_interest.rs` uses it for
`test_support.rs`, within one crate). The cost, written in the module doc: tessera-cli's tests reach outside their
package, so they only build inside the workspace. That doesn't matter, because the crates are not published to
crates.io (`release-plz.toml`).

## 2. A nextest check whose filter matches nothing must fail
**Finding:** `s3-range-read` already failed on a zero-match filter, but only through nextest's default.
nextest 0.9.137 (the version in the check's closure) defaults to `--no-tests=auto`, which resolves to `fail`
(exit 4) outside `--rerun` (`cargo-nextest/src/dispatch/core/run.rs`, `final_result`). There is no nextest config key
for it, but `NEXTEST_NO_TESTS=pass|warn` in the environment turns it off, and an upstream default can change.

**Fix:** `s3-range-read`, `sql-tests` and `workspace-test` (the three `cargoNextest` checks) now pass
`--no-tests=fail` through `cargoNextestExtraArgs`, from one documented binding, `nextestFailOnNoTests`. On the command
line it overrides the environment variable. Every evaluated checkPhase ends with `--no-tests=fail`. No check name
changed, so `.github/nix-flake-checks.txt` stays as it is.

**Proof:** the check's exact nextest argv, run with its nextest binary
(`/nix/store/jhkr7gwyrchkml33gyns9cy0yn7b57qc-cargo-nextest-0.9.137`), filter `cloud` → `cloudNOMATCH`. I didn't
`nix build` the check: heavy builds stay off the shared seat.

| argv | env | exit |
|---|---|---|
| pre-fix, filter matches nothing | clean | **4** (`error: no tests to run`): today's guarantee is the default |
| pre-fix, filter matches nothing | `NEXTEST_NO_TESTS=pass` | **0**: green, 0 tests run (the gap) |
| post-fix (`--no-tests=fail`), filter matches nothing | `NEXTEST_NO_TESTS=pass` | **4** |
| post-fix, real `cloud` filter | clean | **0**, 16/16 passed |
| `sql-tests` post-fix, filter `sqlNOMATCH::` | `NEXTEST_NO_TESTS=pass` | **4** |

**Limit (also documented in the flake):** `--no-tests` doesn't catch a filter that matches *fewer* tests than
intended.

  stayed green.

  clean, and all prek hooks pass.

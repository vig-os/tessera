## Changes Made

- **Status:** `**Status:** Accepted (2026-10-29, ...)` with a history line (Proposed in #661, Accepted here).
- **(a) signed alignment, in §5 declared mode:** PR2 (#667) ships same-producer zips with an unsigned
  `aligned_to`, which the seal covers. This is a documented scope, since PR2 cannot tell producers apart.
  A signed alignment is required before any zip across producers ships. That work is tied to #656/#566 and
  adds an `AlignmentError` refusal of an unsigned claim from another producer. The ADR extends the same
  rule to the `.cidx` that key mode prunes on, and labels this as its own reasoning.
- **(b) local integrity default, in §7:** local `VerifyBlocks` is unspooled by default. The spool is an
  explicit opt-in for remote or untrusted local sources and lands with PR3 (#668), with an acceptance test.
- **(c) key mode under LIMIT or an early stop, in §5:** a key-only pre-pass checks strict increase over the
  whole scanned range, across partition boundaries, before any row is released. This release gate sits
  inside the scan, so a pushed `LIMIT`, a `LIMIT` above the scan, or a dropped stream can only return
  verified rows. The `[5, 6] [3, 5]` swapped-copy counterexample under `LIMIT 1` shows why neighbour checks
  are not enough. Read from the spool, key mode pins each partition's first and last block per input and
  prefetches as every scan does, so it needs at most `4 · k · P` slots (the spool slot rule below).
- The §0 table, the §3 open-block and memory terms, §7 verify-once, the §8 PR2/PR3 acceptance criteria, the
  consequences and the `docs/adr/README.md` index row (now **Accepted**) are updated to match.
- `tessera/docs/FEATURE-MATRIX.md` gains a planned (○) row citing ADR-0062, which the `adr-matrix` gate
  requires of every Accepted ADR.
- "Open questions for the owner" becomes "Open questions (do not block acceptance)": #672 gates #668; #673
  and #674 gate 1.0 and the API freeze; #675 gates the `.cidx` spec change.
- **Spool slot rule (second commit), which resolves #697:** §7 "Spool slots" counts, per input and per
  partition, the current block plus the prefetched next one, and in key mode also the pinned first and last
  block. A plan therefore needs at most `2 · k · P` slots, or `4 · k · P` in key mode. `plan_scan` computes
  the plan's need, makes it the default, and refuses a smaller `spool_blocks` with a typed error before any
  row, so no consumer order can hang a spooled scan. The reason is the old default `P`, which hangs a
  declared-mode zip with k = 2 and P = 1. Prefetch is counted rather than disabled because the measured
  2.6–8× re-read happens inside one block, while prefetch hides the next block's download and hash. Its cost
  is spool disk. §3, §5 and the PR3 criteria follow. The key-mode spool tests move from PR2 to PR3, where the
  spool lands.
- `VerifyBlocks` is labelled the object-store default pending #672 everywhere. The §0 limits note says that
  on the default local unspooled path, a concurrent writer reduces the (c) release gate to row-by-row checks.
- **Split blocks outside key mode (third commit):** §7 said a block §6 splits across partitions is hashed
  once per query. Read from the spool outside key mode, that hangs: with k = 1, P = 2 and runs
  {1, 2, 3} / {3, 4, 5} (need 4), a consumer that drains the second partition first leaves block 3 spooled
  for the first partition, so block 5 never gets a slot. A split block's spooled copy is now released when
  the partitions holding it move on, and a later partition fetches and hashes it again. "Hashed once per
  query" stays for unspooled reads. Key mode keeps the shared boundary block pinned once, which cannot hang
  because the pin is counted once in `4 · k · P` and every other held block is in its partition's own need.
  PR3 and #668 gain a test that drains the second partition first and expects block 3 hashed twice within
  `2 · k · P` slots.
  The same commit closes a second hang a review found: a partition waiting on a block's verify-once cell
  waited for the partition that started the fill, which may itself be blocked on its full channel. §7 now
  runs every fill on the scan's fill pool of `P` threads, waiting on no channel, consumer or slot; §3 counts
  the pool's buffers as `mem(fills) = P · (hash ring + spool_chunk_bytes)`. PR3 and #668 gain a gated test
  in which the first partition starts block 3's fill and then blocks on its channel, so a fill run on that
  partition's producer times out on every run, plus a test that at most `P` fills run at once. The PR3
  tests pin one-window blocks and gate the partitions' order, so each fails the buggy design on every run.
  The fill pool governs the default unspooled local scan, so PR1 (#666) now carries the unspooled leg of
  the fill test and the pool's thread count, and PR2 (#667) the pool-bound test, since only a zip submits
  more than `P` fills while they are held and the "k fills together" rule ships with it.
- #666 lists the fill pool and its PR1 test; #667 gains the pool-bound test. #667's Scope now describes the pre-pass and the release gate. #668 carries the spool-slot and local
  opt-in tests.
- **Pre-pass threads (fourth commit):** §5 said the key-mode pre-passes run "on at most `P` threads"
  without naming them, and running them on the fill pool hangs (with `k = 2`, `P = 2` both pre-passes take
  the pool's two threads and their fills queue behind them). Each pre-pass now runs on its partition's
  producer thread, which the first `execute` spawns for all `P`. The ADR states the invariant that nothing
  that waits on a fill may run on the fill pool, and the pool accepts fills only. Producer lifetime is
  specified: a producer whose send fails stops and releases its pins and slots, and a second `execute` of a
  taken partition errors. Thread costs are recounted as `P · (1 + workers) + P` plus the I/O threads.
  Pinned copies are not open blocks (at most two per input), and the `k = 1` slot hang is a concrete
  schedule. PR2 gains "Pre-pass threads" and "Producer lifetime" tests, and PR3 repeats both read from
  the spool; #666, #667 and #668 mirror these criteria.
- **Gate failure (fifth commit):** the release gate had no rule for a failing pre-pass or boundary check,
  so a consumer polling only one partition could hang on a failure in another. The gate is now a cell
  resolved once, to passed or to the first failure; every producer waiting at it, reaching it later or
  having resolved it sends that error on its own stream and stops, releasing its pins and slots, and no
  producer may wait on the gate without observing its failure state. PR2 gains "Gate failure" (an
  inversion, and a failed boundary check; a gate-without-failure implementation times out), PR3 repeats
  it read from the spool, and #667 and #668 mirror both.

# [PR 490](https://github.com/vig-os/tessera/pull/490) feat(cli,core): resolve a config_ref to its carried block, and walk the provenance DAG

Closes #452 — the two P2 items #417 left open, because each needed a decision rather than a bigger
render.

## 1. `inspect --resolve-config`

`generation.config_ref` is a digest of a config block carried in the same `.tsra` (ADR-0058 §2).
`inspect` printed the digest; `nav::generation_lines` even said so in its own doc comment. It now
dereferences it, so the recipe reads end to end instead of ending at a hash the operator chases by hand.

A flag on `inspect`, not a new verb: "what recipe made this?" is the question `inspect` already answers,
and a separate verb would split one question across two commands. Three rules make it safe:

- **Inline only what belongs on a terminal.** Small valid-UTF-8 text prints verbatim (20 lines, then
  collapse; `--full` prints all). Larger or non-UTF-8 is named with the `tessera extract` command that
  streams it. The choice comes from the Blob spec's recorded `size` — which exists precisely so a
  manifest-only reader knows it — so a multi-GB vendor config is never buffered just to decide not to
  print it. Refusing to dump binary at a terminal is the rule `slice --format npy` already follows.
- **A broken sealed reference is loud.** A `config_ref` naming no carried block is the new
  `Error::UnresolvedConfigRef`, raised only where a caller asked to resolve. Plain `inspect` on the same
  file still works — the reference is sealed and the product is otherwise valid. Resolution happens
  *before* any output, so it fails cleanly rather than half-rendering a summary and erroring mid-way.
- **`--json` stays exactly the manifest.** A resolved config is not in the manifest, so the combination
  is refused instead of silently dropping a flag or widening a shape #417/#479 pinned.

Nothing to resolve exits 0 with the gap stated ("no `config_ref`", "no generation record"): nothing was
promised, so nothing is broken.

## 2. `tessera provenance`

Walks `derived_from` and prints producer + recipe + shared identity per hop. It drives
`provenance::walk` — the same traversal `verify_chain` now uses — through a `Visit` visitor, per the
issue's ask not to grow a second walk. Two walks would drift, and then the verifier and the operator
view would disagree about what the DAG is. They differ only in the visitor: strict refuses what it
cannot prove; the operator view renders the gap and keeps going, because "I cannot reach that parent
from here" is a fact to show, not an error that hides the rest of the chain.

Parent resolution is **local** and ordered: the product's own directory → `--collection` → each
`--search` dir, first source wins. No registry resolver — it needs a fetch policy and a cache, and
putting one in a read verb would make `provenance` quietly reach the network. The `--help` says so.

Six outcomes per hop, each a distinct fact, read off the edge's **shape** and never its role name
(roles are free-form strings the format never constrains):

| Outcome | Gap? | Meaning |
| --- | --- | --- |
| `pinned` | no | the parent on disk is the exact version the edge committed to |
| `different version` | yes | the right lineage, another version |
| `unresolved` | yes | a product-shaped reference nothing was found for |
| `no pinned version` | yes | names a parent but pins no version |
| `external leaf` | no | a vendor path / filename / SOP UID — where a chain *should* end |
| `version not present` | no | a `snapshot_of` breadcrumb whose version is absent |

The last two are deliberately not gaps. A real chain ends at vendor files and `publish` deliberately
drops history, so counting either would leave every product permanently "incomplete" and make
`--require-complete` worthless. A gap is rendered at exit 0; `--require-complete` is the gate mode;
`--json` gives stable `outcome` tokens; a genuine cycle always exits nonzero.

## 3. Version skew is not corruption (the load-bearing change)

`verify_walk` raised `Error::Integrity { what: "provenance_edge" }` when a resolved parent's seal was
not the pinned one. ADR-0036 makes `id` a **lineage handle** and `manifest_hash` the version, so one
reference legitimately addresses many manifests — resolving against a store that has since committed
the parent again returns a different version of the *right* parent. `Integrity`'s own doc reads
"tampering, corruption, or a producer bug", so a metadata edit was being reported as an attack.
Operators who see that learn to wave the error away, and then wave away the real one.

Now `Error::ProvenanceVersionSkew`, carrying role/reference/pinned/resolved. Real corruption stays where
it can actually be observed — payload verification, which reads bytes. `verify_chain` stays strict.

Three consequences, each structural rather than a special case:

- `Resolver::resolve_pinned(reference, pinned)` (defaulted, so no impl breaks). A store holding two
  versions of one parent must return the pinned one; without it the walk reports skew whenever the newer
  version sorts first — skew by coin flip, worse than not knowing.
- **Version pointers are reported, never recursed through.** An edge whose `reference` equals its pinned
  hash names a version, not a lineage (`snapshot_of`). **This was a live bug:** a published artifact
  keeps its lineage `id` while pointing back at an earlier version of itself, so descending re-walked the
  same product and tripped the cycle guard. `provenance --search` on any published artifact reported a
  false cycle until this fix; `verify_chain` had the same latent bug against a resolver holding both.
- Diamonds are visited once (flagged `revisited`) instead of re-walked.

## Consumer audit (the condition on changing `Error::Integrity`)

Every consumer that matches on `Error::Integrity`, maps error kinds to a user-visible outcome, or prints
"tampered"/"corrupt". **No consumer discriminates variants**, so skew is neither reclassified as success
nor still reported as corruption anywhere. `tessera_core::Error` is `#[non_exhaustive]`, so a new variant
is not a semver break.

| Consumer | Where | How it handles kinds | Effect |
| --- | --- | --- | --- |
| CLI exit codes | `main.rs` `main()` | one `match`: `Ok → SUCCESS`, `Err(e) → eprintln + FAILURE`. No per-variant arm in the binary | prints `Display`, exits nonzero ✓ |
| `tessera verify` | `main.rs` `Cmd::Verify` | prints `OK …` only on success; errors propagate via `?`. Verifies L1 seal + L2 payloads, never walks provenance | cannot emit skew; exit stays nonzero ✓ |
| `tessera-py` | `lib.rs` `err()` | `create_exception!(… TesseraError, PyException)`; every error flattens to one exception by `Display` (~28 `map_err(err)` sites) | raises `TesseraError` ✓ (docstring widened) |
| `tessera-wasm` | `lib.rs` | exports `verify_manifest`/`verify_signature` → `bool`, swallowing errors; **no provenance entry point** | unreachable ✓ |
| `collection verify` | `cli/collection.rs` ×2 | the only **production** `Error::Integrity` construction for a pinned-hash mismatch | **left as-is** — see below |
| `verify_chain` | `core/provenance.rs` | **zero production callers**; all sites are tests | the mislabel was latent, not live |

`collection verify` keeps `Error::Integrity` deliberately. A collection **pins its members at seal
time**, so a member whose on-disk `manifest_hash` differs from the pinned one is a broken seal — unlike
a provenance parent, which is resolved by *lineage* and may legitimately be a different version. Same
symptom, different question.

Also checked: "tamper"/"corrupt" appear **nowhere in operator output** — all 30+ hits are doc comments,
test names and book prose. No `println!`/`eprintln!` says either word, so there was no wording to fix
alongside the variant.

## Tests

- `tessera-core` (10 in `provenance`): skew is not `Integrity`; one lineage id addressing two versions
  reads as skew; a version pointer at a present version is **not** a cycle; diamond visited once while a
  real 2-cycle still errors; depth cap reports the boundary edge without descending.
- `tessera-cli` (4 + 1): edge classification reads shape not role names; only unprovable derivation hops
  count as gaps (with the negative cases pinned); `resolve_pinned` picks the pinned version;
  `shared_identity` reports only schema-flagged fields. Plus an end-to-end test that makes **two versions
  of one parent with the real `tessera commit`**, `publish`es the second over the first, and asserts the
  render says "different version" and contains none of `corrupt`/`tamper`/`integrity` — while
  `tessera verify` on the child still passes, which is the whole point.
- `tests/cmd/provenance-walk.trycmd` — a 12-case docs-as-tests walkthrough (ingest → `--resolve-config`
  → the `--json` refusal → a complete chain → `publish` → the gap → `--require-complete` nonzero →
  `--search` closing it → `--json`). Included into the book, so the prose cannot drift from the binary.

A **new** trycmd rather than extending `provenance.trycmd` as #452 suggested: every collection, member
and manifest hash in that file is hardcoded, so adding a member would churn all of them and cost the
#417 walkthrough its stability.

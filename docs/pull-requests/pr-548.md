# [PR 548](https://github.com/vig-os/tessera/pull/548) ci(nix): split nix flake check into one job per group per arch

Splits each arch's single `nix flake check` leg into **six jobs, one per check group**. The groups are defined in the flake and balanced against measured per-check medians. The `nix flake check` gate stays the single required status, and it now passes only on a complete, exact set of per-check verdicts.

Builds on #544 (the nix dependency cache, merged); based on `dev`.

## Why: the legs were throughput-bound

Re-measured after #536 gave the checks distinct derivation names. The earlier figure ("serial floor 77.9 min, a split gains at most 6.9") pooled three derivations under one name and was wrong; see #517.

| | x86 |
|---|---:|
| total check work per leg | ~95 min |
| longest single check (`sql-tests`) | ~19.5 min |
| leg wall-clock (`--max-jobs 2`) | 77–79 min |

## Groups (`flake.nix`: `ciGroupsDeclared` → `legacyPackages.<sys>.ciGroups`)

| job | checks | x86 min (sum of medians) |
|---|---|---:|
| `sql` | sql-tests | 19.5 |
| `seal` | seal-profile-determinism · workspace-clippy | 19.0 |
| `cloud` | minio-range-read · **ingest-gate-a-sql** | 17.8 |
| `registry` | registry-roundtrip · **ingest-gate-a-reduced** | ~18.5 |
| `python` | **ingest-gate-a-workspace** · tessera-py-import · tessera-wheel-import · workspace-test | 19.2 |
| `rest` | **ingest-gate-a** + every check not listed above, *computed* | ~11 |

**`rest` is computed**, so a new check can never fall out of CI. Evaluation **throws** in three cases, each of which has a negative test:

- a listed name is not a check;
- a check appears in two groups;
- two `ingest-gate-a*` checks share a group.

The last rule is the #495 fix. Every post-#514 memory peak (13.7–14.1 GB of 16) came from two dev-profile Gate A builds overlapping. One Gate A per job makes that overlap impossible by construction rather than by scheduling luck. It also covers a *new* Gate A check: an unlisted one lands in `rest` next to `ingest-gate-a` and trips the rule.

`tessera-py-import` and `tessera-wheel-import` stay together because `tessera-py` is the only intermediate two checks share.

## Workflow

1. **`plan`** (x86):
   - runs `nix flake check --no-build --system <sys>` for **both** arches, so every flake output is still evaluated, as each old leg did. That's 3–4 s each. `--system` evaluates exactly the aarch64 outputs from x86, and `--all-systems` is unusable because `x86_64-darwin` no longer evaluates (#545). A broken flake now fails before any runner starts;
   - evaluates `ciGroups` into the matrix: 12 jobs and 50 `arch/check` pairs, with no names hard-coded in YAML. It refuses to emit an empty set;
   - looks up **both** arches' dependency-cache keys without downloading. The key is a derivation hash and evaluation is pure, so x86 computes the aarch64 key exactly (verified: identical drv).
2. **`nix deps (<arch>)`** runs only for arches whose key **missed**. It builds `tessera-deps` once, then exports and saves it. On a hit it's skipped entirely.
3. **`nix check (<arch>, <group>)`**:
   - restores the cache (it never saves, so there's no race);
   - runs `nix build -L --keep-going --fallback --max-jobs 2 --cores 4` on its group, with the sampler;
   - writes per-check verdicts from the store.

   It starts only if `plan` succeeded and `deps` succeeded or was skipped. A failed deps build stops the matrix instead of 12 jobs repeating it.
4. **`nix flake check`** (the required status, same context as today) passes only if all of these hold:
   - `plan` succeeded;
   - `deps` succeeded or was skipped;
   - every planned `arch/check` has a verdict;
   - every verdict passed;
   - the matrix succeeded.

   It refuses an expected set that isn't a non-empty array of strings. Missing verdict files are reported as missing checks, not a silent exit. Verified against 18 simulated cases.

The composite action's `save` mode became **`ensure`** (look up; on a miss build, export, save). The dev/main warmer uses it too, so "make sure this arch's closure is cached" is defined once.

**`!cancelled()` on the gate, and why that's safe.** With `always()`, a run superseded by a push still ran the gate, which posted a red ✗ on the old SHA. I measured what `!cancelled()` does on a probe run cancelled mid-`deps`: the gate is reported as **cancelled, not skipped**. Both the job and its check-run on the head SHA read `completed/cancelled`. A cancelled conclusion doesn't satisfy a required check (only success, skipped and neutral do), so a cancelled run still blocks the merge; it just stops calling itself a failure. A failure or timeout inside a job doesn't cancel the *run*, so the gate still runs and fails.

**Re-running a job doesn't collide on its artifact name.** I re-ran one successful job of run 37248665133. The re-upload succeeded as a second artifact of the run, and the re-run gate downloaded the newer one (12 artifacts, 50/50).

Local `nix flake check` is unchanged.

The runs are [37246299669](https://github.com/vig-os/tessera/actions/runs/37246299669), [37279718318](https://github.com/vig-os/tessera/actions/runs/37279718318), [37248665133](https://github.com/vig-os/tessera/actions/runs/37248665133) and [37284034799](https://github.com/vig-os/tessera/actions/runs/37284034799). The cold runs used fresh branches that can read no cache entry.

**Why v2's wall-clock is higher, honestly.**
- **Warm:** the design costs ~0.5 min (`plan` does two lookups and two full evaluations; x86 `sql` ends at +18.6 vs +18.1). The other 4.6 min is one job (x86 `python`) that waited for a runner until +10.8 min.
- **Cold:** the critical path is now serial (plan 1.1 + deps 12.5 + sql 17 ≈ 31 min), and the rest was runner queueing. Check-job starts spread from +13.9 to +28 min while three other PRs' CI ran; the v1 cold run met no contention.
- Under contention, starts didn't follow matrix order, so reordering the groups wouldn't reliably help, and I didn't do it.
- Cold keys occur only on PRs that change the dependency derivation, and there v2 saves 47% of runner-minutes and removes the save race.

`sql-tests` is the critical path on both arches; splitting it is the next lever if 18 min ever matters.

## Trade-off

Measured warm runner-minutes: **70.5 (x86) / 56.3 (arm)**, against 41 / 45 for a single cached leg (×1.7 / ×1.25), and **below** today's uncached 78 / 60. Wall-clock: 41/45 → 18–23. Hosted minutes are free on a public repo, but **concurrency is not**: 12 jobs per PR. That's now *observed*, not hypothetical: with three other PRs' CI in flight, check jobs waited up to 14 min for runners. If that becomes the norm, the groups can merge pairwise (3 jobs per arch, ~35 min) without touching the rest of the design.

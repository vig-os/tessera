# [PR 544](https://github.com/vig-os/tessera/pull/544) ci(nix): cache the dependency build in the GitHub Actions cache

Caches the shared dependency build in the GitHub Actions cache. On a hit, every `nix flake check` leg skips `tessera-deps` (the serial prefix: 8.8–14.7 min from first to last `tessera-deps>` log line over 14 legs; x86 14.0–14.7, aarch64 10.1–10.6, one fast x86 runner 8.8. An earlier 19.4-min figure came from one pre-#514 x86 leg, where it compiled alongside other derivations.) for **~40 s of restore + import**. No external account, no secret, no substituter configuration.

## What was measured, before building

- `tessera-deps`'s runtime closure: **793 paths, 2.47 GiB**, of which **2.11 GiB is not on cache.nixos.org** — the artifact itself (594 MiB), the vendored crate sources (565 MiB) and the rust-overlay toolchain (~0.9 GiB) were all rebuilt or re-fetched on every run. So the whole closure is cached, not just the artifact.
- Exported as a zstd `file://` binary cache: **1105 MiB** (x86_64) / **1042 MiB** (aarch64), so both arches fit the 10 GB repo limit with room.
- The paths are **unsigned**, so importing needs a trusted nix user (locally, without `--no-check-sigs` the import exits 1). Hosted runners report **`trusted-users: root runner`**, and the import was accepted on every run.

## Design

- **Key = the hash of the deps *derivation*.** It is exposed as `legacyPackages.<system>.cargoArtifacts`, which `nix flake check` does not build. The key changes exactly when the artifact would, including toolchain and crane-argument changes that a key on `Cargo.lock` + `flake.lock` would miss.
- **The logic lives once,** in a repo-owned composite action `.github/actions/nix-deps-cache` (`restore` / `save` modes). nix-check restores and imports before `nix flake check`; on a miss it exports and saves after, under `always()`, so a red leg with a good `tessera-deps` still warms the cache.
- **`nix-deps-cache.yml` warms the cache on pushes to dev and main.** An Actions cache is readable from a run's own ref and its base branch. nix-check never runs on push-to-dev, so without this nothing would exist at the `dev` scope, every PR's **first** run would be cold, and only re-runs would benefit. The warmer looks the key up **without downloading** (`lookup-only`), so unchanged deps cost one eval and a lookup. Only a missing key builds `tessera-deps` and saves it.
- **It can only ever save time.** A miss, a failed import or a failed export falls through to building as before, with a warning annotation. A flake that fails to **evaluate** isn't the cache's failure either: Locate warns and emits no key, restore, import and save all skip, and the build step that follows reports the real evaluation error under its own name. Without this, `nix eval` under `bash -e` would fail the job at "Restore the dependency cache" (review nit, fixed in the third commit). I verified it by running the extracted Locate script under the runner's shell with a shimmed `nix` for 3 cases.

**Effect on the checks** (drvPaths of all 25 x86_64 checks, compared against dev): **23 are identical**. `guardrails-gates` and `mdbook-build` get new derivations because both read the *whole* flake source rather than the filtered crane src, so any file change re-derives them. That's deliberate, not a filter leak. `guardrails-gates` scans `.` (conflict markers, derived docs), and the book `{{#include}}`s trycmd files from `tessera/crates/`. Together they take ~6 s. (An earlier version of this PR said *every* check was identical, after verifying only `workspace-test`. That was wrong, and it's corrected here and in the commit message.)

## Results — `workflow_dispatch` on this branch, same keys

| run | x86_64 | aarch64 | `tessera-deps` |
|---|---|---|---|
| cold (miss → build → save) | 50 m | 60 m | built (8.8 / 10.1 min) |
| warm (hit → import) | 42 m | 49 m | **not rebuilt** (0 build lines) |
| warm, composite-action version | **41 m** | **45 m** | **not rebuilt** |

Cache steps: **locate 23 s + restore 6–7 s + import 7–11 s** on a hit; **locate 23 s + export 5–6 s + save 6–7 s** on a miss.

**Reading the totals honestly.** Leg time across runs mostly measures *runner luck*: the cold x86 leg drew a runner ~35% faster across **every** derivation (deps 8.8 vs a 14.0 median, nextest 2.5 vs 4.6). The like-for-like evidence is within-run — the prefix is skipped and costs ~40 s instead of 8.8–14.7 min — and on aarch64, whose hardware is steadier, cold 60 → warm 49 (−11 min) matches the 10.1-min deps span on that runner. Against the post-#536 medians (x86 77–79, aarch64 59–61 min) the warm legs are well under.

# [PR 747](https://github.com/vig-os/tessera/pull/747) feat(io): add StreamWriter::push_table, a disk-staged streaming partition

Refs #713 (part 1 of 3)

ADR-0064 PR E, part 1: `StreamWriter::push_table`, a disk-staged streaming partition (ADR-0064 §5.1-§5.3, §6).
Part 2 adds the read-hold seam and the §8 barrier test; part 3 deprecates `table_job_streaming`. Both open after
this one merges.

## What changes

- `StreamWriter::push_table(name, spec, groups)` partitions at `BLOCK_ROWS` (`table::block_count`) and names and
  marks the leaves with PR D's `table::block_name` / `table::block_partition`. Names and the terminal leaf are known
  from `spec.rows` before the first row. At most `BLOCK_ROWS` rows it is the one bare-named block. Input off the
  `ROWS_PER_GROUP` grid is re-chunked to it, so the leaves don't depend on the input's chunking.
- Each block's row-groups are written as fragment records (`TableMultiBlockSink`'s format, now writable/readable
  one record at a time) to one file in the session's `staging/`. A complete block goes to a **free** worker (a
  free-worker condition on gate 1 of the credit window); the worker reads it back one row-group at a time and deletes
  it. The next block's file is created only after that hand-over. Each leaf is one staged job under the ADR-0026
  window. The last leaf is handed over once the input has ended.
- `StreamStats::{peak_staged_input_blocks, peak_staged_input_bytes}`: a block counts from the creation of its file
  (partial included; sizes updated per written row-group) until its deletion.
- `Error::StreamedTable` with `StreamedTableError::{TooManyRows, TooFewRows, OversizedGroup}` (`tessera-core`). On
  any error the terminal leaf is never handed over, so `finish` refuses the partial table (`Error::LogicalTable`);
  every staging file is deleted on every path (the one being filled by its guard, the others by their workers or
  when their jobs are dropped).
- `push_table_with_block_rows`: the partition-size test seam (`#[doc(hidden)]`), as
  `TableMultiBlockSink::with_block_rows`; the tests here use it, and so will #714.
- Rustdoc on every new public item covers the staging location and disk cost (up to `(W + 1) · BLOCK_ROWS` rows
  of staged input; page cache, RAM on tmpfs), ordering and errors, and points to #714 for the heap bound (no number
  yet). CHANGELOG and FEATURE-MATRIX updated.

## Tests (`cargo test -p tessera-core -p tessera-io -- --test-threads=4`: exit 0, 211 + 157 passed)

- `push_table_seals_the_multi_block_sink_manifest_for_every_worker_count`: for `W` = 1, 2, 4 (`W` = 2 fed 9999-row
  groups, off the grid), the canonical manifest (without `producer`, `timestamp`, `id`, `id_inputs`,
  `manifest_hash`, ADR-0064 §6) and `content_hash` equal `TableMultiBlockSink`'s, four leaves, nullable `ms`.
- Mutation runs (temporary edits to `dispatch`, run, reverted; not committed): leaf named
  `block_name(&name.to_uppercase(), ..)` → the comparison fails (`EVENTS/0000` vs `events/0000`, equal digests);
  marker set to `None` → the comparison fails on `spec.partition`, equal digests.
- `push_table_of_one_block_is_byte_identical_to_table_job_streaming`: 3 row-groups + 99 rows, fed in 9999-row groups,
  seal the same `.tsra` bytes as `table_job_streaming`.
- `a_wrong_row_count_is_a_typed_error_and_leaves_no_staging_file`: too many, too few, an oversized group; each its
  typed reason; the multi-block cases then fail to seal (`LogicalTable`); `staging/` is empty afterwards.
- Before this change all four fail (no `push_table`).

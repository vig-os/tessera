# [PR 724](https://github.com/vig-os/tessera/pull/724) test(io): fail the S3 tests when the s3-range-read check loses its endpoint

Closes #707

## Problem
The three S3 tests (`cloud::tests::s3_range_read_does_not_fetch_whole_archive`,
`cloud::tests::cohort_prune_before_fetch_skips_non_matching_product`, and the CLI's
`cloud_cli_inspect_and_verify_over_s3_url`) returned early, and nextest reported PASS, whenever `TESSERA_S3_ENDPOINT`
was unset. Inside `s3-range-read` that variable comes from a runtime `preCheck` export. If the export broke, the
check stayed green while testing nothing. Proof below: with the export removed, the check on dev passes 6/6.

## Design: a static "required" marker
- The check sets `TESSERA_S3_REQUIRED = "1"` as a **top-level derivation attribute**, not in `preCheck`. The endpoint
  has to be exported at runtime because the port is only known once the server is up. The marker is static, so
  breaking the endpoint export cannot take the marker down too, and an edit to `preCheck` can't silence the guard.
- Both test entry points decide through a pure function, `s3_endpoint(required, endpoint)`: `s3_store_or_skip` in
  tessera-io, plus a copy in `tessera-cli/tests/cloud.rs`. The rustdoc documents the contract as a table:

  | `TESSERA_S3_REQUIRED` | `TESSERA_S3_ENDPOINT` | outcome |
  |---|---|---|
  | unset | unset | skip (plain `cargo test` keeps working) |
  | unset or `1` | set | run against it |
  | `1` | unset | **panic**: the server was promised |
  | any | set but not UTF-8 | **panic**: set is never "unset" |
  | anything else (`true`, empty, …) | any | **panic**: a typo must not become a skip |

- Because it is pure, the contract is unit-tested without mutating the process environment. The tests are named so
  the check's `cloud` filter runs them next to the tests they guard (5 in tessera-io, 2 in tessera-cli).
- **Rejected alternative: asserting on nextest output** (grep for "skipping", or count PASS lines). That couples
  the check to log text and test counts, and goes stale when a test is added. The marker fails at the source,
  inside the test, with a message naming the cause.
- **Why two copies:** an integration test in tessera-cli can't reach tessera-io's `#[cfg(test)]` code. Sharing it
  would take new public API or a test-support crate, which is too much for ~25 lines. The CLI copy's rustdoc names
  the tessera-io function as the owner of the contract, and it has its own tests.

## Nit: `python3` for the free port is kept, deliberately
The issue suggested letting versitygw bind `:0` and reading the port back. With the pinned versitygw **1.3.1**, bound
on `127.0.0.1:0` it logs `bound on host 127.0.0.1 and port 0` / `http://127.0.0.1:0` (checked by running it). It
never reports the port it actually got. Reading that port back means matching the server's socket inode in
`/proc/net/tcp`. I prototyped this in pure bash and it works, but only on Linux, and `s3-range-read` lives in the
main `checks` set, which Darwin evaluates too. A port drawn at random in shell has no such dependency, but it could
collide with a port in use, which would turn a near-zero race into a real flake. The current pick is free when the
kernel hands it out, and the pick-then-bind window stays caught by the ownership check: if our server can't bind it
exits, and the bucket must appear in this build's own data dir. A flake comment records this.

## Proof (seat, x86_64, `nix build -L --cores 4 --max-jobs 1`)
"Export removed" means the single edit `export TESSERA_S3_ENDPOINT=…` → `TESSERA_S3_ENDPOINT=…` in `preCheck`. The
shell variable still feeds the readiness probe and CreateBucket, so the server comes up and only the tests lose it.

| tree | variant | exit | nextest |
|---|---|---|---|
| dev `41b62c3` (before) | export removed | **0** (green, vacuous) | 6/6 passed, the 3 S3 tests among them having tested nothing |
| this PR `ca89c72` | export removed | **1** (red) | 10 passed, 3 failed: the 3 S3 tests panic with `TESSERA_S3_REQUIRED=1 but TESSERA_S3_ENDPOINT is not set` |
| this PR `ca89c72` | normal | **0** | 13/13 passed |
| this PR `ca89c72` | normal, `--option sandbox false` | **0** | 13/13 passed; build dir `/nix/.rw-store/builds/…` (really unsandboxed), no versitygw left afterwards |

Note on the unsandboxed run: my first attempt used `--rebuild` and exited 1 with `may not be deterministic: output
… differs` after 13/13 passed. That is nix's bit-for-bit comparison of the two builds' `target.tar.zst`, not the
check. I deleted that output and rebuilt with `--option sandbox false` without `--rebuild`, giving exit 0 above.

Local, outside the check: `cargo nextest run -p tessera-io -p tessera-cli --features tessera-cli/cloud cloud` passes
13/13 with no marker (the S3 tests skip). With `TESSERA_S3_REQUIRED=1` and no endpoint, the same 3 S3 tests fail
(exit 100).

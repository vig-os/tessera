# [PR 942](https://github.com/vig-os/tessera/pull/942) feat!: derived blocks leave content_hash (ADR-0028 §4)

Closes #720. This is step 5 of the ADR-0066 implementation plan: the code now does what Accepted ADR-0028 §4 says.
`content_hash` covers the **primary** blocks only. Derived sidecar blocks leave it, and `manifest_hash` still commits
to every block (ADR-0066 rule 12).

## Design (as decided in the architect comment on #720)

- **`class` on the block ref.** A block ref gains an optional `"class": "derived"`. When the key is absent the block is
  primary, and the key is never written for a primary block.
  - Every reader refuses any other value, `"primary"` and `null` included: Rust (custom serde on the new
    `tessera_core::block::BlockClass`), `tessera-wasm` (through `tessera-core`) and the Python reference reader
    (`class` is an enum of `"derived"` in `reader.MANIFEST`).
- **One fold.** `content_hash` = `merkle_root` over the primary blocks, in manifest order. It is computed by the new
  `tessera_core::block::content_root`, which `ProductBuilder::seal` and `Manifest::recompute_content_hash` both call.
  Neither keeps a copy of the fold.
  - A block without a digest is still refused, whatever its class.
  - With derived blocks only, `content_hash` is the root of the empty set, the same as `empty_no_blocks`.
- **Hashes left alone.** `manifest_hash` (the seal over the stored JCS bytes) and `id` are unchanged in definition.
- **Streaming writer.** `WriteSession`'s running roots fold primary blocks only: the per-lane roots, the multi-lane
  refold, `recover` and the seal self-check. So its live root is still the `content_hash` the seal gives.
- **Out of scope:** `from`/`recipe`, the five-root topology (`derived_hash`/`schema_hash`/`metadata_hash`) and the
  #778 carriers.

## Writers that set the class

| writer | why derived |
|---|---|
| `tessera_io::chunk_index::chunk_index_block` (`<name>.cidx`) | A pure function of the block it indexes, rebuilt with `table_chunk_index` / `array_chunk_index`. Every `.cidx` path goes through it: `array_block_with_index`, `table_block_with_index`, `stream::{array,table}_job_indexed`, `multiblock`. The `class` key moved here from the sidecar's `spec` (where it did nothing) to the ref, so it has one place. `recipe` stays in the spec. |
| `tessera pyramid` (`nav::build_pyramid`), levels `BLOCK/1…` | Each level is a 2× max-downsample of the one below, so a pure function of level 0. Level 0 stays primary. |
| `tessera commit --add-block` (`version::load_block`, `rebuild_indexes`) | **Not a derived writer.** A derived block is derived *of the product that computed it*, so a copy lands **primary** whatever its source class (round 2: it used to keep the class, so a copied pyramid level added data under an unchanged `content_hash`). A derived block is never copied (round 3). When the source indexes the copied block, `commit` rebuilds `<name>.cidx` from the copied bytes with the writers' own `array_chunk_index` / `table_chunk_index` and lands it derived, byte-identical to a fresh build. A source's `.cidx` is bound to its block by name only (`indexes` records the name, not the digest), so its bytes are never trusted: a crafted index with min = max = 7 over data spanning -1024..3071 used to land derived beside its block, and `stats` served it as exact. Round 4 closes the copy path: `--add-block` **refuses to copy any chunk index**, by what the block is (kind `chunk_index`, or a spec with `indexes`; `BlockRef::is_chunk_index`), whatever its name (`.cidx` or `notes`) or class, so the only index a commit adds is one `rebuild_indexes` computes. It also verifies the source as `tessera verify` does before reading from it. Round 5: an index already in the parent is not inherited by a later block either (see **Dangling indexes**). |

No writer emits stats, projection or thumbnail blocks: there are no stats blocks (stats live in the `.cidx`), and
`tessera project` writes an image file, not a product. A user-supplied block is primary. No existing API needs an
explicit derived option, so none is added: the Python `Builder` has no sidecar API. Rust callers use
`BlockRef::derived()`.

## Readers that take aggregates from an index

An index is trusted only when it is the writer's: `block::trusted_chunk_index` accepts the `<name>.cidx` of kind
`chunk_index` that is **derived** and whose `indexes` names the block. Anything else, a primary look-alike included,
is never consulted, and the reader computes from the data, as for an unindexed block. Every lookup goes through it:
- `tessera stats` (`nav::stats_from_chunk_index`);
- `LogicalTableView::select_blocks_overlapping` pruning (`multiblock::block_stats`). `tessera-py` exposes no pruning:
  it calls only `block_names` and `column` (`LogicalTableView::column`), which read no index.

`tessera-wasm` and the Python reference reader serve no aggregates: they verify seals and read blocks, and never
read an index's statistics. SPEC §5d states the rule as **Trust**, with every condition `trusted_chunk_index`
enforces: the block named exactly `<name>.cidx`, of kind `chunk_index`, derived, with `indexes` equal to `<name>`.

## Dangling indexes (round 5)

A chunk index (`BlockRef::is_chunk_index`: kind `chunk_index`, or a spec with `indexes`) whose `indexes` doesn't name
another block of the same manifest is a structural defect, in the class of a repeated block name. Before this, an
`orphan.tsra` holding `base` and a derived `ct.cidx` (min = max = 7) but no `ct` verified, imported, and after
`commit --add-block ct=plain16.tsra:volume` `stats ct` served the lie as exact: nothing copied, nothing rebuilt.

- **Readers refuse it.** `Error::DanglingChunkIndex { index, indexes }` names the index and the missing block. It is
  raised by `block::check_block_refs` (unique names, then resolution), which `Manifest::verify` and `from_stored`
  run, so `Reader::open`, `verify`, `import`, `Repository::get_manifest`, the deep verify and `tessera-wasm` refuse it
  before any digest is looked up. The Python reference reader refuses it too (`dangling_chunk_indexes`).
- **Writers refuse to produce it:** `ProductBuilder::seal`, `pack`, `pack_streaming`, `Repository::put_manifest` and
  `Repository::commit`. So no version holding one is written, and the reviewer's attack stops at `import`; a
  repository that already holds such a version can't commit on it either, because the parent no longer reads.
- **`--remove-block`.** The cascade still takes only derived blocks, as round 4 set. A chunk index of the removed
  block that the cascade doesn't take (a primary `NAME.cidx`, or an index under another name, which only a hand-built
  product carries) would dangle, so the remove is **refused**, naming the index and `--remove-block <index>`.
  Refusal rather than cascading it: the cascade never deletes data someone supplied, and counting a primary block as
  derived was the round-4 nit; refusing keeps rule 1 without either.
- **The claim, corrected.** An index in a product built or committed by tessera comes only from a writer that
  computed it or from `rebuild_indexes`, and a dangling one is refused everywhere. A hand-built product can still
  carry a forged **derived** index **on its own block**: its seal holds and readers trust it. That is #943 (should
  verify recompute derived blocks, or stats label them writer-attested), deliberately left out of this PR. The round-4
  commit's message (4edcf38a, now c3b27a55, tree unchanged) is reworded to say exactly this.

## Removal cascade (`tessera commit --remove-block`)

`ProductBuilder::remove_block_with_derived` removes a block and its derived family (`block::derived_family`). It
uses the writers' naming rules, now shared: `block::cidx_name` (`tessera_io::chunk_index::cidx_name` delegates to
it) and `block::pyramid_level_name` (used by `build_pyramid`). The family is:
- `<name>.cidx`, when **derived**;
- for a pyramid's `<base>/0`, every **derived** `<base>/<n>` (n ≥ 1, in the writer's spelling) and its derived `.cidx`.

A primary block of one of those names (a `.cidx` or a level), and a partition leaf, are never touched. A primary
chunk index of the removed block would dangle, so that removal is refused (round 5, above). Removing level 0 used to leave the
downsamples as the only blocks, real data under the empty set's `content_hash`. The commit summary counts the cascade
and the rebuilt indexes: `blocks     +1 (+1 derived) -1 (+2 derived)`.

## Audit of the other paths that carry block refs

Only `--add-block` moves a block ref between products:
- `ProductBuilder::from_manifest`, `publish`, the ingest engine's metadata re-seal (`apply_spec_metadata`), and
  repository import, export, push and pull all stay within one product;
- the aux door adds no ref;
- collections reference whole products, not block refs;
- the py `Builder`, the ingest backends and blobs only create fresh primary blocks.

## Break

- **New products don't verify on older readers.** A product written with a `.cidx` or by `tessera pyramid` now has a
  different `content_hash` and `manifest_hash` than the same input gave before. A reader from before this change
  can't verify it: it reports `blocks[n].class` as a newer field and finds `content_hash` tampered.
- **Old products are unaffected.** A product sealed before this change still verifies unchanged: its refs carry no
  `class`, so its sidecars read as primary.
- **Rust API.** `tessera_core::block::BlockRef` gains the public field `class: BlockClass`, so struct literals must
  set it.
- **CHANGELOG.** There is an Unreleased entry under Changed.

21 cases on `recon_int16`, for 171 in all. All 150 existing cases are byte-identical (the file's `about` text

The Rust reader (`tests/seal_cases.rs`), the reference reader (`run.py`) and `tessera-wasm` reach every verdict.

It also checks a `class: "primary"` refusal and (round 5) a derived index without its block on whole archives, so
the refusal count is 15; the `reference-reader` flake check's literal moves from 14/14 to 15/15.

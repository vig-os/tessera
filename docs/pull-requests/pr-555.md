## The defect

On a **non-seekable input** — a pipe, a fifo, or `<(…)` process substitution — the sealed
`ingested_from` digest was **independent of the bytes**: one constant for every piped ingest,
whatever the data.

The batch path reads the input twice: once to decode, then again in `provenance::source_digest`,
which does its own `File::open`. On a pipe that second open hands back the already-drained
descriptor, so the digest was taken over **zero bytes**.

```
$ tessera ingest table <(zcat a.gz) a.tsra --name p --timestamp … --from csv --column id:i4 --column x:f8
$ tessera ingest table <(zcat b.gz) b.tsra --name p --timestamp … --from csv --column id:i4 --column x:f8

a: content blake3:a03198f6…  source_digest blake3:16287da8bcdcfa3a888ff3e9ab50a7fe747368a3feefe61ff0bb840218a1ed47
b: content blake3:92b304d6…  source_digest blake3:16287da8bcdcfa3a888ff3e9ab50a7fe747368a3feefe61ff0bb840218a1ed47
                                           ^ identical, for different data
```

A **wrong** digest is worse than a missing one here. `Source::content_hash` is optional, so recording
nothing would have been honest; instead the product asserted an integrity link back to a
source-of-record that corresponded to nothing. And it was invisible to everything that normally
catches this class: `content_hash` is correct (the decode saw the real bytes), the product verifies,
and `tessera ingest table` exits 0.

## The fix: hash while decoding

`tessera-core::hash::DigestingReader` is a `Read` that digests every byte it hands on, so a decoder
that reads its input once gets the source digest from the same pass. `StreamHasher` already existed
for "hash a block while copying it"; this is the adapter that lets a parser do the same without
knowing about hashing.

The digest then reaches the seal through `provenance::ingested_from_digest`, which already existed
for exactly this reason — the DICOM series backend uses it so a multi-GB series is read once.

### Why the MMR wrapper is not optional

This is the part that distinguishes a fix from a different bug. `source_digest` takes `merkle_root`
over the per-file digests **even for a single file**, and `merkle_root` of one leaf is a
domain-separated leaf hash rather than the digest itself. Hashing in flight and sealing the raw
content hash would have made the same bytes seal two different digests depending on which code path
read them — trading one wrong answer for another. `provenance::single_source_digest` applies the same
wrapper, and the piped-vs-file agreement test is precisely what holds it.

### Which lanes, and why not the others

| lane | in-flight digest | why |
| --- | --- | --- |
| CSV | **yes** | forward scan; reads a pipe happily, so it must |
| `.npy` | **yes** | `fs::read` of the whole file, so it reaches a pipe too — the same defect, found by asking what the mirror case was rather than fixing only the lane the report named |
| Parquet | no | seeks to a footer index; random-access reads cannot be hashed in order, and a pipe never reaches it |
| Arrow IPC | no | same — the IPC *file* footer requires seeking |
| `.npz` | no | zip central directory requires seeking |

The exempt lanes keep the second pass, which is always over a real file for them, and `None` says so
in the type rather than leaving it to be inferred.

## Tests, TDD

Both were written first and **proven failing** on the parent commit.

| test | before | after |
| --- | --- | --- |
| `two_different_piped_inputs_seal_different_source_digests` | both CSVs sealed `blake3:16287da8…` | `e5bca4ad…` vs `7294f75a…` |
| `a_piped_input_and_a_file_of_the_same_bytes_agree_on_the_source_digest` | file `e5bca4ad…` vs pipe `16287da8…` | identical |
| `two_different_piped_npy_inputs_seal_different_source_digests` | the array lane, same constant | distinct |

The pipe fixture is an **already-open pipe named via `/dev/fd/N`**, which is the shape bash hands a
child for `<(…)`. Deliberately not a fifo from `mkfifo`: opening a fifo for reading *blocks* until a
writer appears, so the second open would hang the test rather than reproduce the defect. Re-opening
`/dev/fd/N` duplicates the existing open file description, so the second reader sees the drained
stream — which is the bug.

`DigestingReader` also has unit tests for the property that makes it safe under a parser: the digest
must not depend on **how** the consumer reads. One byte at a time and a 1 MiB buffer give the same
answer, so a source digest cannot vary with a reader's buffering.

## No golden moves, and why

The file-input digest is **unchanged** — `blake3:e5bca4ad…` both before and after. The fix supplies a
right answer where there was a wrong one and leaves the already-right answer alone. 673 workspace
tests pass, the conformance corpus included, and `seal_generic_product` injects the in-flight digest
so the corpus exercises the same path a real ingest does rather than a parallel one.

Confirmed through the CLI as well, which is where the defect was first observed:

```
pipe a:  blake3:e5bca4ad…
pipe b:  blake3:7294f75a…   (differs)
file a:  blake3:e5bca4ad…   (agrees with pipe a)
```

# [PR 866](https://github.com/vig-os/tessera/pull/866) fix(ci): put the cargo test checks' TMPDIR on a RAM fs

Closes #793

## Cause

This was never a hang. The tests are fsync-bound on a write-loaded volume. Each `WriteSession` commit fsyncs the fragment, its directory and the journal (#695). Counted with strace on tmpfs, `stream::tests::content_hash_is_identical_across_workers_and_windows` issues 1,536 fsyncs and `session_leaf_memory` issues 999. On a ksb ARC pod, Nix runs with `sandbox = false`, so the build's `TMPDIR` sits on the pod's one `/nix` volume, which every concurrent build writes to (as in #688).

Pre-fix evidence, from ksb job `tessera-793-r1-pre3` (`tessera/bench/ksb/793-io-hang`, `#default`, exit 0). Times are content_hash / session_leaf_memory:

| run | result |
|---|---|
| A: tmpfs, 1 process | 0.97 s / 0.07 s |
| B1: tmpfs, 32 processes on `taskset -c 0-1` | 24.1 s / ~1 s. A scheduling deadlock is ruled out |
| B2: B1 plus `ulimit -u 256` | rc=101, a panic in 0.04 s, with EAGAIN in 32/32 logs. A spawn failure panics; it never turns into a wait |
| C: disk scratch, idle | 1.8 s / 92.7 s |
| D: disk scratch plus 2 buffered `dd` writers | **both rc=124 at the 1,800 s cap** (2,028 s / 1,998 s). The stuck thread is in `__flush_workqueue` |
| E: disk scratch, 32 processes | 235 s each |

On the seat's ext4, a single `dd` writer pushes fsync p99 to 26 s, and content_hash goes from 5.6 s to 53.4 s with the committer waiting in `jbd2_log_wait_commit`. In CI (the issue's table), the same two tests were still running after more than 3,240 s and 840 s, and the x86_64 leg timed out at 2 h.

## Fix (owner decision 2026-11-11, #688 precedent)

The flake checks that run tessera's tests through cargo get `TMPDIR` on a RAM fs (`withRamTmpdir` in `flake.nix`, Linux only): `workspace-test`, `workspace-doctest`, `sql-tests`, `s3-range-read`, `seal-profile-determinism`, `ingest-gate-a`, `-sql`, `-workspace` and `-reduced`.

- The temp dir is a `mktemp -d` under `/dev/shm`. Before any test runs, the check fails if that dir is not on tmpfs or ramfs, or if it has less than 256 MiB free (twice the largest measured peak, rounded up). The filesystem assertion runs again at the end of `preBuild` and of `preCheck`.
- The dir is removed from both `exitHooks` and `failureHooks`, and the removal runs last, so a failing check doesn't leak into the pod's shared 1 Gi `/dev/shm`.
- A protected check adds its own exit or failure hooks through `ram_tmpdir_add_hooks`, which puts the removal back at the end straight away. That way s3-range-read's `dump_versitygw_log` still reads its log even when versitygw fails to start partway through `preCheck`. A protected check that writes `exitHooks+=` or `failureHooks+=` directly fails evaluation. The helper is sourced on every platform; only Linux moves `TMPDIR`.
- An **evaluation guard**: any check that runs `cargo test`, `nextest run`, `cargo run`, `cargo bench` or `llvm-cov` (or the `t`/`r` aliases) in a build or check shell field without the helper fails `nix flake check` at evaluation. The match is token-based (flags, `+toolchain` and `\` continuations don't hide a command).
- A **`ram-tmpdir-guard` check** tests the helper itself: it lands on a RAM fs, the filesystem assertion rejects `/proc`, the space check rejects a floor the filesystem can't meet, the removal stays last in both hook arrays right after a check adds its own hooks (with no reordering step in between, which is the early-failure path), and the dir is actually deleted.
- **Not covered:** Darwin, which has no `/dev/shm` and whose build sandbox can't mount one. Also not covered are the checks that run tessera through Python or the CLI rather than cargo; their fsync counts are not measured yet, tracked in #865. Group commit (one journal fsync per batch) is #798.

### Footprint: what `/dev/shm` has to hold

ksb job `tessera-793-r2-footprint3` (`#footprint` app, exit 0). Every protected check was rebuilt with `TMPDIR` on a private tmpfs, peak bytes in use were sampled with statvfs every ~1 ms, and tests ran at CI's 4-thread budget:

| check | peak tmp |
|---|---|
| workspace-test | 106.5 MiB |
| workspace-doctest | 41.1 MiB |
| ingest-gate-a-reduced | 31.8 MiB |
| s3-range-read | 12.3 MiB |
| ingest-gate-a-workspace | 9.1 MiB |
| the others | ≤ 5 MiB |

The compile writes nothing to `TMPDIR`; all of it is test data. With `max-jobs 2`, the worst concurrent pair is about 148 MiB.

**Runner prerequisite:** exo-pet/exo-fleet#1113 mounts a 1 Gi memory `emptyDir` at `/dev/shm` in the ksb ARC runner pods. It was merged and deployed 2026-11-11 via exo-pet/exo-fleet#1114. That is about 7× the worst pair. A memory-backed `/dev/shm` counts against the pod's memory limit, so the protected checks' temp data, about 150 MiB at the worst concurrent pair, now sits in RAM instead of on disk. That is worth knowing on runners with an OOM history (#495). The `ram-tmpdir-guard` and per-check `check TMPDIR:` log lines print the runner's `/dev/shm` size and free space.

## Proof (local, exit codes)

- `nix build .#checks.x86_64-linux.ram-tmpdir-guard`: rc=0.
- Mutants, each of which must fail and does (rc=1):
  - `assert_ram_tmpdir` accepts any fs: "the guard is vacuous".
  - The space floor never trips: "the space check is vacuous".
  - The removal registered in `exitHooks` only (the leak a review caught before this PR): "failureHooks are (dump_check_log), the removal must run last".
  - The removal never registered.
  - `ram_tmpdir_add_hooks` appends without reordering (the early-failure leak a second review reproduced): "exitHooks are (remove_ram_tmpdir stop_check_server), the removal must run last".
  - s3-range-read using a bare `failureHooks+=`: evaluation fails with "a withRamTmpdir check adds to exitHooks/failureHooks directly".
  - `workspace-test` unwrapped: evaluation fails with "these checks run tessera's tests with TMPDIR on disk: workspace-test".
- Guard regex probe: 15 variants that run tests (`cargo -q test`, `cargo +nightly test`, `cargo nextest  run`, `cargo \⏎ test`, `cargo t`, `cargo r`, `cargo bench`, …) all match. 12 that don't (`cargo nextest --version`, clippy, build, fmt, `cargo runner`, `cargo test-support`, …) don't match. Without the flag group, the first two are missed.
- `nix eval .#checks.x86_64-linux` and `.#checks.aarch64-darwin`: all 32 (Linux) and 30 (Darwin) checks evaluate, matching `.github/nix-flake-checks.txt` (`count: 32`).

# [PR 660](https://github.com/vig-os/tessera/pull/660) fix(cli)!: verify-sig no longer trusts ./.tessera/trust/ implicitly

## Description

Closes #576 (P0 security). `verify-sig` without `--pubkey` trusted every key in `./.tessera/trust/` relative to the
current directory, so anyone who could write to the directory a verifier ran in could plant a key and have a forged
file accepted, along with the signer it claimed. This PR implements the triage decision of 2026-10-25.

**Decision**

- The default trust set is the user store only (`$XDG_CONFIG_HOME/tessera/trust` or `$HOME/.config/tessera/trust`).
  Only an **absolute** base counts: an empty or relative `XDG_CONFIG_HOME` is ignored (XDG spec), and an empty or
  relative `HOME` means no user store. Before this, `XDG_CONFIG_HOME=` made `./tessera/trust` the "user store".
- A repo store counts only when named: `--trust-dir <path>` (repeatable, may be relative: typed per run) or
  `TESSERA_TRUST_DIR` (PATH-style, `:`-separated; `;` on Windows), whose entries must be **absolute**. The variable
  is set once and applies to every later run, so `TESSERA_TRUST_DIR=.tessera/trust` would trust the planted key
  inside every unpacked archive. A relative entry is an error naming it, never a silent skip. A flag replaces the
  env var. Empty entries are ignored, a named store that is not a directory is an error, and named stores are
  canonicalized for reporting.
- No git-root discovery, no `--strict` flag.
- `trust add/list/remove --repo` still manage `./.tessera/trust/` and say on stderr that `--trust-dir .tessera/trust`
  is needed (or `TESSERA_TRUST_DIR=$PWD/.tessera/trust`, absolute, if meant). `trust list` prints each store with its
  keys; without `--repo` it shows what `verify-sig` would consult. `trust remove` acts on the user store only, or
  the repo store with `--repo` (it used to search both).
- On success, stderr shows `accepted key_id <hex> via trust store <abs path> (<origin>)` or
  `accepted key_id <hex> via --pubkey <file>`. `--pubkey` and `--trust-dir` are mutually exclusive.
- Docs: a dated amendment to ADR-0037 (status unchanged: Proposed), the index row, the book's signing chapter (resolution
  order, and that automated verifiers pin `--pubkey` + `--require-signer`), and FEATURE-MATRIX.

## Changes Made

- `tessera-cli/src/trust.rs`: `TrustStore`/`StoreOrigin`, `resolve_trust_stores` (pure), `TrustStore::user_from`
  (absolute-only), per-store `list`, single-store `remove`, `verify_sig` reports the accepting key + store on a
  separate log stream, and only on success.
- `tessera-cli/src/main.rs`: `verify-sig --trust-dir`, `trust list --repo/--trust-dir`, `trust remove --repo`, and the
  `--repo` note.
- Tests that silently relied on the cwd store, now passing it explicitly: `tests/sign.rs`
  (`foreign_resign_leaves_integrity_intact_but_untrusted`), `tests/lifecycle.rs` (`persona_lifecycle_e2e`, which now
  also asserts that the unnamed repo store is refused), and `tests/cmd/persona_signing.trycmd` (adds the refusal step
  and the pinned `--pubkey --require-signer` step).

## Evidence

- The issue's repro as a test: `tests/trust_store.rs::a_key_planted_in_the_cwd_store_is_not_trusted`. Run once
  against the unfixed code:
  `assertion left == right failed: a cwd-relative store must never widen trust implicitly — left: Some(0), right: Some(1)`
  (the planted key was accepted). It passes after the fix.
- Review round 2: `a_relative_tessera_trust_dir_entry_is_refused` (planted key present). Before the fix:
  `TESSERA_TRUST_DIR=".tessera/trust" must be refused — left: Some(0), right: Some(1)` (accepted). Passes after.
  `tessera_trust_dir_is_honoured_and_reported` now uses absolute entries only.
- Regression from review: `an_empty_or_relative_config_home_never_makes_a_cwd_user_store`. With the absolute-base
  filter disabled it fails with `XDG_CONFIG_HOME="" HOME="" left: Some(0) right: Some(1)`. It passes with the filter.
- Acceptance tests in `tests/trust_store.rs`: `--trust-dir` accepts and is reported, `TESSERA_TRUST_DIR` is honoured
  and a flag overrides it, the user store is reported, `--pubkey` is reported as such and ignores the env var, a
  `--pubkey`/`--trust-dir` conflict exits 2, the `--repo` notes are printed, and a missing named store is an error.
  Unit tests cover the resolution order, the empty env entries and the absolute-only user store.
- `CARGO_BUILD_JOBS=4 cargo test -p tessera-cli --bins --tests --no-fail-fast`: all suites pass (106 unit, cli 2,
  lifecycle 1, sign 3, trust_store 9, blob 1, migrate 1). `cargo clippy -p tessera-cli --all-targets -D warnings`
  is clean.

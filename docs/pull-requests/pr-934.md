# [PR 934](https://github.com/vig-os/tessera/pull/934) feat(schema): product schemas declare 64-bit string encodings and value ranges

Step 1 of the ADR-0066 implementation plan (epic #897, rule 7): product schemas say how their numbers are encoded and what range they may take, instead of ingest code deciding it. The ±(2^53−1) bound stays a format invariant (SPEC §1); a schema cannot widen it.

## The rules (SPEC §5 "Field rules"; ADR-0020 and ADR-0060 amendments of 2026-11-19)
A metadata `FieldSpec` gains three optional keys. Each is `skip_serializing_if`-absent when unset, so a schema without them keeps its bytes.
- **`"encoding": "string"`** is required on `int64`/`uint64` and refused on any other dtype. Values are then canonical decimal strings (`-?(0|[1-9][0-9]*)`, no `-0`) within the dtype's range. The rule follows the type, never the magnitude.
- **`minimum` / `maximum`** are inclusive bounds on numeric dtypes only, within ±(2^53−1). They apply to a number or to each element of a non-empty array. Integers are compared exactly: `"9007199254740993"` is above a maximum of `9007199254740991`.
- **Refused at definition** (`Error::SchemaField`): a bare 64-bit field, an unknown dtype, a misplaced encoding or range, an empty range, a `default` the field's own rules refuse, and a repeated field id.

## Where the rules are checked
- **At every seal.** `ProductBuilder::seal` runs `check_definition` and `check_metadata` against the embedded or built-in schema, so every writer is held to it: Rust, the CLI, Python's `Builder`, ingest and `WriteSession`. A value is refused as `metadata.<id>` (`Error::FieldValue`). Sealing also refuses an embedded schema this build can't read (a newer rule, or the array form), as ADR-0060 §2.2 already required for a re-seal.
- **At validate.** `ProductSchema::validate` (and so `tessera schema` and the ingest engine) runs both checks. `verify` does not: the rules are part of the schema's contract, not of the seal.
- **At the doors that know the source**, which check first and name it:
  - DICOM, by tag and text: `dicom: (0018,0060) KVP = "5000": field 'kvp' of schema 'recon': 5000 is above its maximum 1000`.
  - The ingest spec, by key: `product[1].metadata.kvp: …`.
  - The CLI, by flag: `--set kvp: …`, `--meta kvp: …`.
- **DICOM number handling now comes from the schema.** The curated tags are a mapping table only; each value's spelling comes from its field. A string-encoded field gets exact decimal digits from the element's text, so a 64-bit `UV`/`SV` never passes through a double. `the_dicom_number_rules_follow_the_schema` swaps the schema and the behaviour follows: the same `UV` element is refused under built-in `recon` and sealed as `"1730000000000000000"` under a string-encoded `uint64` `kvp`. New API: `read_object_with` / `to_recon_product_with`.
- **One behaviour change in DICOM.** A curated numeric tag with non-empty text that isn't numbers is now refused by tag. It used to be dropped silently. An empty (type 2) tag is still left out.

## Built-in schemas
- `recon` 1.1 ranges `kvp` to 0–1000 kV, wide enough for every medical scanner, so only a physically impossible value is refused.
- `slice_thickness` has `minimum: 0` (mm) and no maximum. DICOM sets no upper bound on SliceThickness, and a CT localizer records its scan length there: GE Discovery MI scouts read 1000.636353 and 1300.8 mm (round 2; a negative thickness is the only impossible value).
- `sim` 1.1 declares `seed` a string-encoded `int64`.
- No other built-in field is 64-bit or ranged; the digest fixture shows that only `recon` and `sim` moved.

## Readers agree
- **Shared vectors.** `corpus/schema-cases.json` has 49 cases (`ok` / `schema` / `value`). `tessera-core/tests/schema_cases.rs` checks Rust and `run.py` checks the reference reader's new `schema_verdict` against the same file.
- **Corpus products.** `run.py` also checks each of the 6 corpus products that embed a schema against its own schema.
- **Flake guard.** The `reference-reader` flake check guards both counts against a vacuous pass.
- **Review fix.** Review found that a repeated field id split the readers (Rust takes the first match, Python the last). A repeated id is now refused on both sides, with a case for it.

## Integration note: the ADR-0065 bridge drafts
The #801 consumer drafts declare 14 bare 64-bit fields: `n_singles`, `seed`, `run_id`, `event_id_offset`, …. They still parse. Sealing or validating against them is refused until each field declares `"encoding": "string"`. `the_801_drafts_name_their_bare_64_bit_fields` lists them.

## Round 2 (review fixes)
- **Blocker: `slice_thickness` lost its maximum.** The 1000 mm cap refused real CT scouts (a localizer records its scan length in SliceThickness; this project's GE Discovery MI scouts read 1000.636353 and 1300.8 mm). `minimum: 0` stays and `kvp` keeps 0–1000 kV. `a_scout_slice_thickness_past_a_metre_ingests` builds a synthetic DICOM (no patient data) with both values and seals them.
- **Re-seal keeps the embedded schema's rules.** SPEC §5 and the ADR-0060 amendment say so, and `commit_set_keeps_the_rules_of_the_embedded_schema` pins it: a product embedding `recon` 1.0 (no ranges) takes `commit --set kvp=5000`, and the new version still embeds `recon` 1.0.
- **dtype is not type-checked, and the cases say so.** `corpus/schema-cases.json` adds `int32-holds-a-fraction` (`1.5` → `ok`), and SPEC §5 documents it. Whether to check it is a separate follow-up.
- **CHANGELOG** `## Unreleased` gains the four #895 entries: the `FieldSpec` struct-literal break, `read_object_with` / `to_recon_product_with`, bare 64-bit fields refused at seal, and non-numeric curated DICOM tags refused.

# [PR 481](https://github.com/vig-os/tessera/pull/481) build(deps): pin vortex to a patched fork for the #468 and #472 determinism fixes

Stacked on #474 (which adds the test this PR flips). Targeting #474's branch rather than `dev` so the
diff is only this change; GitHub retargets when #474 merges. Stacked PRs get CI now thanks to #473.

## Why

vortex 0.75.0 has two defects that are **the same underlying bug class**: a write-time statistic
computation leaking into the serialised bytes, so a sealed `content_hash` stops being a function of
the data alone.

| | what leaks | axis | effect |
|---|---|---|---|
| **#468** | the `debug_assertions` `is_sorted` assert calls `cache_is_sorted`, which *sets* `Stat::IsSorted` on the patch indices | build profile | debug wrote 24 bytes more than release |
| **#472** | `sum_float_all` skips NaN, so `+inf` and `-inf` meet and evaluate `inf + -inf`; `Stat::Sum` is persisted | architecture | x86_64 `0xfff8…` vs aarch64 `0x7ff8…` |

Both fixed on a fork of the `0.75.0` tag, pinned here by **full commit SHA** (never a branch name — a
branch would let pinned content move under an unchanged-looking lockfile). #480 tracks removal.

## Two requirements that fail silently

Worth reading before reviewing, because each one produces a confident, meaningless "nothing changed":

1. **All 27 vortex crates must be patched together.** Patching `vortex-array` alone leaves its
   siblings resolving from crates.io → two copies of `vortex-proto`/`vortex-buffer` and ~1000 type
   errors.
2. **The `0.75.0` tag ships placeholder version `0.1.0`** (the real version is injected at publish).
   Without a version-setting commit on the fork branch, cargo prints `patch ... was not used in the
   crate graph` and quietly keeps using crates.io.

So the pin was verified **positively**, not by the absence of a warning: on x86_64 the sealed float
bytes no longer contain `fff8000000000000`, now contain `7ff8000000000000`, and became **byte-identical
to what unpatched aarch64 produced**.

## #474's known-limitation test, flipped

`known_limitation_468_*` asserted the bug was *still present*, so it fails once fixed — by design.
It becomes `full_span_int_container_bytes_are_build_config_independent`, with **one** expected length
per shape and **no `cfg!(debug_assertions)` branch**. That absence is the assertion: `flake.nix` runs
it under both `cargo test` and `cargo test --release`, so a re-divergence fails in exactly one line.

Measured both profiles on the pinned fork before rewriting the expectations, as requested:

| shape | unpatched debug | unpatched release | **pinned (both)** |
|---|---|---|---|
| bare `[i64::MIN, 0, i64::MAX]` | 2796 | 2772 | **2772** |
| same via `table::encode` | 2940 | 2916 | **2916** |
| control `[i64::MIN, i64::MAX]` | 2444 | 2444 | 2444 |

Both profiles agree on the former **release** numbers — the debug build was the one carrying the extra
24 bytes of cached statistic, which is the expected direction.

## Gate B: every line explained

458 insertions against 458 deletions across 8 snapshots — perfectly balanced. **Every** changed line
is identical apart from gaining the `(https://github.com/gerchowl/vortex?rev=…)` source tag, verified
by re-comparing with that tag stripped:

```
arrow-array.txt       OK  (57 lines gained only the git source tag)
arrow-buffer.txt      OK  (100)        arrow-schema.txt   OK  (149)
pco.txt               OK  (7)          vortex-array.txt   OK  (50)
vortex-btrblocks.txt  OK  (4)          vortex-buffer.txt  OK  (90)
vortex-file.txt       OK  (1)
blake3.txt / zarrs.txt / zstd.txt      unchanged
VERDICT: source annotation ONLY — no feature changed
```

No seal-path crate gains or loses a feature, so no codec resolves differently.

## Verification

| check | result |
|---|---|
| crane vendoring of the git dep | **hermetic, no `outputHashes` needed** — verified by building `checks.x86_64-linux.feature-snapshots`, which vendored `cargo-git-https-github.com-gerchowl-vortex` and reached the Gate B diff |
| `gen_corpus` vs committed `corpus/corpus.json` | **byte-identical — no golden moved on this branch** (the ingest corpus is not here; its float fixture does move, see the comment below) |
| `gen_corpus` dev vs release | **identical** (not guaranteed before the fix) |
| conformance tests | 3/3 pass |
| flipped #468 guard, both profiles | pass |
| `cargo deny check sources` | `sources ok` |
| `DECODE_PATH_CRATES` locked versions | all 10 unchanged → the `ingest_decoder` digest **cannot** move |

**cargo-deny tightened rather than left permissive:** `unknown-git` goes from `allow` to `deny`, with
`allow-git` naming exactly the pinned repository. A blanket allow would let a future stray git
dependency in unnoticed, which is precisely the review signal a fork pin should raise.

## Upstream — the exit path

Both defects are filed and fixed upstream, so this pin has a visible end:

| defect | upstream issue | upstream PR |
|---|---|---|
| #468 side-effecting `is_sorted` assert | vortex-data/vortex#10119 | vortex-data/vortex#10121 |
| #472 platform-dependent NaN `Sum` | vortex-data/vortex#10120 | vortex-data/vortex#10122 |

Both were **rebased onto vortex's `develop`**, not the `0.75.0` tag: 23 commits had touched those files
since, including an AggregateVTable rework and a new `sum_v2` that finalises floats through its own
path, so #10122 fixes two sites there. **Both defects were re-verified as still present on `develop`
before filing.** The tessera pin stays on the `0.75.0`-based fork branch and is unaffected by that
rebase.

#480 tracks removing the pin, with the checklist.

## Notes for reviewers

- Crane's vendoring emits `cp: cannot stat 'README.md'` per vortex crate. Cosmetic: the workspace
  `include` key lists a per-crate README that does not exist in the git checkout. No compiled input is
  affected, and `cargo tree` over the vendored deps works.
- `parquet` is absent from this branch's lockfile (the ingest lane arrives with #460), so its version
  is trivially unchanged here. tsra-386 is regenerating the **ingest** corpus under both profiles on
  this branch — expected movement only in the patch-producing int and NaN-sum float fixtures.
- The fork branch is `gerchowl/vortex:tessera/0.75.0-patched`: `0.75.0` + the two signed fixes + one
  non-upstream version commit. It is **branch-protected** (locked, no force-push, no deletion,
  `enforce_admins`) so the pinned commit cannot be GC'd out from under a fresh build.

Refs #468, #472, #474, #480

### Scope correction on "no golden moved", plus the ingest-lane verification

**Clarifying my own claim before it misleads anyone.** The table above says "no golden moved", and that
is accurate *for this branch* — `corpus/corpus.json`, the sealed corpus, is byte-identical. It is **not**
true of the ingest corpus, which is not on this branch. One ingest golden does move, by design.

tsra-386 regenerated `ingest-corpus.json` under both profiles against this pin, on a deliberately fresh
target dir:

```
PROFILE-STABLE under the pin: dev == release        <- the #468 fix, confirmed on the ingest lane

ingest_parquet_floats     2ee5bf4d1b33 -> 33b065510f5e   <== the ONLY content_hash that moved
every other fixture (13)                unchanged
ingest_decoder triples that changed:    NONE
manifest_hash moved:                    only ingest_parquet_floats
```

Two things make that the *right* movement rather than a surprise:

- `33b065510f5e…` is **exactly the value aarch64 was already producing** before the pin — it was
  predicted in advance from #460's failing aarch64 log. So this is x86 coming into agreement with ARM,
  not a new value appearing.
- `ingest_parquet_scalars` not moving is also correct: #460 narrowed it to ±(2^53+1), profile-stable by
  construction, so the #468 shape now lives only in the flipped test on this branch.

The regenerated ingest corpus is **not** carried here — this branch has no ingest corpus to update. It
belongs on #460/#461 after this merges.

### `ingest_decoder` confirmed empirically, not just by code reading

My claim above was from reading `DECODE_PATH_CRATES` and comparing locked versions. tsra-386 confirmed
it end to end: every `ingest_decoder` triple is byte-identical
(`{arrow-rs/parquet, =58.3.0, blake3:606b736dd205…}`), and independently, `manifest_hash` moved for
*only* the one fixture whose content moved — had the decoder digest shifted, every fixture's
`manifest_hash` would have moved with it.

### Two traps in reusing this branch's manifests

Worth recording for anyone combining this with #460: **this branch's `Cargo.lock` has no `parquet`, and
its `Cargo.toml` has no `arrow-array` in `workspace.dependencies`** — both arrive with #460. Taking
either file wholesale onto the ingest branch would *remove* the ingest lane's dependencies while
appearing to test it. The correct manoeuvre is to keep the ingest branch's manifest and lockfile and
append only the `[patch.crates-io]` block, letting cargo resolve. Done that way, `vortex-array` moves to
the git rev and `parquet` stays at `58.3.0` from the registry — so the pin does not perturb parquet,
confirmed rather than assumed.

### A weakness this manoeuvre makes reachable

Filed as the second finding on #477: `lock_version` in `tessera-ingest/build.rs` parses only
`version = "…"` and ignores `source`, so a **same-version git pin of a decode-path crate** would be
invisible to the sealed `ingest_decoder` digest. It does not bite here — vortex is the encoder and is
correctly absent from `DECODE_PATH_CRATES` — but the pattern this PR establishes makes it reachable:
forking `parquet` at `58.3.0` to fix a decode bug would leave every product claiming the unpatched
decoder. This is the same phenomenon as the Gate B source-tag churn, seen from the other side: a git
source changes the *provenance* without changing the version string.

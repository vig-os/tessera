# [PR 990](https://github.com/vig-os/tessera/pull/990) fix(io): lineage names map to ref files injectively

Closes #975

## The bug

A repository named a lineage's ref file by replacing `:`, `/` and `\` with `_`. So `a:b` and `a_b` shared
`refs/a_b`. A commit on one replaced the other's tip; since #946 it was refused with `RefMoved` against the other's
tip.

## Decision: encode, don't restrict

A lineage is a product `id` (ADR-0036 §4, model A), and every id tessera writes is `blake3:<64 hex>`: it contains
`:`. A lineage alphabet that refuses `:` would refuse every real lineage. So the name is **percent-encoded** instead.

- Each UTF-8 byte outside `a-z`, `0-9`, `-` and `_` is written `%xx`, in lower-case hex. Examples: `blake3:3f…` →
  `blake3%3a3f…`, `a:b` → `a%3ab`, `a_b` → `a_b`.
- `%` is itself encoded, so the mapping is injective and reversible.
- Upper-case letters and `.` are encoded too. That keeps it injective on case-insensitive file systems (macOS is a
  release target), and no name can be `.`, `..` or hidden.
- **No ref file name holds `:`.** The output alphabet is `a-z`, `0-9`, `-`, `_` and `%`, and `%xx` is the only
  escape, so `:` is always `%3a`. No lineage, `pin:x` included, maps to a name holding `:` or starting with `pin:`.
  ADR-0067 (#947, PR #988) reserves `refs/pin:<name>` on that basis.
- An empty name, or one whose encoding exceeds 249 bytes, is refused with the typed `Error::InvalidLineage`, before
  the writer lock is taken. A product id needs 73 bytes.

## Layout marker; old repositories refused, not migrated

- A repository now holds a `layout` marker, `tessera-repository 1`, which `init` writes. An empty repository without
  one gets it on its first write. This is the first repository layout version; ADR-0067 bumps it when it moves refs
  into typed, namespaced records.
- A repository with refs or log caches and no marker was named the old way. It is refused by `open`, by `init` and by
  every write under the writer lock, and is never read with the new naming. A marker of any other version is refused
  the same way.
- The refusal is `Error::UnsupportedRepositoryLayout { root, found, required }`. Its message names the layout found
  and the layout required, and says to create a new repository and import the source products again.
- **No migration verb.** The owner ruled on 2026-11-26 that the alpha carries no backwards-compatibility baggage, as
  ADR-0066 rule 10 already does for products. Round 1's `tessera migrate-refs` is removed along with its code, tests,
  docs and CHANGELOG lines. The branch is one commit, so it never reaches `dev`'s history.

## Tests

- `distinct_lineages_keep_independent_tips` was written first. Lineages `a:b a_b a/b a\b Ab ab a%3ab a.b` each get two
  commits, and their tips and logs stay independent. On origin/dev it fails with
  `RefMoved { lineage: "a_b", expected: None, found: Some("blake3:f801…") }` (test exit 101).
- `no_lineage_maps_to_a_file_name_holding_a_colon` covers `pin:x`, `a:b`, `%3A`, `..`, Unicode names and every
  one-character name below U+0800.
- `lineage_file_names_are_percent_encoded_and_bounded`.
- Refusal: `a_repository_laid_out_before_975_is_refused` checks `open`, `init`, and `commit`/`forget`/`gc` on a handle
  opened earlier. It confirms nothing is written, and that a lone log cache also triggers the refusal. In the CLI,
  `a_pre_975_repository_is_refused` runs a real `import` laid out the old way, then `log`, `commit`, `import`, `init`,
  `forget` and `gc`.
- `an_unmarked_empty_repository_is_marked_on_its_first_write` also covers an unknown marker version.

## Docs

- ADR-0036 has a dated amendment (2026-11-25): the layout marker is version 1, ADR-0067 bumps it, and there is no
  migration.
- The book's versioning chapter has a "Lineage names and ref files" section.
- CHANGELOG: Fixed, and Changed (old repositories and invalid names are refused).

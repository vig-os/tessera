## Known limit: reduced hermeticity on ksb

The ksb ARC pods run Nix with `sandbox = false`, delivered with the rest of the pod's Nix config through the `NIX_CONFIG` env var. A check on the x86_64 leg is therefore not isolated from the pod: it shares the pod's network namespace, its filesystem outside the store, and every other build running there. The owner accepted this for now (#688, 2026-10-29); the move back to sandboxed Nix on ksb is **exo-pet/exo-fleet#1081**. What keeps the gate honest:
- **Loopback checks are port- and dir-independent.** The registry checks (`loopbackRegistry` in `flake.nix`) bind port 0, keep their blobs in memory, put config and log in a private `$TMPDIR` dir, wait for readiness with a bound, and kill the server on exit. `s3-range-read` (#702) has the same shape: versitygw on a kernel-picked port, private `$TMPDIR` dirs, a bounded readiness wait, and exit hooks that stop it.
- **aarch64 stays hermetic.** That leg is GitHub-hosted with the sandbox on, so cross-arch determinism is still checked by a hermetic build on one side. The "Check the runner's Nix" step fails any GitHub-hosted leg whose sandbox is not `true`, so this is asserted on every run.
- **Documented where people look:** a KNOWN LIMIT comment at the x86_64 matrix entry in `nix-check.yml`, and a "Known limit (#688)" note on the cross-arch determinism row of `tessera/docs/FEATURE-MATRIX.md`. Both point to exo-fleet#1081.

Gotcha: a job-level `env: NIX_CONFIG: …` silently replaces the pod's whole Nix config (a probe then reported `sandbox = true`, `cores = 0`). No workflow in this repo sets it.

## Fork PRs can't schedule onto ksb

Each ksb label is the non-fork branch of devkit's fork predicate ([ADR-site-agnostic-projects §2](https://github.com/vig-os/devkit/blob/dev/docs/rfcs/ADR-site-agnostic-projects.md), owner-tested):

```yaml
runs-on: ${{ (github.event.pull_request && (github.event.pull_request.head.repo.fork || github.event.pull_request.head.repo.full_name != github.repository)) && 'ubuntu-latest' || 'ksb-vig-os-small' }}
```

Three layers, each doing a different job:

| layer | where | what it does |
|---|---|---|
| 1. workflow guard (this PR) | the `runs-on` expressions | routes a PR whose head isn't this repo (a fork, a deleted fork, any cross-repo head) to GitHub-hosted, so honest fork PRs get green required checks instead of being killed. **Not a security boundary:** a fork PR runs the fork's copy of the workflow and can delete the guard. |
| 2. fork-PR approval | repo + org `approval_policy: all_external_contributors` (checked via the API) | a maintainer approves every outside contributor's run before anything executes |
| 3. runner fork guard (the security boundary) | ksb job-started hook, exo-pet/exo-fleet#949 (merged; enforced by `arc-check-group`) | for `pull_request*` events it admits only head repo ID == base repo ID; otherwise it SIGKILLs `Runner.Worker` before any step, including `always()` steps and action pre/post |

Layer 1 can't drift: `scripts/check-ksb-fork-guard.sh` runs as a pre-commit hook (so in CI's Lint lane, which runs `prek run --all-files`). It fails any non-comment `ksb-<org>-<size>` label that isn't exactly `${{ (<predicate>) && 'ubuntu-…' || 'ksb-…' }}`, any runner-group routing to ksb, and any trigger in a ksb-routed workflow outside the allow-list `push`, `pull_request`, `workflow_dispatch`, `schedule` (the predicate can't see a fork through e.g. `pull_request_target` / `workflow_run` / `merge_group`, ADR §2). Labels are matched in any letter case. A second hook runs its fixture self-test (`scripts/tests/ksb-fork-guard/`, 3 good + 9 bad, asserted by name).

Evidence the check bites:
- Pre-change failure, on the real (unguarded) probe workflow: `.github/workflows/ksb-probe.yml:20: ksb label without the fork guard` → exit 1.
- Mutants of this PR's `nix-check.yml`: guard removed → exit 1; predicate weakened (fork clause dropped) → exit 1; `merge_group` trigger added → exit 1. Unmodified → exit 0.
- `--self-test`: all 12 fixtures OK, exit 0.

No `pull_request_target` anywhere; `permissions:` stay `contents: read` on every moved workflow; the moved checkouts now set `persist-credentials: false` (this also clears zizmor's two `artipacked` findings).

### Devkit-managed lanes: no repo variable, nothing for an admin to set

`ci.yml` can only be routed through `.vig-os` `DEVKIT_CI_RUNNER` (and, from devkit 1.18.0, `vars.DEVKIT_CI_RESOLVE_RUNNER`). Neither is fork-safe: `resolve-toolchain` reads `.vig-os` from the PR's merge checkout, so on a public repo a fork PR would land on ksb (and get killed by layer 3, turning its required checks red), and could even rewrite the key to pick a label. Devkit's ADR documents this exact defect (Problem statement, defect 2), and the fix is in flight upstream as vig-os/devkit#1908 (S1 #1925 runner-selection core; S2 #1928 the other scaffolded workflows), not released yet (latest is 1.18.0). So **no `gh variable set` is needed**, and the devkit lanes stay hosted until a devkit release with fork-safe runner selection; after that they move by adoption, with no hand edit. `codeql.yml` and `scorecard.yml` stay hosted by devkit design (ADR §4: "public-only jobs stay hosted").

### Why the round-1 ksb x86_64 leg failed (as diagnosed then; root cause below)

The summary reads `23 passed, 3 failed or not built`. Nix named two failing attributes, and both start a loopback server inside the check:

- `checks.x86_64-linux.minio-range-read`: every PUT to the check's MinIO on `127.0.0.1:9101` returns `503 SlowDownWrite` ("Resource requested is unwritable"), so all 3 cloud tests fail.
- `checks.x86_64-linux.registry-roundtrip`: `tessera push` gets `error sending request for url (http://127.0.0.1:5055/v2/…/blobs/uploads/)`.

The common factor is the ksb pods' Nix: `sandbox = false`, a per-pod single-user store (probe, and exo-fleet arc-design §5). Every derivation shares the pod's network namespace, `/tmp` and environment instead of getting a private sandbox. The same checks pass in the Nix sandbox on GitHub-hosted runners (the aarch64 leg of this run, and every dev run). I did not root-cause MinIO's `SlowDownWrite` beyond that.

This is a design question, not a test to patch:

1. **A security premise breaks.** `flake.nix` (`minio-range-read`) accepts nixpkgs' INSECURE-marked MinIO *because* it "starts a MinIO on 127.0.0.1:9101 inside the nix build sandbox, which has no network access", with "Revisit if minio ever becomes reachable from outside the sandbox." On a ksb pod it is not inside a sandbox.
2. **Hermeticity.** With no sandbox, every check, including the cross-arch determinism gate the x86 leg exists for, runs with the pod's network and filesystem. A check could pass for impure reasons on ksb only.
3. **No wall-clock win yet.** 67m on ksb (cold deps-cache miss; node load average 50–110 for the whole leg, since meatgrinder is shared) against 45–66m hosted. The dependency-cache export also failed (`Zstd compression failed: Allocation error : not enough memory`), so this pod would never warm the cache.
4. **The sampler lies on ksb.** `free -m` reports the 1.2 TB node, not the pod's 32 GiB cgroup, so the #495 memory diagnostics would be meaningless there.

The fork guard, its lint, the label verification and the hosted fallbacks in this PR are unaffected. The open question is only whether tessera's `nix flake check` may run on a sandbox-less runner.

## Round 2: sandbox off, loopback checks made sandbox-independent

### Root cause of "registry unreachable" on ksb: filesystem storage stalls under the pod's disk load

On the failed leg, `registry-roundtrip`'s readiness `curl` passed within 0.5 s of the build starting, and `tessera push` failed 62 s later. That is two of reqwest's 30 s request timeouts: a slow HEAD, then the upload POST. The registry was up and answering. It just could not finish an upload.

I eliminated the brief's candidate causes on a `ksb-vig-os-large` pod ([probe 1](https://github.com/vig-os/tessera/actions/runs/40871696465), `ksb-vig-os-large-runner-59mng`):
- **Proxy:** no `*proxy*` variable in the pod, and Nix clears a builder's environment anyway. A registry started with `env -i` behaved the same.
- **Port clash:** the pod has its own network namespace (only `lo` and `eth0`), and nothing was listening on 5050/5055 before the test.
- **IPv6:** both sides use the literal `127.0.0.1`.
- **OpenTelemetry exporter:** `OTEL_*_EXPORTER=none` made no difference.
- **Idle pod:** every request takes milliseconds.

Under load ([probe 2](https://github.com/vig-os/tessera/actions/runs/40872939839), `ksb-vig-os-large-runner-n6b4l`, 4 streaming writers on `/nix`, 0.9 GB dirty, 0.5 GB in writeback, max latency of 8 rounds):

| storage | condition | `GET /v2/` | upload `POST` | blob `PUT` |
|---|---|---|---|---|
| filesystem | idle | 1 ms | 2.4 s (first), then ≤ 13 ms | 13 ms |
| filesystem | **disk load** | 2 ms | **60 s cap hit 3× in a row**, then 5.2 s | **11.2 s** |

On ksb, `$TMPDIR` is `build-dir = /nix/var/nix/builds`, which is on the pod's single `/nix` volume (xfs on `/dev/vdf`, shared with `_work`). Every concurrent build writes there, and crane's `target.tar.zst` outputs run to several GiB each. In the failed leg, `registry-roundtrip` started at 08:20:03, just as `tessera-ingest-gate-a-default` finished. The sampler shows `/nix` free space jumping 4.5 GB between 08:19:31 and 08:20:01 as that multi-GiB build dir was deleted, while `tessera-cloud-nextest` compiled into its own. A filesystem-backed registry's metadata writes sit in that queue. The sandbox was never what protected these checks; hosted runners just weren't under this disk load. MinIO's `503 SlowDownWrite` in the same leg looks like the same stall, seen through MinIO's own write throttling (that check is #702's; I posted this evidence there: https://github.com/vig-os/tessera/issues/702#issuecomment-6496811216).

**Fix.** `loopbackRegistry` in `flake.nix` is shared by `oci-roundtrip` and `registry-roundtrip`:
- `inmemory` storage: these checks prove the OCI transport and byte identity, not disk durability, and a few KiB of blobs need no disk;
- `addr: 127.0.0.1:0`: the kernel picks the port, and the helper reads the real port from the registry's `listening on` log line;
- a private `mktemp -d` under `$TMPDIR` for the config and the log;
- a 30 s bounded readiness wait that also fails if the registry process dies, and prints the log;
- an EXIT trap that stops the registry, prints the log when the check failed, and keeps the check's own exit status.

Verified locally: `oci-roundtrip` builds green, a check failing after startup exits 1 and prints the registry log, and no registry process outlives the check. No retry was added, and no timeout was widened.

### Also fixed: the deps-cache export could never succeed on ksb

The round-1 leg's `nix copy` export died with `Zstd compression failed: Allocation error : not enough memory`, so ksb would never warm the dependency cache. With this PR, `nix-deps-cache.yml` also runs there. Nix's `parallel-compression=true` asks libarchive for `threads=0`, which means one zstd worker per CPU online on the HOST. [Probe 3](https://github.com/vig-os/tessera/actions/runs/40873823798) (`ksb-vig-os-large-runner-s8zrj`) showed the pod has `nproc` 16 while `_NPROCESSORS_ONLN` is 84, so each path compressed with 84 workers inside a 32 GiB pod, and `nix copy` compresses several paths at once. For one 2 GiB path, parallel took 14.4 s at 773 MiB peak RSS and serial took **11.8 s at 46 MiB**, so the action now exports with `parallel-compression=false`.

**Root cause: unbudgeted thread fan-out against the pod's PID cap.** This is the same class as exo-pet/exo-fleet#1014. A ksb pod has no CPU limit (`cpu.max` = `max`), so `available_parallelism()` reports the node's 84 CPUs (`getconf _NPROCESSORS_ONLN` = 84; `nproc` says 16 only because it honours the runner's `OMP_NUM_THREADS`). exo-fleet#1014 pins `RAYON_NUM_THREADS` and similar in the runner env, but **Nix clears a builder's environment**, so the pins never reach a check. nextest therefore defaulted to about 84 concurrent test processes, each starting 84-thread rayon and vortex pools, against the kubelet's `pod-max-pids=4096`.

Probes confirmed the picture. The container cgroup's own `pids.max` is 629145, the pod-level cap sits above it, and an idle pod starts 3000 threads cleanly ([run 40888503686](https://github.com/vig-os/tessera/actions/runs/40888503686)). An uncapped spawn probe hit the cap and took its runner down ("lost communication with the server"); that was my probe, and it was a mistake to leave it uncapped. Node load rose from 117 to 172 during exactly that 50 s test phase.

The perf ratchet is gated `cores >= 8` precisely so it skips on CI runners, and on hosted runners it does skip. Seeing 84 cores, it ran on ksb inside that fan-out.

**Fix (f03979c, kept in d2a37d9).** `withCpuBudget` in `flake.nix` sets `NEXTEST_TEST_THREADS`, `RUST_TEST_THREADS` and `RAYON_NUM_THREADS` from `$NIX_BUILD_CORES`, the leg's `--cores` budget, for `workspace-test`, `workspace-doctest` and `sql-tests`. On GitHub-hosted runners the budget is 4 = `nproc`, so they are unchanged. No threshold moved and no retry was added.

**Still open:** tessera's own worker sizing (`config.rs`, `table.rs`, and the ratchet's `cores >= 8` gate) still reads `available_parallelism()`, so on ksb the ratchet keeps running. Changing that is Rust code and out of scope for this PR, so it is filed as #703.

### Also fixed: the per-check summary miscounted on ksb

Every ksb leg's summary read "23 passed, 3 failed or not built", whatever actually failed, while hosted legs read 26 / 0. Nix 2.34.8's `nix flake check` builds only `queryMissing(…).willBuild` and skips checks whose outputs a substituter already holds (`src/nix/flake.cc`: "we skip building derivations whose outputs are already available via substitution"). On ksb the shared cache holds outputs of earlier ksb runs of the same derivations. In the f03979c run, `oci-roundtrip` and `release-tag-resolution` were evaluated but have no `building` or `copying path` line at all, so the summary's local `--check-validity` called them "not built". The summary now asks the configured substituters before calling a check failed. A cached output reads `passed earlier (output in <cache>, so nix skipped it)`, and the summary line counts how many passes came from a cache. A check nix built and failed is in no cache, so it stays red. The job's status is still `nix flake check`'s own exit code. Tested locally with a locally built, a cache-only and a missing path: 2 passed (1 from a cache), 1 failed.

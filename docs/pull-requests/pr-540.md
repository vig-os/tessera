# [PR 540](https://github.com/vig-os/tessera/pull/540) fix(ingest): the arrow lane builds on its own, and the gate proves it

Closes #509.

> **Stacked on #516.** The first commit (`bb9ecd3`) is #516's fold and is **not** for review here — review the
> second (`2ca55a9`). The PR targets `dev` rather than #516's branch deliberately: stacked PRs get no CI in
> this repo (devkit#1759), and a change whose entire point is "this configuration now builds" is worthless
> without CI. Once #516 merges I rebase and its commit drops out.

## The bug

`cargo check -p tessera-ingest --no-default-features --features arrow` did not compile. The Arrow IPC
reader, `read_arrow_table`, lived in `parquet_table` — which is `#[cfg(feature = "parquet")]` — so
selecting the arrow lane without the parquet lane failed on an unresolved module.

Nothing in it ever needed Parquet. Its whole body calls `arrow_table::read_arrow_ipc` and
`arrow_table::canonicalise_batches`, both already in `arrow_table`. Its own doc comment said why it sat
there:

> *"Lives here beside the Parquet entry point rather than in `crate::arrow_table` so that the two `--from`
> values a user can pass have their entry points side by side."*

Which reads better, and cost a lane nobody could select. Moved next to `read_arrow_ipc`, taking
`&std::path::Path` to match that neighbour rather than adding an import.

## Why this is more than tidiness

ADR-0057 §5 wants *which decoders could have produced this artifact* to be a **build-time fact**, expressed
through the feature set. While `arrow` could not be selected alone, the sealed `arrow-rs/arrow-ipc` decoder
triple described a configuration that **could not exist**. `parquet = ["arrow", "dep:parquet"]` already
declares the dependency in the direction that is real; the module layout asserted the reverse.

**Option not taken** (option 3 in the issue): declaring the coupling as `arrow = ["dep:parquet", …]`. That
puts a Parquet reader in a build that asked for Arrow IPC, and the §6a digest would then pin `parquet` on
the IPC lane — re-creating the cross-lane over-claim #477 removed.

## The gate goes in the existing derivation

`--features arrow --lib` joins `ingest-gate-a-reduced` rather than becoming a new check, so the count does
not move: **still 22**. The reason this survived in the first place is that every gate touching ingest
enables `parquet`.

## It found one more hardcoded expectation

`each_lane_pins_only_its_own_decode_path` asserted the digest-less lane set equals `["tessera/npy"]`
unconditionally. An arrow-only build compiles no array lane, so that set is empty and the assertion failed
the moment the configuration became buildable. Now derived from `cfg!(feature = "npy")` — the **third** place
this same shape has needed fixing. The property is "at most one lane may be digest-less, and only the in-tree
parser may be it", and it now holds in every configuration rather than only the default one.

## Verification

- lib tests pass under `arrow`, `parquet`, `csv`, `npy`, `parquet,npy`, and default.
- full workspace tests and clippy clean.
- the folded check built **under nix**; its log shows all four configurations running — 4 / 143 / 126 / 162 / 6
  tests, 0 errors — the 143 being the new arrow leg.

One honest note on that last point: the first sandboxed build failed with `ld.lld: Bus error` at 6.1 GB free
on `/`. I did not take that at face value — a force-rebuild of the #516 check (my first "control" was a cache
hit and proved nothing) passed, and re-running this build at 16 GB free passed with zero linker crashes. So
the failure was host disk pressure, not this diff.

# [PR 543](https://github.com/vig-os/tessera/pull/543) chore(deps): bump dicom-rs to 0.10 to clear the three jxl advisories

Refs #513 — clears Dependabot **#42, #43 and #44**. The fourth (`thrift`, #45) is blocked upstream; evidence at the bottom.

## Why a manual bump was needed

`dicom-transfer-syntax-registry` 0.9.1 declares `jxl-oxide = "^0.10.2"`, and the patched 0.12.6 is outside
that range, so neither bot could fix it in place. 0.10.0 requires `^0.12.6`, so the family moves together:

| crate | before | after | fixed in | advisory |
|---|---|---|---|---|
| `jxl-grid` | 0.5.3 | **0.6.2** | 0.6.2 | GHSA-5pmv-rx8r-wmv5 (high) |
| `jxl-oxide` | 0.10.2 | **0.12.6** | 0.12.6 | GHSA-66m8-c62j-h6v5 |
| `jxl-modular` | 0.9.1 | **0.11.3** | 0.11.3 | GHSA-2v8p-fqpx-2q3w |

24 lockfile versions move in total (ten `dicom-*`, twelve `jxl-*`, and `snafu` 0.8.9 → 0.9.2 which dicom
0.10 requires); one package added (`jxl-jbr`), none removed. **No workspace source change was needed** — the
0.9 → 0.10 API break does not reach our call sites.

Context worth keeping: we do not enable `jpegxl`, so the jxl crates are **lockfile-only** and were never in
the build graph. The advisories were real as lockfile facts and inert as runtime ones — hence `chore`, not
`fix`.

## No sealed byte moves — run, not assumed

- **The ingest corpus regenerates byte-identical** to the committed goldens: no `content_hash` and no
  `manifest_hash` moved. Expected, since the ADR-0056 §6a decoder digest covers the *generic* lanes and dicom
  is a vendor backend outside it — but the DICOM lane carries its own golden hashes (#207), and a pixel-decode
  change would have moved those. **15 DICOM tests pass.**
- **Gate B feature snapshots regenerate unchanged** (`scripts/feature-snapshots.sh`, zero files differ).
  Nothing dicom pulls sits on the sealed byte path those snapshots watch.
- Full workspace tests pass under `--locked`; clippy clean; prek clean; commit signed.

The one deliberate snapshot edit is `info.trycmd`'s human `backends:` line, which pins resolved backend
versions on purpose:

```diff
-backends:   … dicom 0.9.1 · dicom-series 0.9.1 · …
+backends:   … dicom 0.10.0 · dicom-series 0.10.0 · …
```

Hand-edited as the single literal that changed — the JSON block already uses `[..]` for versions. Deliberately
**not** `TRYCMD=overwrite`, which records whatever the binary printed and cannot distinguish an intended value
from a regression.

## Why `thrift` is not here: it is blocked on Vortex, not on us

#513 asks for `parquet`/`arrow-*` ≥ 59.0.0, since parquet 59 drops `thrift` entirely. That is not currently
possible:

```
vortex-array  0.75.0 requires arrow-array ^58.3
vortex-buffer 0.75.0 requires arrow-buffer ^58.3
vortex-error  0.75.0 requires arrow-schema ^58.3
vortex-layout 0.75.0 requires arrow-array ^58.3
vortex-runend 0.75.0 requires arrow-array ^58.3
```

`^58.3` means `< 59.0.0`. So moving our `=58.3.0` pins to 59+ would **not upgrade arrow — it would resolve a
second arrow tree**, which is precisely what the pin comment says those pins exist to prevent:

> *"58.3.0 is the version Vortex already resolves, so `arrow-array` / `-buffer` / `-schema` are ALREADY in the
> default graph (Gate B snapshots all three) and these pins add no second arrow copy."*

Two arrow versions either side of the `tessera-ingest` → `tessera-io` boundary is an ADR-0056 hazard surface,
not a tidiness question. And `thrift` is a **non-optional** dependency of parquet 58.3.0, so no feature
selection drops it either.

So #45 needs Vortex on arrow ≥ 59 first — either upstream, or carried in the `gerchowl/vortex` fork we already
pin for #468/#472 (#481), which is a materially bigger change than a version bump and wants its own decision.
Left open and reported rather than forced.

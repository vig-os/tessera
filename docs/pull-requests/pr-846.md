# [PR 846](https://github.com/vig-os/tessera/pull/846) feat(core): column contract keyed by role in ProductSchema (#809 part A)

Refs #809

Part A of #809 (ADR-0065 §8, gaps G1/G3 and the optional-column flag): the column contract's **types, serde and draft move**. **Part B follows** in a separate PR once this merges: `ProductSchema::check_table` / `check_array`, `ContractViolation`, `Error::Contract` and the refusal tests. Part B, not this PR, completes the issue.

## What
- `ProductSchema.tables` (keyed by role): ordered `columns` (reusing `Column`), `sequence_key`, `order` (absent = sequence-key order, `"producer"`), `keys`, `references` (`columns`, `to { scope, block, columns }`, `note`; `scope` parses only as `"block"` / `"source(<role>)"`).
- `ProductSchema.arrays` (keyed by role): `dtype`, `rank`, `axes`, `unit`.
- `Column.optional`: the column may be absent from a block altogether (distinct from per-row `nullable`).
- All new fields are `skip_serializing_if` empty/false, so builtins and the conformance corpus keep their bytes.
- The contract is parsed, carried and sealed; nothing checks a block against it yet (part B). Strict parsing and `schema_format` are #830, row checks #833, reference checks #780, the contract's own consistency #844.

## Drafts moved
The #801 draft JSONs move from `docs/spikes/801-consumer-schemas/` to `tessera/crates/tessera-core/tests/fixtures/801-consumer-schemas/` (pure renames). The hermetic build only sees `./tessera`, and the acceptance test parses them there. `generate.py` and `check.py` stay in the spike directory and point at the new location; `check.py` passes there.

# [PR 479](https://github.com/vig-os/tessera/pull/479) fix(cli): close the #453 review nits, route verify through the resource caps, and fix the one-column read

Three small issues in one area: the #453 review's follow-ups, the verify worker cap, and the table
read docs.

Closes #462
Closes #373
Closes #351

## #462 — the #453 review follow-ups

**Refuse a silent downgrade on resume.** A stage dir is resumed by whichever binary runs
`WriteSession::recover`, which need not be the one that wrote it. `Header` accepted unknown fields
silently, so an older binary resuming a newer dir dropped what it did not recognise — and since #416
that is `producer`/`generation`, sealed provenance that rides `manifest_hash`. The resumed seal would
differ from the intended one with nothing to show for it: #416's silent-loss class, one layer down.

Chose `deny_unknown_fields` over a `version` integer, deliberately. A version only protects you if
whoever adds the next field remembers to bump it — and #416 happened precisely because a field was
added without its plumbing finished. `deny_unknown_fields` needs no discipline: every future field is
covered the moment it exists. The cost is that cross-version resume fails loudly, which is correct for
a short-lived internal staging artifact that is cheap to redo and is not a distributed format.

**Document the `--json` schema** (subcommand help + the book's provenance chapter). It is exactly the
serialized `Manifest`, with two sharp edges for a consumer: `producer` is an untagged enum — an object
`{tool, version, git_commit?, git_repo?, dirty?}` since ADR-0058, a bare string on older products,
absent on pre-stamp ones — and optional fields are omitted rather than emitted as `null`. On stability:
it is the **format's**, tracked by the `tessera_version` the dump itself carries (that field is the
spec version, and a reader refuses a manifest whose major exceeds its own), not the CLI's version.
Fields are added compatibly; a rename or removal is a major break.

**Pin the `--json` output** in `provenance.trycmd`. It elided its whole body with `...`, so it asserted
only a zero exit; a renamed key or a `producer` that stopped serializing as an object would have sailed
through. Everything is pinned now except the embedded product schema, whose churn is not about this
surface. The legacy-string arm is already held by tessera-core's
`legacy_producer_string_round_trips_byte_identical`, so between them both arms of the enum are covered
— no redundant test added.

**`generation_lines` combined case.** It was tested for `config_ref`, for the key cap, and for `--full`
separately but never together, which is the render most likely to break: the header must name both
halves while `--full` simultaneously spells the digest out and drops the footer. Both the `--full` and
default renders of the same record are now asserted.

## #373 — verify honours the resource caps

`tessera verify`'s parallel payload probe took its worker count straight from
`WriteConfig::for_system()`, ignoring `TESSERA_WORKERS` and `.tessera/config.toml` that ingest already
honours — one verb opting out of the machine's resource policy. It now resolves through
`resource::resolve_write_config` and gains `--workers` for the flag tier, so flag > env > config >
machine default applies here as everywhere else.

The test asserts the flag tier and the end-to-end verb. It deliberately does **not** mutate
`TESSERA_WORKERS`: the process environment is global and would race every other test in the binary,
and `resource`'s own precedence test already covers the env tier through the pure `resolve()` seam,
which is the right place for it.

## #351 — table read docs, and the gap they were hiding

Most of this issue had already landed in #355 (the pooled `READ_RT`, `decode_projected`, and a
"Reading — performance & the intended access pattern" section). What remained was that the section was
**wrong in one place**: it listed `decode_column` beside `decode_projected` as equivalent projections.
True of the runtime, wrong about the cost.

`decode_column` ran a hand-rolled scan loop, materialising chunk by chunk on a fresh single-threaded
runtime, bypassing the shared column-parallel grid (#352/#385):

| one column, 4 M rows x 8 f64 | time |
|---|---|
| `decode_column` as shipped | 13.1 ms |
| `decode_column` moved to the pooled runtime (runtime isolated) | 13.5 ms |
| `decode_projected(&[name])` | 2.2 ms |
| `decode_column` delegating to `decode_projected` | **2.4 ms** |

**5.5x faster**, and it deletes the duplicate loop instead of leaving two paths that must stay
bit-identical by hand (the existing `decode_column` vs `decode` bit-exactness test covers the
equivalence).

The middle row is the point: the first hypothesis was the runtime, since `decode_column` was the last
read still on the bare single-threaded one. Putting it on the pooled `READ_RT` changed **nothing**
(13.1 → 13.5 ms), which is what redirected the search to the materialise path. Had I not isolated that
variable I would have shipped a no-op "fix" with a confident and wrong explanation. The module docs now
say so: the pool parallelises reads, but the **materialise path** is what decides throughput.

The section additionally names every read that runs pooled, says to prefer one `decode_projected` over
N `decode_column` calls, points at `decode_rows` for scattered rows, and tells anyone writing a new read
to reuse the shared helpers rather than hand-roll a third loop.

## Scope note

The brief scoped #351 to docs. The `decode_column` change is code, and it is here because the docs
could not be made true without it — the alternative was to document that one of the two projection
entry points is 5.7x slower for no reason. It is its own commit and can be dropped independently.

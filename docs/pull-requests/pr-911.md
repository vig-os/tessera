# [PR 911](https://github.com/vig-os/tessera/pull/911) test(io): add the ksb commit-cost job for small keyed commits

## Description

Adds the batch job that measured #905's first step: what one small durable commit costs through the write path tessera has today, and whether that meets the budget for small commits. It follows the pattern of `bench/ksb/635-vortex-ab`: the probe is built as a `tessera-io` example at one pinned tessera revision.

Run `tessera-905-commit-5` used exactly the files in this PR and finished with all stages and all verdict records. Results are in the [third comment on #905](https://github.com/vig-os/tessera/issues/905#issuecomment-6999085780).

## Changes Made

New directory `tessera/bench/ksb/905-commit-cost/`. Nothing else is touched; the probe is outside the cargo workspace and is copied into `crates/tessera-io/examples/` by its own flake.

- `commit_cost.rs`, the probe. Modes:
  - `tessera`: N commits of 1, 100 or 10,000 rows through `table::table_block` + `WriteSession::append_block`, timed per commit (encode, append, total). Afterwards the session is dropped unsealed and reopened with `WriteSession::recover`; the watermark must equal the commits, and every fragment must be byte-equal to a re-encode of its rows.
  - `rowlog`: the same rows' column bytes appended to one file with one `sync_data` per commit, then replayed. A lower bound, not a design.
  - `crash`: a writer process killed with SIGKILL; every acknowledged commit must be recovered.
  - `sync-cost`: what one `sync_all` costs on the medium.
  - `verdict`: reads a report and judges each arm against the budget (`mod budget`): p50, p99, rate, growth over a 100,000-commit session, and staged bytes over raw bytes. A line that was not measured gives `incomplete`, never `pass`.
- `flake.nix`, the job: three trials per cell on the SSD scratch and on tmpfs, one 100,000-commit session per arm and medium, the SIGKILL checks, and `strace -c` for the sync counts. `verdict.jsonl` is rewritten after every stage, so a job that reaches its time limit still leaves the verdicts of the stages it finished.
- `flake.lock`.

The budget is the one accepted on 2026-11-19 (nerdmachines/kit#97): for commits up to 100 rows, p50 at most 2 ms and p99 at most 10 ms; at least 500 commits per second from one writer; cost flat up to 100,000 commits in a session; at most twice the raw row bytes on disk before sealing. How the probe judges it (medians of three trials, p99 as the worst trial, "flat" as at most 1.2 times from `perf-budgets.toml`'s default tolerance, no group commit) is the probe's reading and is stated as such in the code. Using the budget as an acceptance line of #905 is a proposal on that issue.

### Manual Testing Details

The job was run on the batch host with `ksb run --cpu 4 --exclusive-cpus --mem 8Gi "path:$PWD#default"`, against `dev` at `81914f6`.

| Run | State | What it gave |
|---|---|---|
| `tessera-905-commit-2` (2026-11-18) | finished | an earlier version of the probe, without `verdict`; results in the [first comment on #905](https://github.com/vig-os/tessera/issues/905#issuecomment-6992831717) |
| `tessera-905-commit-3` (2026-11-19) | reached its 120-minute limit | all SSD results including both 100,000-commit sessions; no verdict output, because the verdict step came last. Results in the [second comment on #905](https://github.com/vig-os/tessera/issues/905#issuecomment-6997624518). This is why the verdict is now rewritten after every stage and the limit is 240 minutes |
| `tessera-905-commit-5` (2026-11-19) | finished, 81 minutes | the files of this PR; 54 records. The probe's own verdict records on the SSD scratch: existing path `fail` at 1 row per commit (every line) and at 100 rows; lower bound `pass` at 1 row (every line) and `fail` at 100 rows (494 commits per second against 500). On tmpfs: existing path `fail` at 1 row (growth 7.92 over 100,000 commits, bytes) and at 100 rows; lower bound `pass`. I recomputed every verdict record from the report and got the same values. Results in the [third comment on #905](https://github.com/vig-os/tessera/issues/905#issuecomment-6999085780). The host's load average was 93 to 183 on 88 threads during the run |

In all three runs: no mismatch in any record, and no acknowledged commit lost to SIGKILL.

Not run locally: the repository's pre-commit hooks and `nix flake check`. The development shell could not be built on the machine I committed from, so this PR's CI was the first run of those gates. CI passed on this commit, including `Lint & Format`, `Tests`, `Commit Messages` and `nix flake check (x86_64-linux)`. The commit is signed.

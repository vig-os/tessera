# [PR 926](https://github.com/vig-os/tessera/pull/926) fix(ci): promote-main builds a verified promotion head with the Git Data API

Closes #925

## What

`promote-main.yml` could not open the promotion PR for v0.1.0-alpha.6 (run 44571980870): GitHub's merges API (`POST /repos/{o}/{r}/merges`) returned an unsigned merge commit, and the `Signed commits` ruleset (`required_signatures` on every ref, no bypass actors) refused it with HTTP 409. The `merge` head kind had never succeeded.

- **New `scripts/promotion-head.sh`** builds the head and creates the branch. For `head=merge` it creates a commit with the Git Data API, `POST /repos/{o}/{r}/git/commits`, sending only `message`, `tree` (the tag's tree) and `parents` (`[main_sha, tag_sha]`). The request has no `author`, `committer` or `signature`, so GitHub signs the commit as the App. No merge is computed, so there is no conflict case.
- **Checked before any ref exists.** The script reads the commit back (`GET .../git/commits/<sha>`) and requires the tag's tree, exactly the parents `[main, tag]`, and `.verification.verified == true`. The `tag` head kind gets the same tree and signature checks. A head that fails a rule fails the run with no branch and no PR. There is no fallback, and no bypass actor was added.
- **Tree invariant.** The head has the tag's tree by construction, and the script still asserts it. `promotion-plan.sh` keeps its merge-tree check, which now does real work: the promotion commit has the tag's tree, so without that check a change made only on `main` would be dropped from `main` without anyone noticing.
- **Workflow and docs.** The `Open the promotion PR` step calls the script. The old delete-the-branch-on-refusal cleanup is gone, because a failed run now creates no branch. The workflow header, the comments in `promotion-plan.sh` and `docs/RELEASING.md` describe what the code does.
- **Tests.** The `promotion-head.sh --self-test` runs the real planner on a throwaway repo and feeds its plan into the head builder. The builder talks to a fake `gh` that answers `POST/GET git/commits` and `POST git/refs` from that repo. The flake check `release-promotion` runs this next to the planner's self-test (it now also needs `jq`).

## The load-bearing claim (GitHub docs)

From [About commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification), section "Signature verification for bots":

> Organizations and GitHub Apps that require commit signing can use bots to sign commits. If a commit or tag has a bot signature that is cryptographically verifiable, GitHub marks the commit or tag as verified.
>
> Signature verification for bots will only work if the request is verified and authenticated as the GitHub App or bot and contains no custom author information, custom committer information, and no custom signature information, such as Commits API.

The [Create a commit](https://docs.github.com/en/rest/git/commits#create-a-commit) reference says `author` defaults to the authenticated user and `committer` defaults to `author`, so a request that leaves both out carries no custom identity.

This repo has already exercised it with the same App: `devkit-upgrade.yml` publishes its commits through `POST git/commits` with no author or committer. The heads of #791 (`bcc46979`) and #557 (`c7020cb9`) read `verification: {verified: true, reason: valid}` with committer `GitHub`.

## Proof

- `bash scripts/promotion-head.sh --self-test`: 25/25 ok, exit 0. `nix build -L .#checks.x86_64-linux.release-promotion`: exit 0, both self-tests run in the sandbox.
- The tests catch the bugs they target. With the `verified` check removed, the self-test fails 4 cases (unsigned merge head and unsigned tag head both get a branch), exit 1. With the parents check removed, it fails 2 cases, exit 1.
- The pre-fix failure is the real run 44571980870: `gh: Repository rule violations found / Commits must have verified signatures. (HTTP 409)`.
- `shellcheck -x`, `actionlint`, `zizmor --config zizmor.yml` (no findings), and the prek hooks (yamllint, pymarkdown, typos, check-action-pins, guardrails gates) all pass.

## After merge

A manual run executes the workflow and its scripts from `--ref`, which defaults to the default branch (`dev`). A `workflow_run` run always uses the default branch.

```bash
gh workflow run promote-main.yml --ref dev -f tag=v0.1.0-alpha.6
```

It should open `release/promote-v0.1.0-alpha.6` → `main` with a verified head whose tree is the `v0.1.0-alpha.6` tree and whose parents are `[ee277ad3…, 7ac85bd5…]`. That supersedes #855, which is left for the owner to close.

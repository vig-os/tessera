# [PR 662](https://github.com/vig-os/tessera/pull/662) fix(io): keep values under a NULL out of the chunk-index digest, decode and streaming encode

## Description

The table chunk-index row-group digest depended on the bytes under a NULL (#632). Two producers of the same
logical table (same present values, same validity, different bytes under a NULL) sealed byte-identical table
blocks but different `.cidx` roots, so a different sidecar digest and `content_hash`.

Writing the regression test for the streaming and multi-block paths turned up two more defects in the same
"values under a NULL" contract. Each is filed and fixed in its own commit:

- **#659:** decode returned the codec's fill value under a NULL (e.g. `-4`, a neighbouring value), not the dtype
  default that the documented `ColumnData::Nullable` contract (and ADR-0056 section 5) promises. This is a fix to
  that **read contract**, not to identity: encoded bytes, `content_hash` and the chunk-index digest don't depend
  on it, because the digest canonicalises its own input (#632). It belongs here because the same fixture exposes
  it, and a caller comparing decoded columns (or recomputing the index from them) relies on the documented form.
  Cost: one extra pass over each decoded nullable column's chunk, noted in the `extend_field` rustdoc.
- **#658:** `encode_streaming` dropped `Column::nullable` from its declared dtype, so every streamed nullable table
  (`TableStreamWriter::finish`, `TableMultiBlockSink`) encoded silently wrong. Inside vortex the mismatch panics in
  the write task in both debug and release builds, and the caller still got `Ok`. The general case, any panic in
  the vortex write task coming back as `Ok`, is filed as #663. Streamed nullable products sealed by alpha.2/alpha.3
  are affected; #658 says so.

## Root cause (#632)

The digest pre-image was `ColumnData::to_le_bytes`, whose nullable form is the raw `values` buffer
followed by the packed validity. `encode` normalises masked slots, but the digest did not.

## Changes Made

All changes are in `tessera/crates/tessera-io`. The commits are ordered so each one builds and passes on its own.

1. `fix(io): decode the dtype default under a NULL` (Refs #659)
   - `ColumnData::zero_masked` is the one masked-slot normaliser (it slices `[from..]` up front).
   - The nullable decode arm (`extend_field`) applies it to the rows it appends.
   - Adds the shared `under_null_fixture`.
2. `fix(io): honour Column::nullable in encode_streaming` (Refs #658)
   - The dtype is built from `ColumnData::empty_for`.
   - A row-group whose dtype differs from the declared one is now an error the caller sees, not a panic swallowed
     inside vortex.
   - Removes the dead `empty_column`.
3. `fix(io): keep values under a NULL out of the chunk-index digest` (Refs #632)
   - One shared `table::row_group_digest`, which puts each column in canonical form **in place**
     (`ColumnData::canonicalise`: masked slots as the dtype default) and hashes its `to_le_bytes`. Both callers
     pass the row-group slice they already own, so canonicalising costs no extra copy.
   - Digest sites changed:
     - `table_chunk_index`, which also covers `table_block_with_index`, `stream::table_job_indexed` and the
       per-block indexes of multi-block products;
     - the `TableStreamWriter::flush` live fold.
   - `multiblock.rs` computes no digest (its stats fallback already excludes NULLs), so it needed no change.
   - `to_le_bytes` is unchanged. It feeds the staging fragments and the Python zero-copy export, and neither
     is identity. No other identity-bearing consumer of the raw bytes under a NULL was found.

## Recipe version (`chunk_index@1` is kept)

Decided against ADR-0059 section 11 step 1 (line 335), which bumps `chunk_index@1` to `@2`. That bump is a step
in ADR-0059's own landing plan, scoped to its schema event (M1-M3 plus the new statistics); the ADR is still
Proposed and gives no general rule that every digest fix bumps the recipe. ADR-0028 section 4 defines a derived
sidecar as a pure function of the canonical block, and the block never stores the bytes under a NULL. A root
that moved with them broke @1's definition, so it was a defect, not a different recipe. Every canonical producer
(all ingest, ADR-0056 H5) is byte-unchanged, and the corpus carries no `.cidx`. The reasoning is in a comment at
the recipe in `chunk_index.rs` and in the #632 commit body.

## Changelog Entry

No hand edit: crate changelogs are generated by release-plz from these commits. The #632 commit body
states the determinism impact: **a library-written product with non-default bytes under a NULL gets a new
chunk-index root** (so a new `.cidx` digest and `content_hash`). Ingest already zeroes masked slots
(ADR-0056 H5), so ingested products do not move.

NaN. Under NULLs it carries `i64::MAX`/`i64::MIN` and `NaN`/`-0.0`/`inf`.

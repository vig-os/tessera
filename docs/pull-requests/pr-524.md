# [PR 524](https://github.com/vig-os/tessera/pull/524) feat(cli): serve array stats from the chunk-index aggregate (#347 P2)

P2 of #347: `tessera stats` serves array statistics from the chunk-index aggregate instead of decoding
the block. Two commits — a correctness fix, then the feature.

Refs #347

## The numbers

127.7 M-voxel int16 volume (487×512×512, 64³ chunks, 151 MiB sealed), median of 7:

| | warm | cold | peak RSS |
|---|---|---|---|
| with `.cidx` (index aggregate) | **0.0061s** | **0.0079s** | **12.4 MiB** |
| full decode | 0.5795s | 0.7113s | 876.5 MiB |

**95× warm, 90× cold, 71× less memory.** The sidecar that buys it is **85 KiB — 0.06 % of the file.**

Both paths report `min`/`max`/`mean`/`std` **identical to the last bit** on that volume, because the
decode path now reduces through the same `i128` monoid the index does.

> **Caveat, stated up front:** no product on `dev` carries a `.cidx` yet, because attaching one by
> default is a corpus event held for the owner (below). So the fixture above was sealed for the purpose
> via `array_block_with_index`. The speedup is real; the files that would benefit do not exist yet.

## Commit 1 — `fix(cli)`: integer stats were computed in `f64`

`array_stats` accumulated `sum`/`sum_sq` as `f64`. An `f64` running sum stops accumulating past 2^53 —
adding 1 to 2^53 rounds straight back to 2^53 — so on a large volume the increments stop landing.

On a 127.7 M-value int16 stream, against an exact reference:

```
sum_sq  exact (i128)  118129291954102976
sum_sq  f64           118129291905977936    abs error 48,125,040
std     exact (i128)  1376.4030171166635
std     f64           1376.4028802165080    abs error 1.369e-4
```

Integer dtypes now reduce in `i128`/`u128`, with the final `f64` conversions mirroring
`ChunkStats::mean`/`variance` exactly — which is what makes the two paths agree bit-for-bit.

Two cases **cannot** be exact and now say so rather than pretending: floats, and 64-bit integers whose
`sum_sq` overflows (`i64::MAX²` ≈ 8.5e37 vs `i128::MAX` ≈ 1.7e38 → three samples overflow; `u64` → two).
Those use checked accumulation and fall back to `f64` labelled inexact, instead of wrapping in release
or panicking in debug. Narrower dtypes cannot overflow and keep the unchecked fast path.

Regression test: `[1<<53]` followed by 1000 ones, where the old code drops all 1000. Fails on `dev` with
`left: 8998201053687.305, right: 8998201053688.303`.

## Commit 2 — `feat(cli)`: the decode-free path and `--json`

`--json` carries `exact` and `method`, so a consumer never has to guess:

| `method` | `exact` | when |
| --- | --- | --- |
| `chunk-index-aggregate` | `true` | sidecar present — no block read, no decode |
| `full-decode-exact-integer` | `true` | integer array, exact integer reduction |
| `full-decode-f64` | `false` | float array, or an overflowed 64-bit accumulator |

The text output gains the same as a `source` line.

**A sidecar is refused, not trusted**, when it does not declare `indexes: <block>` or when its aggregate
does not cover every voxel. A stale or partial index would otherwise be served *as exact*, which is much
worse than being slow. Tested by forging a half-length index over an 8-voxel array and asserting the
fallback reports `max 7`, not the `3` the short index claims.

**The equivalence test compares both paths to an exact `i128` reference computed in the test**, not to
each other — two implementations agreeing proves only that they agree. Covers a non-divisible chunk grid
(5×7×3 over 4³, so edge chunks clip), `i32::MIN`/`MAX`, values crossing zero, `u64` above `i64::MAX`, and
floats.

## Three things found on the way

- **#523 — `ChunkStats::sum_sq` overflows on the *write* path.** Same arithmetic, but there a release
  build **wraps silently into a sealed `.cidx`**, so a product could carry a content-hashed, wrong
  `variance` with nothing to indicate it. Found by a test feeding `u64::MAX` through the read path.
  Out of scope here; filed with three options and a recommendation.
- **#522 — the histogram monoid**, split out because it is a `.cidx` **schema** change while this read
  path is not, and because it is *ordered*: free today (no corpus product has a `.cidx`), a second corpus
  event once one is attached by default. It also has to fix bin edges **at write time** — the
  "aggregate for range, then bin" framing in #347 is two passes over the data, which is the decode this
  issue exists to avoid.
- **#347's acceptance criterion is backwards** and I've [commented the correction](https://github.com/vig-os/tessera/issues/347#issuecomment-5892039093):
  "bit-identical to the full-decode aggregate" cannot hold, and **the index is the correct side**.

## Deliberately NOT done

**Attaching the `.cidx` by default (P1) is held for the owner.** It adds a block digest, and
`content_hash = merkle_root(&digests)` over every block ref (`product.rs:177`), so it moves
`content_hash` *and* `manifest_hash` for every integer array product — a corpus regeneration. The
codebase currently guarantees the opposite on purpose (`chunk_index.rs:8-10`, `stream.rs:56-58`). That is
a format decision, not a fix.

Also: #347 names `tessera-explore` / `crates/tessera-tui/src/data.rs` as the consumer. **Neither exists
on `dev`** — that is #286's explorer, not landed — so this lands in the CLI, the only array-stats
surface today.

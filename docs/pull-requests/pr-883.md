# [PR 883](https://github.com/vig-os/tessera/pull/883) fix(core): verify collections and embedded schemas over the parsed object

Closes #873

## What

ADR-0060 §2.2 / §11 P0b: the #573 rule (PR #875) applied to collections and embedded product schemas, through the
same shared functions (`canonical::parse_strict`, `canonical::hash_without` via `manifest::seal_of`, and the
declared-field walk `manifest::unknown_keys`, now `pub(crate)` with `unknown_keys_each` and `refuse_newer`).
No second implementation.

### Collection (`tessera-core/src/collection.rs`)

| case | dev | this PR |
|---|---|---|
| newer keys (`annotations`, `level.uri`, `members[1].weight`) added, resealed | Integrity | **ok**, `newer_fields()` names all 3 |
| older collection without the `collection_schema` key, resealed | Integrity | ok |
| `"forged": true` spliced at top level / in `level` / in a member, old seal kept | **ok** | Integrity |
| splice + seal (`manifest_hash` or `content_hash`) deleted | **ok** | Integrity |
| repeated key in `id_inputs` / a member | **ok** (last wins) | refused (`duplicate key`) |
| `compute_manifest_hash` / `canonical_bytes` / `verify` on a newer view | dropped the fields | `NewerFormatFields` |

- `from_json_verified` parses strictly, verifies `manifest_hash` over the parsed object, requires both hashes,
  then validates the level schema. `Collection::newer_fields()` is the declared-field walk over the top level,
  `level` (`Coded::FIELDS`) and `members[i]`; `id_inputs` is opaque.
- `Collection::to_sealed_json` (mirrors `Manifest::to_sealed_json`) is what `collection new` and the ingest
  engine now write: it refuses a view whose JSON doesn't reproduce its seal. `Collection::from_json_with_seal`
  returns the seal over the received object for display.
- Consumers checked: `tessera collection inspect`'s seal badge re-serialised the struct (a newer collection showed
  `sealed✗`); it now hashes the parsed object. `inspect` and `verify` warn about newer fields. `collection new` and
  the ingest engine seal fresh builders (no re-seal). The RO-Crate / OCI-index / S3-prefix projections in
  `tessera-io` render, they don't re-seal. MMR member hashes are unchanged (`content_hash` is computed from the
  members, not the struct JSON). Python and wasm have no collection API.

### Embedded `ProductSchema` (`schema.rs`)

`ProductSchema::from_value` now refuses any key no type declares, with `Error::NewerFormatFields` naming its path.
Walked: the top level, `fields[]`, `blocks[]`, `tables.<role>` with `columns[]` (incl. `referencing` and its
`transform`, per `kind`), `references[]` and `references[].to`, and `arrays.<role>`. `fields[].default` is opaque.
`validate_manifest` prefixes the paths with `schema.`. Known keys holding defaults (`inherit: false`,
`requires_generation: false`, `unit: null`) still validate. A `FIELDS` const per type is kept honest by a test built
from exhaustive struct literals (no `..`), so adding a field to any of these types fails to compile until the walk
learns it. `validate_manifest` refuses. Display callers use the new `ProductSchema::view_of` (typed view + newer paths), so
SPEC §4's "reads the product, refuses only to validate" holds. `ls FILE schema` shows the roster and names the
newer rules. The `tree`/`inspect` badge reads `schema=<p>?(newer rules, not validated)`, not `✗`. `tessera
schema` warns, shows the roster and then fails validation, and `--json` prints the embedded object as stored
rather than its re-serialised view. `provenance` shows what it understands. Covered by
`nav::tests::a_newer_schema_rule_is_displayed_and_not_validated`.

### Docs

- SPEC §4: the forward rule now covers collections and the embedded schema, and names the opaque objects. §5 gains
  the `producer`, `generation` and `ingest_transform` rows plus the `Producer` / `Generation` / `IngestTransform`
  shapes. The `schema` row no longer says "JSON Schema (opaque)".
- `tessera inspect --help` states the forward rule (verify, warn, refuse re-seal / validate) instead of "readers
  default them".
- CHANGELOG Unreleased: Security (both bypasses) and Changed (breaking: `Collection` gains a private field, the
  re-seal methods refuse newer views).

## What #830 still adds on top

This PR makes the *embedded* schema refuse unknown keys at every depth with `NewerFormatFields` (a declared-field
walk, the same rule as manifests and collections). #830 builds on that and still owns:

- **`schema_format`**: the integer on `ProductSchema`, and refusing a value that is too high with a typed error.
- **G2**: `BlockRequirement` matched by role, not only by kind.
- **Column strictness in manifests**: the `TableSpec` columns inside `blocks[].spec` stay opaque to the manifest
  walk (ADR-0060 §2.2). #830's comment asks whether `Column` becomes strict or contracts get their own column type.
  This PR walks `Column` only inside schema contracts.
- Its two folded review items (the `ColumnReference.note` byte test, and renaming `Error::Contract { violation }` to
  `reason`).

If #830 chooses `#[serde(deny_unknown_fields)]`, it can replace this walk for the schema types as long as the error
stays `NewerFormatFields` (or another typed refusal), and the honesty test shows which types must be covered. The
two specs don't conflict: both refuse an unknown key, and this PR doesn't touch `schema_format` or role matching.

## Review round 2 (`2bc7d5d`, `008e606`)

### A skipped default in another spelling (`2bc7d5d`)

`form_mismatch` compared only the keys the typed view wrote back, so a key dropped by `skip_serializing_if` was
never compared: `members[0].kind: {"product": null}` resealed verified (same `content_hash`, its own
`manifest_hash`), and so did a schema's `order: {"sequence_key": null}`. It now walks every key of the input. A
key the view wrote back is compared as before, and a key the declared-field walk names as newer is exempt. Any other
key is a skipped default: a non-empty object or array there is refused. What remains (`null`, a boolean, a number, a
string, `[]`, `{}`) is the default's own spelling, because serde coerces nothing between those.

Every `skip_serializing_if` the manifest, collection and schema types reach:

| kind of skip | fields | explicit default | accepted today | another spelling |
|---|---|---|---|---|
| default unit variant | `members[].kind` (`product`), `tables.<r>.order` (`sequence_key`), contract `columns[].sensitivity` (`public`) | `"product"`, `"sequence_key"`, `"public"` | yes | `{"product": null}` refused (was accepted) |
| `Option::is_none` | manifest `producer`/`generation`/`schema`/`study`/hashes, `blocks[].digest`, `sources[].content_hash`, Producer `git_*`/`dirty`, `generation.config_ref`; collection `study`/`level`/hashes, `level.label`; schema `fields[].unit`/`vocabulary`/`default`, `blocks[].kind`, column `codec`/`short_name`/`description`/`unit`/`scale`/`referencing`, `referencing.unit`/`vocabulary`/`frame`, `references[].note`, `arrays.<r>.unit` | `null` | yes | refused by serde's typing (`{}` for a string) |
| `Vec::is_empty` | manifest `ingest_transform`; `members[].derived_from`; contract `sequence_key`/`keys`/`references`, `arrays.<r>.axes` | `[]` | yes | refused (`{}`) |
| `BTreeMap::is_empty` | manifest `metadata`/`extra`, `generation.config`, `ingest_transform[].params`; schema `tables`/`arrays` | `{}` | yes | refused (`[]`) |
| `is_false` | schema `requires_generation`, `fields[].inherit`, column `nullable`/`optional` | `false` | yes | refused (`0`) |

Explicit canonical defaults stay accepted, as SPEC §4 states (an explicit `null` or default is a present key,
hashed as received, never a newer field). Tracked material spells them: the seal case
`recon_int16/study-null-resealed` and the #801 consumer drafts (`sequence_key: []`, `keys: []`, `references: []`).
`forward_compat.rs` has a test per kind: the explicit default is accepted, and another spelling is refused.

### The reference reader checks declared types (`008e606`)

`reader.MANIFEST` is one declarative table, one row per field of the Rust manifest records, checked at every depth.
`blocks[].spec`, `schema` and the map values stay opaque. The reader also refuses:

- a block without a digest,
- a `tessera_version` major that Rust can't parse,
- nesting deeper than 127 levels (serde_json's limit, now stated in SPEC §4),
- an integer out of a double's range,
- a manifest that isn't UTF-8.

Every input gets a verdict, including archives `zipfile` can't read. `seal-cases.json` gains 19 cases shared with
the Rust reader, every reproduction from the review among them, and `run.py` gains 5 crafted archives. The README
lists what the reader checks and where it still differs: it reads manifests only, so the collection and
schema reproductions are covered by Rust tests, and SPEC doesn't define a collection `content_hash` leaf.

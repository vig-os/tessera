# [PR 610](https://github.com/vig-os/tessera/pull/610) ci(release): compare release-plz against the last release tag, not crates.io

## What

release-plz now compares against the last release tag, not crates.io. That unblocks the 0.1.0-alpha.2 release PR (#606).

- `.github/workflows/release-plz.yml`
  - `scripts/last-release-tag.sh` resolves the last release tag, which is checked out as a detached worktree in
    `$RUNNER_TEMP`.
  - release-plz 0.3.169 then runs `release-pr --registry-manifest-path <worktree>/tessera/Cargo.toml`. It is installed
    the way release-plz/action@v0.5 installs it (cargo-binstall pinned by SHA, plus `release-plz/git-config`), because
    the action has no input for that flag.
  - The App-token step and the fallback chain are kept. The token is now scoped to contents + pull-requests, and the
    checkout no longer persists a credential (zizmor `github-app` / `artipacked` are both clean now).
  - The job still runs only `release-pr`; it never tags or publishes.
- `scripts/last-release-tag.sh` picks the highest `v<semver>` tag that is reachable from HEAD and not above the
  `[workspace.package]` version.
  - Ordering is SemVer, pre-releases included.
  - Having no qualifying tag fails the job; it never falls back to the registry.
  - The cap is needed because `v0.1.0` and `v1.0.0-rc1` are older format-milestone tags that sort above
    `v0.1.0-alpha.1`. A plain "newest `v*` tag" would pick `v1.0.0-rc1`. The namespace clash itself is #608.
- New flake check `release-tag-resolution` runs the script's `--self-test` on throwaway repos.
- `release-plz.toml` sets `semver_check = false`, with the reason written next to it.
  - With a baseline, release-plz would run cargo-semver-checks, and that cannot build `tessera-ingest` (libhdf5) on a
    bare runner.
  - The check never ran before this change either. Re-enabling it is #607.
- Header comments in both files now describe the actual flow: held release PR → merge → operator pushes `v<version>` →
  cargo-dist + release-nix build on the tag.

## Found on the way

`cargo-bins/cargo-binstall`'s action sets `BINSTALL_VERSION` from its own `version` input. That overrides a step-level
env, so release-plz/action's env-style pin actually installs the **latest** cargo-binstall. The first dispatch run
showed `releases/latest/download`. Pinning through `with: version:` gives `releases/download/v1.23.0`.

# [PR 894](https://github.com/vig-os/tessera/pull/894) fix(core): seal only integers a double holds exactly (I-JSON, RFC 7493 §2.2)

Closes #886.

JCS (RFC 8785) writes every number as an IEEE-754 double, so integers beyond 2^53 collide: a manifest sealed with `9007199254740993` verified when served as `9007199254740992`. This PR enforces JCS's own input rule, I-JSON (RFC 7493 §2.2), as the owner decided on 2026-11-16. A number whose value is an integer beyond ±(2^53−1) is refused in every sealed JSON document, by readers and writers alike, with the typed `Error::InexactInteger { path, value }`:

> `metadata.daq_start_ns = 1730000000000000000 exceeds ±(2^53−1) (I-JSON, RFC 7493 §2.2): a sealed JSON number is an IEEE-754 double (RFC 8785 §3.2.2.3), which can't hold this integer exactly; write it as a string`

## One check: `canonical::check_i_json`
- **Implementation: neither `arbitrary_precision` nor a raw-token scan.** The rule is read off the parsed value (`u64`/`i64` exactly; an `f64` beyond 2^53−1 is always integral). For every integral token this is exactly the token rule. Rounding to the nearest double is monotone, and 2^53−1 and 2^53 are both doubles, so an integral token lands beyond the bound if and only if it is beyond it. `9007199254740993`, `9007199254740993.0`, `9.007199254740993e15`, `1e300` and tokens past `u64` are refused; `-0`, `1.5` and `9007199254740991` are accepted. The same implementation serves readers and writers. It also refuses one class the token rule would let through: a fractional token that rounds past the bound, starting at `9007199254740991.5` (ties-to-even to 2^53; `9007199254740992.5` reads as `…992`), whose fraction is already lost and which collides the same way. **This is the one deviation from the brief's "decide from the token"; it is stricter, documented in the ADR-0020 amendment, and needs your sign-off.** Agreement at the bound needs correctly rounding parsers: serde_json's `float_roundtrip` (enabled build-wide by `serde_jcs`) and Python's `float`. A test and a seal case pin `9007199254740991.4999999999999999999999` → accepted in both. `arbitrary_precision` was rejected because it is workspace-wide (feature unification) and changes how `serde_jcs` serialises `Number`. A raw-token scan would be a second JSON lexer.
- **Readers:** `canonical::parse_strict` runs the check after the duplicate-key parse.
- **Writers:** `canonical::to_bytes` runs it before producing or hashing any byte, so a `u64`/`i64` from Rust code is refused too. Bytes are still serialised from the original value, so every hash is unchanged.
- **Other I-JSON MUSTs:** §2.1 UTF-8 holds because the input is a `&str`. An escaped lone surrogate is refused by serde_json (new test `lone_surrogates_are_refused`; seal case `recon_int16/lone-surrogate`). §2.3 duplicate names were already refused (`tests/seal_cases.rs::duplicate_keys_are_refused_by_name`).
- **Skipped SHOULD:** non-integral precision loss (`0.1000000000000000055511151231257827` vs `0.1`). RFC 7493 §2.2 makes it a SHOULD and the owner scoped the rule to integers.

## Every place JCS-hashed JSON is parsed or produced
| Path | Direction | Covered by |
|---|---|---|
| `Manifest::from_json{,_verified}` (incl. embedded schema, metadata, generation, ingest_transform params, `id_inputs`) | parse | `parse_strict` |
| `Collection::from_json{,_verified}` | parse | `parse_strict` |
| signature envelope: `tessera_io::sign::read_signature` / `read_embedded_signature`, `tessera-wasm::verify_signature` | parse | **new** `Signature::from_json` → `parse_strict` (was plain `serde_json::from_*`) |
| manifest seal (`manifest::seal_of`, `compute_manifest_hash` via `bytes_without`) | produce | `to_bytes` |
| collection seal (`bytes_without`) | produce | `to_bytes` |
| `identity::compute_id` (`id_inputs`) | produce | `to_bytes` (`canonical::hash`) |
| `signing::signed_bytes` (envelope payload) | produce | `to_bytes` |
| ingest `spec::canonical_bytes` / `spec_hash` | produce | `to_bytes`, now also run first in `spec::validate` |
| ingest `identity::encrypt_identity` (JCS plaintext, encrypted, not hashed) | produce | `to_bytes` |
| streamed `WriteSession` (blocks, metadata, extra, recipe journaled before the seal) | produce | **new** door checks in `admit`, `with_field`, `with_extra`, `with_generation` |
| `tessera provenance --search` discovery (`Reader::open` error classes) | parse | `InexactInteger` now counts as CORRUPT, named via the new `tessera_io::read_claimed_id` (review finding: it was skipped as "not a product", so the parent read as missing at exit 0) |

`chunk_index` and the Vortex/Zarr payloads are hashed as raw bytes and are unaffected.

## User entry points (refused with the advice, never converted)
- Python `Builder.set_field(k, "1730000000000000000")` → `pack` raises `TesseraError` naming `metadata.daq_start_ns`, and nothing is written. `with_generation(config={...})` raises `TypeError` when the int or float is passed. It used to say only `does not fit in 64 bits`, and only for ints past 64 bits.
- TOML `[product.metadata] daq_start_ns = 1730000000000000000` → `spec::validate` refuses it with `product[0].metadata.daq_start_ns = …`, before the engine touches the filesystem.
- CLI `commit --set k=v` and `ingest … --meta k=v` read the value through `canonical::parse_user_value`. Text that is JSON by the RFC 8259 grammar stays JSON, never a string: `--set x=1e400`, `-1e400`, a 401-digit integer, `9007199254740993` or `[1e400]` exit non-zero naming the flag and the typed text (`--set x = 1e400 exceeds ±(2^53−1) …`), and nothing is stored or written. Before this, a number serde_json could not hold fell back to a string and sealed at exit 0. Other text (`hello`, `[draft]`) is still a string. To keep a number as text, quote it: `--set k='"1730000000000000000"'`.

## Typed ingest sources (item 5)
- **DICOM curated fields are JSON numbers** (`KVP`, `SliceThickness`, `PixelSpacing`, `RescaleSlope`/`RescaleIntercept`, plus a series' `ImagePositionPatient`/`ImageOrientationPatient`, which become the `world_frame` affine). They stay numbers, as the owner decided on 2026-11-17. A value beyond the bound is refused when the file is read, before any output exists, naming the tag and its source text: `dicom: (0018,0060) KVP = "1E16" is outside the range a sealed JSON number can hold (±(2^53−1), I-JSON RFC 7493 §2.2)`. There is no "write it as a string" advice, because the person ingesting can't rewrite the file. (An earlier version of this section wrongly said every DICOM value is text.)
- **DICOM header dump** (`extra.dicom_header`): every primitive VR is written as its text form (`to_multi_str`), so `SV`/`UV` are strings by type. `a_64_bit_dicom_value_is_sealed_as_a_string_by_type` pins this.
- **GE HDF5:** attributes are not read into JSON; only data columns are, as Vortex payloads.
- **GE `.ini`:** carried as an opaque Blob block (`config_ref`), not parsed into JSON.
- Other `ingest_transform` params (npy `shape`, arrow `n`/`precision`/`scale`, the `epoch` string) are bounded or strings.
- No golden hash moved.

## Readers agree; old products fail closed
- The reference reader's `parse_int`/`parse_float` hooks refuse the same numbers.
- `corpus/seal-cases.json` adds 11 cases (76 total): the collision (sealed `…993`, served `…992`), `-…993`, `…993.0`, `9.007199254740993e15`, `1e300`, epoch-ns, `…992.5`, `…991.5` (first fraction rounding to 2^53), a nested `generation.config.seed`, plus one `ok` case for the bounds (`±(2^53−1)`, `-0`, `-0.0`, `1.5`, `1e-300`, `…991.4999…`).
- Rust and Python reach the same verdicts: `run.py` → `76/76 seal cases agreed`, `7/7 refusal cases refused`, exit 0.
- Products sealed earlier that hold such a number are refused, as the owner decided. All 13 tracked `.tsra` still `tessera verify` (exit 0). No golden hash moved.

## Review
A fresh reviewer found one blocker: the provenance arm above. It is fixed with a test, `a_parent_refused_for_an_inexact_integer_is_corrupt_not_missing`. The nits are fixed too: the rounding pin and seal cases, SPEC refs in `error.rs`, `# Errors` on `Manifest`/`Collection::from_json`, and MD013 lines. The DICOM header-dump test pins existing behaviour (SV/UV are strings by type) and passes on dev by design.

**Round 1 (owner review):**
- `--set`/`--meta` silently stringified numbers serde_json couldn't hold. They now go through `canonical::parse_user_value` and are refused.
- DICOM curated numbers had no refusal naming the tag. They now get one at read time, before any write.
- The item-5 section above is corrected.
- A fresh reviewer then caught `[1e400]` still falling back to a string. It is fixed: the grammar check is `serde::de::IgnoredAny`, so it computes no number.
- Not done:
  - The TOML entry point still quotes the parsed double, not the source token, because the token isn't available after the toml parse.
  - A NaN in a DICOM DS becomes JSON `null`. That predates this PR and is out of scope here.

# [PR 930](https://github.com/vig-os/tessera/pull/930) feat(core): stored-bytes API and canonical-bytes check

Closes #913

ADR-0066 implementation step 3. The change is additive: no reader or writer changes behaviour, and no seal moves.
Wiring the readers and writers is #914.

## What

- `canonical::check_canonical(bytes)` runs the one strict parser (`parse_strict`, now over bytes, so it also
  refuses non-UTF-8 input). It then refuses bytes that are not their own RFC 8785 (JCS) form with
  `Error::NonCanonical { offset, found, canonical }`, where `offset` is the first differing byte.
- `Manifest::from_stored(bytes, seal)` and `Collection::from_stored(bytes, seal)` check in the order of
  ADR-0066 rule 4:
  1. the canonical check;
  2. no top-level `manifest_hash` key (`Error::InBandSeal`);
  3. `seal == blake3(bytes)`, compared byte for byte (`Error::Integrity` with both values);
  4. the existing typed layer.
- `to_stored()` on each returns `(bytes, seal)`: `bytes` are the JCS bytes with no `manifest_hash` key, and
  `seal` is `"blake3:" + hex(blake3(bytes))`. It refuses whatever `from_stored` would refuse.
- Every failure mode is documented in rustdoc. That includes the encoding gap: an explicit
  `"study": null` is accepted by `from_stored`, as it is by `from_json_verified`, but the typed view
  normalises it away, so `to_stored` on that view fails with `Integrity`.

## Evidence

- On every one of the 13 tracked products (12 distinct manifests), `blake3(to_stored().0)` equals the
  recorded seal. The 8 corpus files also match their `corpus.json` goldens.
- The spike's attack cases are replayed on every product:
  - T4, T5, T6 and T7 (under the old seal) and S7 and S8 (sealed by the attacker) are refused as
    `NonCanonical`.
  - S5b is refused by I-JSON, and a test shows that its raw JCS equals its bytes, so the byte comparison
    alone would pass it.
  - An edit under the old seal is a seal mismatch naming both values.
  - The in-band layout is refused.
- Pre-change failure: with the byte comparison bypassed, the new tests failed (exit 100, 8 of 53 failed;
  for example, `{"a":[64.0,32]}` was accepted, and corpus T4 failed with `Integrity`, not `NonCanonical`).
- `cargo nextest run -p tessera-core`: 248 passed, exit 0. Clippy `--all-targets -D warnings`, `fmt --check`
  and the doctests are clean, all with exit 0.

## The proptest regression file

`to_bytes_output_is_always_canonical` first asserted `check_canonical(to_bytes(v)) == v` as a `serde_json::Value`.
It failed, and shrank to `v = [0.0]`. JCS has one number type, so the double `0.0` is written `0` and parses back as
the integer `0`. serde_json's `Value` compares `Float(0.0)` and `PosInt(0)` as unequal, but the bytes are
identical. So the property was wrong, not the code: a seal covers bytes, and the invariant is byte idempotence
(`to_bytes(check_canonical(to_bytes(v))) == to_bytes(v)`), which is what the property now asserts.

`proptest-regressions/canonical.txt` is committed, as proptest recommends, so the shrunk case re-runs before novel
cases on every machine. It passes under the corrected property; it does not hide a failure. The same case is also
pinned deterministically by `an_integral_double_reads_back_as_the_integer_jcs_writes`.

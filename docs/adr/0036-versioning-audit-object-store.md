# ADR-0036 — Versioning & audit: a content-addressed object store + git-shaped verbs

Status: **Proposed** (2026-06-29) · Realizes the copy-on-write half of **ADR-0022** that was specified
but not built. Relates ADR-0020 (identity / JCS), ADR-0028 (recursive MMR Merkle), ADR-0033
(collections, raw/derived WORM roles), ADR-0034 (object-store range reads).

## Context

The user story that drives this: **the audit trail must not cost a full copy.** The prevailing
practice — duplicate the entire dataset for every edit so there's a trail — is intolerable when a
3 GiB PET acquisition gets a one-field metadata correction. The edit changed kilobytes; the version
should cost kilobytes. Yet it must still be **audit-trailed and tamper-evident**, and it must still be
possible to **re-emit a clean, self-contained `.tsra`** for publication or handover.

ADR-0022 already settled the *model*: versioning is an immutable copy-on-write DAG — a new version is a
new product carrying a `supersedes`/`derived_from` `Source` edge pinning the parent's `manifest_hash`.
It also named an "opt-in exploded form … a new version shares unchanged block objects." But the
exploded form as built stores blocks at **`blocks/<name>`** (keyed by *name*), so nothing is actually
shared across versions — the CoW sharing is unrealized. This ADR pins **how** sharing works, and the
**verbs** that operate it.

A natural question is "why not just put a `.git` repo (+ git-lfs) inside the `.tsra`?" The data models
are isomorphic — but embedding git is the wrong call (recorded below). We adopt git's *architecture*,
not its bytes.

### The four edit shapes (copy is proportional to the delta)

| Edit shape | New objects | Shared | Copy cost |
|---|---|---|---|
| Metadata-only (fix a field, add a note) | manifest | every data block | ~KB |
| Add a block (attach ROI / μ-map) | manifest + 1 block | all prior blocks | the new block |
| Replace a block (re-encode / re-deidentify one) | manifest + that block | the rest | the changed block |
| Full re-ingest (source changed) | everything | nothing | full (correct) |

## Decision

### 1. The repository is a content-addressed object store

A Tessera **repository** is a directory or object-store prefix holding:

```
objects/<alg>/<aa>/<rest-of-hex>   # write-once content-addressed objects (blocks AND manifests)
layout                           # tessera-repository 2 LF
refs/lineages/<enc>               # typed lineage tip: <product|collection> <address> LF
refs/pins/<enc>                   # typed pin: <product|collection> <address> LF
log/lineages/<enc>.jsonl           # append-only audit log: one line per commit (manifest_hash, ts, op)
```

- **Objects are addressed by their existing blake3 digest** — the *same* digest already recorded in
  `BlockRef.digest` and `manifest_hash`. No second hash is introduced. Block bytes live at
  `objects/blake3/<first-byte-hex>/<rest>`; a manifest is itself an object (its `manifest_hash`).
  Two-hex fan-out mirrors git's `objects/ab/cdef…` to keep directory listings bounded.
- **Dedup is automatic and free:** identical bytes → identical digest → identical path → stored once,
  across every version *and* every product in the repo (a shared calibration block ingested by two
  sites is one object). This is git's "only changed blobs are stored," using the blake3 we already
  computed at hash-on-write.
- A **version** is a manifest object; the DAG is the `supersedes`/`derived_from` edges already inside
  each manifest (ADR-0022). `refs/lineages/<enc>` is the only mutable state — a tiny pointer, like git's
  `HEAD`. `log/lineages/<enc>.jsonl` is a **pure rebuildable cache** (decided), *not* canonical — the
  manifests in `objects/` hold the authoritative DAG; the log only spares `log` from walking every
  object and can be regenerated by walking `supersedes` from the ref at any time.

### 2. `commit` (= evolve) — a new version costs the delta

`commit` writes the new manifest object, reusing every unchanged block by digest (already present in
`objects/` → never rewritten), records the `supersedes` edge pinning the parent's `manifest_hash`,
appends a `log` line, and advances `refs/lineages/<enc>` (compare-and-set on the prior value, so concurrent
commits to one lineage are rejected, not silently lost). A metadata-only commit writes exactly one new
object: the manifest. *(How: one fenced writer per repository and a fixed durability order, see the
[2026-11-24 amendment](#amendment-2026-11-24--one-fenced-writer-per-repository-durability-order-946).)*

### 3. The verb set — git muscle memory, Tessera semantics

| git / gh | tessera | semantics |
|---|---|---|
| `git commit` | `tessera commit` | new version; reuse unchanged blocks by digest; advance the ref |
| `git log` | `tessera log` | walk `supersedes` from the ref (or read `log/lineages/<enc>.jsonl`) |
| `git diff` | `tessera diff A B` | **structural** delta: blocks added/removed/digest-changed + metadata fields changed; **plus a lineage verdict** (does B's edge pin A's real `manifest_hash`?) |
| `git show` | `tessera show` (today's `inspect`) | one version's manifest + blocks |
| `git status` | — *(dropped)* | **no staging** — the working flow is edit→`commit` directly (decided) |
| `git fsck` | `tessera verify` | integrity over the object/seal DAG (exists) |
| `git tag -s` | `tessera tag` / `sign` | name + sign a release version |
| `git push` / `pull` | `tessera push` / `pull` | repository ⇄ OCI registry (ADR-0033 §OCI projection) |
| `git cat-file` / `ls-tree` | `tessera read` / `ls` / `tree` | inspect objects/columns (landed) |
| `git blame` | `tessera blame` (future) | which version introduced/changed a metadata field |

### 4. `publish` (= `git archive`) and `seal` (= `git bundle`) — the two re-emit modes

Both collect the blocks **reachable from one manifest** into a single self-contained `.tsra`; they
differ only in what history travels:

- **`tessera publish`** = `git archive` — **history-free**. The emitted manifest **drops the
  `supersedes` version chain** (so the artifact carries no internal revision history) while **keeping
  scientific `derived_from` provenance**, metadata, and data — a clean standalone for DOI / handover.
  Under model A the `id` stays the stable lineage handle (republishing the same logical product keeps
  its handle); only the seal is fresh. **Decided:** by default it carries a *single*
  `snapshot_of: <source manifest_hash>` audit edge — the file stands alone, but that one pointer leads
  back to the full-history version in the repository, so the audit trail is never *lost*, only not
  *carried*. `--anonymous` drops even that pointer for blind / clinical handover. *(As-built: this is
  exactly `ProductBuilder::from_manifest` — which keeps id/blocks/metadata/derivation and drops
  supersedes — plus the optional `snapshot_of` edge, re-sealed.)*
- **`tessera seal`** = `git bundle` — **history-preserving**. Same self-contained `.tsra`, but it keeps
  the `supersedes` chain (and, optionally, the ancestor manifests) so lineage travels with the data —
  for archival where the audit DAG must not be lost.

The sealed `.tsra` remains the distribution/archive unit (ADR-0022 §container, unchanged). The
repository is the **edit substrate**; `publish`/`seal` are the bridges from one to the other.

### 5. Cloud-native + WORM by construction

`objects/<digest>` maps one-to-one onto an **S3 prefix**, which we already range-read and
prune-before-fetch (ADR-0034). The repository is therefore git's model but **range-readable and
cloud-native** — strictly better here than a delta-compressed packfile. Write-once content-addressed
objects are inherently WORM-friendly: `Role::Raw` objects → Compliance retention, `Role::Derived` →
Governance (ADR-0033), enforced at the storage layer with no per-block format change.

### 6. Why **not** embed `.git` / git-lfs (the record)

1. **Double-identity shadowing.** Git content-addresses with SHA-1 over its own object format; Tessera's
   identity is blake3 over raw block bytes + JCS manifest (the seal, the FAIR id). Embedding git gives
   every byte two addresses, and git's DAG identity ≠ `manifest_hash`. The most load-bearing invariant
   in the system would fork.
2. **git-lfs breaks self-containment.** LFS stores large files out-of-band on an LFS server, leaving
   pointer stubs — a `.tsra` whose blocks live on an LFS server is the opposite of self-contained.
3. **Packfiles kill range-read.** Git's delta-compressed packs are not randomly range-readable per
   logical block; the column-level range-read + cohort prune-before-fetch win (ADR-0034) evaporates.
4. **Archival coupling.** Pinning identity to git's on-disk format + SHA-1 + pack heuristics reintroduces
   the external-format archival risk we hedged against (ADR-0034 / S15).

The "`.gitignore` the blocks, let git track the manifest" hybrid still loses on (1) — git's SHA-1 of the
manifest text isn't `manifest_hash` — for `log`/`diff` we can implement natively in ~one module over JCS
manifests, operating on *real* identity with *structural* diffs. Not worth a git dependency.

## Why

- **Copy ∝ delta** is the whole point; content-addressed objects make a metadata edit a one-object
  commit while keeping the trail tamper-evident (the edge pins the parent seal).
- **Reuse, don't reinvent, the proven idea** (git's content-addressed store + commit DAG) while keeping
  **our** identity, range-readability, and archival guarantees.
- **Muscle memory:** because the models are isomorphic, `commit`/`log`/`diff`/`archive`/`bundle` teach
  themselves — and the two re-emit modes you need map *exactly* onto `git archive` (clean) vs
  `git bundle` (with history).
- **Almost entirely already built:** BlockRef digests, `manifest_hash`, the `supersedes` DAG, the
  collection MMR, and the object-store range reader all exist. New machinery = the `objects/<digest>`
  layout + a ref + the verb shell.

## Consequences

- **Two tiers — composition (file i/o) vs encoding (extra handling).** The entire versioning/repo
  layer is pure object-store + zip file-i/o over **already-encoded, already-digested** blocks — no
  codec ever runs: `import`/`seal`/`publish` read & pack existing block bytes; `commit --set` and
  `--remove-block` only write a new manifest object; `commit --add-block [N=]SRC.tsra:BLK` *copies* an
  encoded block from another `.tsra` (store the object if absent + add a `BlockRef`). **Encoding raw
  data into a block** (array→zarr/pcodec, table→Vortex, with dtype/shape) is the "extra handling" tier
  and belongs to `ingest`/`pack`, deliberately kept out of the versioning layer (single responsibility).
  To version in freshly-computed data, encode it once (build/ingest a `.tsra`) then `--add-block` it.
- **No manifest format change.** Versioning rides existing fields (`Source` edges + `manifest_hash`).
  New is the repository *layout* (`objects/`/`refs/`/`log/`) + the verbs — additive, in `tessera-io`
  (store) + `tessera-cli` (verbs).
- **The exploded form of ADR-0022 is refined:** blocks move from `blocks/<name>` → `objects/<digest>`
  in the *repository* form. The sealed `.tsra` keeps `blocks/<name>` internally (a self-contained
  archive has no need to dedup across versions); `publish`/`seal` translate between them.
- **Determinism preserved:** objects are content-addressed, so a repository is reproducible; a re-`seal`
  of the same version yields byte-identical `.tsra` (S15 determinism extends to the round-trip).
- **`publish` changes identity** (new root id) — intended; record the trade in operator docs so a
  history-free publication is never mistaken for the same product as its source.
- **Branch / merge are explicitly out of scope.** Tessera versioning is linear supersession + the
  derivation DAG (collections); there is no content merge. `refs` are single-lineage pointers, not
  branches. Revisit only if a real divergence workflow appears.
- **No staging (decided).** The working flow is edit → `commit` directly; there is no `add`/`status`
  working-tree + index. Keeps the surface lean; revisit only if a real batched-edit workflow demands it.
- **Decided (2026-06-29):** (1) `publish` default = history-free *identity* **with** a single
  `snapshot_of` audit edge back to the source's full-history version (`--anonymous` drops it for blind
  handover); (2) **no staging** (above); (3) `log/lineages/<enc>.jsonl` is a **rebuildable cache**, not
  canonical (the manifests hold the DAG).
- **Still open:** garbage collection / retention for unreachable objects — a `tessera gc` that walks
  `refs` for liveness and honors WORM holds before reclaiming.

## Amendment (2026-11-24) — one fenced writer per repository; durability order (#946)

§2 promised that the ref advances by compare-and-set, so concurrent commits are rejected, not lost. As built it was not:
the check of the tip and the write of the new one were two steps with no lock between them, `commit` compared the tip
against itself (the caller's parent never reached the check), refs and objects were written in place without a rename
or an fsync, `gc` and `commit` did not exclude each other, and `gc` read a manifest it could not load as "nothing to
keep". Each of these loses committed versions (#946; item 5 confirmed by probe in the #942 review). The owner decided
the writer model on 2026-11-22.

- **A fenced single writer per repository.** Every write (`commit`, `set_ref`, `write_object`, `put_manifest`,
  `forget`, `gc`) holds one exclusive lock for the whole repository, from its first check to its last write;
  concurrent writers, threads or processes, queue on it. One lock per repository, not per lineage: `gc` spans every
  lineage, and a writer's cost is dominated by its objects, not by the wait.
- **The lock is an OS advisory lock** (`flock`, through `std::fs::File::lock`; no new dependency) on the file `lock`
  in the repository root. It is **advisory**: it binds tessera writers, not other programs that edit the files. It
  is **local-filesystem only**: it is not valid on NFS or on any network filesystem without working lock support,
  where two hosts can both hold it. Readers take no lock.
- **`commit` takes the caller's parent** (`expected: Option<&str>`, the tip the caller read and built on) and refuses
  with the typed `Error::RefMoved { lineage, expected, found }` when the ref is elsewhere, before anything is stored.
  With a parent, the manifest must carry exactly one `supersedes` edge, to that parent (`Error::SupersedesMismatch`),
  so the ref always reaches every earlier version. A lineage's first version (`expected = None`) may supersede a
  version held elsewhere. `import` into a lineage whose tip is another version is therefore refused; importing the
  tip's own version again moves no ref and rewrites its missing or torn objects.
- **Durability order:** each object is written to a temp file in `tmp/`, fsync'd, renamed to its address, and its
  directory fsync'd (a missing shard directory is created and fsync'd into its parent first); then the ref the same
  way (temp, fsync, rename, directory fsync). A crash at any step leaves the ref at the old version or the new one,
  with every object it reaches complete. That is one sync batch per commit; the cost of many small commits belongs to
  the commit log of #905. The `log` cache is appended after the ref and not synced: after a crash it can lack the
  last commit, which a walk from the ref still finds, or end in a torn line; rebuilding it from the DAG is #971.
- **A torn object is repaired:** a write checks an object present at its address by hash before it skips it, and
  replaces one whose bytes don't hash to it. A block that a commit references but does not supply is checked for
  existence only: reading every unchanged block back would make a one-field edit cost the dataset.
- **A ref holds exactly one `blake3:<64 lower-case hex>` address** (trailing whitespace is allowed), of a stored
  object (`set_ref` checks it). An empty or unparsable ref is
  `Error::CorruptRef` when it is read, never "no commits yet". `forget` removes it.
- **`gc` holds the writer lock for its whole run, and never sweeps on a partial walk.** A ref it cannot read, a tip
  that is not a readable manifest, or an object an edge reaches that cannot be read, does not hash to its address, or
  is manifest-shaped (a JSON object with `tessera_version`) and refused, aborts the run with `Error::GcAborted`,
  naming the object and how it was reached, before anything is deleted. An intact object an edge pins that is not
  manifest-shaped (a stored source file) is kept and has no edges to follow. An edge whose target is not stored
  is not followed: it names a version or source held elsewhere.
- **The object-store form** of a repository maps the lock to a conditional put on the ref (the mechanism #288
  studies). It is **not built** here: there is no object-store repository yet.

This closes the "compare-and-set" half of §2 and the liveness half of "Still open" (`gc` walks refs for liveness and
is fenced against commits). WORM holds before reclaiming remain open, as do refs to collections and marking through
collection members (#947, #781).

## Amendment (2026-11-25) — lineage names map to ref files injectively (#975)

§1 names a ref `refs/lineages/<enc>` and its cache `log/lineages/<enc>.jsonl`, but a lineage is not a file name. As built, the
name was made one by replacing `:`, `/` and `\` with `_`, so `a:b`, `a_b` and `a/b` shared one ref: before #946 each
commit replaced the other lineages' tip, and since #946 a commit to one is refused with `RefMoved` against another's.

- **Encode, not restrict.** A lineage is a product `id` (model A, §4), and every id tessera writes is
  `blake3:<64 hex>`: a lineage alphabet without `:` would refuse every real lineage. So the name is
  **percent-encoded**: each UTF-8 byte outside `a-z`, `0-9`, `-` and `_` is written `%` plus two lower-case hex
  digits (`blake3:3f…` → `blake3%3a3f…`, `a:b` → `a%3ab`, `a_b` → `a_b`). `%` is itself encoded, so the mapping is
  injective and reversible. Upper-case letters and `.` are encoded too, so it stays injective on a case-insensitive
  file system (APFS, NTFS) and no name is `.`, `..` or hidden; every non-ASCII byte is encoded, so Unicode
  normalization cannot merge two names.
- **Independent namespaces (ADR-0067 D1).** Lineages live in `refs/lineages/<enc>` and pins in
  `refs/pins/<enc>`. Both share this encoding; no name or prefix is reserved. A lineage and pin with the same name
  cannot collide. The cache lives at `log/lineages/<enc>.jsonl`.
- **Bounded.** A ref's file name is at most 249 bytes (255 less `.jsonl`). An empty lineage, or one whose encoded name
  is longer, is refused with the typed `Error::InvalidRefName { namespace, name, reason }` by every verb that takes
  a lineage, before anything is read or written. A product id is 73 bytes.
- **Layout 2 (ADR-0067 step 1, #996).** `layout` holds exactly `tessera-repository 2` followed by LF.
  Each ref holds exactly `product SP blake3:<64 lower-case hex> LF`: no other whitespace, upper-case hex, missing
  LF or trailing bytes. Unknown kinds are `Error::CorruptRef`, naming the file and its contents. Collection records
  arrive with collection storage in ADR-0067 step 4. Product records in either namespace are roots of `gc`;
  pin management verbs arrive in step 6. Lineage operations never touch pins.
- **Every other layout is refused.** `open` refuses any other marker, including a missing marker in an empty
  directory. Only `init` creates a marker, in a directory with no ref, log or object entries. `init` on an existing
  repository checks its marker too. Every writer checks the layout under the one repository lock before writing.
  `Error::UnsupportedRepositoryLayout` names what was found and required (2). There is no migration verb. Use the
  build that wrote the old repository to `seal` each lineage tip into a self-contained `.tsra`, then import those
  into a new repository. Stored history edges travel with the sealed versions; the old repository is untouched.
- **Fail closed before sweeping.** Entries directly under `refs/` other than the two namespace directories,
  and entries inside either namespace other than regular files, are `Error::CorruptRef`. A malformed record in
  either namespace aborts `gc` before anything is deleted.
- **Trade-off.** Windows' reserved device names (`con`, `nul`) are not encoded, since Windows builds are deferred.
  Builds from #990 onward refuse layout 2. Earlier builds do not check the marker: their `gc` sees no roots and
  can empty a layout-2 store. Never run those builds against a layout-2 repository.

## Amendment (2026-11-27) — collection objects and member reachability (#999)

ADR-0067 step 4 adds collection objects beside product manifests in the same content-addressed store.
`put_collection` and `get_collection` use the collection seal (`manifest_hash`) and canonical stored bytes;
collection writes hold the same fenced writer as every repository mutation. `set_ref` infers `product` or
`collection` from the target bytes, refuses bare blocks and verifies the object before publishing the ref.
Both ref namespaces accept either kind. Ref reads check the record against `ObjectKind::of` and verify the
selected version; a disagreement is `RefKindMismatch` naming the ref file. Typed object accessors instead use
`ObjectKindMismatch`, naming the requested object kind. Under the writer lock, every ref writer refuses a change
to an existing lineage's recorded kind with `LineageKindMismatch`; product commits check before storing objects.

The `gc` walk dispatches by object kind. Products mark blocks; collections push their member seals and declared
kinds; both follow stored `sources` edges. Members are closed (ADR-0067 D3.1): missing, torn, unreadable or
wrong-kind members abort with `GcAborted` naming the full path from the root ref through each member index.
Nothing is swept after a partial mark. Missing edge targets remain open, and intact non-version edge targets
are retained. A heap stack has no depth cutoff; shared versions are read once while every incoming kind claim
is checked. Traversal provenance uses parent indices, with one local label per traversed edge; full member paths
are rendered only on failure, and consecutive source edges are summarized by their version/object count. This
avoids quadratic path copying in long histories. Sealed hash pins prevent cycles; edits invalidate the seal.
Product payloads are marked without reading them, as before. Atomic collection commit and closure validation are ADR-0067 step 5; separate low-level
storage and ref calls leave the object reclaimable until it becomes reachable.

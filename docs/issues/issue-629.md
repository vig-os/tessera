# [Issue 629]: [ci(release): the release-plz release PR fails the branch-name and commit-trailer convention](https://github.com/vig-os/tessera/issues/629)

## Summary
The release PR that release-plz opens (#626, `chore: release v0.1.0-alpha.2`) fails the required-by-convention **Commit Messages**
check, so CI Summary is red:

```
##[error]Branch name 'release-plz-2026-10-18T13-31-15Z' does not follow the convention <type>/<issue>-<summary>
(types: chore,feat,…,release,…) or chore/<summary>.
```
(run 39131910607, job 117688668904). The alpha.1 release PR #435 used the same `release-plz-<ts>` branch. The dev ruleset requires
only `nix flake check`, so a red CI Summary does not block the merge. Merging the release over a red convention gate is the
shortcut this issue replaces.

The release commit is also `chore: release v0.1.0-alpha.2` with no `Refs: #N` trailer, which the commit standard
(`docs/COMMIT_MESSAGE_STANDARD.md`) requires. Check whether the job validates it once the branch passes.

## Decided fix
Make release-plz's own output conform instead of exempting it:
- the PR branch: release-plz's `pr_branch_prefix` (workspace config) → a prefix that satisfies `chore/<summary>` (e.g. `chore/release-plz-`).
  Verify the option name and behaviour against the pinned release-plz version (0.3.169) docs or source, never by guessing.
- the release commit's `Refs:` trailer: find release-plz's supported way to set the release commit message or body (a config
  key, a template). If release-plz cannot produce a conforming commit, report it with the evidence. Then decide between a
  documented, narrowly-scoped exemption for release-plz's commits in the devkit check (filed upstream on devkit) and
  something else. Never a silent bypass.
- Update the release-plz.toml/release-plz.yml header docs.
Acceptance: the release PR regenerated by release-plz on dev passes **Commit Messages** and **CI Summary**.

# [Issue 971]: [fix(io): the repository's log cache can lag or tear after a crash, and a failed append fails a landed commit](https://github.com/vig-os/tessera/issues/971)

Found in the review of the #946 fix (the fenced single writer, ADR-0036 §2 amendment). Out of #946's scope, which covers refs and objects; the `log/<lineage>.jsonl` cache was left as it is and its limits are now documented in `tessera-io/src/repo.rs`.

## The gap

`Repository::commit` appends the log line after the ref has advanced, with a plain `O_APPEND` write and no fsync (ADR-0036 §1: the log is a rebuildable cache, not canonical). Three consequences:

1. **A crash between the ref and the append** leaves the log without the last commit. `tessera log` then omits a version the ref names. Harmless to the data, wrong in the output.
2. **A crash in the middle of the append** can leave a torn last line. `Repository::log` parses every line and fails on it, so `tessera log` stops working for that lineage, and the next append writes after the torn fragment, corrupting a middle line.
3. **A failed append** (disk full, permissions) makes `commit` return the error although the version landed: the ref names it. A caller that retries gets `Error::RefMoved`, whose message says another commit landed first.

## Proposal

- `log` rebuilds the cache from the DAG (walk `supersedes` from the ref) when the cache's last entry is not the tip, or when a line does not parse. ADR-0036 §1 already promises the cache "can be regenerated by walking `supersedes` from the ref at any time"; nothing implements it.
- `commit` treats the log append as best effort after the ref advance (the ref is the commit point), or reports a typed "committed, log not updated" outcome, so a landed version never reads as a failed commit.
- A test with a torn last line and one with a missing last entry.

Refs: #946, ADR-0036 §1

# [Issue 799]: [epic: C++ producers write tessera products through our writer (C ABI / Arrow C Data Interface bridge)](https://github.com/vig-os/tessera/issues/799)

## Goal (owner 2026-11-11, top priority)
C++ producers write tessera products **through tessera's own writer** (`tessera-io`: streaming `StreamWriter` / `push_table`, hash-on-write, seal). No re-implementation of the format in C++.
- **Consumers:** MorePET gPET-sim (Geant4), gPET-sim2listmode, and the Stage 2 pairwise path (geddf-analysis).
- **Size:** weeks, not days. The owner's two surveys will supply firm consumer facts, and they supersede assumptions here.
- The next alpha ships the bridge for consumer testing.

## Scope (sub-issues)
1. **C++→Rust bridge.** A C ABI crate over the writer. Batches cross the boundary as the Arrow C Data Interface (`ArrowSchema`/`ArrowArray`, zero-copy; nanoarrow or arrow-cpp on the C++ side) or as plain C buffers. ADR first:
   - API surface and lifecycle: open session, declare product, push batches/arrays, aux/identity, seal;
   - ownership and release callbacks, the error model (no panics across FFI), ABI versioning, and a header generated by cbindgen;
   - build/packaging (static + shared lib, pkg-config/CMake config, nix, cargo-dist).
2. **A schema per product.** Each product type a C++ producer writes is declared as data in the product-schema registry, not as engine code (ADR-0035 / the schema registry). The bridge validates batches against it.
3. **Deterministic ordering across threads.** Many C++ threads feed one product, and the sealed bytes / content_hash must not depend on thread scheduling: an explicit sequence key or ordered lanes, never arrival order. This extends the existing worker-count invariance (#677 test (c)) to producer threads.
4. **Port every downstream reader** (sim2listmode, Stage 2, …) to read tessera products through the logical APIs (ADR-0064). This is tracked here and done in the consumer repos once the surveys report.

## Process
Design before code: ADR (Proposed → Accepted by the owner) before the implementation PRs. Spikes may build throwaway prototypes to answer design questions with evidence.

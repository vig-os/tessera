# [Issue 441]: [Decide: retire release-plz for the vigOS devkit release train, or stay and document why](https://github.com/vig-os/tessera/issues/441)

## Status: DECISION, not work. Do not implement from this issue.

tessera's continuation is uncertain. This records what a migration off `release-plz` onto the vigOS devkit release train would require, so the analysis is not lost and so the cost is visible **before** anyone starts. Nothing here should be built until tessera's future is settled and this decision is taken deliberately.

## The question

Every other active vig-os repo is converging on the devkit release train (`prepare-release` → `release` → `promote-release`, with two repo-owned extension seams). tessera is the outlier: `release-plz` opens a held release PR, a human pushes the tag, and cargo-dist + `release-nix` build artifacts from the tag.

Should tessera converge, and retire `release-plz`, the `tessera-release-plz` App and its `RP_APP_ID` / `RP_APP_PRIVATE_KEY` secrets?

## Why it is not obvious

**ADR-0052 would have to be superseded — but not on the grounds it was written.** §3 chose release-plz *over release-please*, reasoning that release-plz "understands the Cargo workspace natively (crate versions, inter-crate deps, `cargo publish`)" versus "generic + a rust plugin + a bolted-on publish step". That argument is sound and is **not** an argument against the devkit train, which does not use release-please either: it dispatches an explicit version and runs `cargo set-version --workspace` in a repo-owned seam. ADR-0052 §1 (two independent version axes — software SemVer vs the `tessera_version` format version) is unaffected either way and survives.

**The pattern is not yet proven anywhere.** As of 2026-09-24:
- `vig-os/h5v` is on the train, but both extension seams are no-op seeds — no crates.io, no binaries, no version bump. It proves the floor, not the ceiling.
- `vig-os/scitadel` is **still on release-please** on both `main` and `dev`. Its train migration is open, unmerged PR [scitadel#208](https://github.com/vig-os/scitadel/pull/208).

So no vig-os repo has yet shipped a Rust release through the train with crate publishing or binaries. tessera would be the second adopter at best. **scitadel#208 landing is the natural prerequisite** — it is the same problem one repo ahead, and tessera's workspace is simpler (one `[workspace.package] version`, all six crates `version.workspace = true`, versus scitadel's explicit per-crate versions).

## Blockers, in the order they would bite

### 1. The train cannot express `0.1.0-alpha.2`

The train's version model is a `version` input of `X.Y.Z` plus `release-kind: candidate|final`, where a candidate publishes as `X.Y.Z-rc{N}` with N auto-incremented from existing tags. There is no `-alpha.N` path.

tessera is mid-alpha-series at `v0.1.0-alpha.1`. The options are all decisions, not implementation details:

- treat alphas as RCs — but `0.1.0` is already burned as a legacy tag (2026-06-25, on an ordinary feature commit);
- start the next series at `0.2.0-rc1`;
- drop alpha naming and ship `0.1.x` finals.

**This gates everything else.** It should be decided before a single workflow is written.

### 2. cargo-dist and `release-publish.yml` both want to own the Release

`release.yml` is generated by cargo-dist 0.32.0, must never be hand-edited (its `plan` job regenerates it and fails on drift, #433), fires on tag push, and creates the GitHub Release itself. The train's `release-publish.yml` also creates the tag and the (draft) Release. They collide.

Either cargo-dist is reduced to building and uploading into an existing draft — not its default shape — or it is replaced with a scitadel-style `binaries.yml` matrix, which would give up the `curl | sh` installer that ADR-0057 deliberately chose. This is the piece with real design risk and deserves a spike rather than an estimate.

Note this interacts with #440: the train's draft-Release model is *structurally* the fix for the immutable-release 422, so convergence would resolve that bug as a side effect. That is an argument in favour, but #440 needs fixing either way and must not wait on this decision.

### 3. The changelog model changes, and it is a habit change

The train reads a **hand-authored** root `## Unreleased` section and does not generate from commit messages. release-plz generates **per-crate** changelogs from conventional commits.

Today tessera has both, inconsistently: the root `CHANGELOG.md` is an empty Keep-a-Changelog skeleton that release-plz has never touched (byte-identical at `dev` and at `v0.1.0-alpha.1` — it has never recorded a release), while six generated `tessera/crates/*/CHANGELOG.md` files were created in one shot by release PR #435. A migration means deciding whether those six are archived or kept, and changing what every contributor does in every PR. This is the item most likely to be underestimated, because it is not a workflow change.

### 4. Prerequisites that are real but routine

- **Devkit scaffold adoption** (#364) — tessera has no `.vig-os` and zero devkit-managed files; this is a greenfield adoption, not an upgrade. Its stated blocker, `vig-os/devkit#1365`, **closed 2026-08-07**, so #364 is unblocked. Worth noting #364's scope is sync-issues only and says nothing about releases; the two can proceed independently, and the scaffold adoption is useful on its own.
- **Two GitHub Apps** — the train needs Release App and Commit App credentials (`RELEASE_APP_CLIENT_ID` / `RELEASE_APP_PRIVATE_KEY`, `COMMIT_APP_CLIENT_ID` / `COMMIT_APP_PRIVATE_KEY`), replacing the single `tessera-release-plz` App.
- **`justfile.project` must define `sync` and `test`** — `release-core.yml` runs them verbatim as a repo contract.
- **`DEVKIT_TAG_PREFIX=v`**, to keep the existing `v`-prefixed tag namespace.
- **Legacy tag hazard** — `v0.1.0` and `v1.0.0-rc1` are pre-graduation markers on ordinary commits, and they sort lexically above `v0.1.0-alpha.1`. Any "latest tag" logic, including RC-number discovery, should be checked against them.
- **First release after migrating needs a manual promote** — `promote-release.yml` is not dispatchable until it exists on the default branch, and the sequence cannot be resumed partway.

## If the answer is no

Also a legitimate outcome, and cheaper. release-plz is currently green and live (four consecutive successful runs since 2026-09-23). Staying put means: finish the #337 checklist (crates.io credentials, `publish = false` on `tessera-py` / `tessera-wasm` before any publish), fix #440 independently, and accept that tessera's release mechanism differs from the rest of the org — with this issue as the record of why that was chosen rather than overlooked.

## Order, if the answer is yes

1. Decide the version series (blocker 1).
2. Supersede ADR-0052 §3 with a new ADR.
3. Wait for scitadel#208 to land and learn from it.
4. Spike the cargo-dist seam (blocker 2).
5. Adopt the devkit scaffold (#364).
6. Change the changelog habit (blocker 3).
7. Cut one release on the train, then retire release-plz: delete `release-plz.yml` and `release-plz.toml`, uninstall the `tessera-release-plz` App, delete `RP_APP_ID` / `RP_APP_PRIVATE_KEY`.

## Cross-repo note

`RP_APP_ID` and `RP_APP_PRIVATE_KEY` were created 2026-09-23T17:53:25Z and are undeclared in `vig-os/org-config`'s otterdog config, so they show as proposed deletions on every plan there. That is tracked separately in org-config and does not block anything here; nothing can delete them (`apply` omits `--delete-resources`).

# [Comment #1]() by [c-vigo]()

_Posted on September 24, 2026 at 07:45 AM_

## Retiring `RP_APP_ID` / `RP_APP_PRIVATE_KEY` — usage evidence and the required order

Recording this here so the removal path is written down, whichever way the decision above goes.

### The keys are live, not stale

| | |
|---|---|
| Last used | **2026-09-23T23:27:30Z** — `release-plz` run, `push` event, **success** |
| Created | 2026-09-23T17:53:25Z (App `tessera-release-plz`, `app_id=5050387`) |
| Only consumer, org-wide | `vig-os/tessera/.github/workflows/release-plz.yml` — a code search across the `vig-os` org for `RP_APP_ID` returns exactly one file |
| Run history | 4 consecutive successes (18:26, 18:37 dispatch; 23:05, 23:27 push) after the 17:02 failure that #432 fixed |

Since #436 the workflow triggers on **every push to `dev`**, so the next push uses them again.

### Deleting the secrets alone would regress #430/#432

`release-plz.yml` mints the App token with `continue-on-error: true` and falls back:

```yaml
GITHUB_TOKEN: ${{ steps.app-token.outputs.token || secrets.RELEASE_PLZ_TOKEN || secrets.GITHUB_TOKEN }}
```

`RELEASE_PLZ_TOKEN` **does not exist** in this repo — the live secrets are exactly `APP_SYNC_ISSUES_ID`, `APP_SYNC_ISSUES_PRIVATE_KEY`, `RP_APP_ID`, `RP_APP_PRIVATE_KEY`. So the chain collapses to `GITHUB_TOKEN`, which cannot create PRs — precisely the `ERROR Failed to open PR` failure of the 2026-09-23T17:02 run that #432 was opened to fix.

The soft-fail makes this worse rather than better: nothing errors at the token step, so the workflow goes red later, on every push to `dev`, with a failure mode that looks unrelated to the secret deletion.

### Correct order

1. Remove `release-plz.yml` and `release-plz.toml` (a PR, so it is reviewable and revertible).
2. Then delete the two repo secrets.
3. Then uninstall the `tessera-release-plz` App from the `vig-os` org.
4. Nothing further is needed in `vig-os/org-config` — the undeclared-secret drift disappears with step 2.

Steps 1-3 are not independently useful: doing 2 without 1 breaks the release path, and doing 1 without 2/3 leaves credentials with no consumer.

### What this means for the decision above

Retiring these keys is not neutral housekeeping — it **implements the "stop using release-plz" half of this issue**. If tessera continues in any form, it should follow a decision here rather than precede it. If tessera is being wound down, the sequence above is the clean exit, and step 1 is the one that actually needs review.

# [Comment #2]() by [gerchowl]()

_Posted on September 28, 2026 at 11:52 AM_

Filed the upstream devkit cut this analysis pointed at: **vig-os/devkit#1746** — "Release train: first-class Rust release extension via a general publish/Release-owner seam".

It's the general shape, not tessera-specific — three cleanly bounded changes to the train contract that collapse the four blockers listed here:

1. **Pluggable pre-release format** (dotted, `pre_release_format = "alpha.{N}"`) — resolves blocker (1) without forcing tessera to burn `0.1.0` semantics or drop the alpha series. Default stays `"rc.{N}"`, byte-identical for h5v/scitadel.
2. **Draft-Release-first "Release Owner" contract** with a named pre-publish assets window, plus a documented cargo-dist adopter recipe (`create-release = false` + `github-release = "host"`, verified against cargo-dist 0.32 source) — resolves blocker (2). Structurally fixes tessera#440 as a side effect.
3. **New standalone `publish-release-extension.yml` seam** on `release: published` — resolves the missing live-publish altitude. Standalone (not `workflow_call`) is forced by crates.io/PyPI Trusted Publishing OIDC subject binding to the workflow file path.

Blocker (3) (changelog habit change) is deliberately left out of that cut per reviewer scope guidance and will file as a separate `git-cliff`-in-`prepare-release-extension.yml` recipe follow-up; the tessera-specific "publish = false on tessera-py / tessera-wasm before the first cut on the train" landmine is noted in the issue's follow-ups section.

Nothing in this comment changes the disposition here — the tessera-migration decision remains what it was. The devkit issue just means "if the answer is yes, three specific blockers dissolve".
